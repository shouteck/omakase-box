## Why

`merged.ts` builds candidates from collected attempts **and** from every PR the tool has seen (`candidatesOf`, lines 105–109). `checkOne` then asks only whether the candidate commit is in `rev-list refs/heads/<branch>` (line 133). A pull request whose head is an old commit already on the branch therefore counts as merged: the bounty closes and a pay message can fire for work that added nothing.

`collect.ts` already refuses a pull request whose history does not descend from the posted commit (`merge-base --is-ancestor`, line 293). The two paths disagree, and the merge path is the one that states "merged" and triggers payment.

## Outcome

A bounty is called merged only when a candidate commit is new to the branch and descends from the commit the bounty was posted on. A pull request pointing at an existing commit leaves the bounty open and emits no merge notice.

## The change

1. Resolve the posted base once in `checkOne`: `publication.commit` for a history post, else `baseCommitOf(record)`. If it is null, keep today's behaviour and say so in the Result — no regression for records that cannot answer.
2. For each candidate, require both, with local Git only:
   - `merge-base --is-ancestor <base> <candidate>` succeeds (the solution descends from the posted work);
   - `merge-base --is-ancestor <candidate> <base>` fails (the candidate is not the base and not already in its history).
3. Only candidates passing both are checked against `onBranch`.
4. No new GitHub call, no change to `collect.ts`.

## Done when

- A test that must fail first: a PR whose head is the parent of the posted commit, with the branch advanced past it, leaves the stage open, emits no merge notice and produces no pay message.
- A second failing case: a PR whose head equals the posted commit (a zero-change PR) also leaves the bounty open.
- Positive controls: a fast-forward land and an ordinary merge commit each still close the bounty and name the merge commit.
- A test proves the guard bites: remove either ancestor check and the suite goes red.
- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit; the BACKLOG line is removed.

- Ruling on point 1 (one `rev-list --parents` walk instead of `merge-base --is-ancestor`): **equivalent for every candidate that can close a bounty.** The parent map holds every commit reachable from `refs/heads/<branch>` and is closed under parents. (a) A candidate on the branch: its whole ancestry is in the map, so "base reaches candidate" is exact. If the base is not on the branch, it cannot be an ancestor of an on-branch commit, and the walk correctly answers false. (b) Novelty, "candidate reaches base": when the base is on the branch the walk is exact. When it is off the branch, the map has no parents for it, so the walk answers false unless the candidate equals the base. That is correct, because an on-branch candidate cannot be an ancestor of an off-branch base. (c) A candidate off the branch can differ from `merge-base`, but `onBranch` drops it either way, so the result is the same. Replace refs and grafts affect `rev-list` and `merge-base` alike. SHAs are compared as full lowercase hex from Git and GitHub; a mismatch would fail closed (stays open). The cost is O(candidates × branch history) in-process, inside the existing explicit `maxBuffer`.
- Ruling on point 2 (snapshot-kind GitHub post): it is a retired route. `retiredRoute` (`record.ts:744`) names any `github.kind !== 'history'` publication as `legacy-delivery-retired`, and `post.ts` writes only `kind: 'history'`. For such a legacy record the guard uses `baseCommitOf` (`snapshot.baseCommit`). Attempt commits are parented on that base (`record.ts:372` comment), so a real applied attempt passes descent and novelty. Its seen PR heads live in the snapshot's own history, not the owner's branch, so they were never closable by membership anyway. It is untested, as the cook said.
