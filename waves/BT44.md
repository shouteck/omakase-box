## Why

`merged.ts` builds candidates from collected attempts **and** from every PR the tool has seen (`candidatesOf`, lines 105–109). `checkOne` then asks only whether the candidate commit is in `rev-list refs/heads/<branch>` (line 133). A pull request whose head is an old commit already on the branch therefore counts as merged: the bounty closes and a pay message can fire for work that added nothing.

`collect.ts` already refuses a pull request whose history does not descend from the posted commit (`merge-base --is-ancestor`, line 293). The two paths disagree, and the merge path is the one that states "merged" and triggers payment.

## Outcome

A bounty is called merged only when a candidate commit is new to the branch and descends from the commit the bounty was posted on. A pull request pointing at an existing commit leaves the bounty open and emits no merge notice.

## The change

1. Resolve the posted base once in `checkOne`: `publication.commit` for a history post, else `baseCommitOf(record)`. If it is null, keep today's behaviour and say so in the Result — no regression for records that cannot answer.
2. For each candidate, require both, with local Git only:
   - `merge-base --is-ancestor <base> <candidate>` succeeds (the solution descends from the posted work);
   - `merge-base --is-ancestor <candidate> <base>` fails (the candidate is not the base and not already in its history).
3. Only candidates passing both are checked against `onBranch`.
4. No new GitHub call, no change to `collect.ts`.

## Done when

- A test that must fail first: a PR whose head is the parent of the posted commit, with the branch advanced past it, leaves the stage open, emits no merge notice and produces no pay message.
- A second failing case: a PR whose head equals the posted commit (a zero-change PR) also leaves the bounty open.
- Positive controls: a fast-forward land and an ordinary merge commit each still close the bounty and name the merge commit.
