# BT16: a project with several remotes can still be allowed

Milestone: BT · Station: packaging · Base: master at dispatch, after BT15 · Branch: `wave/BT16` · Timebox: 120 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 14 October 2026; the owner agreed the direction that day. The head chef checks names against master at dispatch.

## Why

The tool names a project by its GitHub address (BT8a), worked out from the project's remotes in `packages/box-bounty/repository.ts`. Today it refuses whenever the remotes are not all one GitHub repository:

- remotes naming two different GitHub repositories: `repository-address-ambiguous`;
- any remote that is not a GitHub address at all: `github-remote-required`.

So two very common setups cannot use the tool: **the fork workflow** (`origin` is the owner's fork, `upstream` the original project) and **a mirror** (a GitHub remote beside a GitLab or company remote). The refusal is honest, but its only advice is to change the remotes, which most owners will not do for one tool.

The convention for the same problem: `gh` asks once which repository a checkout's commands go to, remembers it for that checkout, and says which it is using from then on (`gh repo set-default`). Here the owner's list of allowed repositories already says which one they mean, so no separate choice is stored.

## Outcome

A project with a fork remote or a mirror can be allowed with the same one command. The owner's list of allowed repositories is the only setting involved, and a yes still covers exactly one GitHub repository.

**Remotes that are not GitHub are ignored**

- A remote that names no GitHub repository plays no part in which repository this is. The tool never pushes to it or reads from it for a bounty. `status` may mention it as a fact once; it never refuses because of it.

**When GitHub remotes disagree, the owner's list decides (owner, 14 October 2026)**

The owner's settings already hold the list of allowed GitHub repositories. That list is the choice; nothing else is stored.

- The tool works out, every time, the GitHub repositories this checkout's remotes name, and compares them with the owner's list.
- **Exactly one of them is on the list:** that is the repository, with nothing asked.
- **None is on the list:** the first post waits, as any first post does, and the waiting message lists the GitHub repositories found, with the remote each came from. The owner's yes, `allow <owner/name>` run in this project, puts one on the list, and that settles it.
- **More than one is on the list:** any command that needs the identity refuses by name, changes nothing, lists them, and says the owner must take all but one of them off the list for this to work here, or work from a checkout whose remotes name one. A yes for one repository never silently covers another. The Result says whether this case was met in practice and whether a lighter answer is needed.
- Nothing is keyed to the checkout's folder and nothing is written into the repository's Git configuration. A different repository at the same folder has different remotes and is judged on its own. Adding or removing a remote changes nothing as long as the allowed repository is still one of them.
- Every command that acts on the repository says which one in its first line, for example "acting on owner/name (2 GitHub remotes; the one on your list)".
- The chosen repository must be one the owner's GitHub sign-in can push to, since the bounty branch goes there; if it is not, the tool says so by name before anything is published.

**Everything already guaranteed still holds, for the chosen repository**

- The bounty branch is pushed to, the issue opened on, and pull requests read from the chosen repository only.
- A Git URL rewrite that would send a push for it anywhere else is refused, as today.
- Letter case and a trailing `.git` are still normalised; a fork is still a different repository; a yes for one repository never covers another.

**Cases that must fail, each a named refusal that changes nothing:** `allow <owner/name>` for an address none of this project's remotes name; two of the checkout's GitHub remotes on the owner's list; a chosen repository the owner cannot push to; a rewrite that sends the chosen repository's pushes elsewhere; a remote edited to claim the chosen address while pushing elsewhere.
