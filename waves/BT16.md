# BT16: a project with several remotes can still be allowed

Milestone: BT · Station: packaging · Base: master at dispatch, after BT15 · Branch: `wave/BT16` · Timebox: 120 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Brief.** Pre-brief written by the CTO on 14 October 2026; the owner agreed the direction that day. Detailed on 15 October 2026 against master `e20f4ca` so that a cook without deep reasoning can carry it out: the "How to build it" section names the functions, the order of the rules, the tests whose expectations the owner's decision changes, and the traps. Line numbers are as of that commit; the head chef checks names against master at dispatch.

## Why

The tool names a project by its GitHub address (BT8a), worked out from the project's remotes in `packages/box-bounty/repository.ts`. Today it refuses whenever the remotes are not all one GitHub repository:

- remotes naming two different GitHub repositories: `repository-address-ambiguous`;
- any remote that is not a GitHub address at all: `github-remote-required`.

So two very common setups cannot use the tool: **the fork workflow** (`origin` is the owner's fork, `upstream` the original project) and **a mirror** (a GitHub remote beside a GitLab or company remote). The refusal is honest, but its only advice is to change the remotes, which most owners will not do for one tool.

The convention for the same problem: `gh` asks once which repository a checkout's commands go to, remembers it for that checkout, and says which it is using from then on (`gh repo set-default`). Here the owner's list of allowed repositories already says which one they mean, so no separate choice is stored. This departs from `gh` on purpose (owner, 14 October 2026): nothing new is stored, so nothing can go stale.

## Outcome

A project with a fork remote or a mirror can be allowed with the same one command. The owner's list of allowed repositories is the only setting involved, and a yes still covers exactly one GitHub repository.

## The rules, in the order the code applies them

These are the whole behaviour. Build exactly this; anything not here stays as it is today.

1. **Read the remotes once.** For each remote name, take its `url` and every `pushurl`. An entry is a *GitHub address* when it starts with `https://github.com/`, `git@github.com:` or `ssh://git@github.com/` and `repositoryAddress` accepts it. Anything else (a path, GitLab, a company host) is *not GitHub*.
2. **Not-GitHub entries are ignored.** They take no part in identity, the tool never pushes to or reads from them, and they never cause a refusal. (A mirror set up as one remote with a GitHub `url` and a GitLab `pushurl` is therefore fine: the tool's own pushes always go to `https://github.com/<owner/name>.git`, never to a named remote; see `remoteGit` and `remoteUrl` in `github.ts`.)
3. **One remote naming two different GitHub addresses** (its `url` one repository, a `pushurl` another) refuses `github-remote-mismatch`, as today. This is the "remote edited to claim the address while pushing elsewhere" case.
4. **The candidates** are the distinct GitHub addresses left, each with the names of the remotes that gave it.
   - No remotes at all: no identity (`null`), as today; `requireRepository` refuses `repository-address-required`.
   - Remotes, but none GitHub: refuse `github-remote-required`, as today, with the message "no remote names a GitHub repository; add one, then run box bounty allow".
   - **Exactly one candidate:** that is the repository. The owner's list is not read. (This is today's behaviour for every project that already works, so they see no change.)
   - **Several candidates:** the owner's list decides. "On the list" means a `repositories` entry whose `bounty` is `allowed` or `ask`. A denied (`null`) or `off` entry is **not** on the list.
     - exactly one candidate on the list: that is the repository, nothing asked;
     - none on the list: the result is *unlisted* (see rule 6);
     - more than one on the list: refuse `repository-several-allowed`, change nothing, name each listed address with its remote, and say: "a yes for one repository never covers another; take all but one off the list with box bounty deny <owner/name>, or work from a checkout whose remotes name one".
5. **URL rewrites, for the chosen repository only.** Run today's rewrite check (the `insteadOf` / `pushInsteadOf` loop at the end of `repositoryIdentity`) over the chosen address's canonical URL and every remote URL that names the chosen address. Rewrites on the other candidates' URLs are ignored: the tool never contacts them. Any rewrite that sends the chosen repository elsewhere refuses `repository-destination-mismatch`, as today.
6. **Unlisted, several candidates.** Nothing is chosen and nothing is stored.
   - `readDecision` returns `decision: null` for this checkout, **even when the all-projects setting says allowed or ask**: the all-projects extra never chooses between remotes. So `post` waits through the normal owner gate (`ownerGate`) exactly as a first post does, with the same exit code.
   - The waiting lines (`ownerWaitLines` in `record.ts`) replace the three generic options with one line per candidate:
     `  allow owner/name (remote origin): box bounty allow owner/name`
     plus the same with `--ask`, written once: `  or ask me each time: add --ask`. The "only this one bounty" option (`box bounty allow <id>`) is **not offered** here, because a one-bounty yes cannot say which repository; if someone runs it anyway it refuses `repository-choice-needed` with the same list and changes nothing.
   - `allow` with no name in this checkout refuses `repository-choice-needed`, listing the candidates and their commands; nothing is written.
   - `requireRepository` (used by `create`, `post`, the gate's preview) refuses `repository-choice-needed` with the same list. `create` itself must still work in such a checkout: check that `create.ts:228`'s use is only for the preview and falls back cleanly, as today's other read paths do with `try { … } catch`.
7. **`allow <owner/name>` with a name** works exactly as today from anywhere, including from a checkout whose remotes do not name it (that is current, tested behaviour: `bt8a.test.ts` "allows an explicit address outside its checkout"). It releases this checkout's waiting bounties only when, after the write, this checkout's identity *is* that address (`currentAddress === address` in `owner.ts`: compute it **after** `writeRepository`, since the write is what settles the choice). When the name is not one of this checkout's remotes and the command runs inside a checkout, add one line: `owner/name is not one of this checkout's remotes; nothing here was released`.
8. **Saying which repository.** When a checkout has several GitHub candidates and one is chosen, the first line of `post`, `look`, `apply`, `close` and `status` output is `acting on owner/name (2 GitHub remotes; the one on your list)`. With one candidate nothing new is printed. One helper builds that line; do not repeat the wording in five places.
9. **Push access, before anything is published.** `publicRepository` in `github.ts` already reads `repos/<owner/name>`. Also require `permissions.push === true` in that response; otherwise refuse `github-push-denied`: "your GitHub sign-in cannot push to owner/name, and the bounty branch goes there; nothing was posted". It runs before any branch push or issue, as the visibility check does. Applies to every post, one remote or several.

## How to build it

**Where the code goes (avoids an import cycle).** `settings.ts` imports `repository.ts`, and `loadSettings` itself calls `repositoryIdentity` while migrating legacy `projects` entries (`settings.ts` around line 261). So `repository.ts` must not read settings.

- `repository.ts` keeps `repositoryAddress` and gains two pure Git functions:
  - `githubRemotes(root)`: rules 1 to 4's reading, returns the candidates with their remote names, or throws the rule-3 and no-GitHub refusals;
  - `chooseRepository(root, listed: ReadonlySet<string>)`: returns `{ kind: 'one', address, candidates }`, `{ kind: 'unlisted', candidates }`, or `null` for no remotes; throws `repository-several-allowed`; runs the rule-5 rewrite check on a chosen address.
- `repositoryIdentity(root)` and `requireRepository(root)` move to `settings.ts`, where the list is: they call `chooseRepository(root, activeAddresses(settings))`. `repositoryIdentity` returns the address, or `null` for *unlisted* or no remotes. `requireRepository` throws `repository-address-required` for no remotes and `repository-choice-needed` for unlisted. Update the imports in `create.ts`, `github.ts`, `owner.ts`, `record.ts` (they move from `./repository.js` to `./settings.js`) and the re-exports in `index.ts`. Keep the function names so callers do not change.
- **The legacy migration** inside `loadSettings` calls `chooseRepository(key, new Set())` directly, never `repositoryIdentity`: with an empty list only a single candidate resolves, and the migration keeps today's rule (two remotes means "no permission moved"). Calling `repositoryIdentity` there would recurse into `loadSettings`.
- **`readDecision`'s early return** (empty list, only the all-projects setting): today it returns the all-projects decision without reading Git. Keep that early return when the checkout has one candidate. To know whether it has several, it must read the remotes; do that read only when an all-projects decision exists (`settings.default !== undefined`), so a command that started no Git process before still starts none. If the K14 budget test (`k14-start-budget.test.ts`) still goes over, **stop and report**; do not raise a budget.
- **The GitHub stand-in.** In `tests/box/bounty/github-fixture.ts` line 136, the `repos/<repository>` answer gains `permissions: { push: state.push ?? true }`, and `GhState` gains an optional `push?: boolean`. Every existing test then behaves as before.
- **Wording** goes through the existing refusal style: reason name, then a sentence that says what happened, what changed (nothing) and the next command.
