# K14: far fewer Git starts, in the tool and in its tests

Milestone: K (kitchen and product speed) · Station: packaging · Base: master at dispatch, after K12 · Branch: `wave/K14` · Timebox: 150 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 12 October 2026 at the owner's direction: the cause is known, so fix it, no experiment first. It cooks only when named. Revised by the CTO against K12's Result on 12 October 2026.

## Why

The K12 cook counted what the bounty suite starts: 11,402 processes, of which Git is 10,496 (92%), the stand-in `gh` 784 (7%), the tool itself 121. With about 215 tests that is roughly 49 Git starts a test, at 30 to 55 ms each on this host and several times that under load. The suite's time is the cost of launching Git ten thousand times to do almost no work. The same waste is in every command an agent runs: 7 to about 30 Git starts per command, one to three seconds on Windows, more on a busy machine.

## What K12 left (its Result, merged at `2b65ce5`)

- The bounty suite went from about 700 s to 320 to 355 s with three workers. Six workers were slower than three (241 s against 212 s on the five biggest files): the suite is bound by process starts, so more parallelism buys nothing and only fewer starts will.
- K12's step 4, building a bounty once per test file and copying it, was not attempted. It is taken up here.
- The count: 11,421 starts in one run, Git 92%, mostly under the fixture repositories; one fixture repository alone accounted for 1,073. The breakdown by Git subcommand was not taken.
- Under six busy processes the suite still hit its 30 s limits. The package suite, unchanged, ran 164 to 308 s with timeouts and is now a large share of a full verify.

## Outcome

The tool asks Git each thing once per command and several things in one call; the tests use Git only where Git is what is being tested; and a test that counts keeps it that way. The bounty suite makes at most a third of the Git starts it makes at K12's close, and no command makes more starts than the budget written down in this wave.

## Done when

- `node scripts/verify.mjs --full` exits 0 on the final commit.
- **First, the count as it stands:** Git starts and `gh` starts for each bounty command through the built CLI on one standard fixture, and for the suite as a whole, by Git subcommand. The same count is taken for the package suite. This is the "before", and the list of what is asked more than once.

**In the tool**

- Within one command, a fact Git has already given is not asked for again: where the repository and its Git folder are, the current branch and commit, each configuration value, the list of tracked files. Questions that can go in one Git call go in one.
- **Nothing remembered outlives the point where it could change.** An answer is reused only while nothing the tool has done since could alter it. The report names each remembered fact and the event that discards it. A solver's content never decides what is remembered: the reviews of BT7 settled that the tool writes no Git configuration, and that must still be true.
- The owner/foreign split (what may run depends on whose content a call works on) is untouched. No call moves from one side to the other to save a start.
- Behaviour is unchanged: every existing test passes as written, and the output of each command on the standard fixture is byte-for-byte the same before and after.

**In the tests**

- **A bounty is built once per test file and copied for each test** that only needs "a posted bounty with a solution waiting" (K12's step 4). Copying is by exact path into the test's own folder; a test that changes its copy cannot affect another, and the pass will try to make one do so. Tests that check the building itself keep building.

- The stand-in `gh` costs at most one process per call, and none where the test reaches the tool as a library.
- A test that checks a decision or a wording (which refusal a state gives, what `status` prints, how a record moves, how arguments and paths are judged) gets its facts as data and starts no Git, **where the code already takes facts as input or can with a small extraction that leaves callers unchanged**. Its assertions stay word for word. Where the logic is too mixed with Git calls to separate that way, the cook lists the place and leaves it; a wider restructuring is a later wave.
- **Every guarantee stays on real Git:** nothing a solver wrote is run, never-ship in both directions, the owner's tree, index and branch untouched, hostile paths, filters, the merge itself. The report lists the tests kept on real Git and, for each test moved off it, why Git was not what it tested.

**So it stays fixed**

- A test counts Git and `gh` starts per command on the standard fixture and fails when a command exceeds its budget. It counts and does not time, so a busy machine cannot make it fail. The budgets are the counts this wave reaches, written in one table in the test.
- The Result gives before and after: starts per command, starts for each suite, and each suite's wall time over three runs with the spread.
- **Under load, once:** the final bounty suite is run against six busy processes started and stopped by the wave (`kitchen-K14-*`) and reported as it is. K12 could not pass this; fewer starts is what should.

## Review lenses

- [x] **Security:** remembering what Git said is the risk. The pass tries to make the tool act on a stale answer: a configuration, branch, commit or file list that changes between two points in one command (a solution being collected, a merge landing, the branch moving, a record edited), and checks each remembered fact is discarded where the report says. It confirms no guarantee's test was moved off real Git, and that a test moved off Git would still fail if the logic it checks were wrong.
- [ ] **User experience:** not applicable; output is unchanged byte for byte.
- [x] **Measurement fairness:** before and after counted the same way on the same fixture and commit; wall times with their spread; a count is reported as a count, not as time saved.

## Notes for the worker

- Refactoring playbook. The tool first, then the tests, then the guard. Stop when the outcome is met.
- Count, do not guess: the list of repeated questions comes from the "before" count, not from reading the code for likely suspects.
- BT7's first cook cut some of this already (configuration read once per repository path in the CLI, the Git folder looked up once) and BT7a cut from that branch. Find what survived before redoing it.
- A long-lived Git process that answers many questions is allowed only if it is simpler than what it replaces and every exit path closes it. If in doubt, combine calls instead.
- Report at the timebox. Do not run on.
- Not in this wave: another runtime (K13), another language, network calls to GitHub, any change to what a command does.
