## Why

The hosted run on master `6cd8a24` (run 39273307351) went red on Linux in `tests/box/bounty/bt15-guarantees.test.ts` › "a solver-added never-ship path is refused before recording or writing owner files" with `Error: ENOENT, No such file or directory '/tmp/box-bt1-posted-scratch-…/remote.git/objects'` (syscall `cp`). A rerun of the same commit passed: it is intermittent. The copy is `cloneWorld` in `tests/box/bounty/github-fixture.ts` (around line 474: `cpSync(master.scratch, scratch, { recursive: true, preserveTimestamps: true })`), which copies the shared posted master world K24 introduced for each test. Suspected cause, **to be confirmed, not assumed**: a Git process left running in the master world's bare remote (`git gc --auto`, which Git may start detached after a push, or `git maintenance`) moves or deletes objects while the copy walks the folder.

## Outcome

- Findings and limits:
  - **Mechanism confirmed.** Node 24's `fs.cpSync` takes a C++ fast path (`CpSyncCopyDir` in `node_file.cc`) when no filter is passed. A `copy_file` failure throws `ThrowStdErrException(error, "cp", dest_str)` — the *destination directory*, not the failed source file. So `ENOENT … posted-scratch-*/remote.git/objects` (syscall `cp`) means a **regular file listed directly inside `remote.git/objects/` vanished between the directory scan and its copy** — a transient `tmp_obj_*`-style file. Nothing deletes `objects/` itself; the dest-path reading is a Node reporting quirk. Reproduced the error shape locally: deleting a dest tree mid-copy yields `syscall=cp` errors naming dest paths; deleting source entries mid-copy yields `stat` errors naming the source.
  - **Candidate writer bounded.** Every push to the fixture's bare remote makes `receive-pack` spawn `git maintenance run --auto` (observed via `GIT_TRACE`); on newer git it is invoked with `--detach` (`maintenance.autoDetach`/`gc.autoDetach` default true), so a git process can outlive the synchronous push and still be working the object store when `cloneWorld`'s `cpSync` runs. `gc --auto`/`maintenance --auto` thresholds (6700 loose / 50 packs / 100 loose / 100 commits) are far above the fixture's ~6–15 loose objects, so the exact transient file was not identified beyond "git housekeeping in the copied world". The fix removes the whole class: `gc.auto=0` + `maintenance.auto=false` pinned on the world repo, bare remote and solver clones at creation — with it, `GIT_TRACE` shows **no** maintenance/gc spawned on push. Retry-once-on-ENOENT around `cpSync` added as the documented second line for any non-git transient writer.
  - **Reproduction:** not reproduced on this host — 30/30 runs green pre-fix (2 runs in an earlier loop failed only on 30s timeouts while race probes loaded the host — load artifact, per station card) and **30/30 green post-fix**. The hosted failure is intermittent on Linux and needs the CI git's detached-maintenance path plus timing.
