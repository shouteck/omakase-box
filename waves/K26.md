# K26: what every agent on the project shares, and what stays on one machine

Milestone: K (kitchen) · Station: evidence (also packaging) · Base: master at dispatch, after BT29 · Branch: `wave/K26` · Timebox: 180 minutes; at expiry the cook stops and reports what it has

**Brief.** Written by the CTO on 17 October 2026 after a design discussion with the owner. A design investigation: **it changes no product code and no test.** Its product is a field-by-field design, the evidence from an experiment with fresh agents, and a ready-to-brief outline for BT30, which builds it. Detailed for a cook without deep reasoning.

## Why

K25 found that a bounty record (`.box/bounties/<id>.json`) mixes three kinds of content, and the tool says nothing about whether to commit it. Committing it today publishes local, machine-only detail (the tool posts only from public repositories); not committing it means an agent on another machine, or a later agent, knows nothing of the bounties: what exists, what each was for, what was already tried, how they fit the larger job. **The owner wants the bounty mental model shared by every agent working on the project, on any machine, now and later** (17 October 2026).

**The owner's decisions of 17 October 2026, which bind this design:**

1. **Split the record** into a shared part, committed with the code, and a local part, kept out of Git by default.
2. **Three audiences, not two:** *anyone* (what is already public on the issue); *the project's agents on any machine* (the shared mental model); *this machine only*.
3. **The why and what was tried are shared, and so public in a public repository, in the spirit of a commit message.** The tool tells the agent once, at `create`: what it writes in them is shared with everyone who can read the repository; write them like a commit message. The secret scan covers those fields as it covers the task.
4. **Drafts stay local until posted.** Nothing enters the shared part before the owner has allowed posting (it would publish the task without their yes).
5. **Machine-local detail never goes out:** branch, uncommitted-file list, local paths, pending owner questions, scan findings, rejected solutions' text.

This reverses BT15's "the why is private" (`docs/box-v4/BOUNTY.md` "Return to the job"; `waves/BT15.md`), and restores PLAN.md's 11 October rule that the why and the tried-note reach the solver.

## The worked example the design must serve

On her laptop, Agent A is migrating login to OAuth. She cannot fix a flaky token-refresh test after three tries and creates a bounty: task "Make `test_token_refresh` pass reliably…"; why "tried 3 fixes (retry, longer timeout, freezing time); suspect clock skew in the mock; cheaper to hand off"; part of "OAuth migration"; resume note "was halfway through moving the session store; uncommitted edits in `auth/session.ts`". Locally: branch `oauth-wip`, a folder path, one scan finding, two rejected solutions. A week later Agent B, on another machine, continues the project. B must know: the bounty exists and is part of the OAuth work (do not fix the same test in parallel); what was tried and suspected (do not repeat it); that the session-store move is half done (the larger job is unfinished). B does not need A's branch, uncommitted files, path, scan finding or rejected solutions.

## Outcome

A design that places every piece of a bounty's content in exactly one of three tiers, says where each tier lives and when it is written, splits fields that mix tiers (the resume note does), and is backed by an experiment showing that a fresh agent with only the shared part avoids duplicate and repeated work that an agent without it does not.

## Method: five steps, in order, with a time budget each

**Step 1: classify every field (40 minutes).** One table, one row per field of `BountyRecord` and its nested types (`resume`, `content`, `attempts[]` items, `events[]` items, `waiting`, `scanFindings`, `allowedBy`, `github` and its sub-fields, `reward`, `partOf`, `conflicts`, legacy fields), plus `.box/bounties/OPEN`, `.box/hook-told.json`, `.box/hook-on.json` and `.box/limits.json`. Columns: field; what it holds; already public on the issue or branch? (yes, no, partly); tier (anyone / project agents / this machine); and the reason. Start from K25 step 4.2's lists. Rules:
- A field that holds machine state (a path, a local branch, an uncommitted-file list, a timestamp of a local action, a pending owner question) is **this machine**.
- A field that holds knowledge another agent needs to avoid duplicate or repeated work, or to understand the larger job, is **project agents**.
- A field already on the public issue is **anyone**, whichever tier it would otherwise be.
- Text written by a stranger (pull-request descriptions, comments) stays where it is today (`fromOthers` rules apply) and is **this machine** unless it is the merged solution's.

**Step 2: split the mixed fields (25 minutes).** Name each field that mixes tiers and propose how to split it. At least: the resume note (the larger job and where it stood, shared; the uncommitted files and branch, local); the generated note (`content.note`, built from local changes); events (dates of public milestones, shared; local reasons, local). For each, say whether the agent writes two things at `create` or the tool derives the split, and which costs the agent less. **Prefer no new `create` option:** an existing field may change tier, or the tool may derive the split.

**Step 3: where each tier lives and when it is written (25 minutes).** Propose the layout, for example: `.box/bounties/<id>.json` holds only the shared tiers and is committed; `.box/local/` holds the machine tier, with a `.box/local/.gitignore` containing `*` (the pytest, mypy and ruff convention); a draft lives entirely in `.box/local/` until it is posted. Say for each: when it is written (only at milestones for the shared file: posted, solution merged, closed, part-of changed; never on reads), how two machines changing the same bounty would conflict and how often, and what happens to the five existing records in this repository (they are tracked and public today; `tests/box/bounty/bt23.test.ts` reads them from the checkout). Check every reader in `render.ts`, `json.ts`, `find.ts`, `hook.ts` and `instructions.ts`: which tier each needs, and whether a fresh clone with only the shared tier still shows a correct `status`, `find` and instruction block (K25 found the block and `OPEN` never sync on read; say whether a clone that pulls records needs that fixed).

**Step 4: the second-machine experiment (65 minutes).** Prove the design with fresh agents before anyone builds it.
- Build a scratch project (a small real program with a flaky test and a half-done refactor, in the shape of the example) and, with the built tool against the GitHub stand-in, create and post two bounties in it as Agent A would, with real why, part-of and resume text.
- Make three clones that differ only in what they carry: **(a)** the full records as today; **(b)** only the shared tiers as the design proposes (write them by hand in the proposed shape); **(c)** nothing but the public issue text.
- Start three fresh agents (the head chef dispatches them; the cook prepares the worlds and the instructions, and is not one of the agents), one per clone, each told only: "continue the OAuth migration in this project; use whatever tools are here." Record each transcript.
- Score each on fixed questions, from its transcript: did it notice the open bounty before touching the test (yes/no); did it try any of the three already-failed fixes (count); did it pick up the unfinished session-store work (yes/no); what did it read to learn this. The design passes if (b) scores as well as (a) on all four and better than (c).
- If the head chef cannot start fresh agents on this host, the cook stops step 4 at the prepared worlds and the Result says so; the head chef runs the agents and appends their transcripts.

**Step 5: the design and the BT30 outline (25 minutes).** Write the report (below) and a BT30 outline: the field moves, the new layout, the migration of existing records (including this repository's five, moved into a test fixture so the BT23 test keeps working), the once-told line at `create` (exact wording, within BT17's output budget), the scan over the newly shared fields, and the tests BT30 must add (at least: a draft writes nothing to the shared file; a post writes the shared file once; a read writes neither; a fresh clone with only the shared tier answers `status`, `find` and `status --json` correctly).
