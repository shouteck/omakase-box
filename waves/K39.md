## Why

PLAN.md's engineering roadmap states four scale targets nobody has measured, so each is currently an untrue statement waiting to happen:

| Target (PLAN.md) | Today (K30) |
|---|---|
| `create` under 1 s on a 10,000-file repository | not measured |
| one whole `post` under 30 s | only the push leg measured (`tests/box/bounty/measure-post.mjs`) |
| `status` and `look` stay usable with 100 solutions on one bounty | not measured |
| `apply` and `close` stay cheap with 1,000 records in the store | not measured (K25 measured reads only) |

## Outcome

`kitchen/memory/scale/measure.mjs` measures all four on this host against the built CLI and the GitHub stand-in, and `kitchen/reviews/K39-scale.md` reports each target as met or missed, with numbers, spread and the host's load beside them.

## What to measure

Each measurement: five runs, median and range reported, wall time from process start to exit of the built CLI (`packages/box-cli/dist/…`), scratch repositories outside the checkout, scratch settings, the stand-in for GitHub. State the host's CPU load beside each run (the evidence card's rule).

1. **create on 10,000 files:** a scratch repository with 10,000 tracked files across nested folders (realistic sizes, a few large), a handful of uncommitted edits and untracked files; `box bounty create --task TASK.md --why "scale"`. Also 1,000 and 100,000 files, so the curve shows.
2. **whole post:** from `post` start to exit, against the stand-in with a local bare remote, for a project with 0, 5 and 50 unpushed commits and with `--with-changes`. Note which part dominates (push, scan, GitHub calls) from timing within the run if the tool's own output allows; otherwise from repeated runs with each part removed.
3. **100 solutions:** one posted bounty with 100 pull requests in the stand-in (each a real commit on the bare remote); time `status`, `status --full`, `status --json`, `look <id> 1` and `look <id> 100`; also the output size of `status` (BT28's bounds must hold).
4. **1,000 records:** a store with 1,000 records (K25's generator) plus one posted bounty with one solution; time `apply` and `close` on it, and on the same bounty with 10 records, to show whether cost grows with the store.
