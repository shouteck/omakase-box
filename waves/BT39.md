**Brief.** Written by the CTO on 20 October 2026 from K39 (`waves/K39.md`, `kitchen/reviews/K39-scale.md`, `kitchen/INBOX.md`). Detailed for a cook without deep reasoning. Cook: medium; reviewer: medium.

## Why

K39 measured, five runs each, on this host:
- **`create` crashes on a 100,000-file project, every time.** `snapshot.ts` (around line 70) lists the captured tree with `git ls-tree -r -z` through the shared helper in `packages/box-bounty/git.ts` (around line 204), whose `spawnSync` sets no `maxBuffer`; Node's 1 MiB default overflows (`ENOBUFS`). This is the same class of bug as K15-ci (the evidence card's rule: Git output that grows with history or size needs an explicit buffer and a named failure). Other `spawnSync` calls in the same file set 512 MiB (`cat-file`, around lines 337 and 352); the generic helper does not.
- **`create` is slow:** median 20.6 s at 10,000 files (2.3 s at 1,000), about 2 ms per file. PLAN.md's target (under 1 s at 10,000) was never derived from anything; nobody knows yet where the time goes.
- **`status` takes about 8.7 s with 100 solutions on one bounty** (steady state; 9.1 s on first discovery), though its output is bounded. A command an agent runs in its loop should not take nine seconds.

## Outcome

`create` never fails because of a project's size; `create` and `status` are measurably faster, with the cause of their cost named from a profile; and PLAN.md's scale targets for them are replaced by numbers derived from the profile and from an agent's needs.

## Part 1: no buffer limit anywhere (do first)

1. In `git.ts`, give the generic helper's `spawnSync` the same explicit large `maxBuffer` the `cat-file` paths use, and make an `ENOBUFS` (or any `result.error`) a **named** failure (`git-output-too-large` or the existing `GitFailed` with the command named), never a silent truncation.
2. Audit every `spawnSync`, `execFileSync` and `spawn` in `packages/box-bounty/` and `packages/box-cli/src/` (`grep -n "spawnSync\|execFileSync\|spawn("`): list each in the Result with its `maxBuffer` and whether its output can grow with project or history size; fix every growing one the same way.
3. Test cheaply (a 100,000-file fixture takes about 30 minutes): a repository holding one blob larger than 2 MiB, read through the generic helper (for example `git show <blob>` or `git ls-tree` over a tree with a very long listing built by `git mktree`), fails on master with `ENOBUFS` and passes after the fix. Then rerun K39's target 1 at 100,000 files **once** (`node kitchen/memory/scale/measure.mjs --target=1`, adapted to run only the 100,000 size if needed) to show `create` completes, and record its time.

## Part 2: profile, then fix the biggest causes

1. **Profile before changing anything.** For `create` at 10,000 files and `status` at 100 solutions (K39's fixtures, `kitchen/memory/scale/measure.mjs`), record: the number of Git and `gh` process starts (the K14 spy, `tests/box/bounty/k14-start-budget.test.ts`, shows how) and a CPU profile of the CLI (`node --cpu-prof packages/box-cli/dist/cli.js …`, profile files in a scratch folder outside the checkout). Name, with numbers, what dominates: per-file process starts, per-file filesystem checks (never-ship's link and case checks), reading every file for the secret scan, the snapshot's index work, or something else; for `status`, whether it is per-solution Git reads, per-solution merge checks, or rendering.
2. **Fix the top one or two causes for each,** without changing behaviour: batch per-item Git calls into one (for example one `git ls-files`/`cat-file --batch` instead of one call per file), avoid re-reading what the record already holds (`status` re-deriving facts K31b showed are stored at collection), and remove repeated filesystem walks. Each fix keeps every existing test green; the never-ship and scan guarantees (CONTRACTS.md C1 to C4) must still bite (repeat K30's C1 bite in a scratch copy after the change).
3. **Measure again** with K39's script: `create` at 1,000 and 10,000 files, `status` at 100 solutions, five runs each with spread and host load.
