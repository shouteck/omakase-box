# BT73: the why is described truly, and one test watches everything that leaves

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT73` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short. Bug fix playbook (part 1), feature playbook (part 2); principles: prove-it-works, fix-root-causes.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `create` with the owner, who asked for this wave ("All three").

**Part 1, a false sentence.** Every place the tool describes the `--why` line says it is never published:
- `create.ts:133`, the `missing-why` refusal: "It is kept only in the record, never shipped";
- `create.ts:248`, the preview: "(record only — never shipped)";
- the comments at `create.ts:48`, `create.ts:50` (`--part-of`, "record only") and `record.ts:252`;
- the comment in `publish-plan.ts` `planGitHub` ("`job`, `why`) documented as never shipped", split over two lines, so a one-line search misses it). The record files themselves really do stay off the bounty branch; only the sentence's reason is wrong.

That was true before BT32. Since then, `sharePosted` (`chain.ts` near line 306) puts `why` (and `partOf`) into the `posted` event of the bounty's shared memory. That memory is a Git ref pushed to the repository on GitHub, so for a public repository anyone who fetches it can read the why. The tool knows it: `SCANNED_FIELDS` scans the why for secrets before sharing. But an agent that believed the sentence might put in the why what it would never put in public. A false sentence the tool tells an agent is a defect (AGENTS.md: "the tool states facts").

**Part 2, a test of every exit.** Each guard has tests of its own (C1, P2, R3 and the rest; `proof-map --check`; the K66 audit of 22 breaks). No test checks the one property all of them serve: **nothing never-ship and nothing secret-shaped is in anything the tool sends out, over a whole journey.** Such a test also catches a guard that a new code path forgets to call, which per-guard tests cannot.

## Outcome

1. Every sentence and comment about the why says what is true: it is not in the issue, it is in the project's shared memory, and on a public repository that memory is public. The same for `--part-of`.
2. One journey test plants never-ship files and secret-shaped values in every place a bounty could pick them up. It runs `create`, `post` (with and without `--with-changes`, with an `--include` of a planted file refused), a solution, `apply` and `close` against the stand-ins. Then it inventories **everything the outside world holds**: every ref and every reachable object in the stand-in remote, every issue, comment and pull request in the stand-in GitHub, and every request the stand-in board received. It finds none of the planted paths or values.

## Traps

- No secret-shaped literal in any committed file, test files included: build it at run time (`tests/box/bounty/secret-literals.test.ts`).
- The inventory must read objects, not only ref names: a leak hides in a blob.
- The stand-in GitHub keeps request bodies in its state file; read that file, not the tool's record of what it sent.
