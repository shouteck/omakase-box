# PF56: the money path, proven by one deterministic script in the providers' sandboxes

Milestone: platform · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF56` · Timebox: 300 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-01-pay-on-merge
Horizon: long: real providers, a throwaway deploy and a browser; starts with `/plan`. Feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the board with the owner ("I agree with your recommendation"). The owner's conditions:
- every check is **deterministic**: a script, never an agent (owner, 23 November 2026);
- it runs against the providers' **sandboxes only**: live keys are never used, and live behaviour is trusted to match the sandbox's.

**Why.** The board is not a read-only mirror. It writes:
- sessions;
- saved cards;
- the card's maximum per bounty (each repository's pay-on-merge switch and amount, until [PF59](PF59.md) removes them);
- solvers' Stripe accounts and PayPal connections;
- charges on merge;
- payment states from webhooks.

The tool depends on what it answers: `discover`, `take`, the solver's `status` and `close`'s pay message all read it.

Every hosted run checks the money rules against **our own** stand-ins (`tests/platform/stripe-standin.ts`, the PayPal stand-in). Real Stripe test mode was used once, by hand, in PF11, which lists what it did not prove:
- saving a card on Stripe's own page in a real browser;
- a solver's disconnect;
- a dispute's webhook.

`scripts/live-providers.mjs` checks configuration only. So if Stripe's real answers differ from our stand-in, or change, the suite stays green while payments break. Nothing can be re-run to find out.

## Outcome

1. **One script, `scripts/sandbox-money.mjs`, runs the whole money path against the sandboxes.** Same inputs, same result:
   - a throwaway board, deployed as its own Worker named `kitchen-pf56-<run>` with its own database, sandbox keys and webhook endpoint;
   - the sandbox repository `shouteck/box-bounty-sandbox` (`kitchen/sandbox.md`);
   - Stripe test mode, and PayPal's sandbox once PayPal ships.

   The script is never an agent. Its fixed steps:
   1. sign in as the test owner;
   2. save a card on Stripe's real Checkout page, driven by the repository's pinned browser with Stripe's published test card;
   3. set the card's maximum per bounty (before PF59: turn pay on merge on for the sandbox repository at an amount);
   4. onboard a test solver account;
   5. post a $1 bounty with the tool;
   6. open a solution as the solver, and merge it on GitHub;
   7. wait for the charge and the webhook;
   8. refund it;
   9. raise a dispute with Stripe's published dispute test card, and wait for its webhook;
   10. a card that requires authentication: the board settles `owner-must-authenticate`, and the owner's page finishes it in the browser;
   11. the solver disconnects; a merge then names no payee.
2. **Every wait is bounded and named.** A step polls the board's own state for its expected value with a fixed deadline; nothing is tuned by hand. Running out of time is a failure stated as one: "the dispute webhook did not arrive in 120 s". It is never retried until it passes.
3. **Every resource is named for the run and removed at the end, pass or fail:** the Worker, the database, the webhook endpoint, the test customers and accounts, the issue, the branches and the chain ref. The script's last step lists what it removed, and anything it could not.
4. **The stand-ins are held to the sandbox.**
   - The script records the **shape** of each real sandbox answer it used, as a fixture in `tests/platform/provider-shapes.json`: field names and types, never values, keys or ids.
   - A test in the ordinary suite compares our stand-ins' answers with that fixture, so a stand-in that drifts from the real API fails in every hosted run, with no network and no keys.
5. **Old copies of the tool keep working.** A test in the ordinary suite installs the last published `omakase-box` from npm, at an exact version read from the registry and recorded in the Result. It runs `discover`, `take --preview` and the solver's `status` against the current board built locally (`local.mjs`, the GitHub stand-in), and each must answer without an unreadable-board refusal.
6. **When it runs:** the sandbox script by hand, before each board deploy, and named in `packages/box-platform/DEPLOY.md` as a step before deploying. The shape test and the old-tool test run in every hosted run.

## Stops

- Deploying the throwaway Worker and using the sandbox keys are covered by this milestone's go, as in PF11 and PF18. If the script needs anything else that costs money, a new paid service, or a new remote destination, stop and bring the owner one recommendation.
- If the sandbox shows a money rule answering wrongly, record it and continue the run. Do not change the rule in this wave.

## Traps

- **No key, token, card number or account id in the repository, the fixture or the Result.** Shapes only. Read keys from the environment the owner sets, never from `.env*` or `secrets/` (AGENTS.md rule 5).
- **Stripe's sandbox webhooks arrive at their own pace.** Wait on the board's recorded state with a deadline. Never `sleep` a guessed time.
- **The live board lists nothing from the sandbox repository** (`UNLISTED_REPOSITORIES` in `wrangler.toml`). The throwaway board must not set it, or nothing lists.
- **Cleanup must run even when a step fails,** and must touch only resources named `kitchen-pf56-<run>` (AGENTS.md rule 6).

## Lenses

- [x] **Measurement fairness:** both runs give the same step results. Any difference is a finding about determinism and is explained, not averaged away.
