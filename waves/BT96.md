# BT96: the store lives where Git keeps its own, and no event is lost

Milestone: BT (the bounty tool) · Area: Records (one writer) · Station: packaging · Base: `master at dispatch`, after BT99 merges · Branch: `wave/BT96` · Timebox: 300 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-26-bt96-simple-move, D-2026-11-26-never-twice-is-hard, D-2026-11-26-chain-expected-head
Horizon: medium to long: a one-time move of every checkout's store, and a write-path change under shared memory; starts with `/plan`. Bug fix playbook; principles: fix-root-causes, boundary-discipline, prove-it-works.

**Brief.** Rewritten by D3vin on 26 November 2026 with the owner, after BT101 absorbed the original brief's compare-and-swap ([BT101](BT101.md), Outcome 1 and its split table). It rests on two read-only reports by Records: the code's facts (`bots/Records/reports/bt96-facts.md`) and the references (`bots/Records/reports/bt96-references.md`). Every design choice below names the reference it follows.

**Why.** The local store is `.box/local/box.db` in each checkout. Since BT101 it holds five tables: `records`, `events`, `outbox`, `shared` and `meta`. Four faults remain:

1. **`git clean -fdx` deletes every local record.** `.box/local/` is ignored, so `-x` removes it: drafts, resume notes, scan findings, attempt reports, the event log, owed outbox rows and the chain provenance keys (`chain_authored:`, `chain_pushed:`, `chain_tip:`). Without those keys, an owed shared-memory push is never retried.
2. **Each worktree has its own store**, while branches, refs and merge recognition are shared. A bounty made in one worktree is invisible in another. The kitchen's own bots now work in worktrees.
3. **Two appends to one bounty's chain can hide one of them.** `appendEvent` reads the tip, then `commitEvent` moves the ref with no expected old value (`chain.ts` 177–193, `git.ts` 490–493). Two racing appends both build on the same tip, and the later ref update hides the earlier event. The losing store's owed row then names a tip that is no longer the ref, and retry skips it (`chain.ts` 715–718).
4. **Every command reads the whole outbox**, and settled rows stay forever (BT101 question 6, BACKLOG). The cost grows with every bounty ever posted.

A checkout inside a synced folder can also corrupt SQLite silently. That part of the original brief stands (Outcome 5).

## Outcome

1. **The store moves to the shared Git folder** (D-2026-11-26-bt96-simple-move).
   - The path is `git rev-parse --git-path common/box/box.db`. Git keeps everything under `common/` in the common directory for every worktree. Verify that against Git's documentation and `path.c` before relying on it; if it doesn't hold, use `git rev-parse --git-common-dir` and `box/box.db` under it, never `.git` appended to a path.
   - The folder is checked component by component as `checkInside` does today: a link or a non-directory refuses `local-store-path-blocked`.
   - What stays in the working tree: files meant for the agent to read (`look --export`'s `.box/local/solutions/`) and the old JSON compatibility input.
2. **The first worktree to open moves its store, once.**
   - `VACUUM INTO` a temporary file beside the new path; row counts compared per table; the temporary file renamed into place only if no store is there yet. The old file is renamed `box.db.moved-<date>` and left. Never delete.
   - Two worktrees racing the first move: exactly one store results. The loser opens the winner's store and joins it as a later worktree (Outcome 3).
3. **A later worktree's old store joins by bounty, never by merge.**
   - A bounty whose id is not in the shared store is imported whole: its `records` row, its `events` with their own sequence numbers (they are numbered per bounty, so nothing is renumbered), its `outbox` rows, and its `meta` provenance keys (`chain_authored:<id>`, `chain_pushed:<id>`, `chain_tip:<id>`).
   - A bounty in both is **not** imported. The tool says once: "`<id>` has a different local history in `<worktree>`; kept the shared store's; the other is in `<file>`, which nothing reads". When that copy has owed outbox rows, each is named by kind ("an issue", "a decision comment", "a shared-memory push", "a board hint"), so nothing owed is silent.
   - The old file is renamed `box.db.moved-<date>` and left, readable.
4. **Shared-memory ref updates name the old value** (D-2026-11-26-chain-expected-head). `commitEvent` moves the chain ref with `update-ref <ref> <new> <old>`. A mismatch re-reads the tip and builds the event on it once; a second mismatch refuses `chain-changed` ("`<id>`'s shared memory changed while this ran; nothing was written; next: run it again"). An owed row keeps naming the tip it was built on.
5. **A synced checkout is named once, and the store adapts.** Unchanged from the original brief: when the checkout is inside a known synced folder (`OneDrive`, `OneDriveConsumer` and `OneDriveCommercial` environment variables; the paths in Dropbox's `info.json`; `~/Library/Mobile Documents`), say once: "this checkout is inside `<folder>`, synced by `<service>`; sync can corrupt SQLite databases and Git repositories while they are in use; keep projects outside synced folders". The store then opens with `journal_mode=DELETE`, not WAL. Nothing is refused.
6. **The outbox reads only what is owed** (D-2026-11-26-never-twice-is-hard). An index on `outbox(state)`; `retryPending`, `status` and `boardTold` ask SQLite for the rows they need instead of filtering every row in code. No row is deleted, now or by a later wave, without a test proving that a pruned key is never owed again. BACKLOG records that, and that clearing a sent row's payload while keeping its key (NServiceBus) is the one pruning the rule allows.
7. **Copies of a live database use `VACUUM INTO`**, never a file copy.
8. **The docs name `node:sqlite`'s status:** a release candidate from Node 24.15, experimental on the tool's minimum, Node 22.13. The packaging tests on three systems catch an API change.
9. **The hook's state follows the store.** [BT93](BT93.md) moves `hook-told.json` and `hook-on.json` under `.box/local/`. BT96 lands first, so this wave writes in BT93's brief that they go beside the shared store.

## Traps

- **The JSON compatibility import becomes dangerous once the store is shared.** `syncJsonFiles` (`store.ts` 514–574) deletes rows whose tracked files have disappeared. With one store for every worktree, a worktree without the files would delete rows another worktree imported. Each imported row must remember the checkout it came from, and only that checkout's sync may remove it. Test it with two worktrees.
- **`.git` can be a file** (a worktree, a submodule): ask Git for paths.
- **On this host `.git` belongs to the owner's Windows account** (AGENTS.md, Environment). Chain refs are already written under it, but test that a store there opens on the Windows runner.
- **Never hold a write transaction across a network call**, and never across a Git call that can wait.
- **The move must never lose a row:** copy, compare, rename into place. Never delete in this wave.
- **Not in this wave**, BACKLOG only: the fold ignores `dropped` although its comment says it ends the row (`fold.ts` 52–54, 69–70), and nothing checks for an impossible lifecycle such as applied, then a merge noticed again (`fold.ts` 69–82).

### The `common/` path check

The claim holds, with one naming detail to keep exact: `git rev-parse --git-path common/box/box.db` resolves to `<git-common-dir>/common/box/box.db`, not `<git-common-dir>/box/box.db`.

Evidence:

- Git's repository layout documentation says that with multiple working trees most of `$GIT_DIR` is per-worktree, but "All files under 'common' however will be shared between all working trees" (`Documentation/gitrepository-layout.adoc`, `common::`, lines 180-184 in current master).
- `git-rev-parse` documents `--git-common-dir` as `$GIT_COMMON_DIR` if defined, else `$GIT_DIR`, and `--git-path <path>` as resolving `$GIT_DIR/<path>` with Git's path relocation rules (`Documentation/git-rev-parse.adoc`, lines 268-283).
- `git-worktree` says `--git-path` chooses `$GIT_DIR` or `$GIT_COMMON_DIR` depending on the path and warns not to assume which without Git's rules (`Documentation/git-worktree.adoc`, lines 381-392).
- In `path.c`, `repo_git_pathv` appends the requested path under the worktree gitdir and calls `adjust_git_path`; when the repository has a separate common dir, `adjust_git_path` calls `update_common_dir` (`path.c` lines 387-429 in current master). `update_common_dir` checks the path against the common-path trie and replaces the worktree gitdir prefix with `repo->commondir` (`path.c` lines 351-360).
- Empirical check in this repository's linked worktree `bt96-docs-plan`: `--git-dir` was `C:/Users/shout/orca/omakase-box/.git/worktrees/bt96-docs-plan`, `--git-common-dir` was `C:/Users/shout/orca/omakase-box/.git`, and `--git-path common/box/box.db` was `C:/Users/shout/orca/omakase-box/.git/common/box/box.db`. In the main checkout the same query was `.git/common/box/box.db`. By contrast `--git-path box/box.db` in the linked worktree was the per-worktree path `.git/worktrees/bt96-docs-plan/box/box.db`.

So Outcome 1 can use exactly `git rev-parse --git-path common/box/box.db`. The implementation must not "correct" the extra `common/` component away: that component is the documented opt-in namespace Git uses for shared files. The fallback, if a supported Git version fails to resolve it this way, is `<git rev-parse --git-common-dir>/box/box.db`, with the difference named in the wave Result.

### Amendments before code (D3vin review, 26 November 2026)

1. **Atomic installation.** The copy temporary file is created beside the destination and installed with `fs.linkSync(temp, destination)`, then `temp` is unlinked. Hard-link creation fails with `EEXIST` if a racer won, unlike `fs.renameSync` on Windows. If hard links are unavailable the fallback is an exclusive `wx` lock file in the destination folder held across copy, compare and rename; the chosen primitive is named in the Result. The race test runs on the Windows hosted runner.
2. **WAL companions.** Before moving, checkpoint with `PRAGMA wal_checkpoint(TRUNCATE)`, close every connection this process holds, and require any remaining `-wal` to be empty. A non-empty WAL means the store is not quiescent: do not move it. Empty `-wal`/`-shm` companions, if still present, are renamed beside the moved database; they are never paired with the new destination.
3. **An open old store.** First rename `box.db` to a recovery-named `box.db.moving-<id>` before installing the shared copy. On Windows `EBUSY`/`EPERM` (or another rename failure) stops there: no destination is installed, nothing is half-moved, and the command prints `local-store-move-deferred` with the store path and process action needed; the next open retries. While any move is deferred or refused, the command keeps reading and writing the old store, says so, and never opens an empty shared store. If the first rename succeeds, copy from the renamed file, compare, install with the atomic primitive, then rename it `box.db.moved-<date>`; a crash before completion is recoverable because the renamed original still exists.
4. **Corruption preflight.** Before any rename run `PRAGMA integrity_check` and parse every event payload in the old store. Either failure refuses the move with `local-store-corrupt`, names the failing check and store path, and leaves the old store in place and in use. A corrupt-store fixture proves no destination appears and the old store still opens.
5. **Windows account ownership.** The hosted Windows runner test opens the store under the common Git folder, writes one row, closes and reopens it. This covers the `.git` ownership trap on the real platform.
6. **First chain append.** Expected-head uses `git update-ref <ref> <new> the all-zero object id for the repository hash length (40 zeros for SHA-1, 64 for SHA-256), derived rather than hard-coded, when the ref should not yet exist, so two racing first appends cannot both create it. The chain-race test covers both first appends racing and later appends racing.

### Main risks being designed around

- The destination path is shared, but the old stores are per-worktree; migration must distinguish "first move" from "later join" by whether the shared store already exists, never by checkout order assumptions.
- `VACUUM INTO` must not overwrite an existing destination; the final rename is the collision point.
- No write transaction may span GitHub, network, or a Git call that can wait.
- Sequence numbers stay per bounty and are not renumbered; `outbox.event_seq` therefore remains valid for imported unique bounties. Duplicate bounties are not imported at all in this wave.
- The hard never-twice rule means no deletion of sent outbox keys in this wave.
