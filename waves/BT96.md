# BT96: two commands cannot undo each other's record changes, and the store lives where Git keeps its own

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT96` · Timebox: 300 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: medium to long: a write-path change under every command, and a one-time move of every checkout's store; starts with `/plan`. Bug fix playbook; principles: fix-root-causes, boundary-discipline, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the local store (`packages/box-bounty/store.ts`, `record.ts`) with the owner ("yes").

**Why.** Each checkout keeps its records in one SQLite database, `.box/local/box.db` (BT31). The store is careful: link-checked, self-ignoring, WAL with a 5-second wait for a concurrent writer, and compatible with older JSON files by fingerprint. Three faults remain:

1. **Lost updates.** `persistRecord` (`record.ts`) calls `writeStored`, which upserts the whole record as this process loaded it. It never checks whether another process wrote the same record in between.
   - The hook loads records, then spends up to 20 seconds refreshing GitHub (`HOOK_GITHUB_BUDGET_MS`), then writes.
   - If the agent runs `apply` in that window, `apply` marks the bounty `applied`, and the hook then writes its older copy back. The bounty is open again.
   - The next command recognises the merge again: a second `merged` chain event, and the pay message repeated. The comment markers prevent duplicate GitHub comments, but the record and the shared memory disagree with what happened.
2. **A routine `git clean -fdx` deletes every local record.** `.box/local/` is ignored, so `-x` removes it. Posted bounties come back from the shared memory (BT52). Lost for good:
   - drafts;
   - `--resume` notes;
   - local state;
   - the chain provenance keys (`chain_pending:`, `chain_authored:`), without which an owed shared-memory push is never retried.
3. **Each worktree has its own store.** A bounty created in one worktree is invisible in another worktree of the same repository, while branches, and so merge recognition, are shared.

How established Git tools keep local state: inside the repository's Git directory, which `git clean` never touches and which every worktree shares through `git rev-parse --git-common-dir`. Git LFS uses `.git/lfs/`, rerere uses `.git/rr-cache/`, and this tool's own shared memory already lives in Git refs.

## Outcome

1. **Every record write is a compare-and-swap.**
   - Schema version 5 adds a `rev` integer to each row.
   - A record loaded from the store carries the revision it was read at, out of band: a `WeakMap` from the record object, never in its JSON, so its shape is unchanged.
   - `writeStored` writes inside its `BEGIN IMMEDIATE` only if the row's `rev` is still that revision (`UPDATE … WHERE id = ? AND rev = ?`), and bumps it. A record new to the store inserts with `rev = 1`.
   - A mismatch writes nothing and raises `record-changed`.
2. **Each caller handles a conflict by what it is doing:**
   - **A command the agent ran** (`post`, `apply`, `close`, `allow`, `config set paid`, `take` and the rest) refuses `record-changed`: "`<id>` changed while this ran (another omakase-box command or the hook wrote it); nothing was written by this command; next: run it again". Its outward effects keep their existing retry safety: the markers and `recoverIssue`.
   - **A background refresh** (the hook's `refreshGitHubStatus`, the merge scan's `landingChecks`, the shared-memory settle) reloads the record and reapplies its own small change once, through a new `updateRecord(repoRoot, id, change)`. The `change` is a pure function, with no network inside the transaction. If the record changed again, it skips and says so in its notice line. It never overwrites.
3. **The store moves to the shared Git folder:** `<git-common-dir>/box/box.db`. `git clean` never removes it, and every worktree of one repository shares it.
   - **The move happens once,** on the first open after this wave: `VACUUM INTO` the new path, row counts compared, then the old file is renamed `box.db.moved-<date>` and left. Its rows stay readable until the owner deletes it.
   - **A second worktree's old store** is merged in when that worktree is first used. A row whose id is new is imported. A row that exists in both keeps the one with the later `updatedAt`, and the other is named once: "`<id>` had two copies, in `<worktree a>` and `<worktree b>`; kept the later".
   - **The folder is checked** component by component like today's `checkInside`: a link or a non-directory refuses with `local-store-path-blocked`.
   - **What stays in the working tree:** files meant for the agent to read (`look --export`'s `.box/local/solutions/`), and the old JSON compatibility input.
4. **The hook's state follows the store.** [BT93](BT93.md) moves `hook-told.json` and `hook-on.json` under `.box/local/`. Whichever of the two waves lands second puts them beside the store, so they survive `git clean` too.

## Traps

- **Never hold the write transaction across a network call.** `updateRecord`'s change runs inside `BEGIN IMMEDIATE` and must be pure; compute anything that needs GitHub first.
- **`.git` can be a file** (a worktree, or a submodule): resolve the common directory with `git rev-parse --git-common-dir`, never by appending `.git`.
- **On this host `.git` belongs to the owner's Windows account** (AGENTS.md, Environment). Writing under it already happens for chain refs, but test that a store under it opens on the Windows runner.
- **The move must never lose a row:** copy, compare counts, then rename. Never delete in this wave.
