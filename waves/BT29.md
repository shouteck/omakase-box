# BT29: the overview stays bounded for posted bounties too

Milestone: BT · Station: packaging · Base: master at dispatch · Branch: `wave/BT29` · Timebox: 90 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 17 October 2026 after reviewing K25 and BT28. Detailed for a cook without deep reasoning.

## Why

BT28 bounded the overview: compact `status` and `box bounty` show every open bounty plus a count and the five most recent ended ones, and K25's `kitchen/memory/measure.mjs` showed it flat from 100 to 1,000 records. But the measurement's synthetic records were never posted to GitHub (they have no `github` block), and one older line escapes the bound for posted ones:

- `renderStatus` in `packages/box-bounty/render.ts` (around line 151, added in `c61c07f` on 13 October) loops over **every** record and, for each ended record with a `github` block, prints in the compact view: `<id> compact status uses the cached last observation; current comparison: box bounty status <id> --full`.
- So at 1,000 ended posted bounties, compact `status` prints about 1,000 such lines, roughly 100,000 characters, above the capped list. Running `box bounty status` in this repository today prints four of them, before the header, for four ended bounties.
- The line also breaks BT17's contract: it is the same standing explanation repeated per record, and it is true every time (so it belongs in help, said once, not in output).

## Outcome

Compact `status` and `box bounty` stay within BT28's bars at any number of records, posted or not, and the measurement proves it with posted records.

## Scope

- Write: `packages/box-bounty/render.ts` (and `json.ts` only if a matching field must go), `kitchen/memory/measure.mjs`, `tests/box/bounty/**`, `kitchen/reviews/K25-memory.md` (append the rerun table), `docs/box-v4/BOUNTY.md` if it quotes the line.
- Do not touch: the `--full` view's format lines (the long form keeps its per-record format facts: it is on request); the refresh behaviour; BT28's caps.

## The changes

1. **Remove the per-record compact line.** Delete the `if (!isOpenStage(record.stage) && !options.full) lines.push(... compact status uses the cached last observation ...)` line. The fact it carries (the compact view uses the cached GitHub observation; `--full` reads it fresh) moves to `box bounty help`'s description of `status --full`, said once there. If `json-agreement.test.ts` or `bt17.test.ts` maps or budgets that line, update only the mapping row for the removed label, and say so.
2. **Check the loop for other per-record lines** in the compact view of `renderStatus`, `renderOverview` and `owner.ts`'s `renderConfig`: any line printed once per ended record outside the capped list is the same bug. List each found in the Result; remove or cap each the same way.
3. **Measure with posted records.** In `kitchen/memory/measure.mjs`, add **Mix C: five open, the rest ended, every record posted**. Give each synthetic record a `github` block of the shape `post` writes (copy the field set from a record the suite's GitHub stand-in produces, for example by running one real `post` against the stand-in in the script, then cloning its `github` block with the id changed), plus one attempt. Run the same surfaces at N = 1, 10, 100, 1,000.
4. **Pin the bound in a test.** In `tests/box/bounty/bt28.test.ts` (or a new `bt29.test.ts`), build 60 ended **posted** records plus 2 open, and assert compact `status` and `box bounty` stay under the same character bar BT28 used for the steady state (state the bar in the test), and that no line contains `compact status uses the cached last observation`.
