# BT94: one build, published from GitHub with provenance, after the owner's approval

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT94` · Timebox: 180 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short to medium: release tooling, with three one-time steps on the owner's own accounts. Refactoring playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the release pipeline with the owner ("yes"). A release stays the owner's decision. This wave changes how it is carried out, not who decides it.

**Why.** The package is built well: one bundled file, no dependencies installed, no install-time scripts (`packages/box-cli/pack.mjs`), a frozen lockfile, the tag checked against the version, and the packaging and install tests before any release (`.github/workflows/release.yml`). But:

1. **The npm package is built on the owner's computer and carries no provenance.**
   - `docs/box-v4/PUBLISH.md` has the owner run `pack.mjs` locally and `npm publish` the tarball. `npm view omakase-box` on 24 November 2026: latest 0.4.3, one maintainer, no attestation.
   - The GitHub release is a second, separate build, so the two can differ. They were compared by hand once.
   - npm's current way is **trusted publishing**: GitHub Actions publishes through OIDC with no stored token, and provenance is attached automatically for a public package from a public repository. It needs npm CLI 11.5.1 or later and Node 22.14 or later. ([GA changelog](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/); [npm docs](https://docs.npmjs.com/trusted-publishers/))
   - Classic npm tokens were revoked in late 2025 ([changelog](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/)).
2. **`PUBLISH.md` is out of date and partly wrong.** It names the branch `wave/PF16-npm`, version 0.1.3, and "The command stays `box`", where BT63 made it `omakase-box`.
3. **Most workflow steps use moving tags** (`actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `actions/cache@v4`), while two steps are pinned to a full commit. A moved tag runs whatever it now points to, as the March 2025 compromise of `tj-actions/changed-files` showed. GitHub's guidance is to pin to a full commit.
4. **Anyone with write access can cut a GitHub release** by pushing a `v*` tag.

## Outcome

1. **One build, two channels.** `release.yml`, on a `v*` tag, builds once, runs the packaging tests (as today), then:
   - attaches that tarball to the GitHub release, as today, under the fixed name `box-bounty.tgz`;
   - publishes **the same bytes** to npm with trusted publishing: `permissions: id-token: write` on that job only, and no npm token anywhere.

   The tarball is passed between jobs as an artifact, and its SHA-256 is printed in both jobs and compared.
2. **The owner approves each release.** Both the GitHub release and the npm publish run in a GitHub environment named `release`, which the owner protects with themselves as the required reviewer (the owner's step). Pushing a tag starts the run; nothing leaves until the owner approves it in GitHub.
3. **Checked after publishing.** A last step reads the registry and fails the run, naming the difference, unless:
   - the published tarball's integrity equals the built tarball's;
   - an attestation is present for the version.
4. **Every action in every workflow is pinned to a full commit SHA,** with the version in a comment. A test (`tests/kitchen/actions-pinned.test.ts`) fails, naming the file and line, on any `uses:` that is not.
5. **`PUBLISH.md` is rewritten.** It gives the owner's three one-time steps:
   - add this repository and `release.yml` as a trusted publisher of `omakase-box` on npmjs.com, and set the package to require it;
   - create the `release` environment with the owner as required reviewer;
   - make sure npm's 2FA is on.

   Then, for each release: tag, approve the run, read its last step. The manual `npm publish` path is kept only as a stated fallback, marked as producing no provenance.

## Done when

- The hosted run on the final commit is green on Linux, Windows and macOS, quoted with its run id; the suites the change affects: `test:kitchen`, `test:box-bounty`.
- `actions-pinned.test.ts` passes, and is shown to bite: one `@v7` put back fails, naming the line.
- **A rehearsal without publishing:** the workflow's build, artifact hand-off and SHA comparison run on a scratch tag (`v0.0.0-bt94-rehearsal`, deleted after) up to the environment gate. The publish step uses `npm publish --dry-run`, the approval is not given, and the Result shows the run stopping at the gate. No real version is published.
- `PUBLISH.md` lists the owner's three steps and the per-release step. A search for `wave/PF16-npm` and "command stays" finds nothing.
- The first real release after this wave records, in its own wave file, the attestation and the integrity check passing. This wave cannot, since releasing is the owner's.

## Stops

- The trusted-publisher setting on npmjs.com and the environment rule on GitHub are the owner's accounts. Write the steps and stop there; never change account or repository settings (AGENTS.md rule 7, and the owner-only list).

## Traps

- **The npm CLI on the runner must be 11.5.1 or later** for trusted publishing. Check what the pinned Node ships, and upgrade npm in that job only if needed.
- **Provenance needs a public repository and a public package:** both true here. Say so in `PUBLISH.md`.
- **Never put an npm token in the repository's secrets** as a fallback. The point is that none exists.
- **Rehearse without leaving anything public:** delete the scratch tag and any draft release, and name both in the Result.
