# BT49: the text the tool posts and prints has a size ceiling

Milestone: BT · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT49` · Timebox: 150 minutes; at expiry, report partial findings and stop
Owner decisions: none
Horizon: short

**Brief.** Written by the CTO on 21 October 2026 from the engineering review. GitHub refuses an issue body over 65,536 characters and a title over 256; today that arrives as a raw `gh` failure after the branch is pushed. `look --full` has no byte cap, so a large solution floods the context the product says it protects. Both get a named refusal with a next step.

**Refined by the CTO on 22 October 2026** (owner's request to review the nine engineering-review briefs): code claims checked against master `24bb6b8`; changes are listed under "CTO refinement" at the end of this brief.

## Why

An issue body is assembled in `post.ts` (around line 381) from the task text, the why and the history. Nothing checks its length, so a long `TASK.md` fails at GitHub after the branch push, with a raw message. `look.ts` caps by lines (`LOOK_DIFF_LIMIT = 200`) but `--full` and `lookDocument`'s diff have no byte cap; a large change is printed in full or serialised whole.

## Outcome

Before anything is pushed or created, an over-size body or title is refused with its size and a next step. A solution too large to display says so, names the file count, and points at a way to inspect it without flooding the agent.

## The change

1. Named constants with a comment and a source: `ISSUE_BODY_MAX = 65_536`, `ISSUE_TITLE_MAX = 256`, `LOOK_BYTES_MAX = 2 * 1024 * 1024`.
2. Refuse in `post`, before the branch push and the issue create: `issue-too-large` with the character count and "split the task or shorten it"; `title-too-long` with the count and the limit. Check the title where it is derived, so a caller cannot bypass it.
3. In `look`, `--full` and the diff in the JSON document share the byte cap: over it, print the file list, the byte count and `solution-too-large-to-show`, with "inspect it with your own git or apply it". Never truncate a diff and present the remainder as complete.
4. Count characters as GitHub counts them; state the method in the Result. Use bytes for the diff.

## Done when

- Tests that must fail first: a 65,537-character task is refused at `post` with `issue-too-large`, the branch is not pushed and no issue is created; a 257-character title is refused with `title-too-long`.
- A 3 MiB change with `--full` prints the file list and the named refusal, not the diff; the same under `--json`; a change just under the cap still prints in full.
- No partial diff is ever rendered without its refusal line.
- The counts in the message match the input (assert the number, not just the reason).
- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit.

## Notes

- Do not truncate silently. The file list is the useful part when the diff is too large.
- `post` already has a preview path; the refusal should appear there too, before the owner approves anything.
- Keep the reasons in the existing naming style; `status` and the tests will show them.
- If GitHub's limit differs from the constant on the day (it is documented, not contractual), the constant stays the tool's own bar and the Result says why.

## CTO refinement (22 October 2026)

- New refusals (`issue-too-large`, `title-too-long`, `solution-too-large-to-show`) must carry a `next:` step that names a real command or action. BT40's guard test fails otherwise.
- Record the source of GitHub's limits (its documentation, read on the day) in the Result. The CTO adds the new refusals to `CONTRACTS.md` at close.
