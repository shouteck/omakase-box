# K23: the heavy bounty tests get cheaper, not longer limits

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch, after K22 · Branch: `wave/K23` · Timebox: 120 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 15 October 2026 after reviewing the run BT16 to K21. Detailed for a cook without deep reasoning.

## Why

The bounty suite has grown slower and flakier during the run:

- A full `verify` of `test:box-bounty test:box-package` took 680 s at BT15-ci, 741 s at BT16, 974 s and 1,036 s at BT17.
- `tests/box/bounty/report.test.ts` › "no attempt's report carries a verdict word" ran 21 s alone and 30 to 53 s under three workers. BT17 raised its limit to 120 s (`{ timeout: 120000 }`), against the backlog's recorded preference: make the test cheaper rather than raising the limit.
- `tests/box/bounty/bt11.test.ts` › "the promise lock makes the limit check and the bind one span" ran 16.3 s against its 15 s limit under load (7.8 s alone).

Every later wave pays for this in waiting time and false reds.

**And verify reruns everything for a commit that changed nothing the suite reads** (added 15 October 2026, after K22 stalled). K22's code commit `8abca8f` had a green verify. The cook's Result commit `b466bfc` differs from it only in `waves/K22.md`, but verify reuses a recorded PASS only for the exact same commit (`reusableStep` in `scripts/verify.mjs`), so the reviewer ran the whole bounty suite fresh on `b466bfc` four times, 20 to 27 minutes each, all red only on timeouts under host load. The same thing happened at BT15-ci. Hours were lost proving a wave file again.

## Outcome

The two named tests fit comfortably inside the suite's default limits again with their assertions unchanged, and the bounty suite's wall time is back near where it was before the run, measured the same way before and after. A suite's recorded PASS also stands for a later commit when nothing that suite reads changed in between.

## Scope

- Write: `tests/box/bounty/**` (test structure and fixtures only), `scripts/verify.mjs` and `tests/kitchen/verify-reuse.test.ts` (the reuse rule), `BACKLOG.md` (the flake line).
- Do not touch: product code; any assertion; what a test proves. Moving fixture setup into `beforeAll` or sharing one built world between cases is allowed; dropping a case is not.

## Method

1. **Measure first.** On master, run `node scripts/suite.mjs box --suite bounty` twice (the suite's own runner, three workers) and record the wall time and the 15 slowest tests with their durations (vitest's `--reporter=verbose` output, or its JSON reporter to a scratch file outside the checkout). Run the two named tests alone too.
2. **For each of the 15 slowest, find where the time goes** before changing anything: count the Git and `gh` processes it starts (the K14 spy, `tests/box/bounty/k14-start-budget.test.ts`, shows how) and look for repeated fixture building, such as a fresh repository and a full `create` per case when the cases only read.
3. **Make the expensive part shared or smaller:** build the world once per file where cases only read it; reuse one built CLI; avoid a real Git process where the case checks pure text (K21 found the format, pay and scan-text cases could run without Git; move those into a plain unit file if they are currently inside fixture-heavy ones).
4. **Restore the limits:** remove the `{ timeout: 120000 }` on the verdict-word test; keep bt11's 15 s. Both must pass under the full suite run three times in a row.
5. **Measure again**, the same way as step 1.
6. **Reuse across commits that changed nothing a suite reads.** In `scripts/verify.mjs`, when no recorded PASS exists for this exact commit, look for one on an **ancestor** commit (walk back at most 20 commits with `git rev-list`) whose tree was clean. Reuse it for a step only when every path changed between that ancestor and this commit is one the step does not read, decided by the same rules `scripts/suite.mjs` already uses: `isInert` for every step, and for `test:kitchen` also nothing in `KITCHEN_TEST_READS` or `waves/*.md` (K22 made those kitchen inputs). `check` and `build` reuse under the same rule. The summary line says it: `test:box-bounty=reused@<run>(ancestor <sha7>, only inert paths changed)`. `--fresh` still forces real runs. Tests in `verify-reuse.test.ts`: a wave-file-only commit reuses `test:box-bounty` and reruns `test:kitchen`; a commit touching `packages/` reuses nothing; an ancestor with a FAIL or a dirty tree is never used.

## Done when

- `node scripts/verify.mjs test:box-bounty test:box-package` exits 0 on the final commit, and the bounty suite run passes three times in a row on this host with the default limits.
- The Result has a before/after table: suite wall time, and each of the 15 slowest tests' durations.
- No assertion changed: `git diff master -- tests/` shows only moved setup, shared fixtures and the removed timeout. The pass checks this line by line.
- BACKLOG.md's flake line is closed or updated with what is left.
- Step 6 is shown on this wave's own Result commit: its verify reuses the bounty suite from the code commit and reruns only what the wave file can affect.
