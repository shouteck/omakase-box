Horizon: short. Feature playbook; principles: experience-first, boundary-discipline, prove-it-works

**Brief.** Written by the CTO on 3 November 2026, from the owner's question in PF19: how much of the owner's setup belongs to the CLI and how much to the board, so that moving between them has no friction. Awaits the owner's "go".

## Outcome

An owner's agent runs everything from the CLI except authorising money. That one human step, pay on merge, is named by the CLI with its exact link and its state, and the board's page starts from what the board already knows. The two "limits" no longer share a name.

## The split (owner, 3 November 2026)

| Lives in | What |
|---|---|
| CLI, run by the agent | Repositories allowed, reward, budget, ask-first, posting, merging, marking paid |
| Board, done by the owner | The card, which repositories charge automatically, and the most each may charge |
| Board, for solvers | Everything |
| Both can read | What is owed; pay on merge's state |

## Scope

- Write: `packages/box-bounty/` (wording, `allow` and `config` output, reading the board's pay-on-merge state), `packages/box-platform/components/PayOnMerge.jsx` and `MeView.jsx` (the renamed field and its starting value), `packages/box-platform/src/` (an answer the CLI can read, if none exists: a fact, no secret), `tests/`
- Do not touch: how a charge is decided or made; the switch itself, which only the signed-in page turns on

## Build

1. **One name per limit.** The board's per-repository field becomes **"Charge up to"**; the CLI's `--reward-limit` keeps its meaning, the most promised across open bounties. Sweep both packages and the site for the old words.
2. **The CLI names the human step.** After `allow`, and in `config`, each allowed repository shows pay on merge's state as the board reports it, as a fact, with the link: off, with `<board>/me/#pay`; on, with its "charge up to". No board set: says so. The tool cannot turn it on.
3. **The board starts from what it knows.** Adding a repository for pay on merge fills "Charge up to" from the highest reward the board sees on that repository's bounties, which the owner confirms or changes.
4. **Read as a stranger:** a fresh agent, given only the install and the README, sets up a repository and reports to its owner what pay on merge is and where to turn it on; record what it said.

## Done when

- `node scripts/verify.mjs test:box-bounty test:platform test:kitchen` exits 0 on the final commit.
- A test fails if `config` shows pay on merge's state from anything but the board's answer, or offers to turn it on.
- A test fails if the two limits share a name anywhere in the CLI's words or on the site.
- The owner's approval of the before-and-after of the changed page area, quoted.

## Lenses

- [x] **Security:** the CLI reads the state and never changes it; the answer it reads holds no account or card detail.
- [x] **User experience:** the fresh agent's report is quoted; the owner's one visit is one link.
- [ ] **Measurement fairness:** not applicable.

## Notes

- Established tools draw this line the same way: GitHub's and Stripe's CLIs do the everyday work, and adding a payment method or authorising charges happens in the browser.
- Participants run as fresh sessions in scratch folders, from an owner turn.
