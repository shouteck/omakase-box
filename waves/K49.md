### 1. The tool (the CLI): sound. No wave for speed or memory.

| What | Measured today (this Windows host, 1 or 2 runs each, small repository) |
|---|---|
| Node starting, doing nothing | 0.10 s |
| `box --version` | 0.12 to 0.15 s |

At size, from [BT46](BT46.md) (five runs each): `create` 1.5 s at 1,000 files, 5.5 s at 10,000, 66 s at 100,000; a hundred solutions and a thousand records are met ([K39](K39.md)). Memory: one stated 512 MiB ceiling on Git's output, with a named refusal past it. These fit the product; making 100,000-file repositories faster is not worth a wave until one appears.

The design holds up: one process per command, plain Git and `gh` underneath, a local SQLite cache, the shared record in Git itself. One wart is worth fixing **now, while nobody depends on it:** the shared record's ref name collides with the bounty branch's name (BT58). After the npm release every bounty posted carries the old name forever.

### 2. The board: works at today's size, with a low ceiling and no operations.

- **The ceiling.** The Worker spends 2 GitHub reads a minute (`worker.ts` `SLICE.tickReads`), because Workers Free allows 10 ms of CPU a run. That is 120 reads an hour, whatever the token allows. A bounty needs one to several reads to refresh. **Estimate, not a measurement:** past a few dozen open bounties the board cannot keep its "every 15 minutes" promise for a merge it was not told about, and at 1,000 a bounty would wait most of a day. The tool's own "look now" hint hides this for bounties posted with the tool; a listed issue and a merge made by hand rely on the reading alone. Search also stops completing past about 200 issues (BACKLOG, PF8). Nobody has measured the board at size, as K39 did for the tool. Briefed as PF36: measure first, then choose the route.
- **No operations.** `DEPLOY.md` has no backup, no restore, no rollback and no record of which migrations ran; nothing watches the board, so a stopped reader or a failing payment step is found by someone noticing. The database holds payment records and people's connections. Briefed as PF37.
- **No security headers on the pages.** The front page answers with `Cache-Control` and nothing else: no content security policy, no frame rule, no `nosniff`, no referrer policy. The session cookie is `Secure; HttpOnly; SameSite=Lax` and every write checks the request's origin, so this is hardening, not a known hole. Briefed as PF38.
- **The slow detail** is PF34, already briefed.

### 5. Not sure: for discussion

1. **The route past the board's ceiling,** after PF36 has numbers. The candidates: (a) Workers Paid, about $5 a month, which lifts the CPU limit and is the plain answer, but is spending; (b) a scheduled GitHub Actions job doing the reading and handing facts to the board, free on a public repository, but the board must then trust a writer; (c) a GitHub App with webhooks, which is how GitHub means this to be done, but adds an install step for every owner; (d) conditional requests and batching, which stretch the free plan without changing it. My guess is (d) now and (a) when real bounties pass the measured line, but it is a guess until PF36.
2. **The acceptance rule.** K50 makes the hosted run available before a merge. Whether it becomes *the* acceptance run (KITCHEN.md calls it "a safety net, never a gate") is a rule change. Recommendation: yes, for the full run; local runs stay for file-scoped checks.
3. **`gh` as a hard requirement.** Long-running agents in cloud sandboxes often have a GitHub token and no `gh` program. Speaking to GitHub directly with a token from the environment would remove an install from the adoption cost, the one cost the strategy says to keep lowest. It reverses the 12 October decision and is a real rewrite of `gh.ts`. I think it is right for the audience; I am not sure it is right now.
4. **What the public repository carries.** 2,737 tracked files under `.execution/` and 37 under `docs/legacy/` are frozen history of the retired product, and `kitchen/platform-prototype` pins a Next version with critical advisories. They are the first thing an agent or a person sees when the launch points at the repository. Git keeps all of it if the working tree drops it. Deleting is the owner's.
5. **A second machine identity.** Every real proof used one GitHub account, so a stranger's fork has never been proven on real GitHub. The owner scrapped a second account on 3 November; I only note that K50 and PF36 do not close this.
