# BT46: create is fast on a real repository, without giving up exactness

Milestone: BT · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT46` · Timebox: 240 minutes; at expiry, report partial findings and stop
Owner decisions: none
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 21 October 2026 from the engineering review and BT39's numbers (10k median 17.823 s; 100k 194.476 s). The K39 planning target was under 1 s at 10k; this wave does not promise that. It promises a measured floor, a structural fix and no exactness regression.

**Refined by the CTO on 22 October 2026** (owner's request to review the nine engineering-review briefs): code claims checked against master `24bb6b8`; changes are listed under "CTO refinement" at the end of this brief.

## Why

`create` is the first command an agent runs for every hand-off. At 10k files it takes about 18 seconds; at 100k it takes over three minutes. Most real repositories are in that range, so the cost lands exactly where adoption begins. BT39 fixed a crash and proved the snapshot exact; it did not make it cheap.

The cost is not one thing. The snapshot path deliberately seeds a bare temporary index so every entry is re-hashed (BT39's stale-bytes lesson), then enumeration reads the tree and the emitted blobs. **Profile before changing anything**; the expected hot spots are per-file Git reads and per-file hashing, but the brief does not assume which dominates.

## Outcome

`create` is measurably faster at 10k and 100k files with the same published set as today. **Aims**, not the acceptance bar: under 5 seconds median at 10k and under 60 seconds at 100k; a miss is reported with the profile, not hidden. The 1k case does not regress beyond noise. A structural test pins the shape of the fix, so a later change cannot quietly reintroduce a per-file process.

## The change

1. **Measure first.** Add a phase table to the Result: snapshot commit, tree walk, scan, plan/render, total, at 1k, 10k and 100k. Five isolated runs each; medians and spread; every run counted.
2. **Batch what the profile shows is per-file.** `git.ts` already has `cat-file --batch` helpers (around lines 355–396); first check whether the snapshot and scan paths use them. If per-file Git processes remain, route them through the existing helper. If the cost is per-file filesystem reads in the scan (`create.ts`, `readFileSync` per file), batch or stream those instead. The structural test pins whichever shape the profile justifies.
3. **Re-hash only what differs.** Use a stat/index comparison against the seeded tree to keep exactness while avoiding a full re-hash, and keep the BT39 probe (a file edited under assume-unchanged/skip-worktree must still ship its current bytes) as the guard.
4. **Do not** copy the real index, and do not weaken the snapshot's exactness to buy speed. If a change makes the BT39 probe fail, it is wrong.

## Done when

- A structural test that must fail first: `create` at 10k spawns a bounded number of Git processes (state the number; one batch read, not one per file) and the old path exceeds it.
- The BT39 stale-bytes probe still passes, and a test proves it bites (break the re-hash rule and the probe goes red).
- The 100k accepted-code case still completes; the failure mode for an unreadable tree is still named, not silent.
- A before/after table with five runs per size, medians and spread.
- No wall-clock assertion in the default suite; timing lives in the benchmark, so the suite cannot go flaky.
- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit; BACKLOG's BT39 performance line is updated with the new floor.

## CTO refinement (22 October 2026)

- The brief assumed one Git process per blob, but `git.ts` already batches with `cat-file --batch`. Step 2 now follows the profile and reuses the existing helper. BT39 found the remaining cost in per-file reads for the scan and in `add -A` hashing.
- The 5 s and 60 s figures are aims, not acceptance: K39 and BT39 showed fixed targets set before profiling mislead. Acceptance is exactness intact, a structural bound that bites, and an honest before-and-after table.

## Plan (agreed with the owner, 31 October 2026)

Profile at 10k before any change: scan reads 4.6 s, `add -A` 4.3 s, realpath 1.0 s, `ls-tree`, `write-tree`, `stat` 1.4 s. Options on the same world: serial reads 5.0–5.7 s, a worker thread 1.0–1.5 s, `cat-file --batch` 8.2–8.5 s (ruled out).

1. **Re-hash only what differs** (`snapshot.ts`). Keep the bare `read-tree` seed. At 1,000 or more index entries (header read in Node): read the real index once with `ls-files -s --debug`; `lstat` each stage-0 entry; trust only a regular 100644/100755 file whose size and mtime match, whose exec bit matches where the file system has one, and whose mtime is older than the index file's. Flags are ignored. Write trusted entries with `update-index --index-info`; list what is left with `ls-files -z --cached --others --exclude-standard`; nothing left means no `add`, up to 1,000 means `add -A` on literal paths, more means plain `add -A`. Below the threshold or on any doubt, today's path.
2. **Read in parallel, same bytes** (`read-many.ts`, used by `create.ts`). Above the threshold, one worker reads live files async, width 64, in-flight bytes capped at 64 MiB; the blocked main thread scans and stores hits by index, so output order holds. A worker failure falls back to the serial loop.
3. **Re-measure.** Five runs each at 1k, 10k, 100k, baseline and candidate alternating; realpath left alone unless the aims are missed, and a miss is reported.

Tests: tree-id differential between the stat path and the plain path over a scenario table; a structural test (at most 16 Git starts, no `add`, no per-file main-thread read on a clean world of about 1,001 files); bites on the trust rule and the racy rule; no wall-clock assertion.
