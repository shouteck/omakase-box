**Pre-brief.** Written by the CTO on 13 October 2026. The owner's decision of that day, after BT10 stopped twice to ask them test questions: "there should be a way to test this properly; if it requires this input from me, something feels wrong." A kitchen wave: it cooks only when named. **It creates a new public repository on the owner's GitHub account, so its pre-cook card waits for the owner's "go"** (the owner approved the idea on 13 October 2026; the go covers the exact name and what is put in it).

## Why

BT10's real journey ran on the kitchen's own repository, where the rulebook rightly reserves public posts and changes to instruction files for the owner. So a test needed the owner's go, the owner's choice of how agents learn of a bounty, and, by the head chef's mistake, the owner's answer to a comprehension question. A test that needs the owner is testing in the wrong place.

## Outcome

The kitchen has one throwaway public repository where it may post, solve, merge, close, switch the hook on and edit instruction files as often as a wave needs, with nobody asked. The owner is involved once: the go for this wave. No later wave's real run touches `shouteck/omakase-box` or asks the owner anything.

## Scope

- Write: `kitchen/**` (a page on the sandbox and how a wave uses it), `templates/wave.md` (one line), `docs/box-v4/KITCHEN.md` ("Verification", a short paragraph), `tests/kitchen/**`. On GitHub: the new repository only.
- Read for context: `waves/BT10.md` Result (what a real journey needs and what it left behind); `waves/BT9.md` Result (the hook's missing live-host proof); AGENTS.md "Who decides what".
- Do not touch: product code; `shouteck/omakase-box` on GitHub beyond reading; the owner's settings for any repository but the sandbox; this repository's instruction files or hooks.

## Done when

- `node scripts/verify.mjs --full` exits 0 on the final commit.

**The sandbox exists and says what it is**

- One public repository on the owner's account, named so nobody mistakes it for a product (the pre-cook card proposes the name; the owner's go fixes it). Its description and its README's first lines say: a test area for the bounty tool, run by the repository's owner; bounties here are tests, solved by the owner's own agents; no reward stated here will be paid; outside solutions are welcome to look but nothing is promised.
- It holds a small, plain project made for the purpose (a few text and code files with room for a real small task and a clash), nothing copied from this repository beyond what the tool needs to run, and no secret-shaped text anywhere.
- It is cloned beside this checkout as `kitchen-sandbox`, outside it, and is never a worktree of this repository.

**The owner's yes, once**

- The sandbox is added to the owner's allowed repositories with the tool's own `allow`, as "allowed", by the head chef on the owner's go for this wave. The wave file records the exact command and the time. Nothing else in the owner's settings changes; `shouteck/omakase-box` stays "ask me each time".
- The two notices the owner chose not to have on the working repository are switched on in the sandbox only: the instruction block in the sandbox's own instruction files, and the session hook for the host cooking this wave.

**It works, proven once**

- One whole journey is run there with the merged tool and the kitchen as solver, with nobody asked at any step: create, post, two blind solutions as pull requests, a fresh collecting session that learns of the bounty by itself, a merge, the tool closing the bounty. The Result gives each step and lists by exact name what is left on GitHub.
- **The hook's live-host proof, owed since BT9:** the fresh collecting session is started on a real host with the hook on, and the Result quotes what the hook put in front of it and says which host. If the host gives no way to observe it, that is reported as it is.
- **Two fresh agents stand in for the first-time owner:** one is given only the tool's first-use output and told to ask its owner; the second has never seen the tool, reads only the first one's message, and writes down what it believes it is agreeing to. A check looks for the three facts (public, merged, this repository only). Five runs. The Result gives the count and each relayed sentence. This is the kitchen's standing way to test owner-facing wording; it is a proxy for a person and the Result says so.

**How later waves use it**

- A page in `kitchen/` says: real-GitHub steps run in the sandbox; what a wave may do there without asking (everything the tool does, inside that repository); what still goes to the owner (anything on another repository, spending, a new destination, real money); and how a wave cleans up (close what it opened, list what it leaves).
- `templates/wave.md` gains one line: a wave with a real-GitHub step names the sandbox, and a step that needs the owner as a test subject is not written.
- A test in `tests/kitchen/` fails if a wave file under `waves/` written after this one asks for a real post on `shouteck/omakase-box`.

**Cases that must fail:** the tool allowed on the sandbox still refuses a private repository and a never-ship path there; a wave pointing its real step at the working repository is caught by the test above.
