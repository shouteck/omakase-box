**Brief.** Written by the CTO on 10 November 2026 from [K48](K48.md). [PF26](PF26.md) found the live board's bounty detail answering in 0.4 to 9 seconds against the tool's 2.5-second limit (`board.ts` `DEADLINE_MS`), so a solver's `status` often says "board: not read (it took too long)". The Worker showed 13 to 20 ms of CPU and 4 to 6 s of wall time; it was not the GitHub re-check. Never investigated. Bug-fix playbook: reproduce, then the root cause, then the smallest fix.

## Outcome

The cause of the wait is named from a measurement, and a bounty's detail on the deployed board answers under 1 second at the median and under 2.5 seconds at the slowest of 30 reads, or the Result says which part cannot be made faster on the free plan and what the tool tells a solver instead.

## Steps, in order

Written so any model can cook it. Lines are as read on 10 November 2026.

**What the detail does today** (`packages/box-platform/src/feed.ts`, `bountyDetail`, line 236). It waits for these one after another, each a trip to the database or beyond:

| # | Call | Line |
|---|---|---|
| 1 | `readBounty` (the row, its pull requests, its history) | 237 |
| 2 | `ownerRecords` | 241 |

| 7 | the author's Stripe state, further down | after 258 |

Read the function to its end and correct this table in this file first; it is the list of suspects.

1. **Measure locally, per call.** Write `kitchen/demo/pf34-measure.mjs` (named for the wave): start the local board (`packages/box-platform/local.mjs`), seed one bounty with pull requests and a payment as `tests/platform/support.ts`'s `rig` does, then call `/bounties/<id>.json` 30 times and print, per call in the table, the time it took. Get the per-call times by wrapping each `await` in `bountyDetail` with `performance.now()` behind a debug flag in a scratch edit that is **not committed**. A local run cannot show Cloudflare's own waits; say so.
2. **Name the suspects from the numbers.** Three shapes to confirm or rule out, in this order:
   - **an outside call inside the request** (number 7, Stripe): does the detail call Stripe's API while the reader waits? If yes, this is almost certainly the seconds: the fix is to answer from what the database already stores and refresh that state elsewhere (the minute tick, or `defer`), never inside the read;
   - **trips made one after another** that do not depend on each other (2, 3, 4, 5, 6 all need only the row from 1): the fix is to start them together with `Promise.all`, or one D1 `batch`;
   - **a cold start:** the first read after idle is slow and the next fast. Nothing in this wave fixes that; report it with the numbers.
3. **Ask for the one live reading, if the owner allows.** The live board has no bounty, so the detail cannot be timed there. What can be read without one: `wrangler tail` while requesting `/bounties/<any id>.json` (a 404 path, which runs only call 1) and `/numbers.json`, to see wall time against CPU time for a database trip from the real Worker. Running `wrangler` against the live account is the owner's to allow: put it to them as one question with the exact command. If they say no, the local measure is the limit and the Result says so.
4. **Write the round-trip test first.** In `tests/platform/`: count the database statements the detail runs for one bounty (wrap the test rig's `DB.prepare` and `DB.batch` and count `run`/`all`/`first`/`batch` calls) and assert today's number; then lower the asserted number to the target and see it fail.
5. **The smallest fix** for the confirmed suspect only. Keep every field of the answer identical: add a test that the JSON for the seeded bounty is deep-equal before and after (store the "before" from master's code as a fixture).
6. **Measure again** the same way, 30 reads, and put before and after side by side: median, slowest, per call.
7. **If nothing can be made faster** on the free plan: do not touch `DEADLINE_MS` in `packages/box-bounty/board.ts` by guesswork. Report what a solver is told today ("board: not read (it took too long)") and propose the wording or limit as a question for the owner.
8. **Verify, merge;** deploying is the owner's word.
