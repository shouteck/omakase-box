# BT18: every command reads its options the same way, and ignores nothing

Milestone: BT · Station: packaging · Base: master at dispatch, after K22 and K23 · Branch: `wave/BT18` · Timebox: 150 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 15 October 2026 from K20's report (`kitchen/reviews/K20-conventions.md`, departures 1, 3 and 4); the owner agreed the queue that day. Detailed for a cook without deep reasoning: the whole option table is below, and the parser's rules are listed in order.

## Why

The product rule is that no command returns nothing or fails silently. K20 found commands that silently ignore what they are given, measured on the built CLI:

- `box bounty status --help` prints status and exits 0: the request for help is ignored.
- `box bounty status --json` is ignored, exit 0.
- `box bounty status --repo=<path>` ignores the path and uses the current folder; `--repo <path>` works.
- `box bounty status -h` is read as a bounty id and refuses `unknown-bounty`.
- `box --version` and `box bounty --version` exit 2 with usage.
- Each command parses its own options in `packages/box-cli/src/cli.ts`: `create` (through `parseCreateArgs` in `packages/box-bounty/args.ts`) and `allow`/`deny`/`config` refuse unknown options; `status`, `look`, `apply`, `close`, `post`, `describe` and `hook` mostly skip whatever they do not recognise.

The conventions (git, gh, npm): every command answers `--help`/`-h` with its own usage on standard output and exit 0; an unknown option is an error naming it; `--flag=value` and `--flag value` are the same; the program prints its version with `--version`.

## Outcome

Every `box bounty` command reads options through one parser with one table, so an option is either understood or refused by name; every command answers `--help`; and `box --version` prints the version.

## The parser's rules, in order

One function in `args.ts`, for example `parseOptions(command, argv)`, returns `{ positionals, values, switches }` and is used by every command in the table. `parseCreateArgs` becomes a thin use of it, keeping its retired, removed and money tables.

1. `--help` or `-h` anywhere: print that command's usage (its line from `bounty help`, then one line per option with what it does) on **standard output**, exit 0, do nothing else. Applies to every command, including `create` with no other options.
2. `--name=value` is read exactly as `--name value`. A switch given as `--full=x` is an error: `--full takes no value`.
3. The existing named refusals run before the unknown-option rule, so an old or money option still gets its own reason (`checks-removed`, `reward-agent-set`, `create-option-retired`, `folder-delivery-retired` for `--out`, `--from`, and `--to` other than `github`).
4. `--json` on a command that does not support it yet: refuse by name, `json-not-supported`: "--json is not available on box bounty <command> yet". (BT19 adds it to `status`, `look` and `config`.)
5. Any other option the command does not list: usage error, exit 2, on standard error: `unknown option --x for box bounty <command>`, then that command's usage line. This replaces `allow`/`deny`/`config`'s `authority-arguments` refusal for unknown options; keep `authority-arguments` for the cases that are about values (a repeated option, a missing amount).
6. An option that takes a value, given without one (end of arguments, or the next word starts with `--`): usage error, exit 2: `--x needs a value`.
7. An option given twice that is not repeatable: usage error, exit 2: `--x was given twice`. `--include` is the only repeatable one.
8. More positionals than the command takes: usage error, exit 2, naming the extra word.
9. `-` alone is a positional (standard input), never an option. Any other word starting with `-` that is not `--` plus a name is an unknown option (rule 5); this is what stops `-h`-like words being read as ids.

**`--version`.** `box --version` and `box bounty --version` print `box <version>` on standard output and exit 0. The version is `packages/box-cli/package.json`'s `version`, read at build time (or at start from the package file next to the built CLI; choose whichever the build already supports and say which). BT12 will set the real version; this wave only prints it.
