**Brief.** Written by the CTO on 15 October 2026 after reviewing the run BT16, K20, BT17, K21; the owner agreed the queue that day. Detailed for a cook without deep reasoning: each change names the file, the exact rule and the test that proves it.

## Why

Master went red twice in one run, and the second red has still not been confirmed fixed by the hosted check:

1. **BT16 changed what the GitHub stand-ins must answer** (`permissions.push`). Its verify ran `test:box-bounty test:box-package` only. The kitchen demo (`kitchen/demo/gh-standin.cjs`, driven by `tests/kitchen/k16-record.test.ts`) drives the built CLI too, so `test:kitchen` went red on master, and only the hosted run caught it (run 38687637404). There are three GitHub stand-ins (`tests/box/bounty/github-fixture.ts`, `tests/box/bounty/bt7-ux-fixture.mjs`, `kitchen/demo/gh-standin.cjs`), and `tests/kitchen/k19-github-standin.test.ts` compares only chosen fields, so the drift had no guard.
2. **A head-chef edit to `docs/box-v4/KITCHEN.md` pushed AGENTS.md + KITCHEN.md over the 20 KB rule** that `tests/kitchen/kitchen-stats.test.ts` checks ("0 on the real repo"). The hosted run on the next code push went red (38711900053). K21's repair changed only `.md` files, and both the workflow's `paths-ignore` and `scripts/suite.mjs`'s `INERT` treat every `.md` as untestable, so no hosted run has confirmed the repair. A test reads those two files, so they are not inert.

## Outcome

A product change cannot skip the kitchen suite, the files a test reads always trigger the tests that read them, the three stand-ins cannot drift apart unseen, and the hosted check on master is green again.

## The changes

1. **The kitchen suite runs whenever the bounty tool changes.** In `scripts/verify.mjs`: when the committed diff from `master` (use the same changed-path reader `scripts/suite.mjs` exports as `changedPaths`) touches `packages/box-bounty/` or `packages/box-cli/`, and `test:kitchen` is not among the named suites, add it and print one line: `added test:kitchen: the change reaches the built CLI the kitchen demo drives`. `--only` does not suppress this. A test in `tests/kitchen/verify-reuse.test.ts` style proves both directions (a product path adds it, a docs-only diff does not).
2. **What a test reads is not inert.** In `scripts/suite.mjs`, `INERT` exempts the files the kitchen tests read from the "every `.md` is inert" rule: at least `AGENTS.md` and `docs/box-v4/KITCHEN.md`, plus any other file `scripts/kitchen-stats.mjs` reads (read it and list them; name the list once, as a constant). A change to one of them selects `test:kitchen`.
3. **The hosted workflow agrees with `INERT`.** In `.github/workflows/verify.yml`, replace `paths-ignore` with a `paths` list: `'**'`, then the negations for what is inert, then the exempted files re-included after the negations (GitHub applies `paths` patterns in order; a later positive pattern re-includes). Keep the comment saying it mirrors `INERT`. If a kitchen test already asserts the mirror (`k7-ci-clean-checkout.test.ts` or similar; search for `paths-ignore`), update the code it reads so the same assertion holds; do not weaken the assertion.
4. **The stand-ins answer the same shapes.** Extend `tests/kitchen/k19-github-standin.test.ts` so that, for every endpoint at least two stand-ins answer, it compares the full set of keys recursively (key names and value types, not values) of their answers. It must fail on today's master before BT16's repair (check by reverting `gh-standin.cjs`'s `permissions` line in a scratch copy, outside the checkout) and pass now. Where the three already differ in a key, make them agree by adding the real-GitHub key to the stand-in that lacks it; say each one in the Result.
5. **One line in KITCHEN.md's verify rules:** "A brief that changes what a command does or prints names `test:kitchen` in Done when; verify adds it anyway." Run `node scripts/kitchen-stats.mjs` after the edit and keep AGENTS.md + KITCHEN.md at or under 20,480 bytes.
