# K71: command cost, step 1 (fewer process starts per command)

Milestone: K (kitchen) · Station: evidence · Branch: `wave/K71` · Timebox: 240 minutes
Owner decisions: on 13 November 2026 the owner asked for a recommendation after the test conversions and said "yes" to the first step of it: reduce what a command costs (every test that runs the tool pays it, and so does every agent that uses it). The owner's rule from the same day holds: optimise the tool's code and the tests, never the machine.

## What a command costs (measured in K68, K51c)

A command is 13 to 24 starts of Git or `gh` (status of a posted bounty 13, collecting a pull request 24, close 23). Almost none repeat: the cost is the number of distinct steps. Three of those starts were avoidable without changing what any command says or does.

## What changed

| change | where | effect |
|---|---|---|
| The `gh version` probe is remembered across processes. A `gh` that passed it is stored in the project's local store keyed by its path and stamped by its size and modification time; a later command asks nothing. A moved, replaced or upgraded `gh` has a new path or stamp and is probed again; a missing or unreadable store means the probe runs as before. | `packages/box-bounty/gh.ts` | one `gh` start fewer in every command after the first in a project |
| The event append reads the branch tip and the tip's event with one `rev-parse` instead of `rev-parse` plus `cat-file -e`. The provenance check on the tip (`provenTip`) is unchanged: a planted or foreign tip still yields no parent. | `packages/box-bounty/chain.ts` (`appendEvent`) | one Git start fewer per chain event |
| Refreshing shared memory lists the remote-tracking and the local chain namespaces with one `for-each-ref` over four patterns (split by prefix) instead of two starts. | `packages/box-bounty/chain.ts` (`listTipsIn`, `adoptAndImport`) | one start fewer per refresh that reads both |
| The per-command start budgets are lowered to what each command now costs (several were caps with slack: `status-posted` allowed 9 Git starts and used 5). | `tests/box/bounty/k14-start-budget.test.ts` | a regression of even one start now fails |

## Tests

New `tests/box/bounty/k71-probe-remembered.test.ts`, two tests, each seen red on the old code:

1. `status <id> --comments` in three separate CLI processes: the stand-in `gh` records exactly one `version` call (old `gh.ts`: three).
2. `refreshSharedMemory` on a posted world starts `for-each-ref` once, naming all four chain namespaces (old `chain.ts`: two starts, restored from master to prove it).

## Changed expectations

None. The budgets in `k14-start-budget.test.ts` are ceilings that moved down; no assertion about what a command prints or does was edited. The edit gate reports no removed, skipped or loosened test.

## Result

Done on 13 November 2026.

- **Smaller than the K68 estimate.** The journey in `k14-start-budget` (post, look, apply, close and the status reads between) went from **200 to 192 starts: −4%** (Git 164 to 162, `gh` 36 to 30). K68's "about a quarter" was an estimate from a single command's step list; it did not hold for a journey, where the probe was one start in twelve commands and the other two savings land only in two commands each. The combined `for-each-ref` saves nothing in this journey (no remote chain is imported in it); it saves one start where a project has a remote shared memory.
- **What the numbers do not say:** no wall-clock gain is claimed or measured. Four percent of the starts in one journey is well inside the ±20 to 30% run-to-run variation measured in K69, so a timing comparison could not show it.
- **Probe-cache limits:** it lives in the project's local store, so a project without one (no `init`, no posted bounty) probes every time, as before. It trusts size and modification time, which is the same trust the operating system gives an executable; a `gh` replaced by one of the same size and timestamp would not be re-probed. That is a version check, not a security check: the tool never relied on it for authority.
- **Checks run:** typecheck clean; the whole bounty suite on this host green (110 files, 1359 tests, 4 skipped) before the second test was added; the kitchen suite green (24 files, 203 tests) after rebuilding the CLI; the budget test, the new file and `k16-record` green on the final tree.
- **Not done, and next in the plan:** an in-process GitHub transport seam (the test stand-in `gh` costs a whole Node process per call, which is most of what the journeys pay; BT59's token-only transport needs the same seam), and `git fast-import` for chain events (seven starts per event; security-sensitive, so last). Neither is started: the owner stops at each checkpoint.
