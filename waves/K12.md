# K12: verify takes a third of the time

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch · Branch: `wave/K12` · Timebox: 120 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 12 October 2026 at the owner's request. A kitchen wave: it cooks only when named. Run as an experiment with a before and an after (the hillclimb playbook).

## Outcome

A full `node scripts/verify.mjs test:box-bounty test:box-package` on this host takes about a third of what it does now, catches every break it caught before, and no longer times out because another session is using the machine.

## What the CTO measured on 12 October 2026

A full run on master at `9a59b25` took 655 s: the bounty suite 530 s (188 tests in 11 files), check 94 s, build 23 s, the rest starting a database. On the parked BT7 branch the bounty suite reached about 950 s for 233 tests. Two causes, from the runner and from a BT7 cook's trace:

- `suiteWorkers` in `scripts/suite.mjs` gives the bounty suite one worker; the packaging suite has three; the host has six cores.
- Each test builds a Git repository and drafts, confirms and posts a bounty from nothing: about 13,000 process starts across the suite at about 55 ms each, of which roughly 900 are the stand-in `gh`.

Also seen: verify starts a disposable Postgres on every run although the bounty tool uses no database; `check` ran the bootstrap, auth, contracts and planner suites on waves that touched only the bounty tool; under outside load tests sat at 11 to 24 s of a 30 s limit and timed out.

### What changed and what it measured

**Step 1 — bounty files run in parallel, 3 workers (`6018ab0`).**
Audit first: every fixture repo lives under its own `mkdtemp` root; `PATH`, `GIT_EXEC_PATH`, `BT6_GH_STATE` are restored in `finally`; per-repo `safe.directory` args and `GIT_OPTIONAL_LOCKS=0`; no fixed ports, no writes under the checkout, no global Git config mutation; vitest runs files in forked workers so `process.env` is per-file. Pinned in `tests/kitchen/k12-bounty-parallel.test.ts` (6 tests). Worker count chosen by measurement: the five biggest files took 211.9s at 3 workers and 241.3s at 6 — spawn contention wins past 3.
Measured on this host, same suite (215 tests, 18 files): before (1 worker) 696.2s and 762.4s — both runs had 30s test timeouts under ambient load, so these are floors, not a clean pass; after (3 workers) 353.8s and 318.6s, all 215 passing, plus 370.6s for the spy-instrumented run (1 timeout under instrumentation). Roughly a halving even against the optimistic end of the baseline.
Deliberate break (drop `required` from the `git.ts` pin regex): `bt7-pins` fails before the step, fails after, passes again when restored. Same proof re-run after steps 2–3: fails in ~1.1s.

**Step 2 — database only when a named suite uses one (`9d1bf56`, fixed by `0fa9cb5`).**
`DB_SUITES` in `suite.mjs` keys suites like `suiteKey` does: `box --suite auth`, `box --suite delegation`, `compiler`, `e2e`, `portal`, `runner`, `security` (the last five reach Postgres through `*-live` tests). Under `--db=auto`, `verify` starts a disposable Postgres only when a named suite is in that set; explicit `--db=embedded|docker` still forces one. The summary line reports `db=none` when none was started.
**Found by `verify --full`, then fixed:** `check` is a step, not a named suite, and its auth/contracts/planner selections run `*-live` tests that exec `scripts/verify-*.mjs` into `acquireHostRuntime` — a database is needed whenever those check suites are selected. `DB_CHECK_SUITES` names exactly `auth`, `contracts`, `planner`; only bootstrap-only or empty check selections stay `db=none`. Pinned in `tests/kitchen/verify-reuse.test.ts`.
Measured: `verify --only build` → `db=none`, 19s total; `verify --only build --db=embedded` with build reused → 8s, i.e. the embedded Postgres lifecycle costs ~8s per verify run and is now skipped for bounty/package-only verification.

**Step 3 — `check` runs only what the diff can reach (`df9ad07`).**
`tests/box/` and the milestone-BT product packages (`box-bounty`, `box-cli`, `box-package`, `box-trace`) map to zero check suites — an import scan found them referenced only by `tests/box` and each other. `packages/box-contracts` keeps the every-suite fallback because `services/private-api` imports it; unmapped/shared-tooling paths still run all four. Pinned in `tests/kitchen/verify-reuse.test.ts`.
Proved on real Git: a scratch worktree whose only diff vs master was `packages/box-bounty/git.ts` selects `suites: []`. Measured floor of such a check: `tsc --noEmit` + `boundaries.mjs` = 18s, versus ~64–109s observed when all four legacy suites run. Note honestly: this wave's own diff touches `scripts/` and `tests/kitchen/`, so `check` on `wave/K12` still runs all four — the gain lands on product-only waves.

**Step 4 — not attempted.** Timebox: steps 1–3 plus the measurement and load runs consumed it. Building a bounty once per file stays available as the next lever; the process-start breakdown below says where it would pay.

### Under load

Six `kitchen-K12-busy-*` CPU spinners saturated the six-core host; the final-configuration bounty suite was started against them and is reported as it was: after ~7.5 minutes the only file to complete was `bt7-cli` with **both tests failed** (file 292.6s; one test alone 225.4s — far past the 30s limit). The run was abandoned at the timebox with the rest in flight; all six busy processes were stopped. Honest conclusion: parallel workers do not rescue a fully saturated host — under this load the suite still hits its 30s test limit, and the wave's "no longer times out because another session is using the machine" is **not achieved** for full CPU saturation. No timeout was raised.
