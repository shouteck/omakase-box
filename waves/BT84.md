# BT84: a `take` or `submit` that fails halfway can be run again and finishes

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT84` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-03-solver-in-the-tool
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `take` with the owner, who agreed with the finding and asked for it ("yes brief it").

**Why.** `takeBounty` (`packages/box-bounty/take.ts`) does five things in a row, and saves its record only after the last:
1. fork (or not);
2. clone into a new temporary folder;
3. an empty start commit on `box-solve/<id>`;
4. push that branch to the target;
5. open the draft pull request.

If anything fails after the push, for example GitHub erroring or a lost answer on the pull request call, no record exists, and a rerun cannot finish:
- `eligibleTake` sees nothing taken, so it starts again from step 1 in a **new** folder;
- step 3 makes a **new** empty commit (a new timestamp, so a new commit id);
- step 4 pushes it to the same branch without force, and the remote refuses it, because the commit ids differ;
- the refusal from step 5 says "open a draft pull request from it… on GitHub", but if the solver does that, `submit` refuses (`not-taken`), because there is no record.

`post` solved the same problem long ago: it saves its state after each step, and `recoverIssue` finds an issue whose answer was lost. `take` has neither, and no test covers a fault there (`tests/box/bounty/pf25.test.ts` tests the happy paths, the owner's switch, the filter and close).

**`submit` has a smaller gap of the same kind** (found in the walkthrough of `submit`, added on the owner's "yes"). `submitTakenResult` (`packages/box-bounty/attempt.ts`) sends one GraphQL mutation with two parts:
- mark the draft ready for review;
- replace the tool's own sentence ("Started on bounty … A draft: work in progress…", `DRAFT_BODY`) with "A solution to bounty … ready for review."

It checks only the first part's answer. When the answer is lost, or the description part fails, the rerun finds the pull request no longer a draft and takes the "already ready" path. That path records `submitted` and never replaces the sentence. The poster then reviews a ready pull request whose description, in the tool's own words, still says it is a draft in progress.

## Outcome

1. **`take` records its progress before it acts on GitHub.**
   - A new stage, `starting`, is saved once the target and workspace are known, before the push. It carries `target`, `branch`, `bountyBranch`, `baseCommit`, `workspace` and `reward`.
   - The stage moves to `taken` only when the draft is open, as today.
2. **A rerun of `take <id>` on a `starting` record continues; it never starts over:**
   - **The workspace:** it reuses the recorded one if it still exists. If it is gone, it clones again into a new folder and records that.
   - **The branch:** if the target already has `box-solve/<id>`, it fetches it and continues from it. It never makes a second start commit and never force-pushes. If the target lacks the branch, it pushes the local start commit as today.
   - **The draft:** before opening one, it looks for an open pull request from `box-solve/<id>` against the bounty branch (as `recoverIssue` does for `post`), and adopts it if found. It opens one only if none exists.
3. **Every refusal after the push says to run `take <id>` again.** The "open a draft pull request on GitHub" advice is gone. A rerun is now the way to finish.
4. **The other commands know `starting`:**
   - `submit` refuses with a new reason, `take-unfinished`: "`take <id>` did not finish; nothing changed; next: omakase-box take `<id>` again".
   - `status` lists the attempt as unfinished.
   - `close` withdraws it, closing a draft if one is found open, and says the branch on the target stays, as it does today.
5. **`submit` finishes its own words.**
   - On the "already ready" path, if the description still holds `DRAFT_BODY(id)`, `submit` replaces it, with the same `updatePullRequest` mutation, and says so.
   - On the normal path, it checks the description part's answer as well as the ready part's. A description not confirmed refuses with the existing `github-response-invalid`, whose `next:` is "omakase-box submit `<id>` again". A rerun then fixes it.
   - Words the solver wrote stay untouched, as today.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master. If the stand-in has no way to lose a pull request's answer, add a `losePullResponse` switch next to `loseIssueResponse`: the pull request is created, then the call fails once.
2. **The stage:**
   - add `'starting'` to `TakenStage`, and to the list `loadTaken` accepts;
   - in `takeBounty`, call `saveTaken({ … stage: 'starting' … })` after the clone and the start commit, before the push loop.
3. **The rerun:**
   - in `eligibleTake`, a `starting` record is not `already-taken`; return it;
   - in `takeBounty`, when it is there, use its `target`, `workspace` and `branch`;
   - if the workspace is missing, clone again into a fresh folder;
   - `git ls-remote` the target's branch: if present, fetch it and `git switch -C <branch> FETCH_HEAD`; skip the new commit and the push;
   - before `api(… /pulls …)`, read `repos/<repository>/pulls?head=<owner>:<branch>&base=<bountyBranch>&state=open` with `readOnlyApi`, and adopt the first entry opened by the signed-in account.
4. **The words:** replace the "open a draft pull request from it… on GitHub" `next:` with "omakase-box take `<id>` again"; add `take-unfinished` in `attempt.ts`.
5. **`submit`:** in `submitTakenResult`, read `data.data.described.pullRequest.body` when a body was sent, and refuse when it is not the new body. On the `!attempt.draft` path, when `attempt.body` still includes `DRAFT_BODY(id)`, send the `updatePullRequest` mutation alone, then record `submitted`. If the stand-in's GraphQL handler cannot lose an answer once, add that switch beside the pull request one (Step 1).
6. **Docs, surface;** verify, push, hosted run, Result, merge.

## Traps

- **Never force-push** the solver's branch. If the remote branch is not the tool's start commit, it is the solver's work: keep it.
- **The draft lookup must filter on the signed-in account.** Another agent's open pull request from a branch with the same name in another fork is not this attempt. `head=<owner>:<branch>` names the owner; check the author too.
- `--into` on a rerun: the folder now exists, so `checkWorkspace` refuses it. With a `starting` record that names that folder, reuse it instead of refusing.
- **An approval from "ask each time" is consumed only when the take ends `taken`, as today.** A failed first run must leave it in place, so the rerun is still allowed.
