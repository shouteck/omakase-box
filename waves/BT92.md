# BT92: every claim made to an agent is listed once, worded once, and proven

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch`, after [BT91](BT91.md) · Branch: `wave/BT92` · Timebox: 300 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-board-only-what-needs-a-website
Horizon: long: one list across the tool, the board and the published skill; starts with `/plan`. Refactoring playbook; principles: encode-lessons-in-structure, prove-it-works, subtract-before-you-add.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of `describe` with the owner ("yes"). The owner's direction: deterministic checks, not fresh agents (23 November 2026).

**Why.** An agent decides whether to use the tool from what the tool tells it, and the code says so: `wording.ts` calls itself "the product of wave BT4: wording is product". The same promises are made in seven places:
1. `describe` (`DESCRIBE_LINES`, `SOLVING_LINES`, `renderDescribe` in `packages/box-bounty/tell.ts`);
2. the skill (`SKILL_TEXT`, and its published copy under `docs/box-v4/launch/skill-repo/`);
3. the instruction block (`RULES_LINES`);
4. AGENTS.md's "Handing work off" (this repository's own block);
5. the board's `llms.txt` (`packages/box-platform/src/llms.ts`);
6. the board's how-it-works page;
7. the npm package's README, which is `FIRST-FIVE-MINUTES.md` copied in by `packages/box-cli/pack.mjs`.

The promises include: posting is free apart from the reward; it goes only to this repository's own public GitHub; nothing a solver wrote is ever run; the preview says exactly what becomes public; the owner decides once; only the merged solution is paid; the board holds no money.

Nothing checks these. They have drifted, found on 24 November 2026:
- **`describe` prints the reward sentence before it says what the tool is.** `renderDescribe` inserts it after the line `available.`, which no longer exists, so `indexOf` returns -1 and the sentence falls to the top. Run in a scratch home, the first line printed is "No reward is set: a bounty is not posted without one."
- **"the task and what you tried":** no "tried" exists apart from the task text until [BT87](BT87.md).
- **"The project keeps the record":** true, but it does not say the record is public on a public repository.
- **"Only the merged solution is paid, all of it":** not true of a bounty listed from the board, where the owner chooses a payee from any linked pull request. [PF57](PF57.md) stops new ones; held ones keep that rule.
- **"with none of the owner's credentials in reach":** [BT85](BT85.md) already fixes it.

BT4 chose the wording with fresh-agent runs (`kitchen/scenarios/bt4.md`), and the text has been edited since without them. [BT89](BT89.md)'s pin test covers command spellings, not claims.

## Outcome

1. **`docs/box-v4/CLAIMS.md`, one row per claim the tool makes to an agent.** Each row has:
   - an id (`K-free`, `K-public-only`, …);
   - the one wording, which every place uses exactly;
   - the guard ids in `docs/box-v4/CONTRACTS.md` that keep it (P1, R3, …) and so the tests that prove it, through `node scripts/proof-map.mjs`;
   - the places allowed to say it;
   - any exception, stated in the claim itself. For example: "only the merged solution is paid, all of it, for a bounty posted with the tool".

   A claim with no guard is either given one, with a test, or removed from every place. The Result lists which.
2. **Every place says only listed claims, in the listed words.**
   - Each place's text is built from `CLAIMS.md`'s wording, through constants generated from the file as BT78 generates its rules.
   - Where a place cannot use constants (AGENTS.md, a board page), a test checks it.
3. **The test, `tests/box/bounty/claims.test.ts`,** fails, naming the place and the sentence, when:
   - a place states a claim not in the list, found by a phrase list per claim;
   - a place's wording differs from the list's;
   - a claim's guard ids do not appear in `proof-map.mjs --check`'s proven set;
   - `describe`'s sections are out of order. The order is what, then worth it, then whose call, then the facts, then next; the reward sentence sits inside the facts section.
4. **The drift is fixed:**
   - the reward sentence moves into the facts section, where the cost line already is, instead of standing alone at the top;
   - "what you tried" says where it lives (the task text, or `--tried` once BT87 lands);
   - "the project keeps the record" names that it is public on a public repository, in BT73's words;
   - the paid-on-merge claim carries its exception while held board listings exist.
5. **What a test cannot prove is stated in `CLAIMS.md`:** whether the words *persuade* an agent well. That would need agent runs, on the owner's request only. BT4's runs are cited as the last such evidence, with their date.

## Traps

- **Instruction blocks already written into other people's projects never update** (BT89's trap). A wording change reaches them only when the block is rewritten. Say so in `CLAIMS.md`; do not try to reach them.
- **"Wording is product": keep it short.** A claim that grows to carry exceptions should be split, not lengthened. BT4 found more detail is not better.
- **A claim must not promise what a hard stop does not keep.** Where a claim and a guard disagree, the guard wins and the claim is reworded.
