# BT98: pages follow GitHub's Link header, and a refused token names the permission it lacks

Milestone: BT (the bounty tool), with a board part · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT98` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Bug fix playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the GitHub transports (`packages/box-bounty/gh.ts`, `gh-direct.ts`, `github-auth.ts`) with the owner ("yes").

**Why.** The transports follow GitHub's guidance:
- requests one at a time;
- rate limits read from `Retry-After` and `X-RateLimit-Reset`, never hammered;
- reads retried once, writes never;
- the API version header sent;
- the token on a child's standard input with an empty environment, only `api.github.com` reachable, and no redirects followed;
- Git's credential helper given per call.

Two things are short of the guidance:

1. **Pagination builds page numbers by hand.**
   - `pages()` (`gh.ts`) asks `?per_page=100&page=<n>` until a page holds fewer than 100. The board's refresh does the same for its search (`packages/box-platform/src/refresh.ts`, `&page=${page}`).
   - GitHub: "you should not try to manually construct pagination queries. Instead, you should use the link headers to determine what pages of results you can request." ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api))
   - Endpoints that page by cursor ignore `page`, so a hand-built loop can repeat the first page or stop early, silently.
2. **A token is refused with no word on what it lacks.**
   - An agent using `GH_TOKEN` (BT59) has no list of the fine-grained permissions to ask its owner for.
   - On a 403 for a fine-grained token, GitHub can send `X-Accepted-GitHub-Permissions` naming what the endpoint needs. The tool says only `github-permission-denied` (`classifyGitHubFailure`, `gh.ts`).

## Outcome

1. **Every list follows `Link: rel="next"`.**
   - `pages()` asks the endpoint once with `per_page=100`, then follows the `next` address from each answer's `Link` header until there is none.
   - Each `next` must be on `api.github.com`, the same origin the direct route already enforces (`requestOf`), or the read stops with `github-response-invalid`.
   - The board's search does the same, within its existing cap of ten pages.
   - The run's call budget and deadline still bound every loop.
2. **The tool says which permissions a token needs.**
   - `docs/box-v4/BOUNTY.md` and FIRST-FIVE-MINUTES.md list the least fine-grained permissions for each half: posting and closing; solving (fork, push, pull requests). Each is confirmed against GitHub's permission pages for the endpoints the tool calls, listed with the endpoint.
   - On a 403 carrying `X-Accepted-GitHub-Permissions`, the refusal names that header's value: "GitHub says this token needs `<permissions>` for this; next: give the token that permission, or sign in with gh auth login". Without the header, the message is today's.

  - **A foreign `next`:** a `Link` pointing at another host stops the read, and nothing is sent there.
  - **Permissions:** a 403 with `X-Accepted-GitHub-Permissions: issues=write` names `issues=write` in the refusal; a 403 without the header keeps today's words.

## Traps

- **`gh api --include` returns the headers too** (`splitResponse`), so `Link` is read the same way on both transports. Do not switch to `gh api --paginate`: that would print a different shape than the direct route.
- **The header's value is GitHub's text:** shape-check it (`name=level` pairs, separated by commas) before printing it.
