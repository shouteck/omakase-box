# BT30: tests reach bounty records only through the support helpers

Milestone: BT · Station: packaging · Base: master at dispatch, after BT29 · Branch: `wave/BT30` · Timebox: 120 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 17 October 2026. The first of three waves that move the tool's memory to the design K26 and K27 settled (`kitchen/reviews/K26-shared-memory.md`, `kitchen/reviews/K27-storage.md`): **BT30** prepares the tests, **BT31** moves records into a local SQLite database, **BT32** splits each record into a shared part and a local part. Detailed for a cook without deep reasoning. **A test-only refactor: no product code changes, and no assertion changes.**

## Why

BT31 will store records in a database instead of `.box/bounties/<id>.json` files. Product code already reaches records only through `packages/box-bounty/record.ts` (`loadRecord`, `persistRecord`, `listRecords`, `writeNewRecord`, `recordPath`, `recordDir`) plus one line in `render.ts` that writes `.box/bounties/OPEN`. The tests do not: 22 files under `tests/box/bounty/` reach record files directly, about 136 times. The commonest spellings:

- `join(repo, '.box', 'bounties', `${id}.json`)` (about 25), `'.box/bounties'` literals (about 26), `join(repo, '.box', 'bounties')` (about 9);
- `readFileSync(recordPath(...))` and `writeFileSync(recordPath(...), ...)`;
- `join(repo, '.box', 'bounties', 'OPEN')` and `'FIRST_MERGE'`;
- hand-written broken files (`x.json`) for the corrupt-record cases.

If BT31 had to change the storage and all those lines at once, a failure would be hard to attribute. So this wave moves every one of them behind a few helpers, with records still in JSON files, and the suite stays green. BT31 then changes only what the helpers do inside.

## Outcome

No test outside `tests/box/bounty/support.ts` names a record file, the records folder, `recordPath` or `recordDir`. Every test reads, writes, lists or corrupts records through named helpers, and the whole suite passes unchanged in what it asserts.

## Scope

- Write: `tests/box/bounty/support.ts` (the helpers), every file under `tests/box/bounty/` that touches records, and `tests/kitchen/**` only if a kitchen test reaches records the same way.
- Do not touch: `packages/**`; any assertion's expected value; what any test proves.

## The helpers (in `support.ts`)

Name them exactly so BT31 can reimplement them:

| Helper | Today's body | What tests use it for |
|---|---|---|
| `readRecord(repo, id): BountyRecord` | parse the record file | asserting a record's state after a command |
| `readRecordRaw(repo, id): string` | the file's text | byte-identity checks ("the record is unchanged") |
| `writeRecord(repo, record)` | write the JSON file exactly as `persistRecord` formats it | planting a hand-made record (old shapes, forged fields) |
| `writeRecordRaw(repo, id, text)` | write the text as is | planting a corrupt or tampered record |
| `recordIds(repo): string[]` | the sorted ids of the record files | counting or listing records |
| `recordExists(repo, id): boolean` | does the file exist | asserting a record was or was not written |
| `removeRecord(repo, id)` | delete the file | the "record deleted by hand" cases |
| `openLine(repo): string` | the text of `.box/bounties/OPEN` | asserting the open-bounties index |
| `boxFile(repo, name): string` | path of a tool file beside the records (`FIRST_MERGE`, `hook-told.json`, …) | the few cases that read other tool files |

Add a helper only if a real case needs one these do not cover, and list it in the Result with the case.

## Method

1. List every occurrence: `grep -rn "\.box/bounties\|'\.box', 'bounties'\|recordPath\|recordDir" tests/` and paste the list (file, line, what it does) into the Result before changing anything.
2. Write the helpers. Their bodies do exactly what the test code did, so behaviour is unchanged.
3. Replace occurrences **one file at a time**, running that file with `node scripts/suite.mjs box --suite bounty tests/box/bounty/<file>` after each. Never change an `expect(...)` value; if a replacement needs one changed, the replacement is wrong.
4. Add a guard test, `tests/box/bounty/record-access.test.ts`: it reads every file under `tests/box/bounty/` except `support.ts` and the guard itself and fails, naming the file and line, if any contains `.box/bounties`, `'.box', 'bounties'`, `recordPath` or `recordDir`. BT31 and later waves keep it.
5. Run the full suite.

## Done when

- `node scripts/verify.mjs test:box-bounty test:box-package test:kitchen` exits 0 on the final commit.
- The guard test passes, and is shown to fail when one direct `.box/bounties` path is put back in a scratch copy (Result says how).
- The assertion lines are unchanged: a scripted comparison of every line containing `expect(` across `tests/box/bounty/`, master against the candidate, shows the same multiset of assertions (only the arguments that name a path may differ, through a helper call). The pass reruns the comparison.
