# K69: test conversions from K68 (the slow tests, each with its break proof)

Milestone: K (kitchen) · Station: evidence · Branch: `wave/K69` · Timebox: 480 minutes
Owner decisions: on 13 November 2026 the owner chose "test conversions" first, after [K68](../kitchen/reviews/K68-slow-tests.md)'s review of the 30 slowest tests. Order, scope and method are the CTO's.

**The method for every conversion** ([TESTING.md](../docs/box-v4/TESTING.md)): the old test and the new test meet the same one-place breaks of the code (`node scripts/guard-audit.mjs --ref master` runs the table against the old tests; the plain run against the new). A test goes only if, for every break where it is red, a remaining test is red too. Each removal is listed below with its reason. `guard-audit.mjs` gained `--ref`, so old and new tests can be run against the same break.

### The classifier's proof (13 breaks, the four old files against the new table plus the same files)

- **Nothing the removed tests caught is missed:** no break turns a removed test red while nothing new is.
- **The table catches more:** environment references (`$HOME/...`, `%TOOLS%`) were noticed by no old test; two more breaks (a host wrapper, an inline `git -c` alias) were silent in the old tests and in the first version of the table, and turned red once the table got a row only that rule can explain (a wrapper in front of a safe alias; an inline alias to an outside program).
- **Three rules stay unprovable on their own, in old and new alike:** a pipe as a command separator, a semicolon as one, and "a file that exists in the tree is not placed". Each overlaps with the rule that every word of a configured line is checked, so removing it alone changes no verdict. That is defence in depth, noted rather than forced.

## Result

Done on 13 November 2026. Hosted run @@RUN@@.

- **Per piece, one worker, measured old then new** (table above): `bt7c-review` −5 s, `bt38` −25 s, `pf5` −15 s, `bt56` −16 s, `first-merge` −32 s, the four `bt6b` files −145 s: about **240 s** in all. Every conversion was proven by running the same breaks against the old tests (`--ref master`) and the new (K69-breaks.json has all 22 breaks).
- **The whole bounty suite, old against new, run back to back on this host** (108 files, 1345 tests against 109 files, 1362): summed test time 5886 s to 4481 s (−24%), wall time 2018 s to 1537 s (−24%). **Most of that is the machine, not the tests:** the 90 files none of K65 to K69 touched took 4152 s in the first run and 3379 s in the second (0.81), so the host itself ran 19% faster the second time. Adjusting the old figure for that, the touched files went from about 1405 s to 1102 s, **a suite about 6% faster** (about 300 s of 4770). One host, two runs, ±20% between identical runs: the order of magnitude is the finding, not the digit.
- **A bug found by running the suite on a new day:** `bt61-text` stored the issue body's date ("posted 12 Nov 2026") literally, so it failed on any run after midnight UTC on 13 November; the old suite fails it today and master's next hosted run would have too. Its normaliser now turns the date into `<date>`; the snapshot changed in that one field (checked by script). The new suite has no failure.
- **Not provable alone, in old and new alike:** a pipe and a semicolon as command separators, and "a file that exists in the tree is not placed": each overlaps the rule that every word of a configured line is checked. Noted, not forced.
- **The first measurement of this wave was wrong,** and was caught: a whole-suite comparison across two runs of different load read +44% (4961 s against 3444 s). The files I had not touched were slower by the same amount. The comparison above is the second attempt, with that control.
- **Not done:** the `bt43` renderers (42 s), the shared journey transcript (27 s), the retired-shape tests (an owner question), and the remaining eleven `bt6b` landing journeys (about 120 s), which could share a world.
- **Tools:** `guard-audit.mjs --ref`; `proof-gaps.json` loses R1, T1 and T4 (now tagged).
