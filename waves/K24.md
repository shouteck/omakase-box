# K24: no test runs close to its time limit, and editing a wave file costs no rerun

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch, after BT26 · Branch: `wave/K24` · Timebox: 150 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 16 October 2026 after reviewing K23 and BT18 to BT25. Detailed for a cook without deep reasoning: one measurable rule for the tests, one rule for verify.

## Why

K23 fixed the two named slow tests, but the suite kept growing (bounty: 496 tests at K23, 597 at BT25) and load timeouts kept reddening runs that had nothing wrong with them. In the run after K23:

- BT23's pass: three full runs red, each only on `bt19.test.ts` › "reads the whole journey as one document" timing out at 30 s (19 s alone).
- BT23's cook: `tests/box/package/verify.test.ts`'s nested owner check hit its 5 s limit once under load.
- BT22's pass: a vitest worker-fork failure on one run.
- BT21's cook: `github.test.ts` alone takes about 80 s, so one worker carries it while the others finish early.
- BT25 and BT20: the cook edited the wave file while verify ran; the run was recorded dirty, so it could not be reused and every suite ran again (12 to 14 minutes each time).

Each of these cost a full rerun of 10 to 15 minutes, and some cost several.

## Outcome

On this host, under the suite's normal three workers, no test takes more than half its time limit in any of three full runs, with no limit raised and no assertion changed; the bounty suite's files are balanced so no single file dominates; and a verify run whose tree is dirty only in paths a step does not read still counts for that step.

## Part 1: the half-the-limit rule

1. **Measure.** On master, run `node scripts/suite.mjs box --suite bounty` three times and `node scripts/suite.mjs box --suite package` three times, with vitest's JSON reporter writing to a scratch folder outside the checkout. For every test record its duration in each run and its limit (the file's or the test's `timeout`, else the suite default). Note the host load beside each run (Task Manager's CPU figure or `Get-CimInstance Win32_Processor`), as the evidence card asks.
2. **List every test whose longest duration is above half its limit.** That list is the work. Expect `bt19.test.ts`'s journey, the package `verify.test.ts` nested check, the K14 budget test and the BT17 journey on it; take whatever the measurement shows.
3. **For each, make it cheaper** the way K23 did: share a built world between cases that only read it (a case that writes gets its own copy); batch Git reads (`gitBlobs`, one `cat-file --batch`); build fixtures with `git fast-import` instead of many plumbing calls; move pure-text cases into a file that starts no Git. A long end-to-end journey that cannot get cheaper may be **split** into consecutive tests sharing one world (each step its own `it`), so each stays under half its limit, with every assertion kept and in the same order.
4. **Balance the files.** If one bounty test file takes more than a quarter of the suite's wall time (expect `github.test.ts`), split it into files by theme (posting, collecting, closing, refusals), moving tests unchanged. Shared setup moves to a helper module.
5. **Measure again**, three runs each, the same way.

## Part 2: a tree dirty only where a step does not read

In `scripts/verify.mjs`: today a run on a dirty tree is recorded `+dirty` and never reused. Change the rule per step. A step's PASS on a dirty tree is recorded as reusable for the commit when every dirty path (from `git status --porcelain`, at the start and again at the end of the run) is one that step does not read, decided by the same rules K23's ancestor reuse uses (`isInert`, and for `test:kitchen` also `KITCHEN_TEST_READS` and `waves/*.md`). The summary line still says `+dirty` and names the dirty paths; a step that read a dirty path is recorded as not reusable. Tests in `verify-reuse.test.ts`: a run with only `waves/X.md` dirty is reused for `test:box-bounty` and not for `test:kitchen`; a run with `packages/` dirty is reused for nothing.
