# BT87: "done when" and "already tried" become facts of their own, shared and shown beside each solution

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT87` · Timebox: 180 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short to medium. Feature playbook; principles: prove-it-works, subtract-before-you-add, encode-lessons-in-structure.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of shared memory with the owner. The owner: the shared memory is the one infrastructure the tool owns, and it must help an agent's delegation more than it hurts it ("yes").

**Why.** The shared memory's substrate is right (the chain, BT32 and K28). What it carries is thin exactly where an agent's judgment needs it. `docs/box-v4/MEMORY-SPEC.md` lists, for each moment, the question and the facts that answer it. Two facts behind the hardest questions are marked **missing**:

| Question (MEMORY-SPEC section 2) | Needs | Today |
|---|---|---|
| M6, M7: does this solution do what was wanted? which one do I merge? | **F-done**, what "done" looks like | inside the task text, if the agent happened to write it |
| M3, M6: what was already tried? (a solver should not repeat dead ends) | **F-tried** | missing |

The tool's own issue template already has a place for F-tried: `renderBountyIssue` (`packages/box-bounty/issue.ts`) writes `## What was already tried` from `note`. But `post.ts` passes `null` whenever `record.noteSource === 'generated'`, and `finalizeBounty` (`create.ts`) writes every new record with `noteSource: 'generated'`. So the section appears only for records made before that change, and no current agent can fill it.

A reviewing agent without F-done judges a solution against its own guess of the intent. A solver without F-tried pays to rediscover the same dead ends.

## Outcome

1. **`create` takes two optional options:**
   - `--done "<text>"`: what done looks like, the checks a reviewer can apply;
   - `--tried "<text>"`: what was already tried and what is suspected.

   Either may be left out: the tool offers, never enforces. When both are missing, the create preview adds one fact line, "done and tried: not given; a reviewer will judge against the task text alone", and nothing more.
2. **Both are the bounty's own text, treated like the title and task:**
   - scanned at `create` and again at `post` (`scanFields`, `TEXT_FIELDS` gains `(done)` and `(tried)`);
   - a hit cannot be settled through the publish lists (BT45's rule);
   - counted against the issue body limit (`assertBodyFits`).
3. **Published:** the issue gains `## Done when` (after "What is wanted") and fills `## What was already tried` from `--tried`. Neither section appears when its option was not given, so issues without them read exactly as today.
4. **Shared:** the `posted` event carries `done` and `tried`:
   - `chain.ts`: the event allow-list for `posted`, `SCANNED_FIELDS`, `validEvent`, `foldEvents`;
   - `find`'s search text.

   Older events without them still import.
5. **Shown where the question is asked:**
   - `look <id>` prints "done when" above the solutions it lists, so the reviewer reads the test before the diff;
   - `look <id> <n>` prints it above that solution's diff;
   - `status <id>` and `status --json` carry both fields;
   - the overview stays as it is (bounded, K25).
6. **The board reads both** (corrected 24 November 2026 from the walkthrough of the board).
   - `taskOf` (`packages/box-platform/src/refresh.ts`) cuts the task out of the issue up to the next of the tool's headings, `## What was already tried` or `## How to answer`. A new `## Done when` is not one of them, so it would land inside the board's task text. "Already tried" never reaches the board's data at all.
   - `taskOf` stops at `## Done when` too, and the board reads the two sections into `done` and `tried` on a bounty's detail (`/bounties/<id>.json`, the MCP `get_bounty`, the schema), each bounded like the task.
   - The feed list stays as it is.
7. **The spec:** MEMORY-SPEC rows F-done and F-tried name their source and field (`done`, `tried`), and are no longer "missing". If [BT75](BT75.md) has landed, they get its **Lives** value `shared`; if not, BT75's table picks them up.

## Done when

- The hosted run on the final commit is green on Linux, Windows and macOS, quoted with its run id; the suites the change affects: `test:box-bounty`, `test:kitchen`.
- `bt87.test.ts`, against the stand-in world, each seen red on master first:
  - **Published:** `create --done "<d>" --tried "<t>"`, then `post`. The stand-in issue body holds `## Done when` with `<d>`, and `## What was already tried` with `<t>`.
  - **Shared:** the posted event in the bare remote carries `done` and `tried` exactly as written. A second clone (`secondMachine`, its own owner settings) shows both in `status --json`.
  - **Shown:** after a solution arrives, `look <id>` prints the done-when text before the first solution line. `look <id> 1` prints it before the diff.
  - **Scanned:** a secret-shaped value built at run time in `--tried` refuses `create` naming `(tried) line 1`, and a planted one in a record refuses `post`. Neither prints the value. The stand-in holds no issue.
  - **Left out:** a bounty created without either: the issue body is byte-for-byte what master renders for the same inputs; the preview shows the one fact line.
  - **Old events:** a chain written by master's `sharePosted` still imports, and the record has no `done` or `tried`.
- **The board:** `taskOf` on an issue with all three sections returns the task alone. The detail JSON carries `done` and `tried`. An issue in today's shape gives today's task, byte-for-byte (the board's existing `taskOf` tests pass unchanged).
- `node scripts/surface.mjs --write` shows the two new options and nothing else; the Result shows the diff (BT62).
- A break proof: drop `done` from the `posted` allow-list, and the shared test turns red, naming the field.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master.
2. **The options and the record:**
   - `args.ts` declares `--done` and `--tried`;
   - `create.ts` trims them, refuses an empty value given explicitly (as `--part-of` does), and scans them with the title and task;
   - the record keeps `done` and `tried`.
3. **The issue:** `renderBountyIssue` takes `done` and `tried`. `post.ts` passes `record.tried` for the "already tried" section in place of the generated-note rule. Records made before this wave keep today's behaviour: an authored note still shows, a generated one does not.
4. **The chain:** add both to the `posted` allow-list, `SCANNED_FIELDS`, `validEvent`'s string fields, `foldEvents`, and the search text.
5. **Shown:** `look`, `status --json`, `find`.
6. **Docs:** MEMORY-SPEC, BOUNTY, CONTRACTS, the solver `describe` text; surface; snapshots under `## Changed expectations`.
7. **Verify,** push, hosted run, Result, merge.

## Traps

- **Both texts are public once posted,** on the issue and on the chain. The option help and BOUNTY.md say so in those words, as BT73 does for the why.
- **The issue body limit counts the new sections.** A long `--tried` must refuse at `create`, not fail at `post`.
- **Keep the old generated-note rule for old records.** Changing it would publish a note those records were promised stays local (BT14, F4).
- **`look`'s output is read by the deciding agent:** "done when" is the poster's own words, so it is the tool's to print plainly. A solver's text stays in its frame as today.
