### 1. Product model: how an agent comes to use the tool

| Practice | Who | Ours |
|---|---|---|
| One command sets up every agent found on the machine | Firecrawl (`npx -y firecrawl-cli@latest init --all`), Beads (`bd init` writes AGENTS.md and the Claude, Codex and Cursor integrations) | **Have it:** `npx -y omakase-box setup` |
| A fallback that prints the lines for an agent the tool does not know | Beads (`bd onboard`) | **Have it:** `describe --rules`, `config set instructions true` |
| The skill lives in a public repository agents can add by name | Arcjet (`npx skills add arcjet/skills`), Firecrawl (`firecrawl/skills`) | **Gap:** ours is written only by `box setup`, from inside the package. A skill added that way is invisible to the registries, and installs are how they rank. PF6 plans the repository; note added there to settle how installs are counted |
| Sign-in with a token from the environment, no browser | Arcjet, Firecrawl | **Briefed today:** BT59 |
| A free route that needs no account at all | Firecrawl (a keyless tier, rate-limited) | **Have it:** nothing to register; a GitHub account the agent already has |
| The CLI and the MCP server are peers; the agent picks | Arcjet | **Have it:** tool, feed and MCP with three tools |

The evidence on "a CLI with a skill beats an MCP server" is mixed: one vendor's benchmark claims a 17-fold cost difference, an independent test of one tool found none. We offer both and the MCP side is small, so nothing changes.

### 2. Engineering practice

| Practice | Who | Ours |
|---|---|---|
| Never prompt; unknown flags fail; distinct exit codes | Arcjet | **Have it** (0, 2, 3; no prompt anywhere) |
| Every command's help has a usage line and a real example | Arcjet | **Have it** (seen on `post --help`) |
| Machine output carries a version | Arcjet (a frozen contract) | **Have it** (`"schema":"box-bounty/status@1"`) |
| **With machine output on, an error is data too:** one JSON shape with a code and the fix | Arcjet | **Gap:** `look --json` on a refusal prints nothing on standard output and plain text on standard error. A program must parse a sentence |
| **Machine output on every command** | Arcjet, Beads (`--json` throughout) | **Gap:** only `status`, `look`, `config`, `discover`. `create --json` answers "not available yet", so a script cannot read the new bounty's id as data |
| Commands, flags and fields frozen at 1.0, additive after | Arcjet | For discussion: we are at 0.x |
| **A standing evaluation: realistic tasks, run by agents, rerun when a description changes, with a held-out set** | Anthropic's guidance | **Gap, for discussion:** our fresh-agent checks are real but written anew per wave and never rerun. This is the practice I would most like us to have |
| Review the tool with an agent-CLI linter | Arcjet (found things they had missed) | Folded into BT61 as a first step |

### 3. Business model

| Model | Who | What it teaches us |
|---|---|---|
| Open core, paid hosting, priced per unit of use, with a real free tier | Firecrawl (1,000 free credits a month, then from $19) | The paid part is what is costly to run, not the code. For us that is the payment the board automates |
| Open client, closed backend, free tier with a key | Context7 | **It cut its free tier by about 90% in January 2026 and is still written about for it.** Say what will cost money before people depend on it being free |
| No revenue; one maker; spread by usefulness | Beads | An agent tool can become a default with no business at all; its reward is being the standard |
| A share of each reward, paid by the poster on top | Algora (9% on its own pricing page; third parties report 10% to 23%), Opire (about 4% to 5%) | The going rate for exactly our kind of fee is 4% to 9%, charged to the one who posts. D-2026-11-10-revenue-later's "small share on automated payments" sits inside it |

### 5. For discussion

1. **A standing agent evaluation.** A fixed set of situations (stuck on a failing task, needs a machine it lacks, wants paid work, and some where the tool is the wrong answer), run by fresh agents against each release, scored from the logs. It would turn "does the skill's sentence work" from an opinion into a number that can go up. The difficulty is ours: the rule that test agents are fresh desktop sessions started from an owner's turn means it cannot run unattended. Recommendation: allow a headless fresh session in a scratch folder outside the repository for this one purpose, and I brief it.
2. **Say the future fee early.** One sentence on the site: free now; a small share on payments the board automates may come later. Context7 is the cautionary case. It touches wording the owner approved.
3. **A 1.0 promise.** State when commands, flags and JSON fields freeze, and hold it with a test. Agents and their skills are written against exact output; breaking it silently loses them. Recommendation: at launch.
4. **More ways to install** (Homebrew, an install script), as Beads offers. Recommendation: not now; npm covers the agents we are aiming at, and each route is something to keep working.

### 6. The owner's answers (10 November 2026, D-2026-11-10-k55-answers)

- **1 A standing evaluation:** no. Too much plan usage for an uncertain benefit; agent behaviour is tested as before, by fresh desktop sessions, when a wave needs it.
- **2 Say the fee early:** no. It is added when there is volume.
- **3 A 1.0 promise:** not at launch. Stay below 1.0 through launch and first real use; record the surface now so a change is deliberate ([BT62](BT62.md)). This revises section 5's "at launch".
- **4 More install routes:** not now.
