# PF26: `submit`, and the solver's `status` to merged and paid

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF26` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-03-solver-in-the-tool, D-2026-11-03-cli-and-board-split
Horizon: short, with a real-GitHub step in the sandbox. Feature playbook; principles: experience-first, prove-it-works

**Brief.** Written by the CTO on 3 November 2026, replacing part of PF12 (see [SOLVER-CLI.md](../docs/box-v4/SOLVER-CLI.md)). Needs PF25.

## Outcome

A solver agent finishes the work, runs `box bounty submit`, and follows its attempt to the end with `status`:
- the poster's review comments, marked as theirs;
- merged or closed;
- paid or not, and how.

If no way to be paid is connected, `status` names the board's link once. That is the one human step.

## Scope

- Write: `packages/box-bounty/` (a new `submit`, `status` for taken bounties, help), `tests/box/bounty/`.
- Do not touch: the board (beyond reading it), payments, the posting commands' behaviour.

## Build

1. **`submit`:** marks the draft ready for review, with the bounty format's line. It refuses if the branch has no change beyond the empty commit. The record moves to submitted.
2. **`status` on taken and submitted bounties:**
   - the pull request's state;
   - review comments by others, marked as theirs (as `--comments` does today);
   - merged or closed;
   - whether it is paid and how (pay on merge, one click, recorded by the owner). This is read from the board's **public** bounty answer, which already carries the payment facts. The CLI has no board session and needs none.
3. **The payment step:** the board's public solver answer (`/solver/<login>`) already says whether this login can take Stripe or PayPal (`takes`), and lists its public payment links.
   - **When it shows no way to be paid,** `status` prints one line with the board's link, like PF20's pay-on-merge line. The tool cannot connect it.
   - **When `takes` is unknown,** because the solver has no pull request on the board yet, `status` says that, not "none".
   - **No reminders after that** (D-2026-11-02-no-owed-reminders).

## Done when

- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit.
- **Real GitHub, in the sandbox only:** a taken bounty goes through submit, a review comment, a merge by the poster's tool, and `status` shows it merged.
- **Paid state:** a test fails if the paid state is made fixed. Each state is read from a stand-in board's public answers, and a test proves no board session is used.
- **Hostile text:** a review comment is printed as the commenter's words, never as the tool's.

## Lenses

- [x] **Security:** hostile review comments; a pull request renamed or retargeted by someone else.
- [x] **User experience:** a fresh agent follows its attempt to merged without being told how.
- [ ] **Measurement fairness:** not applicable.

- **What shipped:**
  - **`submit <id>` (`attempt.ts`):** reads the attempt's pull request in one GitHub read (GraphQL), bound to the branch the take pushed. It refuses by name when the pull request changes no file (`nothing-to-submit`), is no longer open (`attempt-ended`), targets another branch (`attempt-retargeted`) or comes from another branch (`attempt-mismatch`). Otherwise it marks the draft ready and replaces the tool's own draft sentence in the description with "A solution to bounty <id>, ready for review.", leaving the solver's words. The record moves to `submitted`.
  - **`status <id>` on a bounty this account took:** works outside any checkout and states:
    - the pull request (draft, ready, merged on a date, closed without a merge; a changed target named);
    - a count of comments and reviews, with how many came from the poster, and `--comments` prints them inside the other-account block;
    - the board's public payment fact, from the solver's side ("owed $45 to you", "paid through Stripe, Stripe's word", "you say not received");
    - for a rewarded bounty, how the solver can be paid, as the board says;
    - one `next:` step that fits the state.
  - **`status` with no id** lists the attempts taken, from the local record alone (no GitHub read). It works outside a checkout; inside one, it follows the poster's overview.
  - **The one human step:** with no way to be paid shown, the board's `/me/` link and the person's step are printed once per account, then only the fact. When the board has read no pull request of the solver's yet, status says it cannot say, not "none".

- **"The bounty format's line":** read as the description's line saying it is a solution to the bounty. The format's `pay-to:` line is the poster side's older route and was left alone.

- **Lenses:**
  - **Security:** hostile review text (forged footer, forged `next:`, a claim in the tool's voice) stays quoted in its block, in tests and on real GitHub. A pull request retargeted by someone else is refused before any write and named in status; a record pointing at another branch is refused. The board is read only through its public GET answers. A renamed title is harmless: nothing reads it.
  - **User experience:** every state ends in one `next:` that fits it, and the sandbox journey ran from take to merged on these lines alone. A fresh agent doing it unprompted is PF27's check, and is not claimed here.
- **Principles:**
  - **experience-first:** `status <id>` works outside a checkout, and `submit` refuses an empty attempt with the exact push to make, so the agent never has to work out where it stands.
  - **prove-it-works:** the sandbox run used the real GraphQL API and checked GitHub with `gh` independently; it is also what surfaced the board's slow detail.
