# BT80: `apply` checks never-ship again, under the rules in force at the merge

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT80` · Timebox: 120 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `apply`. The owner asked for it ("Yes, brief it"). Hard stop 1, the inbound side: a never-ship file never comes back in a solution (CONTRACTS R3).

**Why.** The never-ship check on a returned solution, `checkSolutionHistory` in `packages/box-bounty/collect.ts`, runs once, when the solution is collected (by `look`, `apply` or `status`). It reads every path the pull request's new history touches, under `shipRules(root)` as they are **then**.

`apply` later merges the recorded attempt. When the attempt is already recorded, `resolveAttempt` checks only whether the pull request's head moved. It does not ask the never-ship question again. The rules can grow between collection and merge:
- the owner adds a path with `config add never-publish`;
- a release adds built-in rules (BT72 adds credential files);
- BT77 makes the owner's list reach every copy of the repository;
- a copy of the tool from before any of these collected the solution.

In each case `apply` would merge a file that today's rules keep out. `post` already guards its own side this way: BT69's `checkOutbound` reads what is actually sent, under the rules as they are now, at the last moment. This wave gives `apply` the same last check.

## Outcome

1. Just before the merge (after the owner's merge gate and the unsafe-config check, before any byte is saved or the merge runs), `apply` runs the history check on the attempt's commit under the current `shipRules(root)`.
2. A violation refuses with the existing reason `answer-never-ship`, naming each path and its rule. The message says nothing was merged (not "nothing was collected"), and the next step is to close the bounty or ask the solver for a version without the path. The working tree, index, branch and record are unchanged.
3. When the rules did not change, the extra check costs one history walk of the pull request's new commits. Its time on the largest solution in the test suite is quoted in the Result.

## Traps

- The check must run **after** the owner's merge gate. Otherwise a held merge would name never-ship paths to an agent that is only waiting, and the hold's bound state would change meaning. It must also run **before** `snapshotBytes`, so nothing is saved or restored for a refused merge.
- `checkSolutionHistory` also refuses link, submodule and unusual paths. Those are about the tree, which does not change after collection, so a second run cannot newly refuse them; say so in the Result rather than testing it twice.
- The rule set for the "built-in added later" test is injected through the test, never by editing `BUILTIN_RULES` in place.
