# BT72: the never-ship table names the credential files it missed

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT72` · Timebox: 90 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works, subtract-before-you-add.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `create` with the owner, who said "Yes, brief it". Never-ship is the first hard stop: a never-ship file never enters a bounty and never comes back in a solution. The built-in table (`UNFOLDED_RULES` in `packages/box-bounty/never-ship-paths.ts`, mirrored for agents in `docs/box-v4/BOUNTY.md` near line 1405) names env files, `secrets` folders, key and certificate extensions, and nine credential files plus `.aws/credentials` and `.docker/config.json`. Read on 23 November 2026, it does not name files that commonly hold live credentials:

| File | What it holds |
|---|---|
| `kubeconfig`, `.kube/config` (and `*.kubeconfig`, `kubeconfig.yaml`/`.yml`) | Kubernetes cluster access, the client key base64-encoded |
| `*.tfstate`, `*.tfstate.backup`, `*.tfvars`, `*.tfvars.json` | Terraform state and variables: provider passwords and keys in plain text, in no fixed shape |
| `*.p8` | Apple App Store Connect and push-notification keys |
| `.config/gh/hosts.yml` | the GitHub command line's own token |
| `application_default_credentials.json` (gcloud, usually under `.config/gcloud/`) | a Google Cloud developer login |

**Why the secret scan does not cover these:** the scan reads text for known key shapes. A kubeconfig's key is base64 and Terraform's values have no fixed shape, both stated misses (BACKLOG, "Scan coverage after BT45"). Since BT6a such a file leaves only with the agent's uncommitted work (`--with-changes`) or named one by one (`--include`), but the rule for this hard stop is "never", not "rarely". The same table refuses these files in a solution that comes back (apply), so a solver cannot put one into the owner's tree either.

## Outcome

The built-in table names each file above, and any other that an established secret-file list on the day shows to be a credential store and the table lacks, each with a reason in the Result. A path the table names is removed at create, left out at post and refused at apply, exactly as the existing names are. Nothing else changes: no rule is removed or loosened, the existing rule names stay, and no ordinary file is newly matched.

## Traps

- `*.tfvars` sometimes holds harmless settings, and `.p8` is rare outside Apple keys. The table already chooses strictness (`.env.example` is kept out because templates often hold real values), so keep the strict reading, and say in the Result that a harmless file of these names is now kept out too. An owner who needs one shipped can rename it.
- A new name must not catch ordinary project files. Every near-miss row stays unnamed, and the seeded variants keep it so.
- Do not add a new rule name: agents read rule names in removal notes, and BT62's record should show no change. If a file truly fits no existing rule, stop and say so.
- No expected outcome of an existing test changes. A new name that some existing fixture ships would be a changed expectation: list it under `## Changed expectations` with the reason, or the test-edit gate refuses the branch.

## Lenses

- [x] **Security:** this is the first hard stop. Attack it: each new name spelled with a look-alike character, in a different case, inside a nested folder, as a link inside the repository, named with `--include`, carried in a solution at apply. Say what each did.
