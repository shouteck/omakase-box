# K19: the demo's stand-in GitHub answers like GitHub

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch · Branch: `wave/K19` · Timebox: 60 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 14 October 2026 from K18's Result, on the owner's go for this order: this first, then BT13, then BT14. A kitchen wave: it cooks only when named.

## Why

K18 found that the stand-in GitHub inside `kitchen/demo/bt11b-replay.mjs` answers `GET repos/<o>/<r>/issues/<n>` with the whole list of issues instead of one issue, and reads the page number out of `per_page=100`, so every paged list comes back empty. Every "github-status-unavailable" in K18's runs, the `github-issue-mismatch` on `status --comments`, and an empty pull request list were the stand-in's doing, not the tool's. The replay's own committed stand-in transcript has shown the fault since K17, so the stand-in demo has never shown the pull request list. One participant's run looking wrong was the only reason it was caught.

The tool's own test fixture (`tests/box/bounty/github-fixture.ts`) is a different stand-in and, on a first reading, handles both requests correctly. That is to be confirmed, not assumed.

## Outcome

Every stand-in GitHub in this repository answers each request the tool makes the way real GitHub does, and a check fails when one stops doing so.

## Scope

- Write: `kitchen/demo/**`, `tests/box/bounty/bt7-ux-fixture.mjs` and any other stand-in found, `tests/kitchen/**`.

- Do not touch: product code under `packages/`; the tool's tests' expected outcomes; GitHub.

## Done when

- `node scripts/verify.mjs test:kitchen test:box-bounty` exits 0 on the final commit.
- **Every stand-in is found and listed** in the Result: each file that answers `gh api` for a test, a demo or a fixture.
- **Each answers correctly** for every request the tool makes: one issue for `issues/<n>`; the page asked for by `page=`, never a number read out of `per_page=`; lists filtered as GitHub filters them; pull requests numbered as GitHub numbers them, sharing one sequence with issues.
- **A parity check.** A test in `tests/kitchen/` drives the stand-ins through the requests in the committed real-GitHub transcript and compares the shape of each answer (one object or a list; the fields the tool reads; paging) with what real GitHub returned there. It fails if a stand-in drifts. Before the fix, it fails on the replay's stand-in; the Result says so.
- **The stand-in demo shows the pull request list.** The replay's committed stand-in transcript is re-recorded, and its step that lists solutions shows both pull requests with their pay facts. No "github-status-unavailable" appears in it.
- The station card's line from K18 (check a stand-in against a real transcript first) points at the new check.
