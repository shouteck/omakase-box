# BT22: the owner's settings hold only the owner's choices

Milestone: BT · Station: packaging · Base: master at dispatch, after BT21 · Branch: `wave/BT22` · Timebox: 120 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 15 October 2026 after reviewing BT17 and K21 (S4); the owner agreed the queue that day. Detailed for a cook without deep reasoning: the key-by-key split is below.

## Why

The owner's settings file (`settings.json` in `settingsDir()`, `packages/box-bounty/settings.ts`) is where the owner's yes lives. It now also holds the tool's own bookkeeping, and BT17 made an agent's read command (`status`) write to it the first time it says an explanation. So:

- An agent's `status` changes the owner's authority file. The owner, or anyone auditing it, can no longer tell their own choices from the tool's notes; 16 top-level keys are accepted, about half of them bookkeeping.
- `persist` writes the file in place (`writeFileSync`). A crash during one of these frequent bookkeeping writes can leave the owner's settings half-written, and then every command refuses `settings-malformed`.

The convention: `gh` keeps what the user chose (`config.yml`) apart from what the tool remembers (`state.yml`), and never writes the user's config on a read.

## Outcome

The settings file changes only when the owner (or their agent on their behalf) runs `allow`, `deny` or `config`, or answers a held action. Everything the tool remembers for itself lives in a separate state file next to it. Both files are written atomically.

## How to build it

1. **One state module.** `stateFile()` is `join(settingsDir(), 'state.json')`, so `BOX_BOUNTY_SETTINGS_DIR` covers both in tests. `loadState()` and `saveState()` mirror `loadSettings`/`persist`. A missing state file is an empty state. A malformed state file is not the owner's problem: the tool says one line (`the tool's own state at <path> was unreadable and was reset`), starts empty and rewrites it. That means an explanation may be said once more; nothing the owner decided is lost.
2. **Every reader and writer of a moved key** switches to the state module: `saidAlready`/`markSaid`, the reward and ask-merge notice functions, the first-merge notice (`settings.ts` around line 647 and `record.ts` around line 876), `renderConfig`'s migration and first-merge lines (`owner.ts` around lines 304 to 305), `rewardPromiseSaid` in `owner.ts` around line 363. Find them all with `grep -n` for each key name; list them in the Result.
3. **Moving existing values.** `loadSettings` still accepts the moved keys when it finds them in an old `settings.json`. The first time it does, it copies them into the state file (merging with what is there; state wins on a clash), then rewrites `settings.json` without them. This happens once; the Result shows a before and after file.
4. **Atomic writes for both files:** write to `<file>.<pid>.tmp` in the same folder, then `renameSync` over the target. On Windows a rename can fail while another process has the file open: retry a few times over about a second, then refuse by name (`settings-write-failed`) rather than leaving a partial file.
5. **A read never writes the settings file.** After the change, the only paths that call the settings writer are `allow`, `deny`, `config set`, `allow <id>` (answers), the one-time migration of step 3, and the existing BT8a migration. Add a comment above the writer saying so.
