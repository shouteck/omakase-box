# BT34: the bounty tool stands alone

Milestone: BT · Station: packaging · Base: master at dispatch · Branch: `wave/BT34` · Timebox: 75 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 18 October 2026. The owner approved retiring the older Box platform from master that day (PLAN.md, "The roadmap", Lean). This wave cuts the only seam between the bounty tool and that platform, so **K29** can remove the platform without touching the product. Detailed for a cook without deep reasoning. **No behaviour changes.**

## Why

The bounty tool (`packages/box-bounty`, and `packages/box-cli`'s `bounty` commands) imports exactly one thing from the older platform: `resolveProgram` from `packages/box-package/commands.ts`, used in `packages/box-bounty/gh.ts` and `packages/box-bounty/git.ts` to find `git`, `gh` and similar programs on the PATH safely. Three bounty test files import from `box-package` too: `tests/box/bounty/bt7.test.ts` and `tests/box/bounty/github-fixture.ts` (`resolveProgram`), and `tests/box/bounty/github.test.ts` (`resolveProgram` and `runDeclaredCheck`).

## Outcome

Nothing under `packages/box-bounty/`, `tests/box/bounty/` or the `bounty` path of `packages/box-cli/src/` imports from any older package, and everything behaves exactly as before.

## Scope

- Write: a new `packages/box-bounty/program.ts`; `packages/box-bounty/gh.ts`, `git.ts`, `index.ts`; the three test files named above (import lines and the one `runDeclaredCheck` call only); a new guard test.
- Do not touch: `packages/box-package/` (K29 removes it; it keeps its own copy until then); the `box export`, `submit`, `verify` and `trace` commands (K29); any assertion.

## The changes

1. **Copy, do not move,** `resolveProgram` and what it needs into `packages/box-bounty/program.ts`: the function, its `ResolvedProgram` type, `toPosix` (from `packages/box-package/paths.ts`), and the error classes it throws (`ProgramUnavailable`, `ProgramLaunchUnsupported`). Read how `gh.ts` and `git.ts` catch those errors (by class, by `reason`, or by message) and keep exactly what they rely on: if they test `instanceof`, the new classes must be the ones they test against; keep each error's `name`, `reason` and message text byte for byte. Their base class in `box-package` is `ExportFailed`; the copy extends `Error` with the same fields, unless something in the bounty code checks for `ExportFailed`, in which case say so and stop.
2. Point `gh.ts` and `git.ts` at `./program.js`.
3. **Tests:** `bt7.test.ts` and `github-fixture.ts` import `resolveProgram` from `packages/box-bounty/program.js`. In `github.test.ts`, replace the one `runDeclaredCheck({ name: 'parent gh', program: 'gh', args: ['auth', 'status'], … }, repo)` call with a direct `spawnSync` of `resolveProgram('gh')`'s path with the same arguments, working folder and 5-second timeout, and keep the two assertions after it meaning the same (the probe passed; the stand-in recorded exactly `[['auth', 'status']]`): `expect(probe.status).toBe(0)` stands in for `probe.result === 'pass'`. That is the only test change that is not an import line; say so in the Result.
4. **A guard test,** `tests/box/bounty/standalone.test.ts`: it reads every `.ts`/`.mjs` file under `packages/box-bounty/` and `tests/box/bounty/`, and `packages/box-cli/src/bounty.ts` if that file exists (otherwise the bounty part of `cli.ts`), and fails, naming the file and line, if any imports from `box-package`, `box-trace`, `box-contracts`, `analyzer`, `evaluation`, `planner`, `compiler`, `contracts` or `runner-protocol`.
