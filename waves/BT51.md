# BT51: a chosen solution shows as merged on GitHub

**Brief.** Written by the CTO on 1 November 2026. First of the waves that prove the product on real GitHub before launch.

## Why

`apply` merges on the owner's machine and the closing step deletes the bounty branch without ever moving it. A pull request's base is `box-bounty/<id>`, so GitHub records it as closed, not merged. Real example: `shouteck/box-bounty-sandbox` pull request 38 after a real `apply` (`state: CLOSED`, `mergedAt: null`). The board counts a merge only from GitHub's `merged_at` (`refresh.ts`, `payments.ts`), so after a normal `apply` it should show nothing owed and no track record, and the solver gets no credit. PF5's loop passed because the stand-in is not GitHub.

K42 designed the fix (`docs/box-v4/PLATFORM.md` section 3.3, step 3, sub-items 1 to 4) for the money path, and it was dropped when money left the platform. Credit still needs it, on every merge.

## Outcome

After `apply`, a recognised hand merge or a `close` retry, for a bounty with or without a reward, GitHub marks the chosen pull request merged. Once the owner pushes their branch, the board shows the merge, the owed state and the solver's record.

## The change

Follow PLATFORM.md 3.3 step 3 in `syncGitHubDecision` (`close.ts`), for **all** merges, not only rewarded ones:

1. Check the merged head locally: it descends from the posted commit and passes `collect`'s checks. A head that fails is not pushed.
2. The remote tip of `box-bounty/<id>` decides:
   - at the posted commit: push the head without force;
   - at the merged head: nothing to push;
   - any other commit: `github-branch-changed`, as today;
   - missing: never recreate it. Done if GitHub already reports the merge, otherwise pending `bounty-branch-missing`.
3. Read the pull request back. Delete the branch only when GitHub reports it merged.
4. Any failure leaves the branch, closes the issue as today and records `github-decision-pending (bounty-branch-not-advanced: <reason>)`, with a `next:` step. `close` is the retry.

A close without a merge is unchanged. The output states what the owner still has to do for the board to count it: push their own branch, because `apply` never pushes it.

## Plan

Agreed with the owner on 1 November 2026.

- **Widening decision:** this change widens "a stranger's PR can claim the owner's own later commit": the tool would push the owner's commit and GitHub would mark the stranger's PR merged. So the closing step does not advance when the commit that landed the head is older than the pull request (committer date before `created_at`) and the head is already on the default branch on GitHub. Pending `head-predates-pull-request`. Cost, failing safe: a fast-forward hand merge pushed before any bounty command runs reads as landed but not marked merged.
- `collect.ts`: export `solutionRefusal` (tree safety, never-ship); collect's behaviour unchanged.
- `close.ts`: `advanceBountyBranch` replaces the tip check for `apply` and `merged` events on records not yet closed; `decidedSolution` shared with `readPay`; pay recorded before the branch step. Reasons: `head-not-descended`, `head-refused`, `push-refused`, `bounty-branch-missing`, `not-marked-merged`, `head-predates-pull-request`.
- `bounty.ts` and `merged.ts`: one line saying the board counts it once the owner pushes their branch.
- Stand-ins compute `merged`, `merged_at`, `created_at` from reachability on the bare remote. Knobs: refuse the push, delay the mark.
- Tests: `tests/box/bounty/bt51.test.ts` (case table), `tests/platform` (owed; not on the default branch yet).
- Real proof in the sandbox, from an in-repo branch: one account is signed in and it cannot fork its own repository, so the fork route stays unproven on real GitHub.
