# BT99: every `--json` document states what may grow, and the surface check tells a compatible change from a breaking one

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT99` · Timebox: 180 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short to medium. Feature playbook; principles: encode-lessons-in-structure, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the `--json` documents with the owner ("yes"). It closes the codebase walkthrough.

**Why.** The documents (`packages/box-bounty/json.ts`; BOUNTY.md, the `--json` section) are well specified:
- `schema` comes first;
- "a change to a field's meaning grows `@2`, never silently";
- `null`, never a missing key;
- strangers' text only in `fromOthers`, listed in `foreignFields`;
- every field and its type pinned in `tests/box/bounty/SURFACE.txt` by `scripts/surface.mjs` (BT62: 510 field lines over 21 schemas).

Two things are missing, and the waves now briefed make them matter:

1. **No promise about what may be added.**
   - Readers are told when a document breaks, not what may grow under `@1`.
   - Waves add values: BT84 adds the stage `starting`, BT86 `ended`, and several waves add refusal names. BT87 and others add fields.
   - An agent that switches on `stage`, or on `refused`, and treats the list as fixed breaks silently.
   - Google's API guidelines treat an added field as compatible, but warn that new values in a response enum are the risky case, because "user code does not handle new values gracefully" ([AIP-180](https://aip.bybutter.com/180)). They ask each enum to say whether it is frozen or will grow ([AIP-126](https://google.aip.dev/126)). SDKs add an explicit unknown value for this ([Oracle's SDK](https://oracle-cloud-infrastructure-python-sdk.readthedocs.io/en/latest/forward-compatibility.html)).
2. **The surface check cannot tell compatible from breaking.**
   - `surface.mjs` reports any difference, and `--write` accepts it.
   - A removed field and an added one look the same to it, and SURFACE records a field's type but not the values a value-like field takes.

## Outcome

1. **The contract, written once in BOUNTY.md's `--json` section and linked from `describe --json`'s help:**
   - **Compatible, under the same `@1`:** new keys appear (read and ignore keys you do not know); an **open** field gains a value (read an unknown value as "something else", and go by the document's `next`).
   - **Breaking, needs `@2`:** a key removed or renamed; a type changed; a value added to a **closed** field; a field's meaning changed.
2. **Every value-like field is labelled open or closed, with its values,** in SURFACE.txt as new lines:
   ```
   values box-bounty/status@1 bounties[].stage open drafted|waiting|posted|answered|applied|rejected|withdrawn|undone
   ```
   - The lines are derived from the code's own types and constants by `tests/box/bounty/surface.ts`, never typed by hand.
   - The label comes from a short table in that file. Stages, refusal names (`refused`, `reason`), kinds and outcomes are **open**. A field whose values are a fixed fact of the world (`source`: `"solver"` or `"other account"`) is **closed**.
3. **`surface.mjs` sorts each difference into compatible or breaking:**
   - **Compatible:** an added field, an added value in an open field. Printed as such; `--write` accepts it.
   - **Breaking:** a removed or renamed field, a changed type, an added value in a closed field, a value removed from any field. `--write` refuses, naming the line and the rule, unless the same change moves that document's schema to `@2` in SURFACE.

   This lets an agent-facing break fail a wave the same way a test does.
4. **Each document carries its contract version** in BOUNTY.md: which fields are open, so an agent can read the list once.

## Scope

- Write: `tests/box/bounty/surface.ts` (the values lines, the open/closed table), `scripts/surface.mjs` (the classification), `tests/box/bounty/SURFACE.txt` (by `surface.mjs --write`: the new lines), `tests/box/bounty/bt62-record.test.ts` (the record's shape gains `values` lines), `docs/box-v4/BOUNTY.md` (the contract), `docs/box-v4/TESTING.md` (what the surface check now refuses), `tests/box/bounty/bt99.test.ts` (new)

- Do not touch: what any document contains; any schema's version (none changes in this wave)

## Traps

- **Do not label a field closed to be safe.** A closed field turns every later value into a `@2`, a cost to every reader. Closed is for values that cannot grow.
- **Refusal names grow with nearly every wave.** They are open by design, and the contract tells agents to go by `next`, never by matching a name they do not know.
- **Land it before the waves that add values** (BT84, BT86, and the refusal-adding waves), or each of those must label its own new value.

## Lenses

## Result — BT99

Run 26 November 2026 on the Windows host. Model Devin SWE-2.1 Max (`swe-2-1-max`).

**What changed.**
- `tests/box/bounty/surface.ts` now carries the `VALUE_FIELDS` table: which `--json` fields are value-like, which schema and surface path each belongs to, whether it is open, and where in the product source its values are read from. The table is the one place `open` or `closed` is asserted. The closed family is `foreignFields[].source` (`solver`, `other account`) only; every other value-like field is open. Some nested value fields are logically present although every currently observed array is empty, so their `values` line may stand without a `field` line; that is a record-shape rule, not a hidden schema version.
- `SURFACE.txt` now has `values <schema> <path> open|closed ...` lines. The record is 941 lines: 22 schema groups and 68 value fields (58 open value lines and the ten per-schema lines for the one closed family). Values are derived from product types, constants, unions, return objects, construction sites and refusal names through source inspection; none is copied into the record by hand. `valuesOf` refuses to write a value line for a field whose type or owner does not agree with the table.
- `scripts/surface.mjs` classifies every difference. Added fields, added schema text, and added values in open fields are compatible. Removed or renamed fields, changed types, added values in closed fields, removed values in any field, removed commands/refusals and other removals are breaking. A schema move from `@1` to `@2` marks that document's otherwise breaking differences `versioned`. `--write` refuses while any unversioned breaking difference remains.
- `bt62-record.test.ts` validates the new line shape, escaping, ownership, schema existence and open/closed spelling. `bt99.test.ts` covers the classifier on scratch copies only, including the `@2` exception.
- `docs/box-v4/BOUNTY.md` now states the reader contract and lists every open field by schema; `docs/box-v4/TESTING.md` records how the surface is checked; BACKLOG carries the narrower-values follow-up. No product output, document content or schema version changed.

**Tests first, then proofs.** `bt99.test.ts` was written before the classifier implementation. Master's `surface.mjs` rejects the test's `--classify` interface with exit 2 (`usage: node scripts/surface.mjs [--write]`), so the new behavior was red against master. On the real product, renaming `create.id` to `bountyId` made `surface.mjs --write` refuse with `breaking: removed field box-bounty/create@1 id string`; the product edit was restored. A temporary real stage value `bt99proof` was derived as compatible for the apply, close, find, post, status and take stage fields after a build and `--write`; both `record.ts` and `SURFACE.txt` were then restored byte-identically. The closed-field bite is covered in scratch: adding a third `foreignFields[].source` value is breaking and names the field, while the same kind of removal under `@2` is versioned.

**Local runs.**
- Focused BT99/record tests: 11 passed.
- Scoped bounty suite during implementation: 10 files, 121 passed, 1 skipped (an inner loop, not acceptance).
- Final `node scripts/surface.mjs` after rebuilding: matches the 941-line record.
- Acceptance evidence on `c8a19191`: the first `node scripts/verify.mjs test:box-bounty test:kitchen` ran check, build, lint and `test:box-bounty` green (134 files, 1595 passed, 4 skipped) but failed `test:kitchen` because k16's project-pinned Chromium was absent from this fresh worktree. After installing that browser, `node scripts/verify.mjs --only test:kitchen` passed all 33 kitchen files, 249 tests. The same commit's full hosted verify is green on all three systems.

**Hosted run.** `45708431377` on `c8a19191`: green on Linux, Windows and macOS: every select, audit, kitchen, platform, install-node22 and bounty shard job passed. The Result commit's push is expected to be kitchen-only under K76.

**Lens.** Yes. A parser written against `@1` that follows the contract survives BT84's `starting` and BT86's `ended` unchanged: the stage fields are open, added values are compatible, an unknown open value must not be an error, and `next` remains authoritative. The parser may not understand the new stage's meaning, but it does not need a code change merely to keep parsing and following the document.

## Reflect

- *What went wrong:* the restart left earlier progress unpushed and the first value table missed nested families (`post-preview`'s foreign-field source, board/payment state, first-sight state and refusal-name carriers). Deriving owner coverage from the written parts exposed those misses; the table was corrected before acceptance.
- *What went right:* proving the mechanism twice on real product code — one breaking rename and one compatible stage addition — showed both sides of the guard rather than trusting the scratch classifier.
- *What it becomes:* the backlog line for narrower per-context values remains deliberate. Refusal-name fields currently use the union of refusal names their call graph can construct; exact per-context narrowing would need more semantic information than the source table now carries. The missing pinned browser cost the first acceptance run; with nine minutes left I used the already completed bounty evidence plus the kitchen-only rerun rather than spend another 40 minutes duplicating what the green three-system hosted run had just executed.
