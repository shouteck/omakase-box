# PF37: the board can be restored, rolled back and watched

Milestone: PF (the platform) · Station: evidence · Base: `master at dispatch` · Branch: `wave/PF37` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-01-pay-on-merge, D-2026-11-03-stripe-v2-full-key
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md). The live board holds things that cannot be read back from GitHub: who signed in, their payment connections, saved-card and limit settings, recorded payments and confirmations. `packages/box-platform/DEPLOY.md` has no backup, no restore, no rollback, and no record of which migration files have run (each was applied by hand, "migration first"). Nothing watches the board: a reader that stopped, or a payment step that keeps failing, is found when someone notices.

## Outcome

1. **Restore:** a written, tried procedure that brings the database back to an earlier moment, and a copy the owner can keep outside Cloudflare.
2. **Roll back:** a written, tried procedure that puts the previous Worker version back, and says what to do when a migration went with it.
3. **Migrations recorded:** the database itself says which migration files ran and when; applying one twice changes nothing; the deploy guide's step reads that record.
4. **Watched:** a free, scheduled check outside Cloudflare that fails loudly when the board is down, when its reading is stale past a stated age, or when its error counts rise. A failure reaches the owner the way GitHub already notifies them of a failed run.

1. **Read and cite** (Done when, second bullet): Cloudflare's pages for D1 Time Travel (point-in-time restore: how far back on the free plan), `wrangler d1 export`, and Worker versions and rollback (`wrangler versions list`, `wrangler rollback`). Write the facts with their addresses into this file.

2. **Part 3 first, because it needs no account: migrations recorded.**
   - A new table, in `schema.sql` and in a new `migrations/pf37.sql`:

     ```sql
     CREATE TABLE IF NOT EXISTS migrations (name TEXT PRIMARY KEY, applied_at TEXT NOT NULL, note TEXT);
     ```

   - `pf37.sql` also records the earlier files, once: `INSERT OR IGNORE INTO migrations (name, applied_at, note) VALUES ('pf11.sql', <now>, 'recorded by pf37; applied earlier, real date unknown'), …` for all seven, then itself.
   - **Every migration must be safe to apply twice.** Read each existing file: a bare `ALTER TABLE … ADD COLUMN` fails the second time. Do not edit old files. Instead write a small script, `packages/box-platform/migrate.mjs`, that: reads `SELECT name FROM migrations`, and for each file in `migrations/` (sorted) not in that list prints the `wrangler d1 execute open-bounty-board --remote --file <file>` line to run, followed by the `INSERT` that records it. Default mode only prints; it changes nothing. From `pf37.sql` on, each new migration ends with its own `INSERT OR IGNORE INTO migrations`.
   - Tests (rows 1 to 3 below) run against the local database the test rig makes.

3. **Part 4, the watch: also no account.** A new `.github/workflows/watch.yml`:
   - `on: schedule` every 30 minutes, plus `workflow_dispatch`; `permissions: {}` (none); no secrets;
   - one job on `ubuntu-24.04` that runs a new script, `scripts/watch.mjs <board address>`, which fetches the front page (expects 200) and `/numbers.json` (expects 200, valid JSON, `stale` false, and `read_at` no older than the allowed age) and exits 1 with one plain sentence on any failure;
   - **the allowed age:** the board reads GitHub at most every 15 minutes and Cloudflare's cron can slip; start at 60 minutes and state the reason. GitHub emails the repository's owner when a scheduled workflow fails; that is the only notice.
   - Test the script locally: green against a local board; red against one whose clock was moved forward two hours (row 4).
   - It reads the address from a workflow variable with the public address as its default, so nothing personal is in the file.

4. **Parts 1 and 2 need throwaway Cloudflare resources.** Ask the owner one question before creating anything: may the wave create one D1 database and one Worker named `kitchen-PF37-…` on their account, used for an hour and deleted at close? Creating resources on the account is theirs to allow.
   - **If yes:** create them, load `schema.sql` and a few sample rows, then try, in order, writing each command and its output into this file: an export to a file under the scratchpad (never the repository); a change to the data; a point-in-time restore to before the change; a read that shows the change is gone. Then deploy a trivial Worker twice and roll back once. Delete both resources; list them as removed.
   - **If no:** try export and restore on the local database only (`wrangler d1 … --local`), write the remote procedure from the documentation, and mark it clearly "written, not tried".

5. **`DEPLOY.md`,** four new sections, each a numbered list of exact commands with what to expect after each: "Keeping a copy" (export, and where the owner keeps the file: outside the repository, outside any synced project folder, named with the date); "Restoring the database"; "Rolling back the Worker" (and the rule when a migration went with it: a migration that only adds a table or column is left in place; anything else, restore the database to the moment before); "Applying a migration" (run `migrate.mjs`, run the lines it prints, migration first, then deploy). The older "Updating a board deployed before …" sections stay as history under one heading.

6. **What the watch cannot see.** A table in the Result: a failing charge, a webhook that never arrives, a sign-in outage. For each, either a public count that would show it (for example "charges failed in the last day", a number with no personal data, proposed for a later wave) or "unseen".

7. **The fresh-session check** (the User experience lens): the owner starts one fresh session given only `DEPLOY.md`; it lists the restore and rollback steps in order. **Verify, merge;** applying `pf37.sql` to the live database is the owner's word, migration first, `exceededCpu` before and after.

## Traps

- An export holds people's GitHub ids and payment connection ids. Never print it, never `cat` it, never commit it, never upload it as a workflow artifact. Write it to the scratchpad and delete it at close; say so.
- Do not read `.env*`, `.runtime/` or `secrets/` to find account details. If a command needs an account id, the owner supplies it at the prompt.
- The dates recorded for the seven older migrations are this wave's, not the real ones. The `note` column says so; the guide says so.
- A cron that fires every 30 minutes on a public repository is free; GitHub disables scheduled workflows on a repository with no activity for 60 days. Say that in the guide.
- No existing test's expected outcome changes. A test that compares `schema.sql` with the migrations applied in order (search `tests/platform` for `migrations`) gains the new table on both sides.
