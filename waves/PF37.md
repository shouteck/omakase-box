# PF37: the board can be restored, rolled back and watched

Milestone: PF (the platform) · Station: evidence · Base: `master at dispatch` · Branch: `wave/PF37` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-01-pay-on-merge, D-2026-11-03-stripe-v2-full-key
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md). The live board holds things that cannot be read back from GitHub: who signed in, their payment connections, saved-card and limit settings, recorded payments and confirmations. `packages/box-platform/DEPLOY.md` has no backup, no restore, no rollback, and no record of which migration files have run (each was applied by hand, "migration first"). Nothing watches the board: a reader that stopped, or a payment step that keeps failing, is found when someone notices.

## Outcome

1. **Restore:** a written, tried procedure that brings the database back to an earlier moment, and a copy the owner can keep outside Cloudflare.
2. **Roll back:** a written, tried procedure that puts the previous Worker version back, and says what to do when a migration went with it.
3. **Migrations recorded:** the database itself says which migration files ran and when; applying one twice changes nothing; the deploy guide's step reads that record.
4. **Watched:** a free, scheduled check outside Cloudflare that fails loudly when the board is down, when its reading is stale past a stated age, or when its error counts rise. A failure reaches the owner the way GitHub already notifies them of a failed run.

## Scope

- Write: `packages/box-platform/DEPLOY.md`, `migrations/` (the record table and its first entry), `schema.sql`, `src/store.ts` or a small migration script, a new `.github/workflows/watch.yml`, `tests/platform/`
- Read for context: `src/refresh.ts` (the `stale` and `read_at` facts the feed already gives), `src/charge.ts`, `src/paypal-pay.ts`, `wrangler.toml`, [PF8](PF8.md), [PF18](PF18.md), [PF28](PF28.md)
- Do not touch: what any page or feed says; the live database, until the owner says to deploy

## Done when

- `node scripts/verify.mjs test:platform test:kitchen` exits 0 on the final commit.
- **Read first, cite in the Result:** Cloudflare's own pages on D1's point-in-time restore and export on the free plan (how far back, what it costs), and on Worker version rollback. The procedure is written from those, not from memory.
- **Tried, not only written.** Restore and export are run end to end on a throwaway D1 database named `kitchen-PF37-…` created for this wave and deleted at close, or on the local database if the free plan gives no second one; say which. Rollback is tried on a throwaway Worker of the same name pattern, or the Result says it was not tried and why.
- Migrations: a test applies every file to an empty database twice and reads the same schema and one record per file; a test fails when a file in `migrations/` is missing from the record after the guide's step. The live database's first record is written by a migration that only adds the table and marks the earlier files as run: say plainly that their dates are the wave's, not the real ones.
- The watch: it reads only public addresses (`/numbers.json` or `/bounties.json` for `read_at` and `stale`, the front page for 200). Shown red once against a local board made stale, and green against the live board. It sends nothing anywhere but GitHub's own failed-run notice. Its schedule and its allowed staleness are stated with the reason.
- What the watch cannot see is listed: a failing charge, a webhook that never arrives. For each, either a public fact is proposed that would show it (a count, no personal data), or it is named as unseen.
- An export never enters the repository or a log: it holds people's connections. The guide says where the owner keeps it.

## Lenses

- [x] **Security:** an export holds identifiers and payment connection ids. Check nothing in the procedure prints it, commits it or uploads it as a workflow artifact; the watch workflow has no secret and no write permission.
- [x] **User experience:** a fresh session given only `DEPLOY.md` and a stand-in account lists the restore and rollback steps in order without asking.
