# K27: where the tool's memory is stored: a real database, measured and compared

Milestone: K (kitchen) · Station: evidence (also packaging) · Base: master at dispatch, after K26 · Branch: `wave/K27` · Timebox: 240 minutes; at expiry the cook stops and reports what it has

**Brief.** Written by the CTO on 17 October 2026 at the owner's request: "we have to carefully solve the memory context problem because it's absolutely essential to the quality of our tool," and "can't we do a database? … we can find a database solution that doesn't cost anything at all for the initial scale-up phase." A design investigation: **it changes no product code and no test, creates no account anywhere, and signs in to nothing.** Its product is a storage design with measurements, a comparison of shared stores, a prototype in scratch, and the BT30 outline. Detailed for a cook without deep reasoning.

## Why

The tool's memory is plain JSON files today: one per bounty in `.box/bounties/`, read in full by most commands (`listRecords` in `packages/box-bounty/record.ts`), rewritten on many commands, written atomically by hand, searched by scanning (`find.ts`). K25 measured `status` at about 0.2 s with one record and about 1.7 s with 1,000, and K26 decides what is remembered and for whom (three tiers: anyone; the project's agents on any machine; this machine only). Two storage questions remain, and the owner wants both solved properly, with a real database considered:

1. **The store on each machine.** Files plus hand-made indexes would rebuild a database badly. Candidates: SQLite, an embedded database (one file, no server, transactions, indexes, built-in full-text search), shipped either through Node's own `node:sqlite` or through `sql.js` (SQLite compiled to WebAssembly).
2. **The shared store across machines** for the project-agents tier. Candidates: GitHub issues (already required: `gh` signed in), data on a hidden Git reference (the way Beads syncs its Dolt database through `refs/dolt/data`), and hosted databases with free tiers: Turso (hosted SQLite, libSQL), Neon and Supabase (Postgres), Cloudflare D1 (SQLite). A hosted store could make the project-agents tier **private** instead of public, which no public repository can.

## Outcome

A recommended storage design, backed by measurements on this machine and by current documentation, that keeps what an agent sees bounded (K25's three tiers: unasked constant, overview bounded, the rest on request), keeps the package a single file with no native dependency, works offline on one machine, and says exactly what a shared store would cost the owner, in money, setup and credentials, before anything is chosen.

## Constraints every option is held to

- **Package:** the npm artifact stays one bundled file with no native addon and no install script (BT12). Node 22 or later (BT12's floor).
- **The owner's rules:** owner setup stays `allow`, `deny`, `config` (a new setting goes in `config`); memory without demand; the tool offers, never enforces; only what the tool is needed for; host agnostic.
- **Hard stops:** never-ship files never leave; a private repository is never posted; nothing outside the owner's authority. A shared store is an outside destination: choosing one is the owner's decision (AGENTS.md: new remote destinations and paid services are the CEO's), so this wave recommends and never sets one up.
- **Credentials:** no agent ever handles a password or token. For each hosted option, the report states how the tool would get its credentials (for example the way `gh` keeps its own sign-in) and who sets them up.

## Method: six steps, in order, with a time budget each

**Step 1: the requirements (20 minutes).** Copy K26's requirements table into the report and add today's numbers from K25 (sizes, read times). Turn it into the list of operations a store must serve, with how often each runs: list open; bounded overview (open, plus count and five most recent ended); `find` by purpose; read one record; write at a milestone; the hook's start; the instruction-block sync. These are the benchmark's operations.

**Step 2: the local engine (60 minutes).** For each engine, check from current documentation and then by running in scratch:
- **`node:sqlite`:** which Node 22 and 24 versions provide it, behind a flag or not, and whether it prints an experimental warning (run it on this machine's Node 24 and say what it printed; read the Node 22 changelog for 22.x). Whether FTS5 full-text search is compiled in (try `CREATE VIRTUAL TABLE … USING fts5`).
- **`sql.js`:** the size it adds to the bundle (bundle a hello-world with the same `pack.mjs` approach in scratch and measure), whether FTS5 is available in its default build, how it persists (it is in memory; it must write the file itself), and how it behaves when two processes write.
- **Plain JSON files plus an index** (today, improved): a baseline, so the database is compared with the best version of the current approach, not the worst.
Benchmark each in scratch with synthetic records in the shape the tool writes (reuse `kitchen/memory/measure.mjs`'s generator) at N = 1,000, 10,000 and 100,000: time for every operation in step 1; file size on disk; time to open; behaviour when two processes write at once (two scripts writing different bounties, then the same bounty); recovery after a process is killed mid-write. Present one table per engine.

**Step 3: the shared store (60 minutes).** For each candidate, read its current documentation (cite the link and the date read) and fill one row: what is free and its limits (storage, requests, databases, whether it pauses when idle); what the owner must do once (accounts, projects, tokens) counted as steps; how the tool would get credentials without an agent handling them; offline behaviour; privacy (who can read the data); latency of one read from this machine if measurable without an account (otherwise "not measured, needs an account"); how it would sync with the local engine (for Turso, its "embedded replica" model, if the documentation describes it); lock-in and how to leave. Candidates: **GitHub issues** (with the machine-readable block the tool already writes; sub-issues and blocked-by for relations), **a hidden Git reference** (data pushed to a ref outside the branches; say whether GitHub shows or hides it and how fetch handles it), **Turso**, **Neon**, **Supabase**, **Cloudflare D1**. Add any other free option found that fits better, with the same row.

**Step 4: a prototype in scratch (40 minutes).** Build the recommended local engine behind one small storage interface in `kitchen/memory/storage/` (scratch code, not product): the operations from step 1, a schema with the shared and machine tiers in separate tables, full-text search for `find`, and one adapter for the recommended shared store that runs against the GitHub stand-in (or, for a hosted option, against a local stand-in of it; never a real account). Show: a second machine with an empty local store rebuilds the shared tiers from the shared store and answers `status` and `find` correctly; the local store can be deleted and rebuilt with only machine-local detail lost.

**Step 5: migration and growth over time (20 minutes).** How existing JSON records move into the new store once (including this repository's five tracked records), how old records are compacted (an ended bounty's machine detail reduced after a period, the way Beads compacts closed work), and what the store's size is after a year at a heavy but realistic rate (say 20 bounties a week).

**Step 6: recommendation and the BT30 outline (40 minutes).** Recommend one local engine and one shared store, and a fallback for each. State the owner's decision plainly if the recommendation is a hosted store (what account, what it costs now and at what scale it would start to cost, what the owner must do). Then the BT30 outline: the storage interface; the schema; the migration; how each command reads only what it needs; the K26 behaviour tests; the measurements BT30 must reproduce; and how the single-file package carries the engine.

- Local engine: recommendation and the numbers behind it: **`node:sqlite` (WAL + FTS5)** — writes 0.22–0.50 ms at N=1,000–100,000 (vs 480–944 ms for both alternatives at 100k), `find` ~1 ms via real FTS5, `integrity_check` ok after a mid-write kill, SQLITE_BUSY-serialised same-bounty concurrency, zero package bytes. Warts: one stderr ExperimentalWarning (Node 24.11.0, suppressible via NODE_NO_WARNINGS=1); Node 22.5–22.12 need `--experimental-sqlite` → fallback sql.js (default build lacks FTS5 — measured; whole-file persist loses concurrent writes — measured; ~+1 MB bundled).
- Shared store: recommendation, cost and the owner's setup steps: **committed shared file** (`shared.jsonl` in the repo) — $0, zero setup, offline, already-authorised public-in-a-public-repo. Hidden `refs/box-bounty/shared` variant if it should leave the working tree. **Turso** is the private fallback (embedded replicas fit the two-tier shape; free tier 5 GB/10M writes-mo; setup = account + database + token = 3 steps).
- The owner's decision needed: none if shared stays public (recommended). Only "is privacy worth an account + token" would reopen it — Turso then, $0 at this scale.
- BT30 outline: ready (interface, schema, migration, per-command reads, K26 behaviour tests, reproduction numbers, packaging note — all in the report).
- Resources removed: all `%TEMP%\kitchen-K27-*` scratch roots removed by each script's `finally`; leftover roots swept; the scratch sql.js/vite/npm prefixes lived only inside those roots.
- Reflect: sql.js needed two real-world corrections during measurement (no FTS5 in the default WASM build; wasm loaded via `locateFile`, not bundleable as one file) — measuring before judging caught both; making json-indexed's index atomic (matching the tool's own writer) was the fair baseline, and the non-atomic variant's `OPEN FAILED` on kill is retained as evidence.
