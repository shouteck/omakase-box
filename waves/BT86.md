# BT86: the solver hears how its attempt ended, and whether it still merges

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT86` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-03-solver-in-the-tool
Horizon: short. Feature playbook; principles: prove-it-works, subtract-before-you-add.

**Brief.** Written by the CTO on 23 November 2026 after the walkthrough of the solver's whole side (`describe`, `discover`, `take`, `submit`, `status`, `close`). The owner: the solver side matters because without solvers the poster side will not flourish ("sure").

**Why.** The solver's start is well served: `discover` shows each poster's record, how fast they decide and how many attempts are in progress, and `take` and `submit` are tight (BT84 and BT85 cover their gaps). The middle and the end are thin. All three gaps are in `attemptStatus` (`packages/box-bounty/attempt.ts`).

1. **The solver never learns why the attempt ended.**
   - A pull request closed without a merge reads "closed without a merge", with the next step "omakase-box close `<id>` withdraws it on record".
   - The poster's decision is written as a comment on the bounty's **issue**, not the pull request (`syncGitHubDecision`, `close.ts`, marker `<!-- box-bounty:<id>:<command> -->`): "Rejected. Recorded reason: …", "Withdrawn.", or which solution was merged.
   - `readAttempt` reads only the pull request, so the solver cannot tell another solver winning from a rejection, a withdrawal, or a pull request closed by hand.

   A solver who never hears why it lost cannot do better, and is less likely to try again.
2. **Ended attempts stay "taken" forever.** `takenOverview` reads the local record alone, and the record changes only on the solver's own `close`. Lost attempts pile up as "taken" or "submitted".
3. **The solver does not hear that its work no longer merges.** When the bounty branch moves after `take`, the pull request can conflict. The poster's `look` finds out by a trial merge (`dryMergeOnto`); the solver's `status` says nothing, although GitHub reports it in the same GraphQL read (`mergeable`).

## Outcome

1. **When the pull request is merged or closed, or the board says the bounty ended, `status <id>` adds one line saying how the bounty ended.** It reads the bounty's issue comments (one paged read) and counts only:
   - comments by the account that posted the bounty (the board's `poster`);
   - that carry this bounty's marker `<!-- box-bounty:<id>:` (the tool's own decision comments; nothing else is trusted to be a decision).

   It says, as facts:
   - **another solution was merged:** the comment's pull request number, and whether it is this one;
   - **rejected:** the recorded reason, shown in the existing foreign-text frame (`solverBlock('other account', …)`) as the poster's words, never as the tool's;
   - **withdrawn;**
   - **no decision comment found:** "the pull request was closed on GitHub; no decision by the poster is recorded on the issue".

   A bounty listed from the board on an existing issue (PF32, `way_in: listed`) has no tool decision comments. There it says "the issue was closed on `<day>`" and points to the board's page for whom the owner chose to pay.
2. **`status` records the ending locally.** A new stage `ended` is written when status sees the pull request merged or closed, so `takenOverview` says "ended". A later `close` on an `ended` attempt is "already ended; nothing to do". The `next:` for a closed attempt no longer tells the solver to run `close`.
3. **`status` on an open pull request says when it conflicts.** `readAttempt`'s query adds `mergeable`. When GitHub answers `CONFLICTING`, status says "GitHub says this conflicts with the bounty branch `<branch>`", with the next step: merge `<branch>` into your branch in the workspace and push. `UNKNOWN` (GitHub still computing) adds nothing.
4. **The issue number is kept at `take`.** `take` saves the issue number from the board's detail (`links.issue`) in the taken record. A record without one (taken before this wave) reads it from the board's detail at status time.

## Done when

- The hosted run on the final commit is green on Linux, Windows and macOS, quoted with its run id; the suites the change affects: `test:box-bounty`, `test:kitchen`.
- `bt86.test.ts`, against the stand-in world (`postedFixture`: the poster's side and a solver's `take` in one world, as `pf26.test.ts` does), each seen red on master first:
  - **Rejected:** the poster closes with a reason. The solver's `status` names the rejection and shows the reason inside the foreign-text frame, never outside it.
  - **Another solver won:** two takes; the poster applies the other one and closes. The loser's `status` says another solution was merged and names its pull request number.
  - **Withdrawn,** and **closed by hand** (the stand-in closes the pull request, with no decision comment): each named as above.
  - **A forged decision:** a comment with this bounty's marker by an account other than the poster is ignored. Status falls back to "no decision recorded".
  - **The ending is recorded:** after `status` on an ended attempt, `takenOverview` says "ended", with no GitHub call (the stand-in's call log).
  - **Conflict:** the stand-in answers `CONFLICTING`; status says so and names the merge step. `MERGEABLE` and `UNKNOWN` add nothing.
  - **An old record without an issue number:** status reads it from the board's detail and still names the ending.
- `node scripts/surface.mjs` shows no change, or the Result shows the diff (no new refusal or command expected).
- A break proof: drop the poster-account filter; the forged-decision test turns red.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master. Extend the stand-in: `mergeable` on the attempt's GraphQL answer (default `MERGEABLE`), settable per pull request.
2. **The issue number:** in `factsOf`, parse `links.issue` (`https://github.com/<repository>/issues/<n>`, checked against the bounty's repository) and save it on `Taken` as `issue`.
3. **The decision read:**
   - `readOnlyApi(root, 'repos/<repository>/issues/<n>/comments?per_page=100')`, paged as `close.ts` pages its comments;
   - keep only comments by the poster that carry `<!-- box-bounty:<id>:`;
   - take the last of them;
   - map the command (`close` with "Rejected", `close` with "Withdrawn", `merged`/`apply`) to the four facts.

   Only when the pull request is merged or closed, or the board's state is not open: no extra read on an open attempt.
4. **The stage:** add `'ended'` to `TakenStage` and `loadTaken`. `attemptStatus` saves it; `stageWords` names it; `closeTaken` answers it.
5. **The conflict:** add `mergeable` to `QUERY`; one line in `attemptStatus` when `CONFLICTING` and the pull request is open.
6. **Docs;** verify, push, hosted run, Result, merge.

## Traps

- **The reason is a stranger's text for the solver.** It is the poster's words: always inside the frame, and never quoted into a `next:` or any line the tool speaks as itself.
- **Trust only comments by the posting account.** Anyone can write the marker on a public issue. The poster's login comes from the board's detail, which `status` already reads (`readBountyFact`).
- **BT84 adds a `starting` stage in the same files.** Whichever lands second keeps both; the stage list is the one place to merge.
- **Keep the open-attempt status at its current number of reads.** The issue read runs only once the attempt or bounty has ended. The conflict field rides on the existing GraphQL read.
