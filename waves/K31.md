# K31: the tool in real use, measured against the roadmap's questions

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch, after BT32 · Branch: `wave/K31` · Timebox: 240 minutes of cooking, spread over a run of at least three separate sessions; at expiry the cook stops and reports what it has

**Brief.** Written by the CTO on 18 October 2026 from the roadmap's gap G9 ("nobody knows how often agents hand work off, or whether solvers answer") and the product rule "one real use before many". **It posts real, public, $0 bounties to the sandbox repository `shouteck/box-bounty-sandbox`, so it needs the owner's "go" in the dispatch card** (AGENTS.md: external messages are the owner's). It changes no product code. Detailed for a cook without deep reasoning.

## Why

Everything about the tool has been tested with stand-ins, scratch repositories and staged experiments. The roadmap's priorities rest on things only real use shows: whether an agent doing real work chooses to hand off; whether the output tells it what to do at each stage; how long each stage takes on real GitHub; whether a later agent on another machine picks up the memory; and what breaks. The sandbox exists for exactly this (K15: real GitHub journeys never run against `shouteck/omakase-box`).

## Outcome

A report of the whole loop run for real several times, with every stage's actor questions answered from transcripts and timings, every point where an agent hesitated or was misled, and a short list of fixes that real use shows are needed: nothing speculative.

## Scope and limits

- Real GitHub: **only** `shouteck/box-bounty-sandbox`, public, reward $0. Nothing posted anywhere else. No payment of any kind.
- The owner's part: the owner's "go" for this run, given once in the dispatch card. Within the run the head chef plays the owner through a scratch settings folder (`BOX_BOUNTY_SETTINGS_DIR`), allowing only the sandbox repository; the owner's real settings are never touched.
- Write: `waves/K31.md` (the Result), `kitchen/reviews/K31-real-use.md` (the report), `kitchen/memory/real-use/` (scripts, transcripts, timings). Scratch clones outside the checkout.
- Do not touch: product code, tests, the owner's settings, any repository but the sandbox.

## Setup (20 minutes)

1. Build the package (`node scripts/workspace.mjs build`, `node packages/box-cli/pack.mjs`) and install it into a scratch prefix (`npm i -g --prefix <scratch> <tgz>`), as a newcomer would; the agents use only that `box`.
2. Two clean clones of the sandbox in separate scratch folders: **machine A** and **machine B** (B starts with an empty local store).
3. Prepare **five genuine small tasks** in the sandbox's code, each one a real improvement an agent could plausibly hand off (a failing test to fix, a small feature, a documentation fix, a refactor with a constraint, one deliberately unclear task). Write them down before any agent starts.

## The runs

Fresh agents only; the cook prepares worlds and prompts and is not an agent. The head chef starts each agent.

1. **Posting agent (machine A), per task:** told only "work on this task in this project; the tools here include `box bounty`; use them if they help." Record: did it hand off, at which point, with what why; every command run; every hesitation.
2. **Solver agents:** for each posted bounty, a fresh agent with only the issue's URL, told "solve this bounty." (The kitchen is the solver; no outside solver is recruited: finding solvers is outside the MVP.) One task gets two solvers, so review has a choice.
3. **The posting agent again (machine A), in a later session:** told "continue your work in this project." Record whether it noticed the solutions, how it reviewed, what it merged or closed, and whether it understood the payment message.
4. **A later agent (machine B):** told "continue the work in this project." Record whether it found the bounties, their reasons, what was tried, the outcomes and the unfinished larger job from the shared memory alone.
5. **The age and paid questions:** at the end, ask the posting agent: "which bounties are still waiting, and was anyone owed payment?" Record the answers (BT35 and BT36 may or may not have landed; say which).

## Measured

- Per stage: wall time on real GitHub (create, post, the solver's pull request appearing, review, merge, close); GitHub API calls per command (count `gh` starts).
- Per actor question in PLAN.md's roadmap: answered right, partly or wrong, quoting the transcript.
- `kitchen/memory/measure.mjs`-style sizes on the real history (what each agent saw unasked and in the overview).
- Every error, refusal and confusing line, verbatim, with the command.

## Done when

- `node scripts/verify.mjs test:kitchen` exits 0 on the final commit.
- At least four of the five tasks went through the full loop (posted, at least one solution, merged or closed), or the Result says exactly where and why not.
- Every finding is backed by a quoted transcript line or a measured number.
- After the run: every sandbox bounty is closed by the tool, every bounty branch removed, the scratch prefix and clones deleted; the sandbox's open issues count is back to what it was before (state both numbers).
