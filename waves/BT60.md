# BT60: every bounty pays: none is posted or listed at $0

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT60` · Timebox: 300 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-no-zero-bounties, D-2026-11-10-k48-answers, D-2026-11-02-install-is-the-human-step
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from the owner's decision in talk: "we shouldn't allow anyone to create a bounty that is $0. There should be a fixed amount that we allow. And right now, we just keep it as greater than $0. But for now, as we are testing the product, we just allow $0. But as we go into live, we don't allow any $0 to be posted."

Why it matters: a $0 bounty is what an earning agent's first `discover` returns today, and our own advice tells it to decline. A board of unpaid work teaches every visitor to leave. This changes two standing lines, "$0 unless they said otherwise" (PLAN, money per repository) and "beyond the three hard stops the tool enforces nothing" (AGENTS.md).

## Outcome

1. **One minimum reward,** a single constant in whole US dollars, set to 1, read by the tool and the board. Raising it later is one line.
2. **The tool does not post below it.** `post` on a repository whose reward is under the minimum is a named refusal that changes nothing and names the one step that fixes it. A draft can still be made.
3. **The board does not list below it,** on any surface: the board, a bounty's page, the feed, MCP, RSS and the numbers. A bounty some other tool or an old release posted at $0 is simply not there. The listing door already asks for at least $1.
4. **Testing still works.** The kitchen's sandbox bounties must stay at $0, because with one account a stated reward would be a promise nobody means (PF9a's seat 2 stopped on exactly that). The plan chooses the allowance and states it in `help`; see Notes.

## Plan

Started 12 November 2026 at 17:25 UTC (timebox 300 minutes, so stop at 22:25). The brief's choices stand as written (constant in `format.ts`; `allow` records the permission and says a reward is needed; nothing rewritten for a repository already allowed at $0; a stored row stays until the board reads it below the minimum; the testing allowance is `BOX_BOUNTY_ALLOW_ZERO_FOR_TESTING=1` in the tool, read in one function, and `ALLOW_ZERO_FOR_TESTING` on the board, set only by the test board). Differences found by reading the code:

1. **The refusal's next step is `omakase-box allow --reward <whole dollars> --reward-limit <whole dollars>`**, not two `config set` lines. A `config set reward` is itself refused until the repository is on the owner's list and has a limit; `allow` takes both in the same breath and works whether or not the repository is listed, so one line serves every state. No amount is named.
2. **`post --preview` did not pass through `rewardForPost`** (it calls `approveGitHub`, which reads GitHub first), so the check is also called at the head of `previewGitHub`, before any GitHub read.
3. **A hand-edited settings file with -1 or 0.5 is refused as `settings-malformed`**, not `reward-amount-invalid`: that name belongs to `config set`; a malformed file has always been refused by the loader. Tested as that; nothing changed in the loader.
4. **The board has two write paths**, not one: `storeIssue` (a hint's look and a re-read) and the search loop's own batch. The gate is one function, `rewardTooLow`, called in both, and each removes a stored row for that id.
5. **What the plan had to settle.** *`allow` with no reward:* records the permission as today and says, in the owner's lines, `no reward is set on <repo>: a bounty is not posted without one`, then the two `config set` lines in the order they work (limit first). *A repository already allowed at $0:* nothing rewritten; its next `post` gets the refusal; `config`, the overview and `status` say no reward is set. *A $0 bounty a solver already took:* `status`, `submit` and `take` keep working and say what they say; `discover` no longer returns one because the board no longer lists it. *A listed row whose reward was valid when listed:* stays until the board re-reads it below the minimum.
