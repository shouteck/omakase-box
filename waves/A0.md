# A0: prototype the neutral core before building it

Milestone: A · Station: packaging (also evidence) · Base: `3db87b3` · Branch: `wave/A0` · Timebox: 75 minutes; at expiry, report partial findings and stop

## Outcome

A tested answer, on three small throwaway projects, to one question: can a Box be prepared, set up, checked and solved when the core knows only files, commands, exit codes and patches? And specifically: can a cut-down slice of a multi-package repository be installed without the core knowing the package manager? The deliverable is a result page that tells the head chef whether milestone A's plan (A1 to A4 in `PLAN.md`) stands, or what must change.

This is a prototype wave. The code is throwaway. Only the findings are kept.

## Scope

- Write: `research/box-delegation/a0/**` and the Result section of this file. Nothing else.
- Read: `packages/box-package/**` to understand what the product does today; `PLAN.md` milestone A; `kitchen/stations/packaging.md` and `kitchen/stations/evidence.md`.

## What to build

1. **Three fixture projects**, each a few files, under `research/box-delegation/a0/fixtures/`:
   - `npm-single`: one JavaScript package managed by npm, with a `package-lock.json`, tests on Node's built-in test runner.
   - `multi-package`: one repository with at least three packages (`a` depends on `b`; `c` is unrelated to both), in two variants of the same content: managed by npm workspaces, and managed by pnpm workspaces. Lockfiles committed.
   - `python-plain`: a small Python package with `unittest` tests and no JavaScript.
   Each fixture has a guard test (passes on the untouched code) and one request with an outcome check that fails on the untouched code and passes after a small known-good edit. Keep the known-good edit as a patch file beside the fixture.
2. **One throwaway script**, `research/box-delegation/a0/neutral-box.mjs`, that does the neutral loop from a small declaration file and knows nothing about any language or package manager:
   - copies the declared files into a new empty folder **outside this checkout** (system temp, named `kitchen-A0-...`);
   - runs the declared setup commands there, then every declared check, on the untouched files, recording program, arguments, exit code and duration for each;
   - applies a candidate edit (the known-good patch, or nothing), reruns the checks, and reports whether guards stayed green and the outcome check went from red to green;
   - spawns from an argument array, never through a shell.
3. **Trials.** For each fixture, write the declaration an owner would have to write and run the loop twice: with the known-good edit, and with no edit. For `multi-package`, the request is in package `a`. Try these candidates for what the slice must contain, on both the npm and the pnpm variant, and record exactly what happens for each:
   - (i) only the files of `a` that the change needs, plus the root dependency files unchanged;
   - (ii) as (i), plus `b`, because `a` uses it;
   - (iii) as (ii), plus the small package description file of `c` but none of its source;
   - (iv) anything else you find that works with less.
   If a candidate needs the core to know which package manager is in use, say exactly what knowledge it needs and where.
