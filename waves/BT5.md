# BT5: the kitchen uses it

Milestone: BT · Station: packaging · Base: `b0d2764` · Branch: `wave/BT5` · Timebox: 120 minutes; at expiry, report partial findings and stop

## Outcome

Prove the tool by using it, honestly — three parts, per PLAN.md:

1. **The journey.** A person asks for a bounty on this repository's own work; a solver that has never seen the repository answers; a different session collects it from the record.
2. **Judgement.** One or two scenarios from `kitchen/scenarios/bt4.md` run in full — real agents in a real fixture, climbing description-only → rules note → reminder, stopping at the first rung where the agent chooses sensibly.
3. **Open.** The tool stays installed in this repository — `.box/limits.json` and the marked block in `AGENTS.md` — nobody mentions it in future waves, and the recorded `why` lines are read afterwards. (Observation continues past this wave; the wave ships the installation.)

**The bounty task for part 1** is the recorded BT4 nit: `.box/limits.json` with `allowedDestinations: []` makes `describe` print `where post --to may deliver: only inside ` (dangling) and the `destination-not-allowed` refusal print `()`. Real, recorded, self-contained.

## How the wave runs

This wave is an experiment, not a feature: the cook builds the scaffolding and the install; the head chef runs the journey and the judgement rungs (workers cannot dispatch); the pass reviews all of it — code, evidence and honesty.

**The cook** (`wave/BT5`):
- `kitchen/bt5/TASK.md` — the task text for the nit fix, written for a solver who has never seen this repository.
- `kitchen/bt5/check.mjs` — the mechanical check: spins a scratch git repo with `{"allowedDestinations":[]}`, runs the built CLI's `describe`, asserts the line is not dangling and the refusal names no empty parens. **Must fail on the current code.**
- `kitchen/bt5/fixtures.mjs` (or scripts) — builds the two part-2 fixture repos under a scratch dir: (a) a plainly-doable task (rename-style, one-command check); (b) a task whose check requires a program absent on this host — verify the absence by running it (`php`, `lua`, `Rscript` — pick one proven absent), never by assumption.
- `kitchen/bt5/PROTOCOL.md` — the run protocol: how the clone is made, who plays each role, what counts as a sensible choice at each rung (from the pack's rubric), where transcripts go.
- `.box/limits.json` — the real install, honest posture: `reminders: "off"`, `rulesFile: "AGENTS.md"`, cost/expectedAnswer telling the truth (`posts reach local folders only until BT6`, `no live solvers yet`). No `allowedDestinations` — any local folder is allowed today.
- The marked block in `AGENTS.md`, generated by running `describe --rules` — pasted verbatim, markers included.
- Verify: `node scripts/verify.mjs test:box-bounty` exits 0 on the final commit.

**The head chef** (after the cook commits):
- Part 1: `git clone` this repo (wave branch checked out) to a wave-named scratch dir → `create` the bounty in the clone → `confirm` → `post --to` a wave-named folder → dispatch `box-recipient` on the folder only → collect via a *different* fresh session on the clone (`answer`, facts, its own decision). Record everything in this file's Result + `kitchen/bt5/evidence/` (the clone's record JSON, the answer report, transcripts summary).
- Part 2: build the fixtures, run the rungs with fresh agents — one per rung, climbing only until the first sensible choice.
- If the solver's fix is good: its diff comes into the wave branch (the pass reviews it like any code — the journey then produces real product value, not only proof). If bad or absent, the nit stays recorded in STATUS.

**The pass** reviews the scaffolding code, the evidence trail (was the solver really blind — folder only? did the collector decide on the facts? did the check fail before and pass after, in the clone?), and the honesty of the run records.

## Scope

- Write: `kitchen/bt5/**`, `.box/limits.json`, `AGENTS.md` (the marked block only — nothing else in the file), `waves/BT5.md`, `kitchen/scenarios/bt4.md` (notes only if a scenario proved flawed), plus the solver's diff if adopted.
- Do not touch: product code beyond an adopted solver diff (this wave changes no product behaviour), never-ship table, snapshot/merge machinery, `.execution/`, `docs/legacy/`.

- **Part 2:** at least one scenario run in full with the rung ladder — each rung's agent, exposure and choice recorded with its reasoning; "nobody used it" or "needed the reminder rung" are both honest outcomes, recorded as found.
- **Part 3:** `.box/limits.json` and the AGENTS.md marked block ship in the merge; the Result says what future waves' `why` lines will measure.
- The check script demonstrably fails pre-fix and (if adopted) passes post-fix — in the clone, not just claimed.
- Cases that must fail: the check refuses to pass on un-fixed code; the fixture's "absent toolchain" claim is proven by execution; the collector session can name what it did NOT see (no conversation context, no solver transcript).

## Review lenses

- [x] **Security:** the solver must never see this repository — folder only; never-ship must hold inside the bounty (the clone has real `.box/`, `.boxignore`, kitchen files); the limits file read on the real repo must not break any existing command.
- [x] **User experience:** two real cold reads — the solver reads the listing; the collector arrives with nothing but the project. Both are evidence, reported honestly including confusion.
- [x] **Measurement fairness:** the whole wave is a measurement — the pass checks the evidence is real (transcripts, record JSON, actual command output), the scoring honest, and that a favourable result was not engineered.

## Notes

- If the solver produces nothing usable, record it and stop — a failed journey is a finding, not a reason to fudge.
