# C1: record what a failing test ran

Milestone: C · Station: packaging (also evidence) · Base: master at the commit that adds this file · Branch: `wave/C1` · Timebox: 90 minutes; at expiry, report partial findings and stop

## Outcome

A person or an agent runs one command in front of a failing test and gets a trace: a file listing every function in the repository that the test ran, each identified exactly, in the order first called, made in seconds, with the test behaving exactly as it would have without the command.

```
box trace --out <dir> -- <the test command, as it would normally be typed>
```

Python is the first language. This wave selects nothing, packages nothing and sends nothing. The next wave (C2) reads this trace to choose a Box's files automatically. Read "The product" and "Milestone C" in `PLAN.md` first.

## Done when

- `node scripts/verify.mjs` exits 0 on the final commit, with the new suite included in what it runs. Name the new suite in the Result so the pass runs it.
- **The trace is right, against a known answer.** `examples/c1-py-trace` is a small Python project with no outside dependencies (standard-library `unittest`), written for this wave, with one failing test whose executed functions are known by construction. A test asserts the trace lists exactly those and no others. The fixture must contain, and the test must cover, each of these:
  - a function the failing test runs and one it does not;
  - **a property with a getter and a setter of the same name, where only the getter runs: the setter must not be listed.** The lab's first instrument got this wrong by identifying functions by name. Identify a function by its file and the line its definition starts on; the name is a label.
  - a method, a nested function, a lambda and a decorated function (say in the doc page how each is credited);
  - a function that runs only in a child Python process the test starts: it must be listed, and the trace must say how many processes it saw. The lab lost five public tasks to untraced child processes.
  - code at module level: every file whose module-level code ran is listed as a file, since C2 will need every file the test loaded, not only those with a called function.
- **The test is not disturbed.** The traced run has the same exit code as the plain run, and the command's own output still reaches the terminal as it is produced, not after the run ends. A test asserts both, on the failing test and on a passing one.
- **A case that must fail:** a deliberately wrong expected list makes the suite fail. Show it, then remove it.
- **It refuses clearly** when the command starts no Python process, when `--out` cannot be written, and when the program is not found: a named reason and a non-zero exit of its own that cannot be mistaken for the test's.
- **It is fast, and says how fast.** The trace file records seconds for the traced run. On the fixture the test asserts a generous ceiling, not a tight one; the wave file records plain against traced time measured three times each. Use call events, not line events: the lab's line tracing of whole test files hit five-minute timeouts.
- **The file it writes is documented and stable:** schema version; the command and working directory; the command's exit code; the commit if the folder is a Git checkout; the interpreter version; every repository file that was loaded; each function as path relative to the repository root, start line, end line, label and order first called; and a plain list of what it could not see (for example compiled extensions).
- **Only the repository's own files are listed.** Nothing from the standard library or installed packages. Test files are listed and marked as tests by a stated rule.
- It works on this Windows host from Git Bash and from PowerShell.
