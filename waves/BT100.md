# BT100 (prototype): one event log, an outbox, and a reconcile step through the one door

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT100` (the record only; each attempt on its own throwaway branch) · Timebox: 360 minutes (two attempts and a comparison; no hosted acceptance run for throwaway code); at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-one-fact-one-owner
Horizon: long: a design with no precedent here (KITCHEN.md, "Design decisions with no precedent"); starts with `/plan`. Prototype playbook; principles: redesign-from-first-principles, boundary-discipline, exhaust-the-design-space, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026, after the walkthrough of the whole codebase, when the owner asked for architectural changes with the whole picture in view ("yes"). It is placed **before [BT83](BT83.md) and [BT96](BT96.md)**, the two waves its result would reshape.

**Why.** Seen whole, many of the walkthrough's findings come from two things.

1. **A bounty is kept in two models.**
   - The shared memory (`chain.ts`) is an append-only event log, git-bug's design: facts are added and the state is folded from them.
   - The local store (`store.ts`, `record.ts`) is one mutable document per bounty, rewritten whole by about a dozen paths through `persistRecord`.

   The mismatch is behind:
   - lost updates ([BT96](BT96.md));
   - no change history ([BT88](BT88.md));
   - special reconciling code (`settleFromChain`, adoption; [BT86](BT86.md), [BT75](BT75.md));
   - the retired-shape conversions in `asRecord`.
2. **Reads cause outward effects.** `status`, `look` and the hook at every prompt can close a bounty on GitHub, push chain events and print pay messages, as side effects of reading (`merged.ts`, `refreshSharedMemory`). That is disclosed, but it widens the races and makes "what can leave during X" hard to answer (BT82's check 7).
3. **Retry safety is hand-built per exit:** comment markers, `recoverIssue`, `chain_pending`, [BT84](BT84.md)'s `starting`. It is the same "each place guards itself" pattern BT82 found for the safety checks.

**Three established patterns, combined:**
- **Event sourcing** ([Fowler](https://martinfowler.com/eaaDev/EventSourcing.html)): every change is an appended event; the state is derived by folding the events.
- **The transactional outbox** ([microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)): an event that owes something outward records the debt in the same transaction, and a relay sends it until acknowledged.
- **Reconciliation** (Kubernetes controllers, [controller pattern](https://kubernetes.io/docs/concepts/architecture/controller/)): observe, record, then act toward the desired state.

## The two attempts

Both use `post`'s issue creation and `close`'s decision comments (BT82's pair), each on its own throwaway branch, `proto/BT100-a` and `proto/BT100-b`.

- **A: today's model, hardened.** The document store with BT96's compare-and-swap, BT82's winning door (plan first, a branded grant), and retries as today. This is the baseline the real alternative must beat.
- **B: event log plus outbox plus reconcile.**
  - The local store keeps an append-only `events` table per bounty, folded into the state the commands read.
  - An event that owes an outward effect writes an `outbox` row in the same transaction.
  - One `reconcile(root)` step sends what is owed through the door and marks each row done on acknowledgement. Commands call it at their end, and say what it sent.
  - Read-only commands (`look`, `status`) only append observed facts, such as a merge landed. They send nothing themselves.

### Attempt A: `proto/BT100-a` (today's model, hardened)

- `store.ts`: schema 5 adds `rev INTEGER`; a `WeakMap<record, rev>` carries it out of band; `writeStored` does `UPDATE … WHERE id=? AND rev=?` inside `BEGIN IMMEDIATE`, and a mismatch refuses `record-changed` (BT96's design).
- `outbound.ts` (BT82's winning door, rebuilt only for the two actions): `Effect = createIssue | comment`; a branded `Granted` made by `grantPost` and `grantCloseUp` from settings; `runEffects(granted, effects)` checks, then sends. `post` and `syncGitHubDecision` plan their effects first. The markers and `recoverIssue` stay.
- Reads stay as today: check 3 is measured as it is (expected to fail; recorded as a fact).

### Attempt B: `proto/BT100-b` (event log + outbox + reconcile)

- `store.ts`: new tables `events(bounty_id, seq, at, kind, json, PRIMARY KEY(bounty_id, seq))` and `outbox(key PRIMARY KEY, bounty_id, event_seq, kind, state, result, done_at)`. One `appendEvents(root, id, events, owes)` runs inside `BEGIN IMMEDIATE`: insert the events, insert the outbox rows they owe, then fold and write the `records` row as a cache of the fold. Nobody writes a document any more on these paths.
- The fold: today's `BountyRecord` from the creation document plus events, by one reducer, `foldLocal(base, events)`, in the same shape `foldEvents` (chain.ts) uses for shared events.
- `reconcile(root)`: reads pending outbox rows; rebuilds each effect's payload from the folded state and the row's `event_seq`, never from text stored on the row; runs it through the same door as A (`Granted` re-derived from the settings at send time, never-ship and the scan); on acknowledgement appends an observed event (`issue-created`, `comment-posted`) and marks the row done in one transaction. Its key is the effect's marker, so a rerun skips what is done.
- `post` appends `post-planned` (owes `issue:<id>`), then calls `reconcile`. `close` appends `closed` (owes `comment:<id>:<command>`), then calls `reconcile`.
- Reads: `noticeMergedSolutions` appends `merge-observed` (owes the decision comments) and does not call `syncGitHubDecision`; `look` and `status` never call `reconcile`. Mutating commands call it at their end and print what it sent.
- The chain format does not change (trap): the local events are a superset, and the shared events are produced as today.
