# BT15: folder delivery is retired, and `create` asks for less

Milestone: BT · Station: packaging · Base: master at dispatch · Branch: `wave/BT15` · Timebox: 150 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 14 October 2026. **The owner decided both parts in conversation that day (the folder: "I agree B"; the options: "yes add those four changes"), so the removals are approved;** the pre-cook card still shows exactly what goes, and the head chef checks names against master at dispatch.

## Why

Every `create` writes a package folder beside the project (`bounties/<slug>/` with `bounty.json`, `README.md` and a full copy of the shipped files in `repo/`). It is a leftover of the tool's first design. Since BT6a the main flow never reads it: posting publishes the project's own commits to a bounty branch and opens an issue; solutions are collected from pull requests. The folder is used only by folder delivery (`post --to <dir>`), by solutions handed back as folders (`look --from <dir>`, `apply --from <dir>`), and by GitHub bounties posted before BT6a, which exist only in the kitchen's early tests.

Folder delivery was kept as the route for private repositories, which the plan otherwise excludes ("public repositories only"; "Not in this plan: … private repositories"), with nobody described as receiving such a folder. It leaves folders on the owner's disk, adds options every agent reads in `help`, and keeps a second delivery path alive in the code and the tests. The owner's rule: only what the tool is needed for.

## And `create` asks for less

`create` takes nine inputs, two of them required. Agents read `help` more than any other output (K18: about 3,400 characters, read in five of seven runs), and three of the optional inputs duplicate something else:

- `--note <file>` is a second public file beside the task, for what the agent tried.
- `--job <file>` and `--resume` are both private context for whoever picks the work up.
- `--preview` shows the plan without a draft, but a draft is already private and can be discarded, and `post --preview` shows what would go public, which is the preview that matters.

After this wave `create` takes `--task` and `--why`, and optionally `--title` and `--resume`, plus the `--repo` every command takes. `--title` stays because `gh issue create` has it (owner, 14 October 2026: follow the convention), and `--task -` reads the task from standard input as `gh`'s `--body-file -` does, so an agent need leave no task file behind.

## Outcome

A bounty is drafted locally and lives on GitHub. `create` writes nothing beside the project and asks for five things at most, two of them required. There is one delivery path, one way to collect a solution, and much less to read. Private repositories are refused, as the hard stop already says, with no other route.

**What goes**

- `create` writes no folder. `--out` is removed.
- `post --to <dir>` is removed. `post <id>` posts to GitHub. `--to github` keeps working without comment, so the instructions and transcripts already written stay true; it is no longer shown in help or output.
- `look --from <dir>` and `apply --from <dir>` are removed. A solution comes from a pull request.
- Each removed spelling, typed, is a named refusal (`folder-delivery-retired` or the name that fits) that changes nothing and says what to do: post to GitHub; a private repository cannot be handed off with this tool.
- Code that only served folders is deleted, not left behind a flag: building the package, the `repo/` copy, binding a returned folder to its manifest, the folder post's `posted` path. Tests of folder behaviour are removed with it. **Tests of a guarantee move to the GitHub path** where that guarantee still applies (never-ship on what is published, nothing a solver wrote is run, a hostile path refused); the Result lists each one and where it went. No expected outcome of a surviving guarantee changes.

**What stays and what it says**

- `create` still takes the photograph, applies never-ship, previews the secret scan, and writes the record and its bookmark. Its preview now describes **what posting would publish** (the commit the bounty names, commits not yet pushed, and uncommitted changes only if the agent asks), the same plan `post --preview` shows, and not a file count of a copy. Where never-ship removes something that would otherwise be published, it says so.
- **`create` still drafts when GitHub cannot be reached.** Working out what posting would publish needs GitHub (which commits it already has). With the GitHub command line missing, not signed in, or GitHub unreachable, `create` still writes the draft; its preview says in one line that the publication plan could not be worked out, names the reason as the refusal would (for example `github-not-signed-in`), and says that `post` works it out and shows it before anything goes public. A test covers each of the three. `create` needs Git only, as the required-programs rule says (a command checks only for what it needs).
- The issue a solver reads is unchanged.
- `help`, `describe`, the record's next steps and `docs/box-v4/BOUNTY.md` say nothing about folders. The doc page says once, plainly, that the tool is for public repositories on GitHub and has no other route.

**`create`'s inputs**

- Kept: `--task <file>` (required; the help calls it a file describing what needs doing, written for the solver, and says the project's code is included automatically), `--why "<one line>"` (required; private), `--title "<text>"` (optional; without it the title is the task's first sentence, by the rule BT14 set, and the same shortening rule applies to a given title), `--resume "<text>"` (optional; private), `--repo <path>`.
- **`--task -` reads the task from standard input**, after `gh issue create --body-file -` and `git commit -F -`. The preview names it as "standard input" where it would name a file. The same never-ship and emptiness checks apply to what is read. `help` shows both forms in one line.
- `--note` is removed. What the agent tried goes in the task file; `help` says so in one line. The facts the tool adds about what changed are kept and keep appearing in the issue.
- `--job` is merged into `--resume`: `--resume` carries what the agent was in the middle of and the larger work waiting on it, and accepts enough text for both (the Result states the limit). The automatic context (branch, commit, changed files) is unchanged.
- `--preview` is removed from `create`. `post --preview` stays.
- Each removed option, typed, is a named refusal that changes nothing and says what replaced it, in one line. None is kept as an alias.
- Records that carry a note file, a job file or a separate title load and show them as before.

**Records and folders from before**

- Records written before this wave load. One that was drafted with a folder and never posted posts to GitHub as any draft does. One posted to a folder, or posted to GitHub before BT6a, can still be read with `status` and ended with `close`; anything that would need its folder refuses by name and names `close`.
- Folders already beside an owner's projects are left alone. The doc page says they are no longer used and may be deleted by hand.

**Measured:** the characters of `help` and of `create`'s output, before and after; the number of inputs `create` and `post` take.

**Cases that must fail, each a named refusal that changes nothing:** `create --out`; `create --note`; `--task -` with nothing on standard input; `create --job`; `create --preview`; `post --to <any folder>`; `look --from`; `apply --from`; posting a private repository (unchanged, now with no mention of a folder).
