# BT15: folder delivery is retired; a bounty lives on GitHub only

Milestone: BT · Station: packaging · Base: master at dispatch · Branch: `wave/BT15` · Timebox: 150 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 14 October 2026. **The owner decided it in conversation that day ("I agree B"), so the removal is approved;** the pre-cook card still shows exactly what goes, and the head chef checks names against master at dispatch.

## Why

Every `create` writes a package folder beside the project (`bounties/<slug>/` with `bounty.json`, `README.md` and a full copy of the shipped files in `repo/`). It is a leftover of the tool's first design. Since BT6a the main flow never reads it: posting publishes the project's own commits to a bounty branch and opens an issue; solutions are collected from pull requests. The folder is used only by folder delivery (`post --to <dir>`), by solutions handed back as folders (`look --from <dir>`, `apply --from <dir>`), and by GitHub bounties posted before BT6a, which exist only in the kitchen's early tests.

Folder delivery was kept as the route for private repositories, which the plan otherwise excludes ("public repositories only"; "Not in this plan: … private repositories"), with nobody described as receiving such a folder. It leaves folders on the owner's disk, adds options every agent reads in `help`, and keeps a second delivery path alive in the code and the tests. The owner's rule: only what the tool is needed for.

## Outcome

A bounty is drafted locally and lives on GitHub. `create` writes nothing beside the project. There is one delivery path, one way to collect a solution, and fewer options to read. Private repositories are refused, as the hard stop already says, with no other route.

- Read for context: the Results of `waves/BT6a.md` (how a GitHub post publishes), `waves/BT2.md` and `waves/BT3.md` (how folder posts and folder answers came in), `waves/BT14.md` (what `create` now prints); PLAN.md; `kitchen/stations/packaging.md`.

## Done when

- `node scripts/verify.mjs test:box-bounty test:box-package` exits 0 on the final commit; the suites reach no network. The K14 start budgets are re-measured and stated.

**First, the map.** Before changing anything the cook lists in the Result every place that writes, reads or names the package folder, `--out`, `post --to <dir>` and `--from <dir>`, in code, tests, fixtures, the demo and the docs, and what each becomes.

**What goes**

- `create` writes no folder. `--out` is removed.
- `post --to <dir>` is removed. `post <id>` posts to GitHub. `--to github` keeps working without comment, so the instructions and transcripts already written stay true; it is no longer shown in help or output.
- `look --from <dir>` and `apply --from <dir>` are removed. A solution comes from a pull request.
- Each removed spelling, typed, is a named refusal (`folder-delivery-retired` or the name that fits) that changes nothing and says what to do: post to GitHub; a private repository cannot be handed off with this tool.
- Code that only served folders is deleted, not left behind a flag: building the package, the `repo/` copy, binding a returned folder to its manifest, the folder post's `posted` path. Tests of folder behaviour are removed with it. **Tests of a guarantee move to the GitHub path** where that guarantee still applies (never-ship on what is published, nothing a solver wrote is run, a hostile path refused); the Result lists each one and where it went. No expected outcome of a surviving guarantee changes.

**What stays and what it says**

- `create` still takes the photograph, applies never-ship, previews the secret scan, and writes the record and its bookmark. Its preview now describes **what posting would publish** (the commit the bounty names, commits not yet pushed, and uncommitted changes only if the agent asks), the same plan `post --preview` shows, and not a file count of a copy. Where never-ship removes something that would otherwise be published, it says so.
- The issue a solver reads is unchanged.
- `help`, `describe`, the record's next steps and `docs/box-v4/BOUNTY.md` say nothing about folders. The doc page says once, plainly, that the tool is for public repositories on GitHub and has no other route.

**Records and folders from before**

- Records written before this wave load. One that was drafted with a folder and never posted posts to GitHub as any draft does. One posted to a folder, or posted to GitHub before BT6a, can still be read with `status` and ended with `close`; anything that would need its folder refuses by name and names `close`.
- Folders already beside an owner's projects are left alone. The doc page says they are no longer used and may be deleted by hand.

**Measured:** the characters of `help` and of `create`'s output, before and after; the number of options `create` and `post` take.

**Cases that must fail, each a named refusal that changes nothing:** `create --out`; `post --to <any folder>`; `look --from`; `apply --from`; posting a private repository (unchanged, now with no mention of a folder).
