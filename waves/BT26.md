## Why

The run closed its waves honestly, and its passes named what they left open. Each is small; together they are the difference between "reviewed" and "done":

1. **A nested checkout's Git folder can still receive an instruction block** (BT21's pass). `instructions.ts` refuses `.git`/`.box` only as the first path segment and the project's own Git folder, so `sub/.git/config` or `sub/.box/x` is accepted: the same damage BT8b showed (a block appended to a Git config breaks Git there).
2. **`look` can compare against a fake commit** (BT24's pass). `look.ts` (around line 59) falls back to `record.resume.commit`, which `create` sets to the display text `(no commits yet)` in a repository with no commits; `json.ts` (around line 182) already refuses that with a 40-hex test. Two readers of the same fact, one guarded.
3. **No test pins that a new record's merge message has no `snapshot:` line** (BT24's pass checked it by hand only).
4. **Two comments were cut mid-sentence by BT25's extraction** (`record.ts` around line 602; `render.ts` around lines 101 and 117 to 120).
5. **`-h` is read as help even where it is an option's value** (BT18's pass): `box bounty close --reason -h` prints help instead of recording `-h` as the reason. Git and gh take the next word as the value when an option requires one.
6. **Nothing stops the JSON view falling behind the text view** (BT19: the first draft dropped five facts the `--full` text prints; they were fixed one by one, and BACKLOG.md asks for a check so a future text line cannot be missed again).

## Outcome

## The six fixes

**1. Any `.git` or `.box` segment is tool-owned.** In `instructions.ts`, the tool-owned check (the code around `toolOwned`, "Judged on the declared spelling, folded, and again on the canonical path") refuses when **any** path segment, case-folded, equals `.git` or `.box`, on the declared spelling and on the canonical path, not only the first one. Keep the existing `git rev-parse --git-dir` check. Tests: `sub/.git/config`, `sub/.GIT/config`, `a/b/.box/x.json`, and a link inside the project that lands in `sub/.git/` each refuse `instruction-file-tool-owned`, with the target file's bytes and the settings' bytes unchanged. `docs/.github/x.md` and `notes/git.md` are still accepted (only exact segment names count).

**2. One reader for a record's base commit.** Add one exported function in `record.ts`, `baseCommitOf(record): string | null`, holding exactly `json.ts`'s current expression (old records' `snapshot.baseCommit`, else `resume.commit` only when it is 40 hex characters, else `null`). Use it in `json.ts` and in `look.ts`'s fallback (`look.ts` keeps its own first choice, `record.github.commit` for history posts, and its existing empty-tree fallback when the result is `null`). Test: a record in a repository with no commits, whose `resume.commit` is `(no commits yet)` and with one hand-made attempt: `look` compares against the empty tree (it lists the attempt's files as added) and never passes `(no commits yet)` to Git.

**3. Pin the merge message.** In `bt26.test.ts`, a full journey on a new draft to a clean `apply`: the merge commit's message (`git log -1 --format=%B`) contains no line starting `snapshot:`. And for a hand-made old record that has `snapshot`, the line is present (so the test is not vacuous).

**4. Rejoin the split comments.** Read the BT25 Result's finding (1). Put each comment back together above the function it describes; delete the orphaned fragments. Comments only; `git diff` for this item shows no code line changed.

**5. A value is taken before help.** In `args.ts`'s parser, scan for `--help`/`-h` only where an option name or a positional is expected; the word after an option that takes a value is that value, whatever it looks like. So `close --reason -h` records `-h` as the reason, and `close -h` and `close --reason x -h` still print help. Tests: those three, plus `status --since --help` (the value is `--help`; `--since` then refuses it as not a time, as it would any bad time).

**6. The JSON view cannot fall behind the text view.** A new test file `tests/box/bounty/json-agreement.test.ts`, over the standard stand-in journey `bt19.test.ts` uses:
- Run `status --full`, `look <id> <n> --full` and `config --full` as text at each journey step, and collect every **label**: the text before the first `: ` on each line, trimmed, when that text is 1 to 4 lowercase words (regular expression `^\s*([a-z][a-z' -]{0,40}):\s`).
- The test holds one explicit table, `LABELS`, mapping each label to the JSON pointer in the matching `--json` document that carries the same fact (for example `owner` → `/owner/decision`), or to `null` with a written reason when a label is not a fact (for example a heading).
- It fails, naming the label and the command, when the text prints a label the table does not list; and it fails when a mapped pointer is missing from the document at a step where the text printed that label.
- Build the table by running the test, reading each failure and adding the row. The Result lists every label and its pointer.
