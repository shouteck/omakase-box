## What the reading found

- **The three `bt61`/`json-agreement` journey tests are complementary, not duplicates.** `bt61-text` runs the journey in text mode and compares every command's text to a stored snapshot. `bt61-agreement` runs the mutating commands once with `--json` and checks that every label in the document's `lines` is a fact the document carries. `json-agreement` checks the `--full` text views against their `--json` documents at six checkpoints. A mutating command cannot be run twice on one state, and the agreement test's `lines` stand for the text only because `bt61-text` proves the text path prints exactly those lines from its own separate run. One shared transcript would remove that independence (the text path could drift from `lines` unseen). The shared part is the world's set-up, about 1.5 s each. Saving: almost none.
- **The `bt43` trio is door-level by design.** The static walk in the same file (`bt43` lines 331 to 454) already proves that every *declared* solver field reaches the renderer; the three slow tests prove what the *running* tool prints at each door (create, status, status --since, the preview, the held post's owner block, config, close, the merge notice), which is where an undeclared raw print would appear. The first of them (`create, status, ... print each name quoted`) is one world and seven commands, each its own sentence in its own code path; its cost is the commands, and each is a different check. The other two (a commit subject merged by one apply, then shown in a later conflict list; the same subject published by a later post, shown in the preview, the body, close's note and its comment) share a prefix (post a bounty, a hostile solver pull request, apply it), about 5 to 7 s on one worker, which could be merged into one scenario. That is about 0.3% of the suite, in a test of a promise the tool makes about strangers' text. Not worth the risk.
- **The eleven `bt6b` landing journeys cannot share a world.** Each lands one solution under one configuration to show the owner's own program really runs (the tool's verdict matches what Git does); an `apply` consumes its bounty, and each landing is a create, post, pull request, look and apply of about 10 s. The table (K69) already carries the verdict half of each; sharing a world saves its start-up (about 1 s) and nothing else. Fewer landings would mean fewer parse shapes shown to run for real.

What remains is either the cost of a command (a `gh version` start in every process, seven starts to append a chain event, two `for-each-ref`, a Node process per test `gh` call: [K68](../kitchen/reviews/K68-slow-tests.md) lists them), which is product code on paths the hard stops depend on, or the owner's question on tests of retired record shapes (about 42 s and some old readers). Neither is a test conversion; each needs the owner's direction or its own wave.
