## How the case is set up (the replay design)

The requester in this replay is the cook, standing in for a maintainer who has the issue and a failing test.

1. **Request text.** The issue body plus all its comments up to, but not including, any comment that links the fix or is dated after the fix was opened. Fetch the comments read-only and save them beside the issue file. The pull request text and the fix diff are never given to the solver.
2. **Owner repository.** Inside a container volume: the project at the case's base commit, plus one local commit that adds the maintainers' test file(s) from the fix and nothing else ("the requester wrote a failing test"). That local commit is the agreement's base. It never leaves the container.
3. **Agreement**, written by hand as data, with no code:
   - `outcome`: one or two sentences in the requester's words pointing at the request text, which ships in the Box as a file.
   - `files`: chosen by a rule stated before export, not from the fix: the package manifest and lockfile, the entry file(s), everything under `lib/`, the request text, and the test files needed for the declared checks. Record the rule, the file count and bytes, and what share of the repository's tracked files and bytes that is.
   - `editable`: every file under `lib/`, by the same no-hindsight rule. Do not narrow it to the file the fix touched.
   - Recipient and owner `setup`: `npm ci --ignore-scripts --no-audit --no-fund`.
   - `commands`: an **outcome** check that runs the maintainers' test file (red at base, as wave 1 showed) and a **guard** check that runs untouched existing tests covering the same source, in both contexts. Keep the guard set small enough to run in under a minute; say which files and why.
4. **Export** with the product, in the container. The product's own paired check (base clone against staged Box) must agree, or export refuses; a refusal is a finding. Record wall-clock time from "agreement file started" to "Box exported", split into writing the agreement and running export, and list every manual step.
5. **Hand-off.** Copy the exported Box to the host scratch folder. Keep a pristine copy inside the container volume for `--box`. Then **stop and report to the head chef**; the head chef dispatches the blind solver, who is a different agent. Provide in your report:
   - the scratch folder path;
   - one wrapper command per action the solver needs (setup, each check, `node box/submit.mjs`), each of which runs inside a container with only that folder mounted and the network off for checks and submit;
   - a short `SOLVER.md` in the scratch folder (outside the Box contents hashed by the product, or in a sibling file) telling the solver how to run those commands. It must not name the project's repository URL, the pull request or the fix.
6. **After the solver returns** (the head chef will message you again with the submission path): run `box verify` in the container against the owner repository with the pristine `--box`. Record the exit code and report. Then, separately from acceptance:
   - **Held-back probe.** One tiny check written from the issue's own example, never shown to the solver, run against the owner repository with the solver's change applied. Report it on its own line; it is not part of the product's verdict.
   - **Comparison.** Describe in a sentence how the solver's change differs from the maintainers' fix. Run the fix commit's full test suite against base plus the solver's change and record the exit code.
   - **Negative.** Verify a no-op submission (sealed with no edit) and confirm it is rejected.
