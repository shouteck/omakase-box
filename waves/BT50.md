# BT50: a GitHub failure says what happened and what to do next

Milestone: BT · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT50` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: none
Horizon: short

**Brief.** Written by the CTO on 21 October 2026 from the engineering review. Every `gh` failure today collapses into one generic `github-command-failed` (`gh.ts:133`), and the reason is deliberate: gh diagnostics can contain credentials, so the wrapper never prints them. This wave classifies the failure without printing it.

**Refined by the CTO on 22 October 2026** (owner's request to review the nine engineering-review briefs): code claims checked against master `24bb6b8`; changes are listed under "CTO refinement" at the end of this brief.

## Why

`gh()` sees `result.error`, `result.status` and `result.stdout`, but uses none of them except to fail (`gh.ts:132–134`). A rate limit, an expired sign-in, a missing repository and a network drop all read the same: "check gh sign-in and access, then rerun". That breaks the product rule that every outcome is a named state with a next step, and it wastes the owner's time on the wrong fix.

## Outcome

A GitHub failure names one of a small set of causes, says what to do next, and never echoes gh's own text. Reads may retry once; writes never retry blindly.

## The change

1. Classify in one place, from facts already available:
   - `result.error` (spawn failure, timeout) → `github-unreachable`;
   - `result.status` with a known safe marker in stderr (`rate limit`, `secondary rate`, `abuse`, `HTTP 401`, `HTTP 403`, `HTTP 404`, `HTTP 429`, `HTTP 5xx`) → the matching named reason;
   - no marker → the existing `github-command-failed`, unchanged, as the fallback.
2. For `api()` calls, read the status and headers rather than guessing: `gh api --include`, split the header block from the body, and read `x-ratelimit-reset` / `retry-after`. On a rate-limit failure, `GET /rate_limit` is free and gives the reset time; use it once.
3. Named reasons and next steps: `github-not-signed-in` (run `gh auth login`), `github-rate-limited` (wait until the stated time), `github-permission-denied` (the account cannot do this here), `github-repository-missing` (check the remote), `github-unavailable` (GitHub's 5xx; retry later), `github-unreachable` (network; check the connection).
4. Retry rule: one retry, bounded to about a second, for a read that hit 5xx or the network. Never retry a `POST` (issue create, comment) — a retry can duplicate. State the rule in the Result.
5. Never print stderr, a response body or a token. `redact` stays the only place credential-shaped strings are handled.

## Done when

- A unit test drives each case with a synthetic result (spawn error, 401, 403 rate limit with reset, 429 with `Retry-After`, 404, 500, network) and asserts the named reason, the next step, and that no stderr text or credential appears.
- A stand-in `gh` returning a rate-limit marker produces `github-rate-limited` with a reset time; the same call on a `POST` is not retried.
- A read that fails twice still ends in a named refusal, not a hang; the retry is visibly bounded.
- The fallback case still returns `github-command-failed`, so an unknown failure is no worse than today.
- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit.

## Notes

- The existing warning at `gh.ts:104` is the rule: do not include gh/git diagnostics. Classification reads them; output must not.
- `gh api --include` changes the parse path; keep the JSON-only path for success and split the header block only on failure.
- `pages()` calls `api()` in a loop; a rate limit mid-pagination must stop with one named refusal, not a partial list presented as complete.
- Do not add a retry setting the owner must choose; one bounded retry on reads is the whole rule.

## CTO refinement (22 October 2026)

- Reuse existing reason names where they already mean the same thing (for example `github-not-signed-in` and `github-push-denied` are in the BT40 inventory); add a name only for a new cause.
- Every reason carries `next:` (BT40's guard). A retry counts against the hook's call budget and deadline (`ghCallBudget`, `ghDeadline` in `gh()`); it never extends them.
- Checked: the single fallback is at `gh.ts:133`; the "never include diagnostics" rule at `gh.ts:104`; `redact` at `gh.ts:88`; `api()` at 164 and `pages()` at 179.
