# BT83: one door out — every send is planned, checked once, then made

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT83` · Timebox: 480 minutes (several hosted runs of about 25); at expiry, report what has moved, leave the rest listed in the inventory, and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: long: it changes how every command that writes outward is built; starts with `/plan`. Refactoring playbook; principles: boundary-discipline, type-system-discipline, subtract-before-you-add, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the BT82 prototype ([BT82](BT82.md), comparison in [the BT82 notes](BT82-notes.md)). It awaits the owner's go.

**Why.** The tool sends data off the machine from 19 places, plus 3 GraphQL reads that also pass a payload. The BT82 inventory lists them all, mechanically (`tests/box/bounty/exit-sites.ts`, held exact by `bt82.test.ts`). Each place guards itself, and four findings of 23 November are one place that forgot something (BT69, BT73, BT80, BT81).

BT82 tried two shapes on the same two exits. The winner combines them:
- **B's shape:** a command plans what it will send before its first local write, so a refusal changes nothing;
- **A's permission value:** authority is a `Granted` value only the gate functions can make, checked by the compiler, not a record field any writer can set.

## Outcome

1. **One module, `packages/box-bounty/outbound.ts`, is the only code that writes outward.** It holds:
   - `Effect`: one variant per kind of send. That is a branch push or delete, an issue, a comment, an issue edit, a label, a shared-memory push, a fork, a pull request, the ready-for-review mutation, and the board hint.
   - `Granted`: branded with a module-private symbol. It is made only by:
     - `grantPost` (wraps `ownerGate` and the post's recorded answer, then `publicRepository`);
     - `grantCloseUp` (the signed-in account opened this bounty; owner, 15 October 2026);
     - `grantSolver` (the solver's own sign-in acting on its own fork and pull request, for `take` and `submit`).
   - `checkEffects(granted, effects)`: for each effect, the grant's kind allows it; never-ship applies where bytes go (BT69's `checkOutbound` moves here); the pre-publish scan applies to every text; all under the rules read at that moment.
   - `runEffects(granted, effects)`: checks again, then sends in order, keeping today's markers and `recoverIssue` for retries.
2. **Each command plans first.** `post`, `close`, `apply`'s close-up, `take`, `submit` and the shared-memory sends each:
   - build their `Effect[]` before their first local write;
   - call `checkEffects`;
   - make their local changes;
   - call `runEffects`.

   A refused send leaves the record, the store and the remote as they were.
3. **The raw writers are no longer exported:** `api` with a payload, `remoteGit` with `push`, `gitOutcome` with `push`, `boardCalls` with a body. Reads keep `readOnlyApi` and a read-only GraphQL helper.
4. **The inventory becomes the guard.** `bt82.test.ts` asserts that every exit site is inside `outbound.ts`, and that no `unknown` site exists anywhere. The walker is hardened first, against the two routes BT82's lens found it missed (Steps 1).

## Steps, in order

Written so any model can cook it. Each step ends green on the touched tests before the next starts.

1. **Harden the inventory** (tests first): make the two BT82 lens misses fail as `unknown`, then make them pass by fixing the walker in `exit-sites.ts`:
   - a member call named `api`, `remoteGit` or `boardCalls`; an `import()` or `require` of `gh.js`, `git.js` or `board.js` outside the door;
   - a Git call whose first argument array starts with anything but a string literal.

   Commit.
2. **The door:** `outbound.ts` with `Effect`, `Granted`, the three grant functions, `checkEffects` and `runEffects`, and its own unit tests (each effect kind refused without its grant kind, each text scanned). `grantCloseUp` reads the account once; plan and run share it.
3. **`close` first** (it closes BT81's gap):
   - `decisionCommentBody` builds the text;
   - `closeBounty` plans the comments, the issue edit and the branch removal before `settleScanFindings`;
   - `syncGitHubDecision` and `advanceBountyBranch` run the plan.
4. **`post`:** the push (with BT69's check inside `checkEffects`), the label and the issue. Plan after the owner gate and before `persistRecord` of the publication.
5. **Shared memory:** `chain.ts`'s pushes become effects; `scanHold` is replaced by the door's scan.
6. **The solver side:** `take` (fork, push, pull request), `submit` (the mutation), `closeTaken`.
7. **The board hint.**
8. **Narrow the exports** (`gh.ts`, `git.ts`, `board.ts`) and turn `bt82.test.ts` into the guard (Outcome 4). Add the cast guard.
9. **Docs,** CONTRACTS; verify, push, hosted run, Result, merge.

## Stops

- If a send's authority fits none of the three grant kinds, stop and bring the owner one recommendation. A new kind of authority is product direction.
- If planning before the first local write would change what an existing test shows the agent (a different refusal, a different order of output), stop at that command, record it, and keep the commands already moved.

## Traps

- `ownerGate` writes a wait and throws when the owner has not allowed the post. `grantPost` must keep that, and it must run before any GitHub probe, as today.
- `recoverIssue` and the comment markers are what make retries safe. Planning must skip effects already done on GitHub, as the comment loop does today, not plan them again.
- `signedAccount` is not cached. Read it once per command and pass it into the grant; do not add a read per effect.
- One writer per branch; run the touched tests, not the full suite, between steps (16 GB).
