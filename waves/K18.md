# K18: a critique of the whole flow, for the agent and for the owner

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch · Branch: `wave/K18` · Timebox: 150 minutes; at expiry the cook stops and reports what it has

**Pre-brief.** Written by the CTO on 14 October 2026 at the owner's request: an honest critique of the end-to-end flow and of how intuitive the tool is for the two people who use it, an agent and an owner. An investigation: **it changes no product code and no test.** Its product is a report. It cooks only when named.

## The tool, for a cook who has not met it

**What it is.** `box bounty` lets a coding agent hand off work it cannot or should not do. The agent drafts a bounty from its repository; the tool packages the task safely and posts it as a public GitHub issue on a bounty branch; outside solvers answer with ordinary pull requests; a later agent, often a new session, reads the solutions, merges the one it judges best, and the tool closes the bounty. The tool never runs anything a solver wrote and never judges a solution.

**Who uses it.**

- **The agent** runs almost everything. It should need no documentation: every output names the next command.
- **The owner** is the person whose repository and GitHub account it is. They are meant to be involved once: allowing a repository. Most owners will not type commands; they tell their agent what they want and the agent runs it.

**The journey today.**

1. The agent drafts: `box bounty create --task <file> --why "<one line>"`. Private; nothing leaves the machine. A secret scan previews what would be published.
2. The agent posts: `box bounty post <id> --to github`. Public. If the owner has not allowed this repository, the post waits and the agent is given what to tell the owner.
3. The owner, once: `box bounty allow [--ask] [--reward <n> --reward-limit <n>]`. Allows this repository (or asks before each post), and states what each bounty there promises to pay, $0 unless set. Settings live in the owner's own file outside every repository. `box bounty deny` removes a repository; bare `box bounty config` shows every setting with the command that changes it.
4. Solvers open pull requests. One may add a `pay-to:` line with a Stripe payment link.
5. A later agent learns of the bounty from a notice the tool keeps in the project's instruction files (and from a session hook where the owner switched it on), runs `box bounty` or `box bounty status`, reads each solution with `box bounty look <n>`, and merges one with `box bounty apply <n>`. On a clash, `apply` states the facts and stops; the agent merges with its own Git and the tool recognises the merge the next time it runs.
6. The tool closes the bounty. If it stated a reward, the tool gives the agent the message for the owner: whom to pay, how much, the link, what to check. The tool never pays and never opens the link.

## The vision, and the principles to judge it by

The critique holds the tool to these. They are the owner's, from PLAN.md and from decisions made since; where PLAN.md's tables still describe "standing rules", a rule for all projects, or an agent awarding a solver, they predate the owner's decisions of 12 to 14 October 2026 and this section wins.

**The vision.** One command for a coding agent to hand off work: packaged safely, posted where it can be solved, remembered across sessions, and returned for the agent to choose. The bet behind it: bounty sites are short of tasks, not solvers, and a tool in the agent's hand is where tasks come from. It is unproven; demand is thin everywhere and early bounties may wait a long time. The owner chose to build it and learn from use.

**What it is, and is not.**

- **Merely a tool.** It offers actions and states facts. It does not require, forbid or judge any choice the agent makes. Whether to hand off, what the task is, and which solution to use are the agent's judgement; everything mechanical is the tool's.
- **Not a marketplace, and never one.** A bounty is a GitHub issue in an open format. We do not interface with bounty sites; they can interface with us: anyone can find and read every bounty without asking us.
- **Public repositories only.** Posting publishes code, so a private repository is refused with no override.
- **Only what the tool is needed for.** A command or feature exists only if an agent could not do the same with Git, the GitHub command line and its editor without losing something only the tool guarantees. The tool owns the life of a bounty, from posted to closed; it does not own how code is merged or what happens to it afterwards.
- **Not in it:** a site of our own, adapters to other sites, holding or moving money, an agent paying by itself, reputation, running or checking solutions, suggesting prices.

**For the agent.**

- **Every output names the next command.** No documentation should be needed. No command returns nothing or fails silently.
- **Facts, never verdicts.** A solution is described (who, what files, how large, whether it merges cleanly, that nothing was run), never judged.
- **Cheap to use.** Agents should spend as little reading and thinking as possible. Nothing is asked of the agent in words that a fact could replace.
- **Memory without demand.** What an agent sees unasked is only what it needs then: that the tool exists; while a bounty is open, that it is; a solution arriving, at a natural pause. With nothing to say, nothing is said.
- **A stranger's text is never shown as the tool's own,** and never put in front of an agent that did not ask to look at it.
- **Nothing is enforced** beyond the three hard stops: never-ship files never leave or come back; a private repository is never posted; nothing happens outside what the owner allowed. "The onus is on the agents; we merely provide a tool that helps them."

**For the owner.**

- **Involved once:** allowing a repository, with what its bounties pay. After that the agent runs the whole journey with nobody asked.
- **A small surface, like tools people already know.** Three words, `allow`, `deny` and `config`, after `direnv allow` and `git config`; a new setting never adds a command. Most owners never type them; they tell their agent and the agent runs them, so every owner-facing output is written for an agent to act on and for an owner to understand when it is relayed.
- **Safe by default.** One repository at a time; $0 unless the owner names an amount for that repository; "ask me each time" covers publishing only; the secret scan always runs, and a hit waits for the owner, who is always told.
- **Honest about its limits.** It stops accidents and makes changes visible; it says plainly that it is not a lock against an agent that sets out to get around it.

**About money.** The owner states one reward per repository and every bounty there carries it. The merged solution earns all of it; other solutions, and parts used by hand, earn nothing, and every bounty says so before a solver starts. The tool tells the agent whom the owner should pay and never pays. The limit caps what is on offer at once; it is not a balance.

**Host agnostic.** Nothing depends on one agent host; the same notice goes in every instruction file the project's hosts load.

**The critique may question the vision itself,** not only the tool's fit to it: where an agent or a stand-in owner was poorly served by a principle as written, say so, with the evidence. Mark such findings separately; changing a principle is the owner's decision.

**Where to read more, only if needed:** `docs/box-v4/BOUNTY.md` (the tool's own page), `kitchen/demo/` (a replay of the whole journey, and its transcript), PLAN.md.

**Walk it as the people who use it, cold.** Each journey is done by a fresh agent that has not seen this repository's code or docs, given only the built tool, a small project, and one plain instruction. The cook keeps each transcript, and records for each: every command run; each one the tool's output had not named; every hesitation, misreading and wrong turn; how much tool output it had to read (characters); and whether it finished.

1. **A posting agent, first time in a repository nobody has allowed:** "This bug is beyond you; hand it off." Ends when the owner has been asked.
2. **An owner, through their agent:** a second fresh agent plays an owner who has never heard of the tool. It sees only what the first agent tells it, decides, and says in its own words what it agreed to. Then the first agent carries out the owner's answer. Run three times, once each with: "yes", "yes, and pay ten dollars, at most thirty open", "ask me each time".
3. **A collecting agent, a new session, told nothing:** in a project with a posted bounty and two solutions waiting, one with a payment link, one clashing with current code. Ends when the bounty is closed and the agent has said what the owner must do.
4. **A posting agent whose draft holds something shaped like a secret.**
5. **An owner changing their mind,** through an agent given only bare `config`: "stop bounties here", "allow the docs repository too, no reward", "never publish the fixtures folder", "what have my agents done this week?"
6. **A cold arrival:** a fresh agent in a project with one open bounty is asked to do unrelated work. Does the tool's notice help, distract, or go unnoticed?

**Then judge it as an expert would.**

- Compare the owner's side with tools people already know for the same job (`gh auth`, `git config`, `direnv allow`, `npm config`): what do they make easier, and what do we ask that they do not?
- Count, for a whole journey: commands an agent runs, words an owner must read, decisions an owner must make, and places the owner is involved at all.
- Read every message the owner can be shown, and every message an agent is told to pass on, as the owner would. Mark anything vague, alarming without cause, or technical.
- Read the outputs agents saw most for repetition and lines nobody used.

**The report** (`kitchen/reviews/K18-flow-critique.md`):

- **One page first, for the owner:** the five things that would most improve the experience, each in two sentences, in order; then what works and must not be lost; then, separately, any principle that the evidence suggests is wrong for the people it serves.
- **Findings,** each with: who it hurts (agent, owner, solver), how badly (blocks, misleads, slows, clutters), the evidence (a quoted line of output or transcript, with where it came from), and a direction, not a design. No finding without evidence.
- **The numbers** above, per journey.
- **What was not tested** and why.
- Findings already known (BACKLOG.md, the open lists in STATUS.md) are marked as known, so the owner sees what is new.
