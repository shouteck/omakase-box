## The five fixes, in order

**1. An applied merge says how it reaches GitHub** (K31b's most important finding: `apply` merges in this checkout and closes the GitHub side, but nothing prompts a push, so the remote branch never gets the code and the pull request shows "closed, not merged"). In `packages/box-cli/src/bounty.ts` (around lines 239 to 243), after `<id> — applied — attempt <n> merged as <commit> on this branch`, add the facts git itself gives, following **git's own convention** (`git status`: "Your branch is ahead of 'origin/main' by N commits. (use "git push" to publish your local commits)"): read the current branch and its upstream (`git rev-parse --abbrev-ref --symbolic-full-name @{u}`; one Git start, only on this path) and the count ahead (`git rev-list --count @{u}..HEAD`), then print one line:
- with an upstream: `not on GitHub yet: this branch is <N> commit(s) ahead of <upstream> — publish it with: git push`
- with no upstream: `not on GitHub yet: this branch has no upstream — publish it with: git push -u origin <branch>`
The tool never runs the push. The ended line keeps its `git revert -m 1 <commit>` fact.
Also in `close.ts`, the tool's comment on the issue for a merged solution (`Solution #<n> is merged on the bounty's branch as commit …`) gains one honest clause: `merged in the owner's checkout; it reaches this repository when the owner pushes it` (so a reader of the closed pull request is not misled).

**2. `status` never says "no solution yet" while one is waiting.** In `render.ts`'s `ageClause` (around line 133), `no solution yet` is chosen when the record has no **collected** attempt, even when a pull request is waiting (`record.github.availablePullRequests` or `seenPullRequests`, listed elsewhere in the same output as `#38 … new`). Count waiting pull requests too: with none collected but `k` waiting, print `<k> solution(s) waiting`; the last-activity time is the newest waiting pull request's `at` when no attempt is collected. `status --json`'s `lastActivityAt` follows the same rule.

**3. `describe` names the case where a solver cannot help either.** In `wording.ts` (around line 28), the "not worth it when" line gains: `or a solver could not do it either (it needs a machine, access or data you cannot share)`. K31b's B1 agent reasoned exactly this unaided. If `bt17.test.ts`'s `describe` budget (28 lines, 2,000 characters) no longer fits, raise only the number that overflows, by exactly the measured amount, with the reason beside it.

**4. The tracked-records warning is said once.** The `records: N file(s) in .box/bounties/ are tracked in Git …` line (`render.ts` around line 361, `owner.ts` around line 268) currently prints on every `status` and `config`, and K31 and K31b found it crying wolf where records are tracked on purpose (this repository's five fixtures). Say it once per checkout through the said-once mechanism (BT17, the tool's `state.json` from BT22, keyed by the repository's real path); `--full` and `--json` still always state the tracking fact.

**5. The open-bounties file is rewritten only when it changes.** `syncOpenSurfaces` in `render.ts` (around line 628) writes `.box/bounties/OPEN` on every call, so under `core.autocrlf` Git shows a phantom modification after every `box` command (K31b). Read the current file and write only if the new content differs (compare bytes after normalising line endings). Check the instruction-file sync for the same pattern; if it already compares, say so.
