Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF33` · Timebox: 90 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-02-three-ways-to-pay
Horizon: short: two texts and the tests that read them. Bug-fix playbook; principles: subtract-before-you-add, prove-it-works

**Brief.** Written by the CTO on 10 November 2026, from the owner's point while PF32's verify ran (5 November): the line each posted issue gives solvers is vague ("connect an account or list a way at <board>/me/, or say how in your pull request description"), offers a route the board never sees (the pull request description), and should not name providers, which will change (PayPal awaits approval). After PF32.

## Outcome

A solver reading a bounty's issue, or an agent reading the board's guidance, is told one thing: sign in with their GitHub account on the board's own page and set up how they get paid there. Your page already lists every way the board has (by hand, one click, on merge), so the line never goes stale.

## The words (owner, 5 November 2026)

- **In the issue the tool posts**, when the owner's settings name a board: `to be paid: sign in with your GitHub account at <board>/me/ and set up how you get paid there.`
- **When the owner has turned the board off**, unchanged: `to be paid: say how in your pull request description.` (with no board there is no page to send anyone to).
- **In the board's `how_to_get_paid` for agents**, its first line says the same, generic, with no provider named; the rest of that answer (which ways apply to this bounty, from the board's live `ways_set_up`) stays.

## Rules

1. No provider is named in either line; the board's page and `ways_set_up` carry which ways exist.
2. Issues already on GitHub keep their line: the tool never edits an issue after posting it.
3. The tests that read the old words change to the new words, and nothing else about them.

- A test fails when the old line comes back, in the posted issue and in `how_to_get_paid`.
- The owner approves the before-and-after of both texts before merge; deploy on the owner's word (the CLI's line reaches users with the next npm release, the owner's to publish).

## Widened: the whole posted issue (owner, 10 November 2026: "Yes, fold it in")

The owner asked for a review of the issue the tool posts. Found: a noisy second line (raw timestamp, tool version) with the reward only at the bottom; "What was already tried" talking about the tool when there is no note; a hard "The code" section (a 40-character commit, "nothing new was published") overlapping "How to answer"; "Nobody is known to be watching these issues yet"; a reward part that reads like a log; no link to the board's page; no hint for agents.

The posted issue becomes (same facts, plainer; approved as proposed):

- First lines: the title; then `$<reward> for the merged solution · <id> · posted <d Mon yyyy>`; then `On the board: <board>/b/<id>/` (only when a board is set).
- `## What is wanted`: the task, unchanged.
- `## What was already tried`: only when the poster wrote a note.
- `## How to answer`: three numbered steps (start from the bounty branch at its short commit, it holds the code as the poster left it; open the pull request against the bounty branch, not the default branch; the poster reads and decides, the tool never runs anything the solver wrote), then `Agents: box bounty take <id> does steps 1 and 2 (npm i -g omakase-box).` The work in progress the poster shared, when there is any, is one plain line under step 1.
- `## Reward`: `$<reward> for the merged solution, paid by the poster directly. Other solutions earn nothing.`; the payment line above; `Posting an answer doesn't guarantee payment; the poster's payment record is on the board.` (without a board: the first two only); `Licence: …`. A $0 bounty says it has no reward.
- The hidden id marker and machine block, unchanged.

**The board's reader:** it takes the task from "What is wanted" up to the next heading (today: up to "What was already tried"), so issues with and without a note, old and new, read the same. Old issues keep their text; the tool never edits a posted issue.

**Tests:** every test that reads the issue's words moves to the new words; the size budgets stay; a test fails when the noisy line, the "watching" line or the old payment line comes back, and one when the board's reader misses a task with no note.
