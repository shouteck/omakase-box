# BT81: a close reason is scanned before it goes public, and says it will

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT81` · Timebox: 120 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `close`. The owner asked for it ("Yes, brief it").

**Why.** `close <id> --reason "<text>"` sends the agent's text to two public places:
1. **A comment on the public issue,** posted by `syncGitHubDecision` (`packages/box-bounty/close.ts`): `Rejected. Recorded reason: <text>`. No scan runs on this path.
2. **The `closed` event in shared memory** (`shareClosed`, `chain.ts`), which is scanned (`scanHold`) and held on a hit.

`closeBounty` (`packages/box-bounty/commands.ts`) calls `syncGitHubDecision` **before** `shareClosed`. So a secret-shaped reason is already on the public issue by the time the shared-memory scan holds the event.

Every other text an agent writes is scanned before it goes out: the title and task at `post`, the why and part-of before shared memory. Nothing tells the agent the reason is public either:
- the removed-command line in `packages/box-cli/src/bounty.ts` says `--reason` "keeps the reason on the record";
- the `missing-reason` refusal and BOUNTY.md (the `close` entry near line 1261) say nothing about where it goes.

## Outcome

1. `close` scans the reason with the pre-publish scan **before anything changes**, ahead of `settleScanFindings`, `transitionTo` and any GitHub call. A hit refuses with a new reason, `close-reason-held`, naming the rule and line, never the value. Nothing is changed: the record stays open, and nothing goes to GitHub or shared memory. The next step says to run `close` again with a reason that holds no secret, or with none. A reason is the agent's own words at the moment, so unlike a file there is no publish list to settle it (as BT45 decided for a bounty's own text).
2. Wherever `--reason` is described, the words say where it goes: "posted as a comment on the public issue and kept in the project's shared bounty memory". That is:
   - the `missing-reason` refusal;
   - the removed-command lines for `reject` and `withdraw` in `bounty.ts`;
   - `close`'s usage line;
   - `omakase-box help` for `close`;
   - BOUNTY.md;
   - FIRST-FIVE-MINUTES.md, if it names `--reason`.
3. Closing an already-ended bounty (the retry) does not scan again, and never posts a reason that was not posted before. A record written before this wave whose reason was already posted stays as it is.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master.
2. **The scan:** at the top of `closeBounty`, after the `missing-reason` check and before `syncBeforeAction` writes anything, run `scanText('(close reason)', text)` when a reason is given and the record is open. On a hit, refuse `close-reason-held` with the rule and line.
3. **The words:** update every description of `--reason` (Outcome 2). Re-record text snapshots and list each under `## Changed expectations` as the gate prints it.
4. **Docs,** CONTRACTS; surface; verify, push, hosted run, Result, merge.

## Traps

- `syncBeforeAction` may adopt or settle a record from shared memory. Scan before it only if the scan needs nothing it loads. The scan needs only the text, so put it first, and the refusal changes nothing.
- The refusal must not echo the reason: it is the very text that holds the secret. Name the rule and the line number only.
- Do not make the scan's hit settleable through `config` lists: a reason has no file path. Say so in the refusal, as BT45's text-hit line does.

## Lenses

- [x] **Security:** attack it with:
  - the secret split by a line break inside the reason;
  - the secret in a reason passed as `--reason=<text>`;
  - a reason of 10,000 characters;
  - a reason that copies the tool's own comment marker `<!-- box-bounty:… -->`, which could make a later retry think the comment was already posted.

  Say what each did; fix the marker case if it misleads the retry.

## Notes

- Follows the rule the tool already keeps for every other outgoing text: scan before it leaves (BT8, BT45), and say plainly where text goes (the tool states facts). GitHub's own comment box has no scan; push protection covers pushes only, so the tool is the only net here.
