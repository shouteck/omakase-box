> **Direction set by the owner on 14 October 2026, to be folded in when this brief is revised for dispatch. Where the text below differs, this wins.**
>
> **Agents are the main users,** so the aim is not a standalone program for people but this: an agent, in any environment it runs in (including a cloud sandbox that starts empty every session), gets the tool in one command with no human, learns it cheaply, and drives it reliably.
>
> - **An npm package, runnable with `npx`,** with no install step needed. Node is required on the machine, as Git and the GitHub command line are; agent hosts are nearly always installed through npm, so it is almost always present. The tool stays the code that exists and was reviewed; no rewrite in another language.
> - **Everything bundled into one file,** so installing fetches nothing else from the registry: no dependency is resolved at install time.
> - **A stated minimum Node,** declared in the package and checked when the tool starts: below it, a named refusal that says what is required, what was found and where to get it, the same way Git and `gh` are handled. The cook finds the real minimum from what the code uses and proves it with a test.
> - **The install line goes in the tool's instruction-file notice,** so an agent that has never seen the tool can fetch it unaided.
> - **The proof is an empty sandbox:** a fresh agent with only Node, Git and a signed-in `gh` gets the tool with one command and posts a $0 bounty in the sandbox repository, with nobody asked. The demonstration in Part A is driven the same way; Cua or a similar desktop sandbox may be evaluated for recording it, and nothing in this wave controls the owner's own desktop.
> - **A `gh` extension is a possible second route, later.** It would reuse the `gh` sign-in, but needs `gh` installed and signed in before it can be fetched. Not in this wave unless the first route is done.
> - **No single-file executable for now.** It mainly serves people without Node, who are not the users. Revisit only if they become users.
> - **Publishing is still the owner's decision alone (Part B):** the package name, the registry account and the moment it goes public.

## Why

Every wave so far tested the tool from inside this repository, as `node packages/box-cli/dist/cli.js`. There is no command another owner could install, the package is marked private, and a cold copy needs three bootstrap steps before the tool starts. After BT11 the product is complete and proven by us on both sides; nobody else can try it.

## Outcome

1. On a machine that has never seen this repository, with only Git, the GitHub command line and a supported Node, one install command gives a `box` command, and the whole journey of a $0 bounty works from it in someone else's public project.
2. A live demonstration, driven by a fresh agent the way a person would, from a fresh clone of this repository, shows a newcomer installing it and going through the whole workflow end to end.
3. The owner has in front of them exactly what would be published, under what name and licence, and decides.

**Part A: installable, proven from clean**

- **One artifact holds the bounty tool and nothing else.** It contains the `bounty` commands and what they need. It does not contain the kitchen, the wave files, the earlier platform (portal, runner, compiler, analysis, the `export`/`submit`/`verify`/`trace` commands unless the bounty commands need them), tests, or anything from `.box`, `.kitchen`, `.runtime` or `.execution`. A test lists the artifact's contents against an explicit allow-list, so a new file cannot slip in.
- **It carries no secrets and no machine paths.** A test scans the built artifact with BT8's content scan and for this machine's user name and absolute paths.
- **It installs with one command and exposes `box`.** `npx <package> bounty help` works with no install step, and `npm install -g <package>` exposes a `box` command whose `box bounty help` works immediately. Every message in the tool that names a command says `box bounty …`, not a path into this repository; a test greps the built output for the old spelling.
- **The install line travels in the instruction-file notice** (the `<!-- box-bounty -->` block): an agent that has never seen the tool reads one `npx` line and can fetch it unaided. The package's name in the notice is the manifest's name, marked as the provisional name pending the owner's Part B decision.
- **It behaves the way command-line tools that agents use are expected to: checked, not rebuilt.** The point of this wave is a product that works end to end for a newcomer (owner, 11 October 2026: do not reach for the stars before that). So this is a check against the list below. Fix only what would stop or mislead a newcomer in the clean-machine runs or the live demo; list everything else in the Result as found, for a later decision. Do not let it grow the wave.
  - every command and sub-command answers `--help` with its purpose, its arguments and one example, and the tool answers `--version`;
  - nothing ever waits for typing: no prompt, no pager, no editor opened, with or without a terminal attached;
  - results go to standard output and refusals and diagnostics to standard error, so output can be piped;
  - the exit code is 0 for success and non-zero for any refusal or failure, and the doc page lists what each code means; a named state is also printed in a form that can be matched exactly;
  - every command that reports state can also print it in a machine-readable form with one flag, with field names that are kept stable and listed in the doc page; the text form remains the default;
  - no colour or decoration unless writing to a terminal, and the common environment settings that switch colour off are respected;
  - running a command twice does not do the thing twice; a command that changes something outside the machine says so before it does;
  - arguments follow the usual shapes (`--name value`, `--` before anything passed through), and an unknown flag is a refusal that names the nearest real one, not something silently ignored;
  - it works the same from Git Bash, PowerShell and a Linux shell, and paths with spaces or non-ASCII characters in them work.
  This wave changes how the tool is delivered; it does not rename commands or change what they do.
- **It says what it needs and checks it.** Supported Node versions, Git and the GitHub command line are stated in the manifest and the README. Run without one of them, the tool says which is missing and how to get it, as a named refusal, before doing anything.
- **The licence travels with it:** the manifest's licence field, the `LICENSE` and `NOTICE` files inside the artifact, and no dependency whose licence forbids this use. The Result lists every runtime dependency with its licence. This is a first look by the kitchen, not legal review, and says so.
- **Proved from a clean machine, twice:** on the off-machine runner (Linux) and on this Windows host in an empty folder with a clean environment, neither with this repository present. The test installs the built artifact, creates a small public-shaped project, and runs the journey of a $0 bounty against stand-ins: set the rules up, create, post, a solution arrives, look, apply, close. Record both runs.
- **The first five minutes are written down:** one page for a new owner. What it does in three sentences; install; sign in to GitHub; the first bounty; what becomes public and what never does; the three hard stops; that it serves public repositories only; how to switch the hook on and what that costs; how to remove everything. A fresh reader with only that page gets from nothing to a posted bounty in a trial project.
- **Versioned.** The artifact has a version, `box bounty --version` prints it, records written by one version load in the next, and the bounty format's version (BT10, BT11) is stated separately from the tool's.
- **Uninstall is clean:** removing the tool leaves the project's records and the owner's rules where they are, and the page says where those live and how to remove them too.

**The live demo: a newcomer's first run, driven like a person would**

The owner asked for this (11 October 2026): a live demonstration, with computer use, that mimics someone installing the tool and going through the whole workflow end to end. It is the last proof of Part A and the thing an outsider would actually watch.

- **Who drives.** A fresh agent told only: "you have heard of this tool; here is its page; try it on this project." It is given no commands, no brief and no knowledge of how this repository is built. It works the way a person does: it reads what is on the screen and decides what to do next. On this host the cook cannot start the driving agents: the head chef starts them and saves each one's own report verbatim at hand-off (the evidence-card rule). The cook builds the rig, proves it on a toy task, gets the artifact installed in the demo's clean clone, writes the exact issue text for the owner gate, and reports **demo-ready**; the head chef then runs the drive, and every hesitation comes back to the cook as findings.
- **How it is driven on this host (revised 16 October 2026).** This host has no browser tool server and no agent desktop control, so the driver's window is a real terminal the agent reads and types into through the thinnest possible control surface — the same idea as the browser rig, adapted:
  1. **A real pseudo-terminal,** started in the demo's clean clone with a clean environment, rendered into a page by the existing `kitchen/demo/` recorder (`record.mjs`, Playwright) — which already produces the video, stills and a text transcript. Reuse it rather than building a new recorder.
  2. **A control surface for the driver:** a small command the fresh agent runs — read the terminal's current screen text; send keystrokes. Two verbs, nothing more. The driver decides what to type from what it reads; nothing is scripted, no command is prepared for it. This is the host-appropriate substitute for a browser tool server — the pass judges whether it is a fair stand-in (the driver could still choose wrongly, hesitate and err, and the recording shows it).
  3. **GitHub is watched, not clicked.** The repository is public, so the driver reads the sandbox issue and pull request through `gh` in its terminal — signed out reading works, or the existing `gh` sign-in is used read-only. Nothing in the rig or the demo ever types, reads or handles a credential.
  4. **What is kept:** the video, the action log (every read and every keystroke with the screen that prompted it), and the terminal transcript — saved under a wave-named folder as the wave's evidence.
  - **Prove the rig first:** spend the first twenty minutes on a toy task (start the pty, have a driver-shaped caller read the screen, type one command, open one public page's URL through `gh api`, stop the recording, play it back) before any of the real run. If the rig cannot be proven, this part of the wave is not done — report it as not done; do not substitute a scripted replay, and do not describe a transcript as a demo.
- **The rig is kitchen scaffolding, not product.** Reused `kitchen/demo/` pieces stay as they are; new pieces live in a wave-named folder outside the packages, dependencies pinned, nothing from the rig enters the artifact Part A builds, and the new pieces are removed at close unless the reviewer asks to keep them under `kitchen/demo/` as a repeatable demo.
- **Other routes, and why they are second choices.** Desktop control records the owner's whole screen and needs the owner's explicit yes and a cleared desktop; a disposable Linux desktop in a container needs a model key and a GitHub sign-in placed inside it. The pty-and-recorder rig above is the host-appropriate choice; if it cannot be proven, this part is not done — do not substitute a scripted replay, and do not describe a transcript as a demo.
- Whatever the route, nothing is staged: no command is prepared for the driver, no output is edited, and a step the driver could not do is shown as not done.
- **Where (revised).** The sandbox repository `shouteck/box-bounty-sandbox` — per K15 no post-K15 wave runs a real GitHub journey against `shouteck/omakase-box` (there is a kitchen test guarding this; `kitchen/sandbox.md` has the rules). The bounty is a real issue there at **$0 reward** (the owner's 14-October direction), its title and first line say it is a test by the owner. To make it a newcomer's first run, the driver starts from a fresh clone in a clean folder outside the main checkout, with a clean environment and only the built artifact from Part A available: nothing of the kitchen's own build on the path, and no rules set up in the settings folder it uses. GitHub is reached through the sign-in already on the machine; the driver never types, reads or handles a credential.
- **What it goes through, in one unbroken run (commands as they exist today):**
  1. Reads the first-five-minutes page and runs the tool with `npx`.
  2. Tries to hand off a small task (`create`); is told the repository is not allowed; the owner's part is played by the head chef, who answers once with the `allow` command shown, run in the driver's settings dir.
  3. Posts the bounty. **The owner has seen the exact issue text and said "go" beforehand** — the head chef carries the exact text to the owner and waits. The driver reads the posted issue as a stranger would.
  4. A second fresh agent, in another clean folder, plays the solver: finds the bounty through the public reader (`tests/box/bounty/bt10-reader.mjs` shows how the issue text is read unauthenticated), branches and opens a pull request as an outsider would. The reward is $0, so there is no payment link and no award step — both were already proved live in BT11b and are out of this demo's path.
  5. The driver ends its session. A new session of the driver starts cold and learns of the solution from what the tool shows it.
  6. It looks at the solution (`look`), applies it (`apply`).
  7. It closes the bounty (`close`), then removes the tool, and confirms what is left behind and where.
- **What is kept.** A screen recording of the whole run, the driver's own running commentary of what it understood and where it hesitated, the action log and the terminal transcript, saved as the wave's evidence under a wave-named folder. The recording shows no credential, no token and no personal detail of the owner beyond their public GitHub name; the reviewer checks the recording at the points where an account menu or settings could appear.
- **How it is judged.** It passes if the driver completes the run from the page alone. Every place it had to guess, every message that did not say what to do next, and every step that took more than one attempt is a finding, fixed in this wave when small and listed when not. A demo that only works with hints has failed and is reported as failed.
- **What it is not.** It is not published, posted or sent anywhere. Whether the recording is ever shown to anyone is part of the owner's Part B decision.
- Close: the bounty is closed and its branch removed by the tool's own commands, and the fresh clone and its settings folder are removed. Anything left on GitHub is listed in the Result by exact name.
