# BT12: someone else can install it

Milestone: BT · Station: packaging (also evidence) · Base: master at the time this cooks, after BT11 is merged · Branch: `wave/BT12` · Timebox: 180 minutes; at expiry, report partial findings and stop

**Brief, written ahead. Proposed by the CTO, not yet approved by the owner.** Written on 11 October 2026 while BT6's second run was cooking. This wave has two parts with different owners of the decision. Part A (make it installable and prove it from a clean machine) is ordinary product work. Part B (publish it where strangers can install it) is the owner's decision alone, taken only after they have seen Part A's result: publishing under a name is public and is not taken back. The head chef checks this file against the Results of BT6 to BT11 before dispatching.

## Why

Every wave so far tested the tool from inside this repository, as `node packages/box-cli/dist/cli.js`. There is no command another owner could install, the package is marked private, and a cold copy needs three bootstrap steps before the tool starts. After BT11 the product is complete and proven by us on both sides; nobody else can try it.

## Outcome

1. On a machine that has never seen this repository, with only Git, the GitHub command line and a supported Node, one install command gives a `box` command, and the whole journey of a $0 bounty works from it in someone else's public project.
2. The owner has in front of them exactly what would be published, under what name and licence, and decides.

- Do not touch: the behaviour of any `bounty` command; the never-ship table; the earlier platform's packages except to leave them out of what is installed; `.execution/`, `docs/legacy/`; the pstack plugin folder and its licence files.

## Done when

- `node scripts/verify.mjs test:box-bounty test:box-package` exits 0 on the final commit, plus the new install test.

**Part A: installable, proven from clean**

- **One artifact holds the bounty tool and nothing else.** It contains the `bounty` commands and what they need. It does not contain the kitchen, the wave files, the earlier platform (portal, runner, compiler, analysis, the `export`/`submit`/`verify`/`trace` commands unless the bounty commands need them), tests, or anything from `.box`, `.kitchen`, `.runtime` or `.execution`. A test lists the artifact's contents against an explicit allow-list, so a new file cannot slip in.
- **It carries no secrets and no machine paths.** A test scans the built artifact with BT8's content scan and for this machine's user name and absolute paths.
- **It installs with one command and exposes `box`.** `box bounty help` works immediately. Every message in the tool that names a command says `box bounty …`, not a path into this repository; a test greps the built output for the old spelling.
- **It says what it needs and checks it.** Supported Node versions, Git and the GitHub command line are stated in the manifest and the README. Run without one of them, the tool says which is missing and how to get it, as a named refusal, before doing anything.
- **The licence travels with it:** the manifest's licence field, the `LICENSE` and `NOTICE` files inside the artifact, and no dependency whose licence forbids this use. The Result lists every runtime dependency with its licence. This is a first look by the kitchen, not legal review, and says so.
- **Proved from a clean machine, twice:** on the off-machine runner (Linux) and on this Windows host in an empty folder with a clean environment, neither with this repository present. The test installs the built artifact, creates a small public-shaped project, and runs the journey of a $0 bounty against stand-ins: set the rules up, create, post, a solution arrives, look, apply, undo, close. Record both runs.
- **The first five minutes are written down:** one page for a new owner. What it does in three sentences; install; sign in to GitHub; the first bounty; what becomes public and what never does; the three hard stops; that it serves public repositories only; how to switch the hook on and what that costs; how to remove everything. A fresh reader with only that page gets from nothing to a posted bounty in a trial project.
- **Versioned.** The artifact has a version, `box bounty --version` prints it, records written by one version load in the next, and the bounty format's version (BT10, BT11) is stated separately from the tool's.
- **Uninstall is clean:** removing the tool leaves the project's records and the owner's rules where they are, and the page says where those live and how to remove them too.

**Part B: publishing, for the owner to decide**

Nothing in Part B is done by the kitchen without the owner's explicit yes after seeing Part A.

- The kitchen prepares and shows the owner: the exact name and whether it is free on the registry; the exact file list and size of what would be published; the licence; the page a stranger would land on; and what cannot be undone (a published name and version stay public; a version can be deprecated, not erased).
- **The owner creates and holds the registry account and its credentials.** No agent creates the account, signs in, or handles a token. If publishing needs a token on this machine, the owner runs the publish command themselves from the prepared artifact; the kitchen gives them the one command.
- The owner also decides, separately: whether the GitHub repository's description and README should present the tool to outsiders; and whether to tell anyone it exists. Neither is assumed by publishing.
- If the owner says no or not yet, the wave closes with Part A merged and says so. That is a complete result.

## Review lenses

- [x] **Security:** the reviewer inspects the artifact as an attacker would a new dependency. What is in it that should not be (kitchen files, tests with fixtures that look like secrets, records, machine paths, the owner's name beyond the licence notice); install-time scripts (there should be none; a test asserts it); what it executes on first run; whether a hostile project it is installed into can make it run something at startup (a planted config, a project-local file with the tool's name). It confirms nothing in the build or the test publishes anything.
- [x] **User experience:** this is how Part A is accepted. A fresh agent, on a clean machine image with only the README page, installs the tool into a trial public-shaped project and posts a $0 bounty against stand-ins, then removes the tool. The reviewer reports every point where it had to guess, every error message that did not say what to do, and how long it took. A second reader, as an owner who has never heard of the tool, reads only the page and says what the tool will do without asking them, what it will never do, and how to stop it.
- [x] **Measurement fairness:** the artifact's size and install time on both platforms, three runs each with the spread, and the count of runtime dependencies; the reviewer confirms the clean-machine runs really had no copy of this repository to fall back on.

## Notes for the worker

- Feature playbook, investigation first: on a clean machine, find everything the tool reaches for outside its own folder (the repository's scripts, the pinned toolchain, sibling packages, the TypeScript compiler at run time, which the backlog records as needed today). Each one is either bundled, declared, or removed.
- Fewer runtime dependencies is better; each is something a stranger must trust.
- The tool must behave identically installed and from this repository. One code path; the kitchen keeps using the same build.
- Do not rename commands, change output or tidy behaviour in passing. This wave changes how the tool is delivered, nothing else.
- No install-time scripts, no network at install beyond fetching the package, no telemetry of any kind.
- Out of scope: other package registries or installers beyond the one chosen; auto-update; a website; any announcement; an agent wallet; a second hosting service.
- Everything the wave creates in the temp folder is named for the wave and removed at close. Nothing is published, to any registry, by the kitchen.
