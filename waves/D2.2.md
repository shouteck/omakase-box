# D2.2: a blind taster completes a change from the Box alone and submits a patch

Milestone: D2 · Station: packaging · Base: master after D2.1 · Branch: `wave/D2.2` · Timebox: 4 hours

## Outcome

A `submit` step exists such that a recipient with ONLY the exported Box folder — no owner repository, no `.git`, no access to this checkout — can edit the editable paths, run the declared checks, and produce a patch bound to the Box identity, version and base commit with paths mapped back to owner source. Then a `box-recipient` agent actually does it for Request A and a real `submission` artifact exists. D3.1 (next wave) verifies it owner-side.

## Design constraints

- The recipient has no repository, so the submit mechanism must travel inside the Box folder: e.g. a self-contained `box/submit.mjs` (or equivalent) emitted by export, or a declared recipe a generic agent can follow ("produce a unified diff of the editable files against the shipped copies; seal with box.json identity"). Choose the simplest that satisfies binding; the recipient must not need `box-cli`.
- Binding: the submission must carry box id + version + base commit, the editable file set actually changed, and a way for the owner to detect edits outside editable paths or an altered agreement (hash of box.json or the shipped baseline copies — pick one and document it).
- The owner-side half is a CLI `submit`-validation that ingests the artifact and reports what it would apply — full verify+merge is D3.1, but the boundary validation belongs here.

## Scope

- Write: `packages/box-cli/**`, `packages/box-package/**` (submission schema + emit/validate), `tests/box/package/**` (submission tests), `docs/box-v4/delegation/` only if a one-file contract note is needed.
- Read: the D2.1 export output shape, `packages/box-contracts` identity fields, SUPPORTED-CASE.md submission mapping.
- Do not touch: evaluator content, service/console code, `.execution/**`.

## Procedure

1. Worker implements export-emitted submit + owner-side validation, with tests: wrong Box id/version, wrong base commit, edit outside editable paths, altered agreement, malformed patch — each rejected with a reason.
2. Worker exports a fresh Request-A Box to `C:/Users/shout/Desktop/Projects/kitchen-d22-box/` (outside the repo) and reports the path. The folder must be exactly what a recipient gets — nothing extra.
3. Head chef dispatches `box-recipient` with ONLY the folder path (no repository). The taster's report (what it lacked, what confused it) is evidence.
4. The taster's submission artifact is copied to `kitchen-d22-submission/` and validated by the owner-side CLI — recorded in this wave file.
5. Reviewer then reviews the code diff AND the authenticity of the recipient run (the submission exists, binds correctly, reflects real edits).

## Done when

- `node scripts/verify.mjs test:box-package` exits 0 on the final commit.
- A real recipient run produced a submission artifact for Request A that the owner-side validator accepts and maps to `config/response-security.json`.
- Negatives each tested and rejected: wrong-scope edit, wrong box/base, altered agreement.
- The wave file records: what the recipient was (Devin subagent, model), what it was given (the folder only), what it did, every clarification it needed, and what was missing from the Box (its complaint list is a D2.1-quality signal).

## Review lenses

- [x] **Security:** the binding is the point — forged identity, scope violation, altered agreement must all be rejected; reviewer attacks them.
- [ ] **User experience:** the recipient's confusion report counts instead; no screen.
- [x] **Measurement fairness:** the recipient-run record (what it was given, time/steps, clarifications) feeds D4 — the reviewer checks it's honest, not embellished.
- [ ] **Second model family:** not available on this host; record that.

## Carry-overs from the D2.1 pass (non-blocking, in scope to handle or record)

- Windows `realpathSync` preserves declared component case — a case-aliased non-excluded path can emit under the alias spelling and double-ship on crafted agreements. If submit/patch-mapping sees such spellings, normalize; our two fixture agreements are exact so this is adversarial-input hygiene.
- `readContext` naming the bare excluded directory (no trailing slash) is currently accepted; no bytes ship, but if submit scopes anything on read-context fields, fold the check.

## Notes for the worker

- `kitchen-d22-box`/`kitchen-d22-submission` dirs are night-run resources: create under `Desktop/Projects/`, remove at wave close once the submission is validated and its content recorded.
- The taster does NOT need a correct implementation to count — a wrong patch is still a valid submission event; correctness is judged owner-side in D3.1. Do not coach it beyond the folder.
- Keep the recipient contract minimal: it should be openable with "read box.json, edit editable paths, run checks, run submit."
