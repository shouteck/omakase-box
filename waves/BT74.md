# BT74: `post` states whether GitHub's own secret net is on

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT74` · Timebox: 120 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short. Feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `create` with the owner, who asked for this wave ("All three").

**Why.** The tool's own guards (the never-ship table, the secret scan, the preview) are one net. GitHub offers a second: **push protection**, which refuses a push holding a known secret pattern, whoever pushes it. It is a repository setting, free for public repositories. The owner of a repository can't see from the tool whether that second net is there. Today it is **off** on `shouteck/omakase-box` and **on** on `shouteck/box-bounty-sandbox`, as read with:

```
gh api repos/<owner>/<name> --jq .security_and_analysis
```

`post` already reads that same address once (`publicRepository`, `gh.ts:393`, to check it is public and that the sign-in can push). The answer carries `security_and_analysis.secret_scanning_push_protection.status` when GitHub shows it to the reader. GitHub shows it only to readers with admin rights, so the tool must also say when it could not tell.

**What the tool does with it: states it, nothing more.** It never turns the setting on, never refuses a post over it, and never calls it good or bad (AGENTS.md: "the tool states facts and never a verdict"; [tool offers, never enforces](../docs/box-v4/DECISIONS.md)).

## Outcome

1. `post --preview` prints one line, `GitHub push protection: on | off | not shown to this sign-in`, plus the command that shows the setting.
2. `post --json` and `post --preview --json` carry the same fact as `pushProtection: "on" | "off" | "unknown"`.
3. No second GitHub call: the value comes from the read `post` already makes.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** in `bt74.test.ts`, the table below, seen failing.
2. **The stand-in.** Let `github-fixture.ts` take an optional `pushProtection: 'enabled' | 'disabled' | 'absent' | string` for the repository answer; the default is `absent`, so every older test sees what it saw before.
3. **Read it once.** `publicRepository` already holds `info`. Return `{ fullName, pushProtection }` (or add a sibling that returns both from one call); map exactly `"enabled"` → `on`, `"disabled"` → `off`, anything else or missing → `unknown`. Update the two callers in `post.ts`.
4. **State it.** In `renderPlanPreview`, one line after the repository line: `GitHub push protection: on` (or `off`, or `not shown to this sign-in`), then `see: gh api repos/<r> --jq .security_and_analysis`. Add `pushProtection` to the returned facts and the JSON.
5. **Surface:** `node scripts/surface.mjs --write`; re-record text snapshots (`BT61_RECORD=1`); list each changed test under `## Changed expectations`.
6. **Live read** in the sandbox, then verify, push, hosted run, Result, merge.

## Traps

- Most readers are not admins, so `unknown` is the common answer for a solver or a collaborator. The words must not read as a fault: "not shown to this sign-in" is a fact.
- Do not read the separate `secret-scanning` endpoints: they need more rights and a second call.
- The setting is per repository and can change between preview and post. State it in both; promise nothing.
