# BT79: every refused post is proven to leave nothing behind

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT79` · Timebox: 210 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: long: a table of every refusal `post` can give, each with its setup; starts with `/plan`. Feature playbook; principles: prove-it-works, encode-lessons-in-structure, make-operations-idempotent.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `post`. The owner asked for it ("Brief both"): checks before a post "have to be respected fully".

**Why.** Every refusal of `post` says "nothing was posted", and each is tested on its own: 17 test files check it, case by case. No test proves the property for **all** of them at once:
- a refused post wrote nothing to GitHub;
- it pushed no branch;
- it sent nothing to the board;
- it added nothing to the shared memory;
- it changed the local record only in the way that refusal says (a hold records its wait; the rest change nothing).

So a refusal added later in the wrong place (after the first push, say) or a check moved below a write would pass every existing test. BT40 already proves one property over every refusal site: each names a next step. It finds the sites mechanically with the parser (`tests/box/bounty/refusal-sites.ts`, `collectSites`). This wave does the same for "a refusal has no effect". It covers hard stop 3 (nothing outside the owner's authority: CONTRACTS P4, O1) and the "nothing was posted" sentence every refusal prints (the tool states facts).

BT73 proves the other half: when a post **succeeds**, nothing never-ship or secret leaves.

## Outcome

1. `tests/box/bounty/post-refusals.ts` is a table, one row per refusal `post` (and `post --preview`) can give. Each row has the reason, a setup that triggers it, and its **local effect**: `none`, or the exact fields a hold writes (`waiting` with its reason, `scanFindings`).
2. `bt79.test.ts` runs every row against the stand-in world (`github-fixture.ts`) and asserts, after the refusal:
   - the stand-in GitHub's state file is byte-for-byte as before (no issue, comment, label or branch);
   - every ref in the bare remote is as before;
   - the stand-in board received no request;
   - `refs/box-bounty-records/*` is as before, locally and in the remote;
   - the record file equals the row's stated local effect and nothing more;
   - the refusal's message says nothing was posted, or that it waits.
3. **Completeness is mechanical.** From `collectSites()`, every refusal site in the files `post` runs is either a table row or on a short `notFromPost` list with a reason ("only `apply` calls this"). A new refusal site in those files fails the test until it is classified. The files are the ones `post`'s own code imports, read from the import graph by the test, not listed by hand.
4. Refusals that can only come **after** the first push (`github-post-incomplete`, `github-branch-changed`, a label that did not land) are in their own group. For them the test asserts the resumable state instead: the record says how far it got, and a rerun with the fault removed finishes with exactly one issue.

## Steps, in order

Written so any model can cook it. Start with `/plan`; keep the plan in this file.

1. **List the sites.** Run `collectSites()` filtered to `post`'s import graph and print the reasons with file and line. That is the work list; classify each.
2. **The table,** `post-refusals.ts`.
   - For each reason, the smallest setup: a settings write, a file planted, a remote ref removed, a stand-in answer changed.
   - Reuse existing setups from `bt8c`, `bt60`, `github-history` and `bt49` where they exist (import them; do not copy).
3. **The snapshot of the outside world,** one function:
   - the stand-in state file's bytes;
   - `git for-each-ref` in the bare remote;
   - the board's request log;
   - the local and remote chain refs;
   - the record file.

   Take it before and after; compare.
4. **The completeness check** (Outcome 3), then the after-push group with fault injection.
5. **Break proofs,** guard-breaks row, CONTRACTS, verify, push, hosted run, Result, merge.

## Traps

- Holds are not "nothing changed": they write `waiting` on the record, by design. The row states exactly what, and the test checks exactly that.
- `post --preview` may read GitHub (the repository, the remote's refs) but never write. Its rows assert zero writes, not zero requests.
- `ls-remote` and fetches are reads; the stand-in records them. Compare writes only, but list in the Result which reads each group makes.
- The import-graph walk must follow re-exports (`index.ts`, `github.ts`), or files are missed.
