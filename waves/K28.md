# K28: the delegation record: what the project must remember about handed-off work, and how leading agent tools store it

Milestone: K (kitchen) · Station: evidence (also packaging) · Base: master at dispatch, after BT31 · Branch: `wave/K28` · Timebox: 240 minutes; at expiry the cook stops and reports what it has

**Brief.** Written by the CTO on 17 October 2026 at the owner's request. A research and design investigation: **it changes no product code and no test, creates no account, and posts nothing to GitHub.** Its product is a definition of the delegation record, a storage design checked against the tools that solve the same problem, a prototype in scratch, an experiment with fresh agents, and a rewritten BT32 outline. Detailed for a cook without deep reasoning.

## Why

The owner, 17 October 2026: agents must be able to map out the full lifecycle of the tool, "just like how in real life you pass a work to someone, you get it back, there's a reason why you do that, and the whole company understood that"; and "a lot of CLI tools or agent tools rely on the same exact problem… can't we research that?"

Where the design stands:
- **K25** measured what agents see and bounded it (BT28, BT29). **K26** placed every record field in three tiers (anyone; the project's agents on any machine; this machine only) and showed with fresh agents that the shared part carries what matters. **K27** measured `node:sqlite` as the local engine (BT31 builds it).
- **The shared store has been rejected twice by the owner, for real reasons:** a committed file (`shared.jsonl`) leaks into agents' ordinary work (search, diffs, reviews) and grows in every clone; GitHub issues are not built to be a project's memory and can be deleted by an admin. BT32 is **on hold** until this wave reports.
- **A first look at the field (CTO, 17 October 2026)** found that tools built to be an agent's memory of work converge on one shape: a local database for speed; sync through the repository's own Git remote **outside the project's files**; a small injected summary plus query commands; old closed work compacted. Beads (`steveyegge/beads`) keeps a local database in `.beads/` and syncs with `bd dolt push/pull` to `refs/dolt/data` on the Git remote, treating its JSONL file as "an export"; `bd prime` injects a small context, `bd ready` lists actionable work, "memory decay" summarises old closed work. git-bug (`git-bug/git-bug`) stores issues "as objects in a git repository (not files!)", syncs over normal remotes, works offline, "doesn't pollute your project", and bridges to GitHub. Task Master commits `tasks.json`; hosted memory services (Mem0, Zep, Cognee) suit general knowledge more than a tool's own work records.

These are leads to verify, not facts to rely on.

## Outcome

1. **The delegation record, defined:** the lifecycle events, the facts each carries, and the questions the record must answer at any time, by anyone on the project, on any machine, years later.
2. **A storage design** for the project-agents tier that keeps nothing in the project's files, is durable against deletion, needs no new account or program, and is built for the purpose, verified against how Beads and git-bug actually do it, with every claim cited.
3. **Evidence:** a prototype in scratch measured for push, fetch, merge and loss; and fresh agents answering the record's questions from it.
4. **A rewritten BT32 outline** the owner approves before anything is built.

## Method: six steps, in order, with a time budget each

**Step 1: the delegation record (40 minutes).** Write the lifecycle as events, from the owner's framing: decide to delegate; hand over; in flight (questions, solutions arriving); receive; decide (which solution merged, or none); close and settle (paid or not; the larger job resumed); and institutional memory. For each event: the facts it carries (who, when, what, why), its tier from K26, and who writes it. Then the **question list** the record must answer, at least:
- What is outstanding on this project, and who is waiting on what?
- Why was this handed off rather than done here? What had been tried?
- Which larger job does it belong to, and where did that job stand?
- What came back, from whom, and which was accepted?
- **Why does this code look like this?** (from a line of code, through its commit, to the bounty)
- Have we handed off something like this before, and how did it go?
- Was the solver paid?
Mark which questions today's design answers, and from where.

**Step 2: how the leaders store it (50 minutes).** For Beads and git-bug, read the current source documentation and storage specifications (not summaries) and record, with links and the date read:
- the exact objects and refs used (git-bug's entity format and ref namespace; Beads' `refs/dolt/data` and what Dolt stores there);
- how two machines changing the same item merge, and how they avoid id collisions;
- how a new clone gets the data (default `git clone` or an explicit fetch; which refspec);
- how deletion and force-push are handled, and what survives;
- how old items are compacted;
- what the agent sees unasked and by query;
- what they depend on (Beads on Dolt; git-bug on Git only).
Also read Git's documentation on custom refs and refspecs, and `git notes` (which GitHub shows on commit pages), and GitHub's documentation on whether rulesets or the web interface cover refs outside `refs/heads` and `refs/tags`. Add any other tool found that solves the same problem, with the same rows.

**Step 3: our storage design (35 minutes).** Propose, citing step 2 for each choice:
- **the event chains:** each bounty as its own chain of commits of small JSON events under its own ref (for example `refs/box-bounty/<id>`), as git-bug does, or one log ref, with the reason; the event schema from step 1; how events are signed by author (commit author) and trusted (only accounts with write access can push to the remote);
- **sync:** when the tool fetches (only for commands that show bounties, at most once a minute, as BT32 planned) and pushes (at milestones), with the exact refspecs; what happens when the push is rejected (fetch, merge, retry);
- **merge:** two machines appending to the same bounty's chain;
- **the local cache:** BT31's `node:sqlite` database rebuilt from the chains, never the source of truth;
- **the link to code:** the merge commit message carries the bounty id and a short why, so `git blame` reaches the record (read `answer.ts` for what the message holds today);
- **deletion and loss:** a deleted remote ref restored from any clone that holds it; a lost local cache rebuilt; what the tool says in each case;
- **drafts and machine detail** stay local (K26), never in a chain;
- **compaction:** what an old closed bounty's chain keeps.

**Step 4: the prototype (50 minutes).** In `kitchen/memory/delegation/`, scratch code, not product: create, append, fetch, merge and rebuild event chains with plain `git` commands (no dependency), against two scratch clones and a scratch bare remote. Measure and record:
- push and fetch time for one event, and a first fetch of 1,000 bounties' chains;
- repository size growth for 1,000 bounties with five events each;
- a concurrent append to the same bounty from both clones, then merge: no event lost;
- a deleted remote ref restored from a clone;
- a default `git clone` of the remote does **not** download the chains (say what it does download);
- `git grep`, ripgrep and `git log -p` on the default branch show nothing of the chains.

**Step 5: the agents' test (40 minutes).** Build a scratch project with a realistic history: about eight bounties across two larger jobs, some merged, one abandoned, one open, with merge commits carrying the link. Make two clones: **(a)** chains fetched by the prototype; **(b)** no chains, only the public issue texts as files. The head chef starts two fresh agents (the cook prepares the worlds and is not an agent), each given step 1's question list and told "answer from this project; use whatever is here." Score each answer as right, partly or wrong against the known history. The design passes if (a) answers every question right and clearly beats (b). If the head chef cannot start fresh agents, the Result says so and the worlds are left ready.

**Step 6: the report and the BT32 outline (25 minutes).** Recommend the design, with what it costs (time per command, repository size, the owner's setup: target none), its limits, and the BT32 outline: the event schema, the refs and refspecs, sync and merge rules, the cache rebuild, the merge-commit link, the behaviour tests (including K26's), and the measurements BT32 must reproduce. If the evidence favours a different store, say so plainly and recommend it instead.
