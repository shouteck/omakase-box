# BT11: a stated reward, and the solver's own payment link

Milestone: BT · Station: packaging (also evidence) · Base: master at the time this cooks, after BT10 is merged · Branch: `wave/BT11` · Timebox: 150 minutes; at expiry, report partial findings and stop

**Pre-brief.** Written by the CTO on 11 October 2026, while BT6's second run was cooking. The idea is the owner's and is settled; it is deliberately the simplest thing that could work. Command names, field names and file paths below follow the design discussion; the head chef revises this file against the Results of BT6 to BT10 before dispatching, and says in the pre-cook card what changed.

## The idea, as the owner put it

No bounty site in the middle. A bounty can state a reward. The issue tells the solver to put their own payment link in their pull request, Stripe links only to start. If the agent or owner decides a solver should be paid, the link is right there. **The tool never pays, never opens the link, and never holds or moves anyone's money.** It carries two facts (the amount the owner's rule states, and where the solver asked for it to be sent) and records a third (that the owner says it was paid).

## Who decides, and who pays

**The agent decides. The owner pays, by opening the solver's link** (owner, 11 October 2026). Whether a solver is worthy is the agent's judgement alone; no owner approves that. When the agent has marked a solver, it asks the owner to pay, with the amount, the solver and the link in front of them; the owner opens the link and completes the checkout; the payment is then recorded. That one action by the owner per payment is accepted for now.

An agent paying by itself is left out, in the backlog, until agent wallets work without a person: on that date Stripe's wallet for agents still needed the owner's approval for every purchase, and could only be tried with real money. Nothing in this wave builds toward it, and the tool's outputs name the owner as the one who pays.

## Outcome

1. An owner's standing rule can state a reward above $0, and every bounty posted under it says so.
2. The issue asks a solver who wants paying for one fixed line in their pull request.
3. Next to each solution the agent sees, as a fact, whether a recognised payment link was given.
4. One command marks a solver as to be paid and shows the amount and the link; one records that it was paid. Both are independent of using the solution.

## Done when

- `node scripts/verify.mjs test:box-bounty test:box-package` exits 0 on the final commit; the suites reach no network.

**The reward the owner states**

- The reward field in the standing rules (BT8) now accepts an amount above 0, in US dollars, as a whole number. It is still set only by the owner, at either level, and still never by the agent or by anything in the project. 0 stays valid and means what it means today.
- Every bounty posted under a rule states that amount, in the listing and in the readable block. No command lets an agent choose or change it for one bounty.
- The tool states no preference about amounts and suggests none.

**What the issue tells the solver**

- When the reward is above $0, the "how to answer" part of the listing adds, in plain words: the reward; that a solver who wants to be paid adds one line to their pull request description, `pay-to:` followed by their Stripe payment link, with a worked example; and that payment is the poster's decision and posting a solution does not guarantee it. The readable block says the same in fields a program can use, and the format's version changes with a note on the public page.
- At $0 none of this appears. The listing says "Reward: $0" and nothing about payment links, exactly as before this wave.
- A test pins the wording: no sentence in it promises payment, timing or selection.

**Reading the solver's line**

- The line is text written by a stranger and is treated as that. The tool reads only the pull request description, takes only the first line that starts with `pay-to:`, and accepts what follows only if it is exactly one address of the recognised kind: `https`, the host Stripe uses for its payment links, and a path of the shape those links have, with nothing after it. The worker confirms the current shapes from Stripe's own documentation and lists them in the doc page; anything not on that list is not recognised.
- What the agent sees next to each solution is one of four facts and nothing else from that line: a recognised payment link was given; a test-mode payment link was given (no real money moves through it); a `pay-to:` line was given that is not a recognised payment link; none was given. Unrecognised text is never echoed.
- **The tool never opens, fetches or follows the link,** at any step, in any mode. A test proves no network call is made with it. So the tool cannot know what amount the link asks for, and says so: when it shows a link it states the amount the owner's rule gives and that whoever pays must see that same amount at checkout.
- A link is shown in full only by the command that marks a solver as to be paid, and there it is on its own line, labelled as supplied by the solver.

**Deciding and recording**

- `reward <id> <n>` (or the name that fits) records the decision that solver `n` is to be paid, and prints, addressed to the agent, the few lines to put to the owner: the amount from the rule, the solver, and the solver's link to open. It refuses by name, changing nothing, if the reward is $0, if that solution gave no recognised link, or if the bounty is not posted. It does not require that the solution was used, merged or even looked at, and more than one solver may be marked: who is worthy is the agent's or owner's decision.
- `paid <id> <n>` records that the owner says the payment was made, with the time and an optional reference they supply. The record and every output call this what it is: recorded as paid on someone's word, not verified by the tool.
- `status` shows, per bounty: the reward, and for each solution whether a link was given, whether it is marked to be paid, and whether it is recorded as paid.
- Under standing rules, marking a solver to be paid needs no extra permission: it moves no money. Nothing in this wave lets the tool or the agent complete a payment.
- When the bounty is closed the tool's comment on the issue states only facts that are in the record: which solutions were used, and for each solver marked, whether payment is recorded. It never says a payment will be made.

**Everything else**

- **Cases that must fail, each a named refusal that changes nothing:** an amount in the rules that is not a whole number of dollars at or above 0; a reward field anywhere in the project; `reward` or `paid` for a solution that does not exist; `paid` for a solver not marked to be paid; `reward` on a solution whose line is not a recognised link.
- **A stranger's words are not the tool's words,** as since BT6: hostile text in the `pay-to:` line (a second address, text after the address, another scheme, a lookalike host, control characters, a very long line, a line placed in a comment or a file instead of the description) never reaches output except as "not a recognised payment link", and never reaches the hook.
- The three hard stops are unchanged. A never-ship path, a private repository and the owner's rules are not affected by a reward.
- Bounties, records and rules written before this wave load and read as $0.
- The description shown to agents gains at most one line. The doc page gains one section, including in plain words what the tool does not do: pay, verify a payment, hold money, or protect a solver from not being paid.
- Works on this Windows host from Git Bash and PowerShell, and on the off-machine runner.

## The real use: no real money

The owner's standing instruction for testing: prove the flow, spend nothing, the kitchen is the solver.

1. In a trial repository of the kitchen's own, with a trial settings folder: an owner's rule states a reward, a bounty goes out, two solutions come back (one with a recognised link, one with hostile text on the line), a collecting session marks one to be paid and records it as paid. All local or against stand-ins.
2. **One real bounty on `shouteck/omakase-box`,** from the main checkout with the merged tool. Its title and first line say it is a test bounty by the repository's owner, to be solved by the owner, and that no real money will be paid; real people can read it and must not be misled. The stated reward is $1. **The owner sees the exact issue text and says "go" before anything is posted.**
3. The kitchen's blind solver opens the pull request with a `pay-to:` line carrying a **test-mode** Stripe payment link. **The owner made one for this, in test mode, on 11 October 2026, for $1:** `https://buy.stripe.com/test_28E7sLbHrbu70eC5C5afS00`. Use exactly that. It moves no real money and is safe to appear in a public pull request. No agent creates a Stripe account, signs in to one or makes a link. If the link has stopped working by the time this cooks, tell the owner; do not substitute another.
4. A collecting session, new and told nothing, sees the fact "a test-mode payment link was given", marks the solver to be paid, and stops. **No agent opens the link, enters any payment detail or completes any checkout,** test mode or not. This is the product's real flow: the collecting session asks the owner to pay, showing the amount, the solver and the link. The owner has said they will complete the test checkout themselves, with one of Stripe's published test cards; the kitchen waits. No agent enters card details on a payment page, test cards included. On the owner's word that it went through, `paid` is run and the flow is complete end to end. If the owner is not available, the wave closes with the solver marked and nothing recorded as paid, and says so.
5. Closed with the tool's own commands. Anything left on GitHub is listed in the Result by exact name.

What this proves: every step the tool takes around a reward, on real GitHub. What it does not prove: that a real stranger will supply a link, that a real payment completes, or anything about an agent paying by itself. The Result says exactly that.

Nothing in this wave is posted or closed overnight.

## Review lenses

- [x] **Security:** the `pay-to:` line is the first place a stranger's text sits next to money. The reviewer tries to get a link of its choosing shown as recognised (lookalike hosts, mixed scripts, user-info in the address, redirects written into the path, a second line, encoded characters), to get any text from the line into `status`, the hook or the issue comment, to make the tool fetch the address, to get an amount from anywhere but the owner's rule into a listing or an output, and to get something recorded as paid without the `paid` command. It confirms no payment detail, of anyone, is read, stored or printed.
- [x] **User experience:** three readers, each fresh. A stranger with only the issue says what the reward is, exactly what line to add and where, and what it has and has not been promised. An agent with two solutions waiting and only the tool's output says which can be paid through a link and which cannot, marks one, and says what happens next and who does it. An owner, played by the reviewer with only the `reward` output in front of them, says what they are about to pay, to whom, how they know the address came from the solver, and what the tool has and has not checked.
- [ ] **Measurement fairness:** not applicable.

## Notes for the worker

- Feature playbook. This wave is small on purpose. If it grows a wallet, a verifier, an escrow, a second payment provider or a budget, it has gone wrong.
- The parser for the line is the security boundary. Write it as an allow-list of exact shapes, with the tests first, and reject by default.
- Every output about money is a fact with its source: "from your rule", "supplied by the solver", "recorded on your word". BT3a's banned-words test covers them all.
- Do not make marking a solver depend on the solution having been used. The owner settled that these are independent.
- Out of scope, each a later decision of the owner's: an agent paying by itself with a wallet or a capped card (in the backlog until agent wallets work without a person); any payment provider other than Stripe links; checking that a payment happened; a ceiling or budget (nothing in this wave can spend); disputes; any bounty site.
- Everything the wave creates in the temp folder or on the remote is named for the wave or the bounty and removed at close.
