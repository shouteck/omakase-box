## The tests

1. **T1:** run every command that does not change a bounty's state (`status`, `status --full`, `status --json`, `find`, `describe`, `help`, `config`, `hook start`, `look` on an already-collected solution) twice in a project with an open bounty and the instruction block enabled; the instruction file's bytes and modification time are identical before and after. Then change a fact (post a bounty, or collect a solution) and show the block changes.
2. **T4:** for the same list of reading commands, in a project whose bounty has a chain on a local bare remote (BT32's setup), the remote's `refs/box-bounty/*` refs and the local chain tips are identical before and after; no push happened (count transport calls through the existing spy or compare ref SHAs).
3. **C5:** after `create`, the snapshot commit the plan names resolves (`git cat-file -t <sha>` is `commit`), and its tree is the captured working state (compare with the files `create` reported). Choose the form the current code actually keeps; read `snapshot.ts` and BT24's Result first, because BT24 stopped pinning the snapshot for new drafts. **If the guarantee no longer holds as written, do not write a test that pretends it does: report it, and the CTO corrects CONTRACTS.md.**
4. **PL3:** a table-driven test that triggers a representative refusal from each stage (at least one per stage, from `CONTRACTS.md`'s refusal lists) through the built CLI and asserts each prints a `next:` line or names a command to run, and exits non-zero. List in the Result any refusal that does not, and do not change product code to fix it here (the CTO briefs it).
5. **Bite:** for T1, T4 and PL3, break the guarantee once in a scratch copy outside the checkout (for example make a read write the block, push a chain on a read, drop `next:` from one refusal), show the new test fails, discard the copy.
