# K20: the tool against the command-line conventions it should follow

Milestone: K (kitchen) · Station: evidence · Base: master at dispatch, after BT15 and BT16 · Branch: `wave/K20` · Timebox: 90 minutes; at expiry the cook stops and reports what it has

**Pre-brief.** Written by the CTO on 14 October 2026 at the owner's request: "we can take inspiration from these successful CLI tools." An investigation: **it changes no product code and no test.** Its product is a list the owner decides from. It cooks only when named.

## Why

The tool's design has been checked against convention piece by piece, often only when the owner asked. A CTO audit on 14 October found it follows `git`, `gh`, `npm` and `direnv` in most places and departs in some: no machine-readable output, a `config` listing in prose where `git config --list` prints `key=value`, a waiting post that exits with success, and `--help` not confirmed on every command. Since that day the wave template asks every brief to name the convention a command change follows; this wave measures the whole tool once against that standard.

## Outcome

One page that says, command by command, where the tool matches the conventions people already know, where it departs, whether each departure is deliberate and still right, and what the owner could change, in order of what an agent or owner would notice most.

## Scope

- Write: `waves/K20.md` (the Result) and `kitchen/reviews/K20-conventions.md`. Scratch work in `kitchen-K20-*`, removed at close.
- Read: the built tool, `docs/box-v4/BOUNTY.md`, PLAN.md "Other rules of the product", `kitchen/reviews/K18-flow-critique.md`. The reference tools' own documentation, and the tools themselves where installed on this machine (`git`, `gh`, `npm`), run read-only.
- Do not touch: product code or tests; the owner's real settings (use `BOX_BOUNTY_SETTINGS_DIR` for every run); GitHub beyond the sandbox, and nothing posted there.

## Done when

- `node scripts/verify.mjs test:kitchen` exits 0 on the final commit.

**Checked for every `box bounty` command**, each against the closest established command (named in the report) and with the evidence (the command run, the output quoted):

- **Help:** does `--help` work on every command and print usage, with exit 0? Does `help <command>` work? Is the top-level help short, with the common commands first?
- **Machine-readable output:** is there a `--json` or equivalent where an agent would want to parse the result (`status`, `look`, `config`)? `gh` and `npm` both offer one; the agent-testing research of 13 October found structured output helps agents.
- **Exit codes:** 0 for done, non-zero for refused or not done, distinct codes where a caller needs to tell cases apart; what a waiting state returns, and whether it should differ.
- **Output streams:** results on standard output, refusals and warnings on standard error.
- **Flags:** long names with a consistent shape; `--flag=value` and `--flag value` both accepted; `-` meaning standard input where a file is read; no option that does what another already does.
- **Settings:** how `config` lists and changes settings, against `git config` and `npm config`.
- **Quiet by default:** what a successful command prints when nothing needs attention.
- **Destructive or public actions:** what is shown before them, against `gh`'s confirmation and `--yes` conventions in non-interactive use.
- **Version:** does `box --version` or `box bounty --version` print one, as nearly every CLI does?

**The report** (`kitchen/reviews/K20-conventions.md`):

- **One page first, for the owner:** the departures an agent or owner would notice most, at most seven, each in two sentences with a recommendation; then the conventions the tool already follows well.
- **The table:** one row per command and convention: matches, departs deliberately (with the reason given in PLAN.md or a wave file, quoted), or departs without a recorded reason.
- **Each recommendation names the convention and the tool it comes from,** and what following it would cost (new output to maintain, a removal, a change agents would notice).
- Departures already recorded as deliberate are not re-argued unless the evidence shows the reason no longer holds.
