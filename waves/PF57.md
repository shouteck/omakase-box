# PF57: the board stops creating bounties of its own; the ones it listed run until they close

Milestone: platform · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF57` · Timebox: 240 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-board-only-what-needs-a-website, D-2026-11-04-dual-usage
Horizon: medium: a removal across the board. Refactoring playbook; principles: subtract-before-you-add, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the board. The owner asked to keep the board simple, approved the recommendation and asked for the waves ("Sure. You can create the waves in the briefs"). This is a removal, so by the kitchen's rule it waits for the owner's "go" before it is cooked.

**Why.** The board has grown a second way to create bounties, beside the tool's:
- an owner lists an existing GitHub issue from the board (PF32);
- an approval comment admits it (PF44);
- agents import an issue, or prepare and approve a packaged branch, without the tool (PF52, PF53).

It touches 55 files, 86 places in `src/refresh.ts` alone. It has its own payment rule: the owner chooses whom to pay from every linked pull request, merged or not, where the tool's rule is that the merge takes all. It also has special cases in the feed (`way_in`, `closes_issue`), in `take` (`closesIssue`) and in payments.

It was added on 4 November 2026 to seed supply (D-2026-11-04-dual-usage). The new decision replaces that decision's "way in" half; everything after a merge stays shared. The product is the bounty tool, and the board should do only what needs a website: let strangers find work, and let a person do the steps only a person can.

## Outcome

1. **No new bounty is created through the board.** These answer `410 Gone`, with one line naming the way that remains: "Bounties are posted with the tool: npm i -g omakase-box, then omakase-box create and post. Nothing changed."
   - `POST /api/list`, `POST /api/import`;
   - `GET /auth/github/list` and its callback;
   - `POST /api/agents/prepare`, `POST /api/agents/import`.

   An approval comment on an issue never seen before admits nothing.
2. **Bounties already listed this way keep working until they close.** They are still read, shown, taken (`take`'s `closesIssue`) and paid under their own rule, so no solver or owner already in one is stranded. A listed bounty that closes is not replaced.
3. **The ways to create are gone from every surface:**
   - the "list an issue" part of your page (`components/ListIssue.jsx` and its place in `MeView.jsx`);
   - the import and prepare instructions in `llms.txt` (`src/llms.ts`) and on the agents page;
   - `docs/box-v4/PLATFORM-UX.md` and `SOLVER-DISTRIBUTION.md`;
   - the board's README;
   - the skill the tool writes and publishes. `SKILL_TEXT` in `packages/box-bounty/wording.ts` and `docs/box-v4/launch/skill-repo/skills/omakase-box/SKILL.md`, kept identical by `pf6.test.ts`, both say "Imports only: GitHub comment `omakase approve <id> $<reward>`". That line goes. Bump the skill's `version`, and say in the Result that the published skill repository needs the same change pushed (the owner's step, if that repository is separate).
4. **The code that only *created* listings is removed** (`src/listing.ts`'s write side, `src/agent-prepare.ts`, `src/agent-import.ts`, `src/agent-input.ts`, `src/agent-branch.ts`, the admission paths in `refresh.ts` for a listing not yet held). The code that *reads* an existing listing stays.
5. **A backlog line** names the rest of the cleanup and its trigger: no listed bounty open on the live board. At that point, `readListedIssue`, `readLinkedPulls`, the listed payment rule and `take`'s `closesIssue` go too.
