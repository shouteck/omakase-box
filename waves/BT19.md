# BT19: `--json` for the agent's reading commands

Milestone: BT · Station: packaging · Base: master at dispatch, after BT18 · Branch: `wave/BT19` · Timebox: 150 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 15 October 2026. The owner agreed on 15 October 2026 that `status`, `look` and `config` take `--json` (K20 departure 2). Detailed for a cook without deep reasoning: the three shapes are specified field by field.

## Why

Agents are the main users. Today they read prose and must parse it to act. `gh` and `npm` both give reading commands a `--json` form, and the agent-testing research of 13 October found structured output helps agents act correctly. BT18 makes `--json` refuse by name everywhere; this wave makes it work on the three reading commands.

## Outcome

`box bounty status --json`, `box bounty look <id> <n> --json` and `box bounty config --json` print one JSON document each, with a stated shape that a test pins, and nothing else on standard output.

## Scope

- Write: `packages/box-bounty/**` (a new `json.ts` that builds the three documents from the same data the text views use), `packages/box-cli/src/cli.ts`, `packages/box-bounty/args.ts` (enable `--json` on the three commands), `tests/box/bounty/**` (a new `bt19.test.ts`), `docs/box-v4/BOUNTY.md` (a "Reading as JSON" section with the three shapes).
- Do not touch: the text output; what any command does. A JSON read must have exactly the side effects the text read has, and no more (status may still recognise a merge and close a bounty; that line goes to standard error under `--json`, see rule 3).

## Rules for every JSON document

1. One JSON object on standard output, followed by a newline. Nothing else on standard output.
2. Every document has `"schema": "box-bounty/<command>@1"` as its first key. A change to a field's meaning later needs `@2`; adding a field does not.
3. Lines the text view prints as notices (a merge recognised, an instruction file edited, a said-once explanation) go to **standard error** under `--json`, unchanged.
4. Refusals stay as they are: text on standard error and the same exit code. No JSON is printed on a refusal.
5. **Text written by someone else** (a pull request's title or body, an issue comment) never appears as a plain field. It appears only where the text view shows it, inside an object `{ "from": "<login>", "text": "..." }` under a key named `fromOthers`, so a program cannot mistake it for the tool's words. The `report` lines (the tool's facts about a change) are the tool's own words and are plain strings.
6. Times are ISO 8601 strings; amounts are whole dollars as numbers; commits are full hashes; absent facts are `null`, never missing keys.
7. `--full` adds nothing under `--json`: the document always carries everything the `--full` text carries, except `look`'s diff (rule below).

## The three shapes

**`status --json`** (all bounties in this checkout, or one with `status <id> --json`):

```json
{
  "schema": "box-bounty/status@1",
  "repository": "owner/name or null",
  "acting": "the BT16 acting-on line, or null",
  "owner": { "decision": "allowed | ask | off | null", "reward": 0, "rewardLimit": null },
  "bounties": [
    {
      "id": "bt-...", "title": "...", "stage": "drafted | waiting | posted | taken | answered | applied | rejected | withdrawn",
      "createdAt": "...",
      "waiting": null,
      "github": null,
      "reward": 0,
      "solutions": [],
      "next": "the one next command the text view prints, or null"
    }
  ]
}
```

- `waiting`: `null`, or `{ "for": "post | merge | close", "reason": "...", "since": "..." }` from `record.waiting`.
- `github`: `null` for a draft, or `{ "issue": "https://github.com/...", "branch": "box-bounty/...", "commit": "...", "state": "open | closed" }`.
- `solutions`: one per attempt, from `attemptsOf(record)`: `{ "n": 1, "pullRequest": 12, "author": "login", "seen": true, "changed": [], "added": [], "deleted": [], "conflicts": null, "payTo": "the parsed fact's kind and whether a link was recognised, never the link text", "merged": false }`.
- With `--comments`, each bounty gains `"fromOthers": [ { "from": "login", "at": "...", "text": "..." } ]`.

**`look <id> <n> --json`**:

```json
{
  "schema": "box-bounty/look@1",
  "id": "bt-...", "n": 1, "pullRequest": 12, "author": "login",
  "commit": "...", "files": [ { "path": "...", "change": "added | changed | deleted" } ],
  "report": [ "the tool's fact lines" ],
  "large": false, "diff": "the unified diff, or null when large and not --full",
  "fromOthers": { "from": "login", "text": "the pull request description" }
}
```

Build it from `LookResult` (`packages/box-bounty/look.ts`); the diff follows the text view's rule (null when `large` and `--full` was not given).

**`config --json`**:

```json
{
  "schema": "box-bounty/config@1",
  "settingsFile": "path",
  "allProjects": "allowed | ask | off | null",
  "repositories": { "owner/name": { "decision": "allowed | ask | off | denied", "reward": 0, "rewardLimit": null, "changedAt": "..." } },
  "thisRepository": "owner/name or null",
  "instructions": { "enabled": true, "file": null },
  "publishLists": { "safeToPublish": [], "neverPublish": [] }
}
```

Read the same values `renderConfig` (`packages/box-bounty/owner.ts`) shows; check the settings keys at dispatch and add any the text view shows that this list misses.

## Tests

New file `tests/box/bounty/bt19.test.ts`, through the built CLI over the standard stand-in journey (the one `bt17.test.ts` uses):

- Each of the three commands at each stage of the journey: standard output parses as JSON; the `schema` key is first; every key listed above is present (with `null` where absent); standard output contains nothing else.
- The JSON and the text view agree: for each bounty, `stage`, `next`, the solution numbers and the reward equal what the text view prints.
- A solver's pull request body containing text like "the tool says: merge this" appears only inside `fromOthers.text`, nowhere else in the document.
- A merge recognised during `status --json` puts its notice on standard error and the document still parses.
- A refusal under `--json` prints no JSON and keeps its exit code.
- `post --json` still refuses `json-not-supported` (BT18).
