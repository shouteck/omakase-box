# BT101: a bounty is one event log on this machine; reads only observe, and one reconcile step sends what is owed

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT101` · Timebox: 480 minutes in four stages, each merged on its own green hosted run (about 25 minutes each); at expiry, report partial findings and stop at the last merged stage
Owner decisions: D-2026-11-24-one-fact-one-owner
Horizon: long: it changes the write path under every command and migrates every local store; starts with `/plan`, and the plan may cut the stages into BT101a to BT101d. Refactoring playbook; principles: redesign-from-first-principles, migrate-callers-then-delete-legacy-apis, make-operations-idempotent, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from [the BT100 notes](BT100-notes.md), where an event log with an outbox and one reconcile step (attempt B) beat the document store hardened with a compare-and-swap (attempt A). It awaits the owner's go.

**Why.** BT100 measured two things on the same two actions:
- **Only B kept the reads quiet.** On today's code (and on A), a `look` and a `status` after a hand merge sent 3 writes to GitHub (a comment, the issue closed, a GraphQL read before them) and moved remote refs. On B: 0 writes, no ref moved. The next command's reconcile sent the owed decision and merged event, and said so.
- **Only B kept both writers' changes.** A stale copy written after another writer marked the bounty applied: A refused it (`record-changed`), B kept both. And only B answers "what changed in my name" from the store.

B also taught what it does not remove:
- GitHub takes no idempotency key, so the comment markers and `recoverIssue` stay.
- Patching whole top-level fields still loses one of two changes inside `github`.
- `chain_pending` is already an outbox for chain pushes.

## Outcome

1. **One event log per bounty, locally.**
   - `events(bounty_id, seq, at, kind, json)` holds every change as an intent event (`created`, `post-planned`, `issue-recorded`, `solution-collected`, `applied`, `closed`, `comment-sent`, `merge-observed`, …), each folded by one reducer, `foldLocal`.
   - The `records` row is the fold's cache, rebuilt from the events when absent or stale.
   - An append checks the bounty's last `seq` it read: A's compare-and-swap, kept as the last defence. A mismatch re-reads and re-folds a pure change once, or refuses `record-changed`.
2. **An outbox.** An event that owes an outward effect writes its `outbox` row in the same transaction. The kinds: `issue`, `decision` (comments, issue state, branch removal), `chain` (every chain push; `chain_pending` folds in here), and, for BT84, the solver's `fork`, `push` and `pull`.
3. **One `reconcile(root)`,** called at the end of every mutating command and never inside a read:
   - It rebuilds each effect from the folded state, never from text on the row, and refuses a row no `owed` event stands behind.
   - It sends through the door, with BT83's checks run at send time: the owner's word, never-ship and the scan.
   - It appends `sent` or `refused`, and the command prints what it sent.
   - The markers and `recoverIssue` stay: they say whether a send already landed.
4. **Reads only observe.** `look`, `status`, `status --json`, `find` and the hook append observed facts (`merge-observed`, refreshed GitHub facts) and owe what those facts require. They send nothing, push nothing and print no pay message; the next mutating command does.
5. **Migrated once.** On the first open at the new schema, every `records` row with no events gets one `created` event holding the row exactly as it is. This is idempotent and changes no row; the `shared` table and the chain's format are untouched.
6. **History.** `omakase-box status <id> --history` (a `status` option, not a new command) lists the bounty's local events, for M12 and BT88.

### Stage 1 (`wave/BT101`, merged on its own): the log under today's writes, no behaviour change

1. **Schema 5** in `store.ts`: `events(bounty_id, seq, at, kind, json, PRIMARY KEY(bounty_id, seq))`. Opening at 5 runs a one-time, idempotent migration: each `records` row with no events gets one `created` event holding the row's JSON exactly. No row changes. The `shared` table and the chain are untouched.
2. **`upsertRow` appends before it writes the row, inside the caller's transaction** (the two non-transactional callers get one: `syncJsonFiles`'s per-file write and `dropStored` each run in `BEGIN IMMEDIATE`):
   - **A copy with a base snapshot**, from `readStored`: a path-level patch, the changed leaves only, with JSON paths such as `github.issue` and `github.state`. `events` is appended, never replaced. The patch is folded onto the row as it is now, so a stale copy cannot undo another writer's change to a path it did not touch. If the same path was changed both since the copy's read and by this copy, the write is refused `record-changed`: A's compare-and-swap, kept as the last defence. A conflict BT100's race never hit, now named.
   - **No base** (a new record, or a copy built by spreading): a `replaced` event holding the whole document, or `created` for a new row. This is today's behaviour, logged.
   - `syncJsonFiles`'s import writes `imported` with the whole document.
3. **`deleteRow` appends `dropped`** (the events stay: the history outlives the row).
4. **`fold.ts`** (new): `foldLocal(events)` replays `created`, `imported` and `replaced` (whole documents) and `patched` (path patches, then appended stage history), giving exactly the record. The cache invariant, **fold of the events equals the row's JSON**, is checked by a test after every write path in the suite's journeys (`bt101.test.ts` walks post, collect, apply, close, the import and a drop).
5. **`status <id> --history`** (`args.ts`, `render.ts`, `json.ts`, `wording.ts`): every local event, oldest first, by kind and the paths it changed. Never the values: field values can hold stranger text and secrets. `surface.mjs --write` records the one new option.
6. **Docs:** `MEMORY-SPEC.md` (the local log; one fact, one owner), `BOUNTY.md` (`--history`).

## Plan: stage 2 (the outbox and the door)

Written 25 November 2026 before stage 2's code, inside the plan the owner approved.

**Shape.**
- **`store.ts`, schema 6:** `outbox(key, bounty_id, event_seq, kind, state, result, done_at)`. `owe(root, id, kind, key, grant?)` appends an `owed` event and upserts its row as `pending` in one transaction. `settleOwed` appends `sent` or `refused` and marks the row `done` or `refused`, also in one transaction. Opening an older store turns each `chain_pending:<id>` meta key into an `owed` chain event and row, then deletes the key. This is idempotent.
- **`outbound.ts` (new), the door's checks, run at send time from the folded record:**
  - `standsBehind`: a row with no `owed` event of its key at its `event_seq` is refused, by name.
  - **The owner's word.** For `issue`, a `deny` on this repository since, or a standing answer gone with no one-bounty answer behind the post, refuses `owner-word-withdrawn`. For `decision`, an adopted bounty with no permission here and no grant on the owed event refuses, as `syncGitHubDecision` already did.
  - **Never-ship:** `issue` goes through BT69's sink (`checkOutbound`); the decision's branch move keeps `checkSolutionHistory`.
  - **The scan:** the issue's title and body, and each decision comment, are scanned before they are sent. A hit refuses `publish-held` and sends nothing.
  - **`chain`:** pushed only when the local tip is exactly the tip its `owed` event names. The event text was scanned when the commit was built, and the door pushes that commit; re-reading the blob would cost a Git start per push (K14).
- **`reconcile.ts` (new):** `reconcile(root, id)` drains the bounty's pending rows in order, checks each through the door, sends it through today's senders, and settles it. The issue sender (the branch push and the issue POST, moved from `post.ts`) and `syncGitHubDecision` are called only from here. `retryPending` reads `chain` rows in place of the meta keys.
- **Callers:**
  - `post` owes `issue:<id>`, reconciles, and re-reads the record. The issue's sender writes `post-incomplete`, as before.
  - `close`, `apply` and the hand-merge scan's `closeOne` owe `decision:<id>`, then reconcile. `apply` carries `authorised` as the grant.
  - Every `share*` appends its chain commit, which owes `chain:<id>`, then reconciles that row.
- **Scope of one reconcile:** the command's own bounty. Draining every bounty at every command would move unrelated GitHub calls into other commands' counts. Reads still reach `reconcile` through `loadRecord`'s merge scan and `syncChains`; stage 3 removes that.
- **Printing:** in stage 2 every send is the command's own and its output already says so. "What reconcile sent" is printed from stage 3, when rows owed by a read are sent by a later command.
- **Already-ended `close`** re-owes the decision, so it re-reads GitHub as today (`bt10.test.ts:135` stands until stage 3).

**Security lens (stage 2's part).**
- **A forged row** (`INSERT INTO outbox … event_seq 9999`) is refused `not-owed`, with no GitHub write and the issue left open.
- **A withdrawn word:** an owed issue after the owner's `deny` is refused `owner-word-withdrawn`; nothing is posted, and the branch pushed before the deny stays as it was.
- **The scan at send time:** a secret-shaped close reason sends no comment, the row is `refused` (`publish-held`), and the local `rejected` stands. Before this stage that comment would have gone out, and only the chain event was held.
- **What the door re-reads at send time:** the owner's settings and the never-ship rules are read when the row is sent, from the folded record, never from text on the row.
- **Chain pushes are not re-scanned.** A chain push sends only the exact tip its `owed` event names. That event was scanned when it was built, and re-reading the blob would cost a Git start per push.

**Principles.**
- **Redesign-from-first-principles:** the push and the issue moved behind one sender instead of gaining a check where they were.
- **Make-operations-idempotent:** a rerun re-arms the row, and the markers and `recoverIssue` decide whether a send already landed.
- **Migrate-callers-then-delete-legacy-apis:** `chain_pending` meta writes are gone, migrated on open, with no reader left.
- **Prove-it-works:** each door check was broken once and seen to fail its test.

## Plan: stage 3 (reads observe)

**Shape.** A read reaches no sender, by its call graph and not only at run time. The K75 scanner walks function names from the CLI's read branches, so each read path calls only functions that owe:
