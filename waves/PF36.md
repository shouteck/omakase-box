# PF36: the board measured at size, and the route past its ceiling chosen from numbers

Milestone: PF (the platform) · Station: evidence · Base: `master at dispatch` · Branch: `wave/PF36` · Timebox: 240 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k49-answers, D-2026-11-01-pay-on-merge, D-2026-10-22-k43-decisions
Horizon: long: start with `/plan` and keep the plan in this file. Investigation playbook; this wave changes no product code.

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md). The tool was measured at size ([K39](K39.md)); the board never was. What is known:

- The Worker spends 2 GitHub reads a minute (`worker.ts` `SLICE.tickReads`) because Workers Free allows 10 ms of CPU a run: 120 reads an hour.
- Search stops completing past about 200 issues ([PF8](PF8.md)).
- [PF28](PF28.md) fixed one bounty stalling the rest; it did not raise the rate.

K49 estimated that past a few dozen open bounties the board cannot keep "every 15 minutes" for a merge it was not told about. That is an estimate. A redesign should not start from one.

## Outcome

A report, `kitchen/reviews/PF36-board-scale.md`, that says for 100, 1,000 and 10,000 open bounties: how stale a bounty gets, how long a merge waits before pay on merge sees it, what each page and feed read costs, and which free-plan limit is hit first. Then the candidate routes compared on those numbers, with one recommendation for the owner.

## Done when

- The measurement runs on a local board against the stand-in GitHub, filled with generated bounties in realistic shapes (open, with attempts, merged, closed, listed), at each of the three sizes. It reports, per size: reads needed for one full pass; passes per day at 2 reads a minute; the age of the stalest bounty at steady state; rows read and written per run and per day; the time and rows of `/bounties.json`, a detail, `/numbers.json` and the board page.
- Each free-plan limit is quoted from the provider's own page read on the day, with its address: Workers Free CPU and requests, D1 rows read and written and database size, GitHub's rate limits for a token and for search. A limit not found is "not found", not a guess.
- **What a local run cannot show is said:** Cloudflare's real CPU time and D1's real latency. Where a number matters, name the one read-only check on the deployed board that would confirm it, for the owner to allow.
- The routes compared in one table on the measured numbers: stay as it is; conditional requests (does GitHub count a 304 against the limit: quote its documentation) and batching; a scheduled GitHub Actions job as the reader; a GitHub App with webhooks. **Every route stays at $0** (owner, 10 November 2026: "it will still be at $0"); a paid plan is not a candidate and is not priced. For each: the size it carries, what it costs in steps for an owner, what it changes in who the board trusts, and how much code it touches.
- One recommendation, with the size at which it must be in place, stated as a trigger the numbers page can show.
- `node scripts/verify.mjs test:kitchen` exits 0 on the final commit.

## Steps, in order, each with a time limit

Written so any model can cook it. This is an investigation: it writes a report and a script, and changes no product code. When a step's time is up, write what you have and move on.

1. **Read the reader (30 minutes).** `packages/box-platform/src/worker.ts` (the minute tick and `SLICE.tickReads = 2`), `refresh.ts` (what one pass reads per bounty: the issue, its pull requests, the shared record, checks), `github.ts` (how reads are counted and limited). Write in the report: for one open bounty with N pull requests, how many GitHub reads one full refresh of it costs, as a formula with the lines it comes from. This formula is the centre of the report.
2. **Quote the limits (30 minutes).** From each provider's own page, read on the day, with the address: Workers Free (CPU per request, requests per day, cron triggers), D1 free (rows read and written per day, storage), GitHub REST (requests per hour for a token; whether a `304 Not Modified` to a conditional request counts against the limit; the search limit). A limit you cannot find is written "not found".
3. **The script (60 minutes),** `kitchen/demo/pf36-scale.mjs`. It uses the test rig (`tests/platform/support.ts` `rig`) so it runs the real refresh against the stand-in GitHub:
   - fill the stand-in with N bounties in a stated mix (suggested: 70% open with no pull request, 20% open with one to three, 5% merged, 5% closed; one in ten listed from an issue);
   - run the refresh tick by tick with the clock moved one minute each time, until every bounty has been read once: count ticks and GitHub reads;
   - then keep going for a simulated day and record, per bounty, the longest gap between two reads;
   - time `/bounties.json`, one detail, `/numbers.json` and `/api/board`, and count the database rows each reads (wrap `DB.prepare` as PF34's test does).
   Run at N = 100, 1,000 and 10,000, three times each. If 10,000 does not finish in the timebox, report the largest that did and extrapolate with the formula, labelled as an estimate.
4. **The table of results (20 minutes).** Per size: reads for one full pass; minutes for one full pass at 2 reads a minute; the stalest bounty at steady state; the longest a merge waits before pay on merge sees it; rows read and written per day against D1's limit; which limit is hit first, and at what N.
5. **The routes (60 minutes).** One table, one row per route, filled from the numbers and from documentation, not from preference:

   | Route | What changes | Size it carries (from the formula) | Steps added for an owner | Whom the board must newly trust | Code touched |
   |---|---|---|---|---|---|
   | Stay as it is | nothing | | none | nobody | none |
   | Conditional requests and batching | the reader sends `If-None-Match`; unchanged bounties cost less or nothing | depends on step 2's answer about 304s | none | nobody | `github.ts`, `refresh.ts` |
   | A scheduled GitHub Actions job as the reader | reads happen in a workflow on our repository with its own token and limit, and post results to the board | | none | the workflow's token | new workflow, a write endpoint |
   | A GitHub App with webhooks | GitHub tells the board when something changes | | install an App on each repository | the App | large |

   Every route stays at $0. No paid plan appears in the table.
6. **One recommendation (20 minutes):** the route, the size at which it must be in place, and that size written as a trigger the numbers page already shows (for example "open bounties passes N"). If the numbers say the board is fine well past any size the launch could reach, the recommendation is "stay as it is, revisit at N", and that is a good result.
7. **Close:** the report at `kitchen/reviews/PF36-board-scale.md`; BACKLOG gets one line pointing to it; `node scripts/verify.mjs test:kitchen` green.
