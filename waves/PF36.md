# PF36: the board measured at size, and the route past its ceiling chosen from numbers

Milestone: PF (the platform) · Station: evidence · Base: `master at dispatch` · Branch: `wave/PF36` · Timebox: 240 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k49-answers, D-2026-11-01-pay-on-merge, D-2026-10-22-k43-decisions
Horizon: long: start with `/plan` and keep the plan in this file. Investigation playbook; this wave changes no product code.

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md). The tool was measured at size ([K39](K39.md)); the board never was. What is known:

- The Worker spends 2 GitHub reads a minute (`worker.ts` `SLICE.tickReads`) because Workers Free allows 10 ms of CPU a run: 120 reads an hour.
- Search stops completing past about 200 issues ([PF8](PF8.md)).
- [PF28](PF28.md) fixed one bounty stalling the rest; it did not raise the rate.

K49 estimated that past a few dozen open bounties the board cannot keep "every 15 minutes" for a merge it was not told about. That is an estimate. A redesign should not start from one.

## Outcome

A report, `kitchen/reviews/PF36-board-scale.md`, that says for 100, 1,000 and 10,000 open bounties: how stale a bounty gets, how long a merge waits before pay on merge sees it, what each page and feed read costs, and which free-plan limit is hit first. Then the candidate routes compared on those numbers, with one recommendation for the owner.

## Done when

- The measurement runs on a local board against the stand-in GitHub, filled with generated bounties in realistic shapes (open, with attempts, merged, closed, listed), at each of the three sizes. It reports, per size: reads needed for one full pass; passes per day at 2 reads a minute; the age of the stalest bounty at steady state; rows read and written per run and per day; the time and rows of `/bounties.json`, a detail, `/numbers.json` and the board page.
- Each free-plan limit is quoted from the provider's own page read on the day, with its address: Workers Free CPU and requests, D1 rows read and written and database size, GitHub's rate limits for a token and for search. A limit not found is "not found", not a guess.
- **What a local run cannot show is said:** Cloudflare's real CPU time and D1's real latency. Where a number matters, name the one read-only check on the deployed board that would confirm it, for the owner to allow.
- The routes compared in one table on the measured numbers: stay as it is; conditional requests (does GitHub count a 304 against the limit: quote its documentation) and batching; a scheduled GitHub Actions job as the reader; a GitHub App with webhooks. **Every route stays at $0** (owner, 10 November 2026: "it will still be at $0"); a paid plan is not a candidate and is not priced. For each: the size it carries, what it costs in steps for an owner, what it changes in who the board trusts, and how much code it touches.
- One recommendation, with the size at which it must be in place, stated as a trigger the numbers page can show.
- `node scripts/verify.mjs test:kitchen` exits 0 on the final commit.
