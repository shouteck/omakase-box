# BT55: a file's name cannot break the tool

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT55` · Timebox: 120 minutes; at expiry, report partial findings and stop
Owner decisions: none
Horizon: short

**Brief.** Written by the CTO on 10 November 2026 from [K48](K48.md). Two faults a solver's file name can cause, both in BACKLOG since October ([BT43](BT43.md) pass 6, [BT48](BT48.md)), neither yet reproduced through a command. Bug-fix playbook: reproduce first; a fault that does not reproduce is reported as such and left.

## Outcome

A solution containing a file with an unusual name does no lasting harm: after it is merged, `create` still works; after it is refused, nothing of it stays in the owner's working tree.

## The two faults

1. **A quote in a name stops every later `create`.** On git 2.43, `ls-tree -z --format=%(path)` still quotes a name that holds a quote character (`create.ts:308`), so once such a file is on the branch every `create` refuses `unreadable-path`. One merged file ends the tool's use on that repository until someone renames it. Git refuses such a name on Windows, so this shows on Linux and macOS only.
2. **On Windows a refused merge can leave a solver's file behind.** `rmSync` on Node 24.11.0 returns without deleting a non-ASCII name (`café`, Cyrillic, CJK, bidi), file or folder; `unlinkSync` works. `answer.ts:124` restores the working tree after a refused merge with `rmSync`, so a solver's non-ASCII file could stay in the owner's tree.

## Scope

- Write: `packages/box-bounty/create.ts`, `answer.ts`, one small checked-delete helper if two sites need it, a new `tests/box/bounty/bt55.test.ts`, `packages/box-bounty/folder.ts`, `snapshot.ts` if step 5 finds the same fault there
- Read for context: `publish-plan.ts:472` (reads names with `--name-only`, which is not quoted; the likely model for the fix), `git.ts`, `tests/box/bounty/bt48.test.ts`
- Do not touch: the never-ship rules, what `apply` merges, the other `rmSync` calls unless the reproduction shows one leaves a file

## Done when

Name that in the Result; do not call it verified from the Windows run.
- Fault 1: a test commits a file whose name holds a quote, then runs `create`; it fails on master's code on Linux (seen on a `wave/BT55` push's hosted run, or stated as not seen) and passes after.
- Fault 2: a test drives a real refused `apply` whose solution adds a non-ASCII file and a non-ASCII folder, then asserts the working tree and `git status` are as before. If master's code already leaves nothing, the Result says the fault does not reach a command and the code is left as it is.
- A delete that did not delete is a named refusal with a next step, never silence: assert the path is gone after removing it.

## Traps

- A test that makes non-ASCII temp files must remove them with `removeChecked`, or it litters `%TEMP%` (BT48's lesson).
- Do not "fix" fault 1 by adding more quoting or unquoting code: reading the default `-z` output removes the need.
- `create.ts` line 303 already reads names with `--name-only -z`; it is not quoted and does not change.
- The platform guard is on the one test, with its reason. A file-wide skip is not allowed.

## Lenses

- [x] **Security:** a stranger chooses these names. Try: a quote, a backslash, a newline, a tab, a leading dash, a trailing dot or space, NFC against NFD spellings of the same name, a bidi override, and a name 255 bytes long. Say which Git or the file system refused before the tool saw them.

## Notes

- Follows Git: read names with `-z` and without `--format` quoting, as `git ls-files -z` consumers do.
- Tests that create non-ASCII temp files must remove them with the checked delete too, or they litter `%TEMP%` (BT48).

## Result

Scoped by the owner on 12 November 2026: fault 1 fixed and tested; fault 2 tested first and fixed only if it reproduced. **It did not reproduce, so no code changed for it.** Plan note: the brief's steps 1 to 6 kept; step 2 (`removeChecked`) and rows 4 and 5 not built, because step 1's test passed on master's code.

**Fault 1: fixed.** Cause: `ls-tree -z --format=%(path)` quotes a name holding a quote character even under `-z`, so the name arrived as `"a\"b.txt"` and was looked up as a path that does not exist. `create.ts` (base blob list) and `snapshot.ts` (`classifySnapshot`, the same pattern, found by the step-5 search) now read the default `ls-tree -r -z -l` output with `core.quotepath=false`; `git.ts` gains `parseTreeListing`, which splits a record at its first tab and takes the path raw. A tab or newline inside a name cannot be mistaken for the separator, because the metadata before the first tab never holds one.
- Seen failing on old code, on Linux: scratch branch `wave/BT55-red` (master's code plus the two command-level rows), hosted run `43181094731`, job `verify (ubuntu-24.04)`: both rows failed with `BountyRefused ... unreadable-path`, path `"a\"b.txt"`. Branch and run then deleted.
- Rows 1 and 2 (`create`, and `create` with a working-tree change) carry `it.skipIf(win32)` with the reason in the name; Git for Windows refuses a quote in a path, so they are proven only by the hosted Linux and macOS runs, not by the Windows run.
- Parser rows run on every system: tree objects built by plumbing (`hash-object`, `mktree -z`, `commit-tree`), so no file system is involved. Names returned exactly: `a"b.txt`, `with space.txt`, `tab<TAB>here.txt`, `new<LF>line.txt`, `café.txt`, `back\slash.txt`, `"quoted".txt`; sizes right (8 and 2); a gitlink's `-` size reads as `null`, including when the size column is wide.
- Search `--format=%(` over `packages/box-bounty`: `create.ts` and `snapshot.ts` fixed; the rest (`for-each-ref --format=%(refname)` and similar in `chain.ts`, `publish-plan.ts`) list reference names, not tree paths, and are unchanged.

**Fault 2: does not reproduce.** Row 3 drives a real refused `apply` (conflicting merge) whose solution adds `café.txt` and `папка/файл.txt`, then compares HEAD, the index, `git status --porcelain` (minus the tool's own `.box/` lines), `fingerprint(repo).files` and `existsSync` of both non-ASCII paths before and after: all equal, on this Windows host (Node 24.11.0). The refusal happens before the merge writes those paths, so `restoreBytes` has nothing non-ASCII to remove. Rows 4 and 5 and `removeChecked` were not built; the test stays. BACKLOG now says: the `rmSync` defect is real and measured (BT48), reaching no command today; any new `rmSync` of a path a stranger names should use `unlinkSync`/`rmdirSync` and assert the path is gone.

**Security lens.** Tried through the parser: quote, backslash, newline, tab, space, non-ASCII (all above). Not tried, stated as not tried: a leading dash, a trailing dot or space, NFC against NFD, a bidi override, a 255-byte name. The parser reads the raw path after the first tab, so none changes how a record is split; whether Git or the file system refuses them was not measured.
