# K59: the slow tests get a margin on the hosted Windows runner

Milestone: K (kitchen) · Station: evidence · Base: `master at dispatch` · Branch: `wave/K59` · Timebox: 120 minutes (the hosted runs take about 26 minutes each); at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k49-answers
Horizon: short. Hillclimb playbook: a before and an after from named runs.

**Brief.** Written by the CTO on 11 November 2026 after BT54 and K50 each paid a 20-minute rerun; the owner named it ("Yes, K59", 11 November 2026), and the hosted run as the acceptance is the owner's K49 answer. Facts, read from the logs of hosted runs 43007131911, 42975233441 and 43001061001:

- Every test runs under one limit, `testTimeout: 30000` in `scripts/vitest.config.mjs`. Tests that need more name their own (`{ timeout: 180000 }`); the rest share the 30 s.
- On hosted Windows, 13 to 19 tests per run take 15 s or more (Linux: one), and several take 22 to 35 s: "independent bounties in same-address copies…" 35.5 s and "T1: a run that changes nothing…" 33.0 s pass, "every bounty command stays within its Git and gh start budget" 22.7 s, "asks at most five reads per command…" 24.4 s. **A test over the limit can still pass**: the 35.5 s one has no timeout of its own, because vitest's timer cannot interrupt a test that is entirely synchronous (a long `spawnSync`); a test fails only when it still has an async step after the timer is overdue. So the margin is not a clean 25 %: it is that many Windows tests sit at 20 to 35 s, and whether one fails depends on an await landing after second 30. Windows is three to six times slower than Linux on the same files because a Git or Node start costs more there (Linux's slowest are 3 to 17 s).
- The result: about one hosted Windows run in four fails on a single 30 s timeout in a different heavy test each time (`bt7.test.ts:169` on BT54, `report.test.ts:263` on master's K50 STATUS commit; K50's own local runs: five different ones). Each passes on rerun. The rule "hosted green on all three systems" pays a rerun tax.

The limit is a hang detector, not a speed contract: no wave claims a test must finish in 30 s. So the fix is a margin proportional to the system's speed, plus a report that keeps the margin visible, not faster tests.

## Outcome

On Windows a test that uses the default limit may take up to 60 s (twice today's); on Linux and macOS the limit stays 30 s. Every hosted run prints, per system, the eight slowest tests with their times, so a test creeping toward its limit shows before it fails. The rule is pinned by a test, so a later edit cannot quietly undo it.

## Traps

- **Whole-file lines look like tests.** Vitest prints `✓ tests/box/bounty/pf5.test.ts (52 tests) 310275ms` for each file and `✓ <name> <n>ms` for each test; the first kind has totals of minutes. Filter them out or the table says a test took five minutes.
- **A test with its own timeout is not affected** (`bt38`'s T1, `pf5`'s describes: 180000) and must not be listed as one the change helps. A test over 30 s with no timeout of its own that passes (`first-merge`'s "independent bounties…") passes because it is synchronous; say so in the table, not that it "has margin".
- **Do not raise the limit on Linux or macOS.** Their margin is already three times; loosening it only delays a real hang's report.
- **Do not edit a slow test to make it faster in this wave**, and do not add a timeout to a test. If the measurement shows a default-limit test over 40 s on Windows even in a green run, name it in the Result for its own wave.
- The workflow already ends with `perl` and `tr` steps that work on all three systems (K50); BSD `sed` on macOS does not understand `\x1b`, which is why `perl` is used.
