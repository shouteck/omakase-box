# K72: what a command's starts are for, and what the speed work will not do (documents only)

Milestone: K (kitchen) · Station: evidence · Branch: none (a kitchen document, committed directly) · Timebox: 120 minutes
Owner decisions: on 13 November 2026 the owner asked whether the suite's cost is a design fault, asked for research on how others speed up Git and GitHub calls, and said the risk to the tool's functionality, which relies on Git and GitHub, is the concern. Agreed: no product code changes for speed; the read-only count below; test-only conversions where the decision is already a pure function.

No product code or test was changed. Everything below was measured on this host (Windows 10, Git 2.45.1, Node 24) on 13 November 2026, with the host loaded at times; run-to-run variation is ±20 to 30%, so only large differences are claims.

## What was measured

| question | result |
|---|---|
| Can the stand-in `gh` start cheaper? | No. A call is 101 to 110 ms; a bare `node -e 0` is 87 ms in the same run. The preload and the state file add 15 to 25 ms. An earlier wave already made the Windows stand-in a hard link to `node.exe` (one process per call; a copy cost 139 ms against 41). |
| How much of a file does the stand-in cost? | In `bt44`, 56 stand-in calls took 6.7 s of a 30 s file (about 22%). 45 of the 76 files that use the stand-in also run the CLI as a child process, which an in-process stand-in cannot reach. |
| Would Bun start faster? | No: `bun -e 0` 111 and 149 ms against `node -e 0` 77 and 110 ms in two rounds. Bun is also not what ships, and `bun test` is not Vitest, which the edit gate, proof map and guard audit read. |
| Does turning fsync off help Git's writes? | No: 30 four-write sequences (`hash-object`, `mktree`, `commit-tree`, `update-ref`) took 305 and 285 ms with default fsync, 312 and 273 ms with `core.fsync=none`. Each write start costs about 70 ms here, more than `git --version` (28 to 44 ms): the starts do real work. |

## What others do (searched on 13 November; sources are mostly mailing lists, vendor pages and blogs)

- Keep one Git process alive for many object lookups (`git cat-file --batch`, `--batch-check`, `--batch-command`; GitLab runs a pair per repository). It helps a long-running service; our commands are short processes that rarely repeat a lookup.
- Launch fewer processes and cache (Atom, after moving from libgit2 to shelling out; Magit on Windows). K71 did the small version of this.
- In-process Git libraries (libgit2 bindings, isomorphic-git, gitoxide): one vendor reports 1,000 reads falling from 1.9 s to 65 ms; there is no independent benchmark and reports of problems on large clones. For this tool it would replace the Git behaviour the hard stops depend on: not done.
- Windows: process creation is slow; the usual remedies are Defender exclusions and `core.fscache`. Machine tuning is excluded by the owner's rule of 12 November.
- Git's own tests turn fsync off and can use tmpfs; the fsync check above found no gain here.

## What a command's starts are for (read-only count, one run of the `k14` journey)

`look <id> 1` that collects a pull request: **26 starts** (the `k14` budget counts 25 Git and 1 `gh`). `apply <id> 1`: **36** (30 Git, 6 `gh`).

| kind | `look` (collecting) | `apply` |
|---|---|---|
| fixed per process (`git version`, `rev-parse --show-toplevel`) | 2 | 2 |
| GitHub reads | 1 | 3 (the pull request twice: the second, just before the merge, is deliberate (PF27); the signed-in account) |
| GitHub writes | 0 | 3 (answer comment, issue update, graphql) |
| Git moves or writes (fetch, update-ref, merge, push, the chain event of 6 starts) | 9 | 13 |
| Git reads that feed a decision (ancestry, tree and diff reads, the owner's configuration, the merge test, ref and branch reads) | 14 | 15 |

- **About half the starts (14 of 26, 15 of 36) are reads whose result a decision uses.** The same reads are needed in production however the code is arranged: a decision written as a function of plain data still has to be handed that data. What such a split changes is the **test**: a rule test could supply the data instead of building a repository, a posted bounty and a pull request. That is how never-ship (K65), the owner's authority (K67) and the classifier (K69) became tables.
- **Repeated calls are almost absent, as K51c found.** One exact repeat in `look` (the same `diff --name-status` between the same two commits, twice: starts 12 and 13), left as it is: one start of 26, in product code, for no change a user could see. The repeated pull-request read in `apply` is on purpose.
- The chain event (6 starts: `rev-parse`, `hash-object`, `mktree`, `commit-tree`, `update-ref`, `push`) is 23% of `look` and 17% of `apply`. `git fast-import` could write it in fewer starts; it is security-sensitive and is not started.

## Decisions

- **No product code changes for speed.** The benefit is faster tests; the risk is a regression in something users rely on, for a tool whose job is Git and GitHub. K71 was the last such change (4% of starts); it passed every gate and a three-system run, and is kept.
- **The in-process transport seam goes into [BT59](BT59.md)** as its first unit (BT59's base), not as a speed wave.
- **Test-only work stays open:** converting a test to a table where its rule is already a pure function; merging duplicate tests, each removal proven by running the same breaks against the old and new tests ([TESTING.md](../docs/box-v4/TESTING.md)).
- **Left as a cost, stated:** a journey proves that the real calls work together; its cost is the starts of the calls, and no measurement here found a way to make one cheaper.
- **Open owner question, unchanged:** whether tests and readers for record shapes from before 0.2.0 (about 42 s) are still needed.
