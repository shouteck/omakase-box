# BT88: every change to the owner's authority leaves a line the owner can read

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT88` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of `config`, `allow` and `deny` with the owner ("I agree with your recommendation").

**Why.** The owner's authority lives in one file, `settings.json` in the owner's folder (`packages/box-bounty/settings.ts`), and an agent can run `allow` itself. The tool says once that the settings "stop accidents and record changes; they are not a lock" (`NOT_A_LOCK`, `packages/box-bounty/owner.ts`). The owner has chosen offering over enforcing, so this wave adds no lock.

But the settings do not *record changes* as that sentence claims. Each entry keeps only its latest value and time. An agent that allows a repository, posts, and denies it again leaves `config` showing nothing happened. The owner's own audit question cannot be answered: MEMORY-SPEC M12, "what did my agents do in my name?".

## Outcome

1. **An append-only log, `decisions.log`,** next to `settings.json` in the owner's folder, never in a repository. It gets one JSON line for every change to:
   - a repository's decision (`allow`, `allow --ask`, `deny`), and `all-projects`;
   - reward and reward limit;
   - the solving mode and its limits;
   - the publish lists;
   - instructions;
   - the board address;
   - each answer to a held post, merge or take;
   - `paid`.

   Each line holds:
   - the time;
   - the command as the owner would type it (values, never secrets: none of these settings hold one);
   - the value before and after;
   - **`terminal: true|false`**: whether standard input and output were both an interactive terminal when it ran.
2. **Shown where the owner already looks:**
   - `config` prints the last five lines under "recent changes", each with "from a terminal" or "**not from a terminal**";
   - `config --full` prints the last 50;
   - `config --json` carries them;
   - `status --since <time>`, the owner's summary, lists every change since that time.
3. **Stated plainly, once, where the log is first shown:** "the log records changes; it is not a lock: anything that can write settings.json can also edit this file. 'Not from a terminal' is a fact about how the command ran, not proof of who ran it." `NOT_A_LOCK`'s claim, "record changes", becomes true.
4. **Bounded:** the log keeps its last 2,000 lines. When it trims, it writes a line saying how many it dropped.
5. **The write is part of the change:** the log line is appended in the same step as the `settings.json` write (BT22's whole-or-nothing write). A failed settings write leaves no line, and a failed log append is named in the command's output, never silent.

## Scope

- Write: `packages/box-bounty/settings.ts` (`writeRepository`, `writeMoney`, `writeDecision`, the publish-list, instruction, board and merge-answer writes call one `logDecision`), `packages/box-bounty/solving.ts` (`changeSolving`), `packages/box-bounty/take.ts` (`approveTake`), `packages/box-bounty/owner.ts` (`renderConfig`, `renderSummary`, `recordPaid`, the once-ever line), `packages/box-bounty/json.ts` (the config document), `docs/box-v4/BOUNTY.md` (`config`), `docs/box-v4/MEMORY-SPEC.md` (M12 gains its fact), `tests/box/bounty/bt88.test.ts` (new), text snapshots the new lines reach (under `## Changed expectations`)
- Read for context: `waves/BT22.md` (whole-or-nothing writes), `tests/box/bounty/bt17.test.ts` (once-ever explanations), `tests/box/bounty/bt61-text.test.ts` (text snapshots)
- Do not touch: what any setting means; the gates; `NOT_A_LOCK`'s wording beyond making it true

## Done when

- The hosted run on the final commit is green on Linux, Windows and macOS, quoted with its run id; the suites the change affects: `test:box-bounty`, `test:kitchen`.
- `bt88.test.ts`, each seen red on master first:
  - **The scenario that motivated it:** `allow owner/project`, a post, `deny owner/project`. `config` shows three recent changes in order, and `status --since <before>` lists all three.
  - **Every kind of change** in Outcome 1 writes exactly one line with before and after.
  - **`terminal`:** the test runs the CLI without a terminal and the line says `false` and "not from a terminal". The `true` case is tested through the function that reads it, with the two values injected (a test cannot make a real terminal portably).
  - **A refused change** (`--reward` above the limit) writes no line.
  - **Trimming:** 2,005 changes leave 2,000 lines plus the trim line.
  - **A log that cannot be read** (hand-edited garbage) is named in `config` and the tool keeps working: a record must never block the owner.
- A break proof: skip `logDecision` in `writeRepository`; the scenario test turns red.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** seen failing on master.
2. **`logDecision(change)`** in `settings.ts`: appends one line, then trims if over 2,000. Every write site in Outcome 1 calls it after its own write succeeds.
3. **The reads:** a `readDecisionLog(limit, since?)` that skips unreadable lines and reports how many it skipped.
4. **Show:** `renderConfig`, `config --json`, `renderSummary`, and the once-ever line.
5. **Docs, snapshots;** verify, push, hosted run, Result, merge.

## Traps

- **Never put a value that could be a secret in the log.** None of today's settings holds one; a future setting that might is refused by a test that lists the logged setting names.
- **The terminal fact is `process.stdin.isTTY === true && process.stdout.isTTY === true`, read once per process.** Windows terminals answer it too; check it on the Windows runner.
- **The owner's folder can be shared by several checkouts.** Each line names the repository it was about, or `all-projects`.
