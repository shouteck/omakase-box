# BT13: what the owner hears

Milestone: BT · Station: packaging (also evidence) · Base: master at dispatch, after K19 · Branch: `wave/BT13` · Timebox: 150 minutes; at expiry the cook stops and reports where it is, whatever state that is

**Pre-brief.** Written by the CTO on 14 October 2026 from K18's critique (`kitchen/reviews/K18-flow-critique.md`) and the owner's decisions of that day. The head chef checks names against master at dispatch.

## Why

K18's stand-in owners understood the tool through their agent's paraphrase, and the paraphrase lost what mattered. None of the three owners asked about permission learned that merges are not asked about; the one who chose "ask me each time" assumed they were (F1). Owners were shown commit hashes, `git revert -m 1`, command names and "public for the first time"; no message said what a bounty is; one said "I don't type commands" (F2). After an owner marked a hit safe, the preview said "clean" above it (F10). A merge that kept half of a solution earned the whole reward with nothing said (F11).

And the owner decided, after K18: **"ask me each time" means before each post and before each merge** (PLAN.md, "Other rules of the product").

## Outcome

What an owner hears through their agent is a few plain sentences that survive paraphrase, and the setting called "ask me each time" does what its name says.

**"Ask me each time" holds merges too**

- In that mode, `apply` does not merge. It holds the bounty in a named waiting state, as a post is held, and gives the agent one plain sentence for the owner: which solution, from whom, ready to merge into their code. The owner answers with the same `allow` on the waiting bounty, and the merge goes ahead; until then nothing in the owner's tree, index or branch changes.
- A merge the agent made by hand is still recognised and the bounty still closes, as today, since the tool cannot stop it. The closing output, `status` and the pay message state as a fact that the owner was not asked before that merge.
- Closing never waits, in any mode.
- In the default, allowed, nothing about merging changes.
- A setting written before this wave keeps its meaning of "ask"; the tool says once, as a fact, that ask now also covers merges.

**The sentences an owner hears**

- Every message meant for the owner (first use, `allow`, a waiting post, a waiting merge, a secret-scan hit, the pay message) opens with a short block the agent is told to pass on **in these words**, kept apart from anything for the agent. Plain language, no hashes, no command names, no Git words.
- At first use the block says, each in one short sentence: what a bounty is (asking people outside to fix something, publicly, through GitHub); that it is posted publicly under the owner's GitHub account; that it covers this repository only; what each bounty there pays, $0 unless they set an amount; and, depending on the choice, either "you will be asked before each post and before each merge" or "you will not be asked before a post or a merge". The relay must not be able to leave out the merge sentence and still be complete.
- **The owner is offered a question to answer, never a command to run.** The commands the agent runs on the owner's answer stay in the agent's part.
- A secret-scan hit tells the owner, plainly: a file in their project contains something that looks like a password or key; which file; that nothing has been published; what they can choose. Not "public for the first time", not "git push", not "decide in config".
- **"Clean" means clean.** When a hit was let through because its path is on the safe-to-publish list, the preview's headline says so in words, not "clean".
- **The pay message says when only part of a solution was kept.** When the merged commit changes only some of the files the solution changed, it states which, as a fact, so the owner pays knowing. The rule stays: the merged solution earns all of it.

**Measured, as K18 measured it, with fresh agents and never the owner**

- The two-agent relay check: one agent gets only the tool's output and is told to ask its owner; a second, which has never seen the tool, reads only that message and writes down what it agreed to. A check looks for: public, under my account; this repository only; what each bounty pays; and whether I will be asked before a merge, matching the mode. Five runs each for allowed at $0, allowed with a reward, and ask me each time. The Result gives every relayed sentence word for word and the count that carried all of them.
- One stand-in owner run for each of: a waiting merge in ask mode, a secret-scan hit, and a pay message after a partial merge. Each says in its own words what it is being asked or told.
- Words an owner reads per journey, before and after, as K18's table counted them.

**Cases that must fail, each a named refusal that changes nothing:** a merge in ask mode without the owner's yes; `allow` on a waiting merge after the solution or the branch changed underneath it; anything an agent can pass that would mark a merge as approved.

## Review lenses

- [x] **Security:** the reviewer tries to get a merge through in ask mode without the owner's yes by the tool's own commands (odd arguments, a stale approval, approving one bounty and merging another, an edited record), and checks that a hand merge is always reported as not asked.
- [x] **User experience:** the relay check above, read by the reviewer against K18's runs: did each fact that was lost in K18 now arrive, and did anything new get lost.
- [x] **Measurement fairness:** every run counted; stand-in owners called stand-ins; before and after counted the same way.

## Notes for the worker

- Feature playbook for ask-mode merges; for the wording, write the owner's block first and test it with the relay check before wiring it in.
- The three owner words stay three: the merge approval is `allow` on the waiting bounty.
- Fewer words, not more. If the owner's reading grew, cut.
- Report at the timebox. Do not run on.
- Not in this wave: anything only an agent reads (BT14).
