# K21: an architecture review of the bounty tool, component by component

Milestone: K (kitchen) · Station: packaging (also evidence) · Base: master at dispatch, after BT15, BT16, K20 and BT17 · Branch: `wave/K21` · Timebox: 180 minutes; at expiry the cook stops and reports what it has

**Brief.** Pre-brief written by the CTO on 14 October 2026 at the owner's request: "a lot of our components require some scrutiny, especially our architecture." Detailed on 15 October 2026 so that a cook without deep reasoning can carry it out. The "Method" section turns the review into fixed steps, the "Suspects" section names what to confirm or refute first, and the "Ranking" section says how to order findings. Line numbers are as of master `e20f4ca`; BT16, K20 and BT17 land before this wave, so search by name, not by line.

An investigation: **it changes no product code and no test.** Its product is a review the owner and the head chef decide from, and a short list of proposed waves. It cooks only when named.

## Why

The tool was built in about forty waves over a few days, and its design changed under it several times: a whole-repository folder became an issue on real history (BT6a); a staged merge in a side copy was built, failed three reviews and was replaced by recognising any merge (BT7, BT7b); standing rules became one yes per repository (BT8 to BT8c); money arrived per repository (BT11 to BT11c); folder delivery was retired (BT15). Each wave was reviewed on its own terms. Nobody has yet looked at the whole.

Walking the owner through `create` on 14 October already found two things a whole-tool look should have caught sooner: a package folder written on every draft and read by nothing in the main flow (since removed by BT15), and a working-state snapshot whose remaining jobs may all be served better from Git at the moment of use. Those are signs, not the full picture.

## Outcome

A map of the tool as it is, and for each component an honest account: what it is for, how it works, which design decisions hold it up and whether each still holds, what is left over from an earlier design, what is duplicated, where the risk sits, and what to do about it, ranked by how much it would simplify or protect the product.

## Method: six steps, in order, with a time budget each

Write each step's output into the report as you go, so a timebox stop still leaves something usable.

**Step 1: the inventory (25 minutes).** Mechanical, no judgement yet.

- For every file in `packages/box-bounty/` and `packages/box-cli/src/`: line count (`wc -l`), what it exports (`grep -n "^export"`), and which other files import it (`grep -ln "from './<name>.js'"`). Put this in a table: file, lines, exports, imported by.
- Draw the dependency graph as a plain text or Mermaid diagram: an arrow from importer to imported. Mark any cycle.
- For each command (`create`, `post`, `status`, `look`, `apply`, `close`, `allow`, `deny`, `config`, `describe`, `help`), trace from `packages/box-cli/src/cli.ts` to the function it calls and list the modules that call reaches. One line per command.

**Step 2: the data (25 minutes).** Every stored fact and who reads and writes it.

- The record (`BountyRecord` in `record.ts`): one row per field: written by (function), read by (functions), still written by current code (yes or no, with evidence), and the wave that introduced it.
- The record's stages (`OpenStage`, `EndedStage`) and attempt outcomes (`AttemptOutcome`): one row each: which function moves a record into it (`grep` for `transitionTo(` and `stage:` and `outcome:`), and which code only reads it.
- The owner's settings file (`settings.ts`, the keys accepted in `loadSettings`): same table.
- Git refs the tool writes (`refs/box-bounty/<id>`, `-answer-<n>`, `-github`, any others found with `grep -n "refs/box-bounty"`): written by, removed by, read by.
- Instruction files and the hook: what they store and where.

**Step 3: the suspects (50 minutes).** Work through every suspect in the next section. For each: confirmed, refuted, or partly. Evidence is a file and line, a `grep` result, or a command run with its output. A suspect is not a finding until confirmed.

**Step 4: the components (40 minutes).** For each of the eight components below, fill the template in "The report". Use steps 1 to 3; read code only where a question is still open.

**Step 5: ranking and proposed waves (25 minutes).** Apply the ranking rubric. Write at most five proposed waves.

**Step 6: the owner's page (15 minutes).** Written last, from what the steps found.

## The components, in the order a bounty meets them

1. **Drafting** (`create`): inputs, repository identity, the snapshot, never-ship, the create-time scan, the record and bookmark, the publication preview.
2. **The owner's yes** (`allow`, `deny`, `config`): the settings file, per-repository permission and reward, ask mode, first use, the legacy migration.
3. **Posting** (`post`): what becomes public, the publication plan, the work-in-progress commit, the scan, the issue, the bounty branch, the readable block.
4. **Solutions arriving** (`status`, `look`): reading pull requests, pay facts, strangers' text kept apart, seen and new.
5. **Bringing one home** (`apply`, recognising any merge, closing): the owner/foreign Git split, ask mode for merges, the lifecycle.
6. **Telling the owner** (the owner's block, the pay message, the first-merge note).
7. **Memory across sessions** (the record and its stages, the instruction-file notice, the hook, the saved job).
8. **Underneath:** the Git layer (`git.ts`, pins, the owner/foreign split), the GitHub layer (`github.ts`), errors and refusals, wording, and how the tests are built.

## The snapshot, decided on evidence

Using BT15's list and S5's findings, recommend one of:

- **keep it**, with each remaining use and why Git at the moment of use cannot serve it;
- **retire it**: replace each remaining use with a Git read at the moment of use, and say what happens to old records that carry one;
- **a middle course**, saying exactly which part stays.

For the recommendation, state: what it removes (files, record fields, refs, tests, by name and line count); what it costs (which tests must be replaced, not just deleted, and which guarantee each one protects); and what it does to S6.

## Ranking

Give each confirmed finding two scores, each 1 to 3, with one sentence of reason:

- **Simplify:** 3 removes a concept a reader must hold (a stage, a stored copy, a module); 2 removes code but no concept; 1 is tidying.
- **Protect:** 3 touches a hard stop (never-ship, no private repository outside, the owner's authority) or the owner/foreign Git split; 2 can make the tool say something untrue; 1 neither.

Order by the sum, then by Protect. Every finding with Protect 3 goes on the owner's page whatever its sum. A design that changed for a recorded reason is not a finding; a part of it that outlived the reason is.

   - Files and the main functions.

   - Design decisions: decision, the wave that made it, does it still hold (yes, no, partly) and why.
   - Left over, duplicated, more than one source of truth: each with evidence, or "none found" and how you looked.
   - Hard stops and the owner/foreign split enforced here: file and line.
   - Tests: which guarantees rest on real Git, which on the stand-in only, which tests serve only retired paths.
   - Risk: where a change is most likely to break a guarantee, and whether a test would notice.
   - Recommendations, with their scores.
5. **The snapshot** recommendation.
6. **Proposed waves:** at most five, each one paragraph: outcome, what it removes or protects, its dependencies, and the order. Briefs are the head chef's to write.
