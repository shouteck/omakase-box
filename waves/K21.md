# K21: an architecture review of the bounty tool, component by component

Milestone: K (kitchen) · Station: packaging (also evidence) · Base: master at dispatch, after BT15, BT16, K20 and BT17 · Branch: `wave/K21` · Timebox: 180 minutes; at expiry the cook stops and reports what it has

**Pre-brief.** Written by the CTO on 14 October 2026 at the owner's request: "a lot of our components require some scrutiny, especially our architecture." An investigation: **it changes no product code and no test.** Its product is a review the owner and the head chef decide from, and a short list of proposed waves. It cooks only when named.

## Why

The tool was built in about forty waves over a few days, and its design changed under it several times: a whole-repository folder became an issue on real history (BT6a); a staged merge in a side copy was built, failed three reviews and was replaced by recognising any merge (BT7, BT7b); standing rules became one yes per repository (BT8 to BT8c); money arrived per repository (BT11 to BT11c); folder delivery is being retired (BT15). Each wave was reviewed on its own terms. Nobody has yet looked at the whole.

Walking the owner through `create` on 14 October already found two things a whole-tool look should have caught sooner: a package folder written on every draft and read by nothing in the main flow, and a working-state snapshot whose remaining jobs after BT15 may all be served better from Git at the moment of use, and whose preview can drift from what `post` actually publishes. Those are signs, not the full picture.

## Outcome

A map of the tool as it is, and for each component an honest account: what it is for, how it works, which design decisions hold it up and whether each still holds, what is left over from an earlier design, what is duplicated, where the risk sits, and what to do about it, ranked by how much it would simplify or protect the product.

**The components, in the order a bounty meets them.** For each, the review states purpose, files, the data it reads and writes, and its design decisions with the wave that made each:

1. **Drafting** (`create`): inputs, repository identity, the snapshot, never-ship, the create-time scan, the record and bookmark.
2. **The owner's yes** (`allow`, `deny`, `config`): the settings file, per-repository permission and reward, ask mode, first use.
3. **Posting** (`post`): what becomes public, the publication plan, the work-in-progress commit, the scan, the issue, the bounty branch, the readable block.
4. **Solutions arriving** (`status`, `look`): reading pull requests, pay facts, strangers' text kept apart, seen and new.
5. **Bringing one home** (`apply`, recognising any merge, closing): the owner/foreign Git split, ask mode for merges, the lifecycle.
6. **Telling the owner** (the owner's block, the pay message, the first-merge note).
7. **Memory across sessions** (the record and its stages, the instruction-file notice, the hook, the saved job).
8. **Underneath:** the Git layer (`git.ts`, pins, the owner/foreign split), the GitHub layer (`github.ts`), errors and refusals, wording, and how the tests are built.

**Questions every component is held to:**

- **Is all of it still needed?** What remains from a design the product has left behind: code, record fields, stages, refusals, options, test paths kept only for old records. For each: who still depends on it, and what removing it would take.
- **Is anything done twice?** Logic built in two places that must agree (for example what `create` previews and what `post` publishes), and whether one source could serve both.
- **Is there one source of truth?** Where the same fact lives in more than one place (the record, the GitHub issue and its block, the owner's settings, the instruction files, Git refs), which one wins, and where they could disagree.
- **Are the boundaries where they should be?** What depends on what; whether a command needs a module it should not (for example `create` needing GitHub); how large the largest files are and whether their size reflects real complexity or accumulation (`github.ts` and `record.ts` are the largest).
- **Does it hold to the principles?** Only what the tool is needed for; the tool owns the bounty's life, not how code is merged; facts, never verdicts; nothing a solver wrote is run; the owner involved once.
- **Is it tested where it matters?** Which guarantees rest on real Git and which on stand-ins; which tests check logic that could be checked without starting Git (K14's open question); which tests exist only for paths that no longer matter.
- **What is the risk?** Where a change is most likely to break a guarantee, and whether a test would notice.

**The snapshot, decided on evidence.** Using BT15's list, the review recommends one of: keep it, with the reasons; replace each remaining use with Git at the moment of use and retire it; or a middle course. It says what each would cost and what it would remove, including the drift between `create`'s preview and what `post` publishes.

**The report** (`kitchen/reviews/K21-architecture.md`):

- **One page first, for the owner, in plain words:** what the tool is made of (one simple diagram); the five changes that would most simplify or protect it, each in two sentences with what it costs; and what is sound and should be left alone.
- **Per component:** the account above, with evidence (file and line, or a command run), and its recommendations.
- **Proposed waves:** at most five, each one paragraph, in an order that respects their dependencies. Briefs are the head chef's to write.
- What was not examined, and why.

## Review lenses

- [x] **Security:** the review names every place a hard stop or the owner/foreign Git split is enforced, and whether any proposed simplification would weaken one; the pass checks that claim for each proposal.
- [ ] **User experience:** not the subject here (K18 and K20 cover it); the review notes any architecture finding that would show up to an agent or owner.
- [x] **Measurement fairness:** every claim cites code, a test or a run; "left over" and "duplicated" are shown, not asserted; the pass spot-checks five findings against the code.
