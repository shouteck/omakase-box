# BT76: `post` loses the approval path no installed copy can reach

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT76` · Timebox: 120 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Refactoring playbook; principles: subtract-before-you-add, migrate-callers-then-delete-legacy-apis, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `post`. The owner approved briefing it ("Yes, brief it"); this is a removal, so it waits for the owner's go.

**Why.** About 70 lines of `postGitHub` (`post.ts`, the `if (record.github === undefined)` block after the standing-decision path) post a bounty from a `githubApproval`. That field was written only by the `confirm` command, removed in BT8 on 11 October 2026. The first npm release (0.1.3) came out on 2 November 2026. **No released version ever wrote one.** The only real records carrying the field are three of this repository's own early bounties under `.box/bounties/`, and all three were posted long ago (`record.github` is set), so this path never runs for them.

The path keeps alive:
- a second "publish exactly what was approved" check (`github-preview-stale` against the recorded plan);
- a `record-corrupt` refusal for half a plan;
- the `confirmed` stage's `legacyConfirmed` credit in `gate.ts` `allowedByFor`;
- `githubApproval` tests on `previewGitHub`'s reward gate and in `format.ts`.

Readers of `post` must step around all of it. The rest of the code already has one place that decides what "old" means: `retiredRoute` in `record.ts`, which refuses old routes with `legacy-delivery-retired` and the next step "close it".

## Outcome

1. A record with a `githubApproval` and no `github` publication, if one ever appears, is refused by `retiredRoute` with `legacy-delivery-retired` and `next: omakase-box close <id>`, before anything is read from GitHub. Nothing is published.
2. The approval-posting block, its `github-preview-stale` and `record-corrupt` branches, and `legacyConfirmed` in `allowedByFor` are gone. `postGitHub` has one path for a new post and one for resuming a started one.
3. A record that already ended or was posted with a `githubApproval` still reads, shows and closes exactly as before. The field stays in the record type as read-only history (`record.ts`), and `format.ts`'s reward read for it stays.
4. A `confirmed`-stage record with no approval (the `bt15` case) still posts through the standing-decision path, as today.
