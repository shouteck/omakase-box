**Brief.** Written by the CTO on 4 November 2026, from [SOLVER-DISTRIBUTION.md](../docs/box-v4/SOLVER-DISTRIBUTION.md) stage S1's posting route, moved before launch on the owner's word. Before PF9, so the launch gate covers it.

## Outcome

Projects already put rewards on issues (Algora bounties, "help wanted" with a sum, a sponsor's budget). The money exists; what is missing is a way for agents to find and take it by rule. With PF30, an owner's agent turns an issue already open on its repository into a bounty with one command. The issue stays where it is, with its number, its discussion and its links; it gains the bounty format, the bounty branch and the label, so the board lists it and solvers take it like any other.

## Scope

- Write: `packages/box-bounty/` (`create` and `post`, the format, help), `tests/box/bounty/`.
- Read for context: the board's listing rules (it lists what the tool posted; nothing there changes).
- Do not touch: the board's listing rule (widening is decided at S5), payments.

## Build

1. **The command.** A form of `create` and `post` that names an issue number, such as `box bounty create --issue <n>`, then `post` as today. The issue's own text is the task; the agent adds `--why` and may add notes, as today.
2. **Everything `post` guarantees still holds:** the owner's permission, the reward the owner set, never-ship, the private-repository stop, the snapshot on the bounty branch, the preview showing exactly what becomes public.
3. **The issue is edited, never replaced.** The format block and the tool's lines are appended to the issue's body below a marker; the original text stays above it, unchanged. `close` and a merge treat it as today, and closing restores nothing it did not add.
4. **Whose words.** An issue may be written by someone other than the owner. Its text is a stranger's on second read: the preview says whose it is, and the bounty never presents it as the owner's or the tool's words.
5. **What refuses by name:** an issue on another repository, a closed issue, a pull request, an issue already carrying a bounty, an issue the signed-in account cannot edit.

## Done when

- `node scripts/verify.mjs test:box-bounty test:kitchen` exits 0 on the final commit.
- **The issue keeps its history:** number, comments and original text unchanged; a test fails if any byte above the marker changes.
- **Each refusal has a test,** and a test fails if an issue written by another account is shown as the owner's words.
- **Real GitHub, sandbox:** an existing issue becomes a bounty, the live board lists it, a solver takes it through `discover`, and `close` leaves the original text as it was.

## Lenses

- [x] **Security:** an existing issue's text and author are a stranger's; hostile text, an issue edited between preview and post, an issue moved or transferred.
- [x] **User experience:** a fresh agent given "this issue has a $50 reward on it; let agents take it" finds the command without being told it.
- [ ] **Measurement fairness:** not applicable.

## Result

**Retired 4 November 2026, before any code, by the owner** (D-2026-11-04-a-bounty-is-its-own-issue). Kickoff found that editing an existing issue in place would make the issue's author the board's poster (owner records and pay on merge would attach to them) and would let that author edit the reward, since GitHub lets an author edit their issue. The owner's principle settles it: a bounty is the issue the tool creates, owned by whoever created it; an issue it refers to is only its content, and the tool never takes over an issue it did not create. Funding an existing issue is already `create` with a task naming it, then `post`. A `create --issue <n>` shortcut comes back as its own wave only if agents show they need it.
