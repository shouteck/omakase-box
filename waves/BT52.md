# BT52: a later agent on another machine can finish a bounty

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT52` · Timebox: 240 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-01-real-before-launch, D-2026-10-19-k31-sandbox-go
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 1 November 2026, after BT51. The product promises that "a record in the project lets any later agent pick it up". K40 showed that holds only for reading.

## Why

In K40, a fresh clone could read a bounty's public history, but `look` refused with `shared-only` and `status` did not see the waiting pull request (BACKLOG, "K40 continuation/notification boundary"). The agent that posted may be gone, and a long-running or later agent on another machine is exactly who should finish the work.

## Outcome

An agent in a fresh clone with push access and no local record can see a bounty's waiting pull requests, `look` at one and `apply` or `close` the bounty, with the same refusals, scans and merge checks as the machine that posted it. Everything the posting machine alone knew (the private `--resume` note) stays absent, and the output says so.

## The change

1. **Plan first.** List what each command reads from the local record that a shared record lacks, and whether it can be rebuilt from the chain's `posted` event and GitHub, the same facts `look` already binds to.
2. Let `status`, `look`, `apply` and `close` work from a shared record by creating the local record from those facts. The binding checks stay: the issue's marker and author, the posted commit, descent.
3. Permission still comes from this machine's owner settings; a shared record grants none. `ask` still holds.
4. Keep `shared-only` only for what truly cannot be rebuilt, each with a true `next:` step.
5. Two machines racing: the chain's existing fast-forward rule applies. Say what the second machine sees.

## Plan

Approved by the owner on 1 November 2026. No code written yet. The approach: rebuild an ordinary local record from the `posted` event and GitHub, so every command keeps its one code path.

**Rebuilt fields.** Repository from `requireRepository`, with the issue URL matching exactly. Issue number and url from `posted.issue`, bound to GitHub by number, marker `<!-- box-bounty:<id> -->` and author. Account from `posted.actor`, which must equal the issue's author. Commit is `published.pushed.at(-1).sha ?? base` (today's fold wrongly uses `base`) and must equal the format block's `workCommit`. Branch is `box-bounty/<id>` only. Title, body, reward and createdAt from the issue and its format block. Pushed from the event, shape-checked and printed quoted. `resume.branch` is this checkout's current branch, for the hand-merge scan. Attempts and seen pull requests start empty: chain `solution` events are not trusted, so `look`/`apply <n>` collect through `answerGitHub`. `allowedBy` is dropped: a shared record grants nothing.

**Steps.**
1. New `packages/box-bounty/adopt.ts`: `adoptShared(root, id)` runs the binding checks and writes the record at `posted` with `adopted: { at }`. Refusals, nothing written: `shared-record-mismatch` (another issue, commit, branch, repository or author, or no format block), `shared-record-disputed` (chain ended, issue open), `shared-issue-closed` (issue closed, chain open). Each has a true `next:`.
2. `loadRecord`, through a registered seam like `setRecordReadScan`: an open shared row adopts. An ended row still refuses `shared-only`, reworded: ended on another machine, the issue, `next: box bounty status <id>`.
3. `renderStatus` and `statusDocument` adopt open shared rows before listing, so the normal refresh shows waiting pull requests. A row that fails to bind stays read-only with one line of reason. `hook start` and bare `box bounty` do not adopt.
4. Permission from this machine's settings only. `ask` and `off` hold as today. On an adopted record, nothing written or denied also holds `apply` as a merge wait; `close` refuses `owner-permission-needed`; `look` collects but pushes no chain event; `syncGitHubDecision` leaves a named `pending` instead of writing to GitHub. An owner's one-merge answer counts as authority.
5. `look`, `apply`, `close` and `allow` force one chain sync, then settle: a local open record whose chain ended and whose issue is closed moves to that ending with command `shared`, no comment, no chain event, one notice. A forged ending on an open issue does not end it. If two machines are already mid-merge, the branch check gives a named `pending` and the chain joins by its merge event; say so in the docs and the Result.
6. Wording in `wording.ts`; update `BOUNTY.md`, `CONTRACTS.md`, `MEMORY-SPEC.md`; remove the K40 BACKLOG item; check the three GitHub stand-ins. Expect K14's `look`, `apply`, `close` counts to move with the forced sync; a raised budget needs the owner.

**The `--resume` note.** The brief and `create --help` call it private, but `sharePosted` publishes it as `followup` on a public ref. New `posted` events stop carrying it; the allow-list keeps the field so old events import. Adopted records have no note and the output says it stayed on the posting machine. Notes already pushed stay readable: report it, do not rewrite history.

**Changed expectations.** `bt32`, `bt35`, `bt41`, `bt43`, `bt32-pass-toctou` where they assert `shared-only` on an open bounty or the old next step; `bt32-pass-probes` for `followup`. List each in the Result.

**Tests,** new `tests/box/bounty/bt52.test.ts`: the six cases above, plus forged issue, commit, author, branch and repository; forged `solution`; forged `merged`/`closed` on an open issue; reordered events and a second `posted`; no permission and denied for `apply` and `close`; `ask` holds; reward read from the issue; the race. A new git start inside a stand-in must not be counted (BT51-ci).

**Parked 1 November 2026** on `wave/BT52`, because the off-machine run on master went red again (BT51-ci2 comes first). Built: `adopt.ts` and its wiring, permission, settling, the note. `bt52.test.ts` and the affected files pass (121 tests) except `bt32-pass-probes`, whose expectation was changed at parking and not rerun.

**Decided while building.** `apply` and `close` on a posting machine use the once-a-minute chain sync so K14's budgets hold; a machine with no record or an adopted one forces it; `status` forces it when it reads a closed issue on an open record. So a posting machine that runs `apply` under a minute after another machine merged can still merge locally and gets a named pending: state this limit.

**Changed expectations so far.** `bt32` (acting on a shared record is refused -> it is picked up); `bt32-pass-probes` (the `followup` hold, removed with the field; a clean status now excludes `.box/`).

**Left.** Bite check; docs (`BOUNTY.md` line 144 and around, `CONTRACTS.md` line 163, `MEMORY-SPEC.md` lines 68, 134, 138; `nextStep` wording for rows that stay shared; K40 BACKLOG item); merge master in; verify; sandbox proof with a fresh session; close.
