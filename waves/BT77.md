# BT77: "never publish" covers every copy of the repository

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT77` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Bug fix playbook; principles: fix-root-causes, model-the-domain, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `post`. The owner asked for it ("Yes, brief it"). Hard stop 1: never-ship files never enter a bounty.

**Why.** The owner's settings are keyed by the repository's GitHub address (`owner/name`), with one exception: the two publish lists (BT8c), `publishing` in `settings.ts`, are keyed by the checkout's **folder path** (`folderEntry` in `folder.ts`; `changePublishList` and `publishLists` in `never-ship.ts`).

So `config add never-publish notes/private.md` in `C:\work\app` protects nothing in a second clone at `C:\work\app-2` of the same repository, or in a fresh clone after the first folder is deleted. The built-in rules and `.boxignore` still apply there; the owner's own list does not. BOUNTY.md says the list is kept out of "every bounty". A file the owner called private is private in every copy of the repository, so that is what the list should mean.

`safe to publish` loosens a guard (the scan does not hold on it), so it stays per folder: widening it would be the wrong direction.

## Outcome

1. A `never publish` entry is kept for the repository (its GitHub address) and applies in every checkout of it on this machine, in create, post, the outbound check (BT69), and a returned solution.
2. Entries written before this wave, keyed by folder, still apply in that folder. For a checkout, the list in force is the union of:
   - the repository's entries;
   - that folder's old entries.

   Nothing is migrated or rewritten on load.
3. A checkout with no single GitHub address (no remote, or several): `add never-publish` still works and is kept under the folder as today, and `config` says it covers only this folder.
4. `config` states where each entry applies: `never publish: notes/private.md (every copy of owner/name)` or `(this folder only)`.
5. BOUNTY.md gains one honest-limit sentence: the settings file lives under the owner's own account, and an agent running as that account can edit it; the tool cannot prevent that, as Git cannot for its own config.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master.
2. **Settings:**
   - add `neverPublish?: Record<string, readonly string[]>` to `OwnerSettings`;
   - in `loadSettings`, accept the key, check each key is a normalized address (`repositoryAddress(key) === key`, as `solving.skip` does) and each list holds strings;
   - add the key to the allowed top-level names.
3. **Read:** `publishLists(root)` returns `never` as the union of `neverPublish[address]` (when `repositoryIdentity(root)` resolves one) and the folder entry's `never`, de-duplicated without regard to case; and `safe` from the folder entry only. `repositoryIdentity` can throw on a bad remote: a throw means no address, the folder entry alone.
4. **Write:** `changePublishList` for `never-publish` writes to `neverPublish[address]` when an address resolves, else to the folder entry. `remove` removes from whichever holds it (both, if both do). The safe-list check against never entries uses the union.
5. **Show:** `config` prints each entry with where it applies.
6. **Docs:** the two BOUNTY.md sections and the honest-limit sentence; CONTRACTS.
7. **Verify,** surface, proof-map, push, hosted run, Result, merge.

## Traps

- Do **not** put the list inside `repositories[address]`. An entry there means the owner listed the repository for posting (`readDecision`), so adding a never list would silently create a posting decision. Use the separate top-level key.
- A fork is a different address, so a fork's checkout does not inherit the list. That matches every other setting; state it in BOUNTY.md.
- `.box/` inside the repository must never hold the list: `checkProjectClaims` refuses that, and must keep refusing.

## Lenses

- [x] **Security:** attack the union. Try:
  - a second clone whose remote URL differs only in case or a trailing `.git`;
  - a clone with two remotes, one the repository and one a fork;
  - a remote rewritten with `url.<base>.insteadOf`;
  - a folder entry and a repository entry naming the same path in different case.

  Say what each did.

## Notes

- Follows Git's own split: per-repository settings live with the repository's identity, per-checkout ones (`.git/config`, `core.worktree`) with the folder. A path the owner calls private is about the repository's content, so it belongs to the identity.

**Security lens** (a scratch test, deleted, not committed; each asserted):
- A second clone whose remote differs only in case or a trailing `.git` (`https://github.com/OWNER/Project`, `…/owner/project.git`, `ssh://git@github.com/Owner/PROJECT.git`): the entry holds (addresses are normalized).
- A clone with two remotes, the repository and a fork: the repository's entry holds; an `add` there goes to the folder (two unsettled remotes), holds in that clone and not in A.
- A clone of the fork alone: the entry does not hold (another address, as documented).
- `url.https://example.com/elsewhere/.insteadOf` over the GitHub remote: the entry still holds (the read uses the remote as written). A remote spelled `other/thing` and rewritten into `owner/project`: the entry does not hold at `create` there. Nothing can publish from that clone: its post is refused `repository-destination-mismatch`, which no change here touches.
- A folder entry `PROBE-SECRET.md` and a repository entry `probe-secret.md`: listed once; `remove` takes out both.

**Principles.** Model-the-domain: the scope is a typed `NeverEntry`, so `config`, the union and `remove` read one structure instead of two parallel lists. Fix-root-causes: the cause was the key, so the fix is the key, with no copy between folders. Prove-it-works: the post test showed the file reaching the stand-in remote on master before any code changed.
