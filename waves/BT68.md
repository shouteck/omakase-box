## Outcome

A GitHub-marked squash/rebase merge can close and earn payment without the original head surviving. Evidence is GitHub's merged state and merge-result commit, with validated bounty base and landing reachability, never patch likeness. A hand squash GitHub never marked merged stays unrecognised; status states that fact.

## Steps, in order

1. Read BT67's Result. Write the table cases red first; keep its attribution gate on every new recognition path.
2. On the board retain the normal original-head check. When a merged PR's head comparison is `diverged`, read its GitHub merge facts; require base = `box-bounty/<id>` in the right repository and a valid `merge_commit_sha` reachable from default. Persist the landing evidence separately from the original head. Failed reads remain unknown, never eligible.
3. In the CLI, add rewritten-head recognition from GitHub's merged state plus merge-result commit on the creating branch. Validate repository/base and pinned head; do not infer a rewritten landing from original-head ancestry. Preserve ordinary apply/merge/fast-forward paths and BT67's no-payee cases.
4. State the unrecognised hand-squash case and unknown-read case in status, with a next step. Follow `gh`'s merge facts; no commit-message claims or patch-id fallback. Update contracts and surface (`node scripts/surface.mjs --write`) if changed.

Record PRs, head/result SHAs, compares, CLI close and local board payment facts. Use the one sandbox account: different-payee charges stay stand-in tests. No real payment, live board listing or deploy; clean up owned resources.

Board: preserve the original-head compare. For a merged PR whose head is not on default, read `GET /repos/<repo>/pulls/<n>`. Require `merged === true`, bounty base ref, case-insensitive base repository equality, pinned head equality, and a 40-hex merge-result SHA. Compare that result against default in the same direction as the head (`ahead|identical` means reachable). Store verified landing evidence separately. Failed or odd reads store no landing evidence and retry later. Payment eligibility becomes original head on default OR verified landing on default, still excluding `head_on_default_at_sight === 1`; listed rules remain unchanged. Bound the added reads within the refresh read budget.

CLI (part B): for a seen PR attempt absent from the creating branch, read the same merge facts and validate them. The merge-result commit must exist locally, descend from the posting base and be reachable from `refs/heads/<creating branch>`. Close using the original-head attempt so BT67 still decides attribution; record the landing separately. No patch-id or commit-message inference. Status will state unmarked hand-squash and unknown-read cases with a next step.

Part B implementation: the existing original-head scan keeps priority. Only an unexplained tip strictly after the posting base starts PR-detail reads; the existing `rev-list --parents` proves local presence, descent and reachability without extra Git starts. `landingChecks` stores unknown, waiting, closed-unmerged and not-landed outcomes for text and JSON. Settled results are memoised per `(pr, head, tip)`; unknown reads retry on the next command. Applied events add `landing`; attempts retain their original head. K14 budgets are unchanged. The generated JSON surface additions are intentional; no existing CLI test expectations are changed.
