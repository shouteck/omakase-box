# BT71: the dispatcher decides from the parsed command line, not the raw words

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT71` · Timebox: 90 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-14-tool-convention
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of the dispatcher with the owner, who said "Yes, brief it". `runBounty` in `packages/box-cli/src/bounty.ts` reads every option through `parseOptions` (`packages/box-bounty/args.ts`). That parser knows that the word after a value-taking option is its value, and that `--name=value` carries its value inside it. Three decisions are made earlier, by searching the raw words, and do not know either rule (lines as read on 23 November 2026):

- **Line 81, `jsonRequested = bountyArgs.includes('--json')`:** a value that happens to be `--json`, as in `close bt-x --reason --json`, records the reason "--json" (the parser reads it as `--reason`'s value) and also switches the whole answer to a JSON document.
- **Line 111:** whether the board is told at exit is skipped for `take … --preview` and `status … --wait/--timeout` by the same raw search, so `create --why --preview` (a why that reads "--preview") is judged by a word that is a value.
- **Lines 112 and 116, the board hint at exit:** `bountyArgs.indexOf('--repo')` and the next word find the repository. `--repo=C:\other` is accepted by the parser and used by the command, but this search misses it. The hint is then looked up in the current folder, so the repository the command acted on tells the board only at some later command, and the "the board has not been told" line reads the wrong repository's state.

**One more, the same class of fault:** the top-level help list is typed out by hand in both entry files (`HELP_LINES` in `packages/box-cli/src/box.ts` and `src/cli.ts`), from a hand-kept list of names. A new command in `BOUNTY_COMMANDS` works but is missing from `omakase-box --help` until someone edits both.

## Outcome

Each of the three early decisions uses the parser's own reading of the words: a word that is an option's value is never taken as an option, and `--repo=<path>` is found as surely as `--repo <path>`. One small reading, shared by the three, made by the same walk `parseOptions` uses, so the two cannot disagree. The top-level help list is built from `BOUNTY_COMMANDS` in one place both entry files import. No command, option, refusal, exit code or JSON field changes: `node scripts/surface.mjs` shows no difference.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** `tests/box/bounty/bt71.test.ts`, through the built CLI (`CLI_DIST` from `support.ts`) and in-process where possible:
   - row 1: `close <id> --reason --json` in a fixture with one open bounty: exit 0, standard output is text (not JSON), and the record's reason is `--json`;
   - row 2: `close <id> --json --reason x`: one `box-bounty/close@1` document;
   - row 3: `post <id> --repo=<path>` from a different working folder, with the stand-in board (`tests/box/bounty/board-standin.cjs`, as `bt61-solver.test.ts` starts it): the board received the hint for `<path>`;
   - row 4: `post <id> --json --unknown-flag`: one `box-bounty/refusal@1` document, exit 2;
   - row 5: `omakase-box --help` equals the text captured from master before the change, and names every command in `BOUNTY_COMMANDS` but `overview`.

   See rows 1 and 3 fail on today's code.
2. **The shared reading,** in `args.ts`, next to `parseOptions`: `export function readCommandLine(command: string | undefined, argv: readonly string[]): { readonly switches: ReadonlySet<string>; readonly values: Readonly<Record<string, string>> }`. It walks the words with the same rule `parseOptions` uses to skip an option's value (its step 1 loop) and splits `--name=value`, but **never throws**: an unknown option or a bad combination is ignored here, since this reading only answers "was `--json` asked for", "which repository" and "was `--preview` or `--wait` asked for". For an unknown command, or none, fall back to the overview's table. Reuse the existing value-skipping logic; do not write a second rule that can disagree.
3. **Use it in `bounty.ts`:**
   - `jsonRequested = readCommandLine(subcommand, bountyArgs).switches.has('--json')`;
   - line 111's three raw checks become `.switches.has('--preview')`, `.switches.has('--wait')` and `'--timeout' in .values`;
   - lines 112 to 116: the repository is `.values['--repo']` resolved, else `process.cwd()`.

   Nothing else in `runBounty` changes.
4. **The help list:** one exported function in `args.ts`, `topLevelUsage(): string[]`, that builds the same lines `HELP_LINES` holds today, the command names in today's order (keep a small ordered list there; the test of row 5 fails if a command in `BOUNTY_COMMANDS` is missing from it). `box.ts` and `cli.ts` both import it. Compare the text with the snapshot before committing.
5. **Verify:**
   - `node scripts/surface.mjs` (no difference);
   - `node scripts/verify.mjs test:box-bounty test:kitchen` locally (the working rule: before pushing);
   - push, read the hosted run, Result, merge.

- The value-skipping rule lives in `parseOptions`'s first loop: a token that starts with `-`, is not `-`, has no `=`, and names a value option skips the next word. Share it; do not copy it.
- `bt40.test.ts` keeps its own set of command names for `next:` steps. Leave it; it checks something else.
- No expected outcome of an existing test changes. If one would, stop: it means the reading changed behaviour beyond these cases.
