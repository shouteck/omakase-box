# BT89: the owner's three commands, designed once: one table, one way to set each decision, old spellings kept

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT89` · Timebox: 360 minutes (a design part, the owner's approval, then the build); at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-loosening-needs-the-owner
Horizon: long: the surface every other command relies on, with no settled precedent here (KITCHEN.md, "Design decisions with no precedent"); starts with `/plan`. Refactoring playbook, design first; principles: model-the-domain, subtract-before-you-add, encode-lessons-in-structure, prove-it-works.

**Brief.** (No owner decision yet: the table this wave writes becomes one when the owner approves it.) Written by the CTO on 24 November 2026 from the walkthrough of `config`, `allow` and `deny`. The owner: these look simple, everything relies on them, and agents learn them from our references, so "we can't afford to fail" ("yes"). The wave has two parts with the owner's approval between them: no product code changes until the owner approves the table.

**Why.** The three commands are the right three. Every permission system has a grant, a revoke, and a read with preferences, and keeps them apart:
- `ufw allow` and `deny`;
- Claude Code's `allow`, `ask` and `deny` rules;
- phone permissions and OAuth consent, both revocable;
- `git`, `npm` and `gh config` for preferences, with `gh auth` kept apart from `gh config`.

Ours already does several things those tools are known for:
- `config` names where each decision comes from ("by the all-projects setting" or "by this repository entry");
- a deny beats all-projects;
- `config --json` reads reliably;
- unknown settings are refused;
- writes are whole or nothing (BT22).

What is not right is the line between the commands, and how many ways there are to set one thing:

| Decision | Set today by |
|---|---|
| may agents post on this repository | `allow`, `allow --ask`, `deny` |
| may agents post on every project | `config set all-projects true\|false\|ask` |
| may agents take bounties (solving) | `config set solving off\|ask\|allowed` |
| may an agent take this one bounty | `allow <id>` |
| the reward and its limit | **both** `allow --reward/--reward-limit` **and** `config set reward/reward-limit` |

A yes or no about what agents may do goes sometimes through `allow` and sometimes through `config`, and one value has two spellings. Agents learn the spellings from many places, and those places drift apart. Today they include:
- `describe` (`packages/box-bounty/wording.ts`);
- the instruction block (`instructions.ts`);
- the published skill (`docs/box-v4/launch/skill-repo/skills/omakase-box/SKILL.md`);
- `AGENTS.md`'s "Handing work off";
- FIRST-FIVE-MINUTES.md, BOUNTY.md and `docs/box-v4/launch/getting-started.md`;
- the board's `llms.txt` and pages;
- every refusal's `next:` line.

## Outcome

### Part 1: the design (no product code)

1. **`docs/box-v4/OWNER-SURFACE.md`: one table of every owner decision and setting.** For each row:
   - what it means;
   - its scope (one repository, every project, or one bounty);
   - what wins over what;
   - its default;
   - **whether a change to it tightens or loosens** (owner, 24 November 2026, D-2026-11-24-loosening-needs-the-owner);
   - **the one command that sets it;**
   - how a program reads it (`config --json`, the field path);
   - the old spellings that keep working.

   The proposed line, for the owner to approve or change:
   - **`allow` / `deny`: every yes or no about what agents may do.**
     - Posting on one repository: `allow <owner/name>`, `--ask`, `deny <owner/name>`.
     - Posting on every project: `allow --all-projects`, `--ask`, `deny --all-projects`.
     - Solving: `allow solving`, `--ask`, `deny solving`.
     - Answers to a held post, merge or take: `allow <id>`.
   - **`config`: amounts, lists and preferences, and reading everything.**
     - Reward and limit.
     - The solving floor, pays-on-merge only, and the skip list.
     - The publish lists.
     - Instructions and the board address.
     - `paid`.
   - **Tightening is the agent's, loosening is the owner's.**
     - **Tightening** may be done by an agent with no confirmation: `deny`, lowering a reward or limit, adding a never-publish path, turning solving off, raising the solving floor. A mistake only fails safe.
     - **Loosening** needs the owner: `allow`, raising a reward or limit, removing a never-publish path, turning solving on, lowering the solving floor, removing a skip, setting `all-projects` on.
     - The table names each row's direction, and a change that both tightens and loosens counts as loosening.
   - **One way to set each value:** `allow --reward/--reward-limit` either goes, kept as an old spelling, or becomes the one way. The table says which, with the reason.
2. **The references, written down:** one paragraph each on what the table takes from them and what it deliberately does not. For loosening:
   - [Claude Code's protected paths](https://code.claude.com/docs/en/permission-modes): writes to its own settings folder always prompt the human in the default modes, and allow rules cannot pre-approve them;
   - [Codex's approval policies](https://developers.openai.com/codex/agent-approvals-security): the agent pauses for the human before going beyond its sandbox;
   - [GitHub's sudo mode](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode): fresh proof of identity before a sensitive action;
   - [Stripe CLI's login](https://docs.stripe.com/cli/login) and its `--non-interactive` form: a code confirmed in the browser, and for hosts with no terminal a printed address, code and next command, never a skip flag;
   - [MCP's elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation): anything sensitive goes to a page the human opens.

   And for the rest:
   - `git config` (scopes, `--show-origin`, get/set/unset/list);
   - `gh` (`auth` apart from `config`);
   - `npm config`;
   - Claude Code's permission rules (allow, ask, deny; deny wins; scopes);
   - `ufw`;
   - OAuth consent and phone permissions (revoking is as easy as granting; the grantee cannot grant itself; we cannot have that, and BT88 records instead).
3. **Every place that teaches a spelling,** found by search and listed in the design with what it says today.
4. **The design goes to the owner,** with the table and one recommendation per open choice. **Stop here until the owner approves.** The approved table is recorded as a decision in `docs/box-v4/DECISIONS.md`.

### Part 2: the build (after approval)

5. **Loosening asks the owner in the terminal.**
   - A loosening command prints the change in plain words, then asks the owner to type the repository name, or `all-projects`, or `solving`, to confirm. This is the same move as GitHub's "type the repository name to delete it".
   - **There is no flag to skip it:** an agent would pass it.
   - With no interactive terminal (`process.stdin.isTTY` and `process.stdout.isTTY` both true), the command refuses `owner-confirmation-needed`, changes nothing, and names the step: "this loosens your settings; run it in your own terminal". [BT90](BT90.md) adds the board's address-and-code way for hosts with no terminal.
   - Tightening never asks.
   - **The tool states the limit once:** "this stops an agent loosening your settings by accident or in passing; a determined program can imitate a terminal, and BT88's log records every change either way".
   - **The false claim goes:** `solving.ts` and `config` say solving's limits are ones "your agents cannot loosen". The words change to what is true: an agent cannot lower them without the owner's confirmation.
6. **Each decision has its one command, as the table says.** Every old spelling keeps working and prints one line: "this is now `omakase-box …`; the old spelling still works". No agent's existing instructions break, and no old spelling is removed in this wave.
7. **Every teaching place says the new spelling only,** including every refusal's `next:`.
8. **The table is pinned by a test,** `tests/box/bounty/owner-surface.test.ts`, which reads `OWNER-SURFACE.md` and fails, naming the row and the file, when:
   - a command the table names does not do what the row says (run against a scratch owner folder);
   - a teaching place names a spelling the table does not list as current;
   - `config --json` lacks a row's read path;
   - a setting exists in `settings.ts` with no row;
   - a row marked loosening changes the setting without a terminal (run without one, it must refuse and leave the file byte-for-byte as it was).

## Traps

- **Agents' copies of the instructions live in other people's projects** (the instruction block written by `config set instructions true`), and are never updated by a release. An old spelling must therefore keep working indefinitely, not just for one release.
- **`allow <owner/name>` releases waiting bounties as it writes** (`allowRepository`). The new spellings must keep that exactly, and so must the old ones.
- **The setup lines teach the agent to grant itself** (found in the walkthrough of `setup`). `SETUP_LINES` (`packages/box-bounty/wording.ts`), printed by bare `omakase-box` in a repository not yet set up, tells the agent:
  - to ask the owner, then "3. run it";
  - "the answers are the owner's to give, unless they leave them to you", so the agent may choose the reward and the limit itself.

  After this wave the agent proposes, and the owner confirms: in their terminal, or on the board after [BT90](BT90.md). The money is never left to the agent's choice: the lines say so, and a pinned test checks they do. The published skill's "Standing approval: `omakase-box allow`" line changes the same way.
- **Agents set the owner up today by running `allow` after the owner says yes in chat.** After this wave that refuses with no terminal, and the refusal must name the step for the owner in plain words. The owner block the tool prints for agents (`ownerWaitLines`, `gate.ts`) changes to "ask the owner to run this in their own terminal". [BT90](BT90.md) restores a no-terminal way.
- **Tests run without a terminal,** so the confirmation is tested through the function that reads the two terminal facts, with them injected, as BT88 does.
- **The owner's interface stays three commands**: no new top-level command, per the owner's rule.
