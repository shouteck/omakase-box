# BT33: the shared memory can sync privately, through a free online database

Milestone: BT · Station: packaging · Base: master at dispatch, after BT32 · Branch: `wave/BT33` · Timebox: 210 minutes; at expiry the cook stops and reports where it is

**Brief.** Approved by the owner on 17 October 2026 (all five decisions below). Written by the CTO on 17 October 2026 at the owner's request: "let's start creating a wave for the syncing to a private online database, a free one," after choosing the committed shared file as "public for now" and calling the private store "the most scalable and right approach". K27 named Turso as the private destination (`kitchen/reviews/K27-storage.md`, steps 3 and 6). BT32 built the shared part behind one interface (`appendShared` / `readShared` in `packages/box-bounty/shared.ts`) so a destination could be added without touching callers. Detailed for a cook without deep reasoning. **This wave creates no account, holds no real token, and never contacts a real Turso database: everything is proven against a local stand-in.** Using a real database is the owner's own step, after the merge.

## Why

With the committed file, the project's shared bounty memory (purposes, whys, what was tried, larger jobs, outcomes) is public in a public repository, and a teammate sees a new bounty only after a `git push` and `git pull`. A private online store fixes both: the notes are readable only with the owner's credential, and every machine sees a milestone moments after it happens.

## Outcome

An owner who chooses it can point a repository's shared memory at their own free Turso database with `config`; from then on each milestone writes **the outline** of the bounty to `shared.jsonl` as before (so the project still carries its bounty memory) and **the private detail** to Turso, any machine with the credential imports it within one command, nothing private is written to the repository, the tool keeps working offline and catches up later, and the default (the committed file) is unchanged for everyone else.

## Decisions built into this brief (all five confirmed by the owner on 17 October 2026)

1. **Turso, through its HTTP API, with no new dependency.** The package stays one file with no native addon (BT12). Turso's own client library with "embedded replicas" needs a native module, so the tool talks to Turso's HTTP endpoint with Node's built-in `fetch`, and the local `node:sqlite` database (BT31) is the local copy. The tool does its own small sync (below).
2. **Per repository, and off by default.** The choice lives in the owner's settings for one repository; every other repository keeps the committed file.
3. **The credential never sits in the repository or in `settings.json`, and never enters an agent's context.** It is stored once, in a separate file in the owner's settings folder (`credentials.json`, readable only by the owner's account), or comes from an environment variable (`BOX_TURSO_TOKEN`), the way `gh`, npm and the AWS command line keep tokens. The command that saves it reads the token from standard input (typed or **piped**) and never prints it.
4. **Switching to private does not unpublish.** Lines already committed to `shared.jsonl` stay in Git history. On switching, the tool copies them into the private store and says once that earlier lines remain public in history.
5. **The owner's agent does the setup; the owner only signs in** (owner, 17 October 2026: "some of these can be done by an agent"). The owner creates the Turso account, signs in (`turso auth login`), and approves installing Turso's command line. Everything else is the agent's: create the database, read its URL, set `shared-store` and `turso-url`, and save the token by **piping it straight from Turso's command line into the tool**, so the agent never sees it: `turso db tokens create <db> | box bounty config set turso-token - <owner/name>` (check the exact Turso command in Step 0).
6. **In Turso mode the project still carries the outline; only the private detail leaves the repository** (owner, 17 October 2026). The shared part (BT32's `SHARED_FIELDS`) is split in two by one constant, `PRIVATE_SHARED_FIELDS` in `shared.ts`: `why`, `resume.note`, and `content.note.text`. **The outline** (every shared field except those) keeps being appended to the committed `shared.jsonl`: id, title, stage, dates, part-of, the task, the issue link, the outcome; all of it already public on the GitHub issue. **The private detail** (only those fields, with the bounty id and time) goes to Turso. A clone without the token still sees which bounties exist, what they were for and how they ended; a machine with the token also sees why each was handed off and what was tried.

## The design, exact

1. **Settings (owner side, `config`, no new command):**
   - `box bounty config set shared-store turso <owner/name>` and `box bounty config set shared-store file <owner/name>` (default `file`);
   - `box bounty config set turso-url <libsql://… or https://…> <owner/name>`;
   - `box bounty config set turso-token - <owner/name>` reads the token from standard input, writes it to `credentials.json` in the settings folder (created with owner-only permissions: `0600` on Linux; on Windows rely on the user profile folder and say so), prints only "token saved for owner/name; it is never shown again". `BOX_TURSO_TOKEN` in the environment overrides the file.
   - `config` shows `shared-store: turso (url …; token: saved | from environment | missing)` and never the token.
   - **The tool guides the agent.** After `config set shared-store turso <owner/name>`, and whenever `config` shows a missing URL or token, it prints the next commands in order, one per line, including the exact safe pipe for the token (decision 5), and nothing that would make the token appear in output. An agent that has never used Turso can finish the setup from these lines alone.
2. **The remote table**, created by the tool on first use if absent: `box_shared(seq INTEGER PRIMARY KEY AUTOINCREMENT, repo TEXT NOT NULL, bounty TEXT NOT NULL, at TEXT NOT NULL, line TEXT NOT NULL)`, with an index on `(repo, seq)`. One database can serve many repositories; rows are keyed by the repository's GitHub address.
3. **Writing (push):** at each milestone BT32 already detects, the shared line goes into a local **outbox** table in `box.db` in the same transaction as the record. After the transaction, the tool sends the outbox to Turso (one pipeline request, the lines in order) and deletes the sent rows on success. On failure (offline, cold start, rejected credential) the rows stay and are retried on later commands. **The agent is told once per spell, not on every command** (owner's question of 17 October 2026, "is this going to put much load onto agents?"; BT17's said-once rule): the first command that fails to sync says one line, `shared memory not synced yet (reason); the tool will keep trying`; later failing commands say nothing; the first command that succeeds again says `shared memory synced (<n> waiting lines sent)`. Store the spell's state in `box.db`'s `meta`. `status --full` and `status --json` always show how many lines are waiting. The milestone itself never fails because the network did.
4. **Reading (pull):** at most once per command, and **only when the last successful pull is more than 60 seconds old** (agents run commands in bursts; a burst costs one request), before answering, the tool asks for rows `WHERE repo = ? AND seq > ?` using a cursor stored in `box.db`'s `meta`, imports them into the `shared` table exactly as BT32 imports `shared.jsonl` lines, and advances the cursor. Bound the request (for example 500 rows; continue only if a command truly needs more). A command that reads nothing shared (`help`, `describe`) does not contact Turso.
5. **Time limits:** every request has a short timeout (choose it from Step 0's cold-start finding and say why). A timeout is the offline path, not an error.
6. **Switching file → turso:** copy the private fields of every existing `shared.jsonl` line into the remote table (skip lines already present by `(repo, bounty, at)`), and from then on append outline-only lines to the file; leave existing lines in place, and say once that they stay public in history. Switching turso → file: append full shared lines to the file again (the private fields will then be public; say so plainly before the first such line, once); nothing is deleted remotely.
7. **Never in the repository:** with `turso` chosen, no new line in `shared.jsonl` contains a `PRIVATE_SHARED_FIELDS` field, and the URL and token appear in no file under the repository.
8. **Reading both:** import merges by bounty id: the file's outline, then Turso's private detail for the same id overlaid on it. A bounty with an outline but no reachable detail (offline, or no token) shows without its why, and `status --full` says `why and what was tried: private, not available here`.
9. **Errors by name:** `turso-token-missing`, `turso-token-rejected`, `turso-unreachable` (offline or timeout), `turso-response-invalid`; each says what happened and the next step, and none prints the token.

## The stand-in (no real account anywhere)

A small HTTP server in `tests/box/bounty/turso-standin.ts`, started per test on `127.0.0.1` with a random port, implementing only the pipeline requests the tool sends, backed by an in-memory `node:sqlite` database. It checks the `Authorization` header against a test token generated in the test (never a real one), and can be told to fail, time out, or answer as a waking database would (per Step 0). Make it answer in the exact shapes Step 0's documentation shows, and quote the documentation in a comment above each shape.
