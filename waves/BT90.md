# BT90: an owner with no terminal approves a loosening on the board, signed in with GitHub

Milestone: BT (the bounty tool), with a board part · Station: packaging · Base: `master at dispatch`, after [BT89](BT89.md) · Branch: `wave/BT90` · Timebox: 360 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-loosening-needs-the-owner, D-2026-11-24-board-only-what-needs-a-website, D-2026-11-02-site-looks-need-approval
Horizon: long: a new flow across the tool and the board, with a signing key; starts with `/plan`. Feature playbook; principles: boundary-discipline, type-system-discipline, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 after the walkthrough of `config`, `allow` and `deny` ("yes"). It is placed before launch, because launch is when owners whose agents run in the cloud arrive.

**Why.** After BT89, a change that loosens the owner's settings asks the owner in the terminal, and refuses with no terminal. Many owners run their agent where there is none: a cloud agent, or a desktop app's agent. Today they could not loosen anything at all.

The established answer for hosts with no terminal is an address and a code confirmed in the browser, never a flag that skips the confirmation:
- `stripe login --non-interactive` prints the browser address, a verification code and a `next_step` command;
- `gh auth login` uses GitHub's device flow;
- MCP's elicitation sends anything sensitive to a page the human opens ([BT89](BT89.md), the references).

Approving on the board is a step only a person can do, which is the board's role now (D-2026-11-24-board-only-what-needs-a-website).

## Outcome

1. **With no terminal, a loosening command asks the board instead of refusing.**
   - It sends the board a request: what changes, before and after, in plain words, and a digest of the exact change. The board answers with a short request id and a code of three words.
   - The tool prints, and changes nothing:

     ```
     this loosens your settings: <the change in plain words>
     approve it at <board>/approve/<id>/ (code: <three words>) while signed in to GitHub as <owner account>
     next: omakase-box allow --approved <id>
     ```

     The next command is the same for every kind of loosening.
   - The request expires after 15 minutes and can be used once.
2. **The board's approval page** shows the change in plain words, the code, and which machine's request it is (the account, and the time asked).
   - Only the GitHub account named in the request may approve it.
   - Approve and Decline are both one click.
   - The board keeps nothing after the request expires but a count. `/privacy/` says so.
3. **The board signs its answer.**
   - An approval is a statement signed with the board's own Ed25519 key: the id, the digest, the account, the time.
   - The tool carries the board's public key, pinned in the package, and checks the signature itself.
   - So a changed board address, or a server imitating the board, cannot approve anything: the signature would not verify.
4. **`omakase-box allow --approved <id>`** fetches the answer and checks three things:
   - the signature;
   - that the digest matches the change it asked for, recomputed from the current settings;
   - that the account matches the owner's GitHub account on this machine.

   Only then does it apply the change and record it in BT88's log as "approved on the board". Anything else refuses and changes nothing: declined, expired, a different change, a bad signature, a different account.
5. **The board address is itself a loosening setting** (`config set board`), confirmed the same way. A request made to a board whose key does not verify can never approve anything.
6. **The owner's text the tool prints for agents** (the owner block, `gate.ts`) names both ways: "run this in your own terminal, or open the address and approve it while signed in to GitHub".

## Stops

- A new secret on the live board is the owner's to set at deploy. If the flow needs any other new service or cost, stop and bring the owner one recommendation.

## Traps

- **The signing key never enters the repository, a log or the Result.** Only the public key is committed. Read keys from the environment the owner sets, never from `.env*` or `secrets/` (AGENTS.md rule 5).
- **An agent with the machine's `gh` token is not signed in to the board.** The board's sign-in is GitHub's web flow, which needs the human's browser session. Say in the Result what this does not stop: an agent driving the owner's own signed-in browser.
- **Hash the change from the settings as they will be,** not from the command's words, so that two spellings of one change give one digest.
- **Rotating the key:** the tool must accept more than one pinned key, so a rotation needs no release on the same day. `DEPLOY.md` says how.
