# PF32: an owner lists an existing GitHub issue as a bounty from the board

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF32` · Timebox: 480 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-04-dual-usage, D-2026-11-04-a-bounty-is-its-own-issue, D-2026-11-01-pay-on-merge, D-2026-11-02-site-looks-need-approval
Horizon: long: a new way in onto the existing board; starts with `/plan`. Feature playbook; principles: model-the-domain, experience-first, prove-it-works

**Brief.** Written by the CTO on 4 November 2026, from the owner's talk the same day. After PF31, before launch. The owner will email maintainers who already put money on GitHub issues elsewhere and ask them to sign in and list the issue here. Not a small wave, but not a second system: a second way in onto everything the board already does.

## Outcome

A maintainer with no CLI signs in to the board with GitHub, pastes the address of an issue on their public repository and a reward, and it is a bounty like any other: listed in the feed, the pages, MCP and `discover`, taken by agents or people, merged by the owner on GitHub as they always have, then owed, paid and recorded the same way as a bounty the tool posted. The issue on GitHub is never edited.

## The model: one bounty, two ways in

| Step | Agent way (CLI, today) | Human way (this wave) |
|---|---|---|
| Posting | the agent packages and posts a new issue | the owner references an existing issue on the board |
| Where the reward lives | the tool's block in the issue | the board, as the owner's own word at listing |
| Who approved | the owner's standing rules | the owner, themselves, signed in |
| Starting commit | packaged by the tool | the default branch's head at listing |
| Pull requests belong to it | they target the bounty branch `box-bounty/<id>` | they close the issue: "Fixes #N" or GitHub's linked pull requests |
| History | the event chain `refs/box-bounty/<id>` | the board's own records (listing, reward changes, withdrawal) |
| Merging | `apply`, or the owner on GitHub | the owner on GitHub |
| After the merge | owed, paid, recorded: shared | owed, paid, recorded: shared |

Everything after "pull requests belong to it" is shared code. A change that copies a shared path for the human way is the wrong change.

## The form (owner, 4 November 2026)

Two fields, both required: **the issue's address** and **the reward in US dollars, more than $0**. No note: the issue already says what is wanted. Payment settings (pay on merge, its limit, ways to pay) stay on Your page; the form links there.

## Rules, in order

1. **Signed in, or nothing.** Listing needs a board session.
2. **The issue must be readable and open** on a public repository, not a pull request, and not on a repository the board never lists (`UNLISTED_REPOSITORIES`, PF9b). Each refusal states its reason and nothing is stored.
3. **Only someone who can stand behind it lists it:** the issue's author, or a person with write access or more to the repository. The board keeps no GitHub token today (sign-in asks no scope and the token is used once). Plan: listing runs a fresh GitHub authorisation (silent when already granted), uses that token once for the repository's `viewerPermission` and the issue's author, then drops it. The plan step confirms this works with a no-scope token on a public repository before building on it.
4. **One bounty per issue.** An issue already a bounty (either way) refuses, naming the existing bounty.
5. **The bounty's id** has the tool's shape (`bt-` and 12 hex) and can never equal one the tool made or will make. The plan says how.
6. **The reward is the owner's word,** shown as theirs. A change to it is a fact in the bounty's history with its time; it never rewrites the earlier amount. Withdrawing is a button for the owner and also happens when the issue is closed unmerged on GitHub.
7. **Pull requests:** the board reads the issue's closing pull requests (GitHub's `closedByPullRequestsReferences`, including closed ones) as the bounty's pull requests, into the same `pull_requests` rows, with the same draft, head, checks and on-default facts. A merged one landing on the default branch is the merge; "merged takes all" and the payee being its author hold unchanged.
8. **Everything after the merge is unchanged:** owed, one click, by hand, pay on merge (the board's own settings, so it should work; the plan confirms it from `charge.ts`), the owner's record, self-dealt merges left out, the numbers.
9. **The CLI's solver side works on both:** `discover` shows it, `take` opens the draft against the default branch with "Fixes #N" in its body instead of against a bounty branch, `submit` and `status` read it. The poster-side commands (`look`, `apply`, `close`) refuse a bounty the tool did not post, naming the board's page.

## Traps

- **The refresh drops what it cannot read as the tool's.** `readIssueAgain` removes a bounty whose issue lacks the tool's block, and every open bounty the label search does not return goes through it. A listed issue has no block and no label, so without a change the next run deletes it. The board's reading must know which way a bounty came in.
- **Search finds only the label.** Listed bounties are never in it; their freshness comes from the due list (PF28), not the search.
- **Read budget.** The closing-pull-request read replaces the branch list read for these bounties; it must not add a read per run for every bounty. The `refresh.test` call budgets stay unedited.
- **Text from strangers.** The task shown is the issue body, the issue author's text, attributed and escaped as today; nothing from it is stored as the board's words.
- **Look change.** The form and any page change need before-and-after screenshots and the owner's approval before merging.

## Lenses

- [ ] **Security:** nobody can list an issue they cannot stand behind; no GitHub token is kept; a stranger's text is never shown as the board's.
- [ ] **Measurement fairness:** listed bounties count in the numbers exactly as posted ones do, and no test listing survives the wave.
- [ ] **Shared paths:** no copied payment, record or listing code for the human way.

## Settled with the owner in PF31's mock-up (4 November 2026)

- **Whom to pay:** the owner chooses, merged or not; the board never decides; one solution is paid. The window lists only the solutions (person, pull request, open or merged), then every way the chosen person can be paid. The card's tile reads "Reward · N solutions · You choose whom to pay"; nothing says "owed".
- **Open to answers:** "How to answer" (and the bounty as open in the feed) ends at whichever comes first: a payment made or recorded, the issue closed on GitHub (a "Fixes #N" merge closes it), or the owner's withdrawal. The agent way keeps "until merged or closed".
- **The candidates in "Whom are you paying?"** (owner, 4 November 2026): every pull request linked to the issue, merged or not, as GitHub records the link (a closing keyword such as "Fixes #12", or a link in the issue's sidebar). Each is a GitHub account; signing in to the board only changes how that person can be paid.
- **The same list for the agent way** (owner, 4 November 2026): when a bounty posted with the tool shows more than one merged pull request (someone merged by hand on GitHub), the owner chooses whom to pay from every pull request on the bounty, merged or not, the same as the human way; one is paid. This changes who the board may record as paid (`payeeOf`, `recordPaid`, the owner's record and the numbers), so it is built here once for both ways, with one click to the chosen person. PF31 shipped with the earlier rule for that case (choose among the merged).

## Plan

Written by the CTO at kickoff, 5 November 2026. Feature playbook; principles: model-the-domain, subtract-before-you-add, prove-it-works.

- **The settled section wins over rule 7.** For a listed bounty the owner chooses whom to pay from every linked pull request, merged or not; for a tool-posted bounty the merged author is paid, and the rare two-merged case uses the same chooser. One function decides who may be recorded as paid (`payeeOf` and `recordPaid` today), for both ways.
- **The model: a bounty has a source.** `bounties.source` is `posted` (the tool's block, today) or `listed` (the board form). Every place that reads a bounty's shape asks the source once: the refresh (`readIssueAgain` keeps a listed bounty with no block), the pull-request read (bounty branch for posted, the issue's linked pull requests for listed), How to answer, and the stage rules. One migration adds `source`, `listed_by_id`, and a `reward_changes` table (history, never rewritten).
- **The id:** `bt-` and 12 hex from the issue's own GitHub node id hashed, so one issue gets one id, and it can never equal a tool id (the tool's are random; a collision with an existing id refuses).
- **Who may list (rule 3), tested live first:** the board's sign-in asks GitHub for no permissions. Listing runs that sign-in once more (silent if already granted), reads the issue (its author) and the repository with that token (`permissions.push` or more), uses the token once and drops it. GitHub documents that a no-permission sign-in reads public repository information; whether the repository's `permissions` field comes back with it is not documented, so the first build step checks it once on the live sign-in. If it does not, the rule is the issue's author or the repository's owner (personal repositories), which needs no permission at all, and the plan comes back to the owner.
- **Linked pull requests:** GitHub's `closedByPullRequestsReferences` (GraphQL, including closed ones) for a listed bounty, into the same `pull_requests` rows; one read per bounty in its due turn, replacing the branch list read, so the refresh budgets stay unedited.
- **Order:** the source and the refresh (a listed bounty survives runs) → listing and its refusals → linked pull requests → whom-to-pay for both ways with one click to the chosen person → the form, How to answer for listed bounties, the CLI's `take` and refusals → tests, each guard broken once → as-built page → the real run → verify.
- **Gates:** a mock-up of the listing form and of a listed bounty's page before their code (the windows were approved in PF31); the as-built page compared screen by screen before merge.

### Two decisions for the owner

1. **When is a listed bounty "owed" in the owner's public record?** Recommendation: once a linked pull request is merged, it counts as owed to that pull request's author until the owner pays someone (paying anyone, before or after, settles it). Without this, a listed bounty could be merged and never paid while the owner's record stays clean.
2. **The real end-to-end run:** on a local board against the sandbox (recommended; the live board never lists the sandbox), or on the live board with a second public repository (a new remote destination, the owner's call).

**The owner's answers (5 November 2026):** owed "Once merged (Recommended)": a merged linked pull request counts as owed to its author until the owner pays someone; the real run "Local board (Recommended)": a local board against the sandbox.

**Rule 3, as built (5 November 2026):** a no-permission sign-in cannot be tested for real here without the board's secrets (not read) or the owner's hands (tests never need the owner). So the check is ordered so its uncertain part never blocks: the issue's author may list (public on every issue); the repository's owner may list a personal repository (public); anyone else is checked with the one-time sign-in's token (`permissions.push` or more on the repository), and if GitHub's answer has no permissions, the board refuses with its reason ("ask the issue's author or the repository's owner to list it") and stores nothing. The first real listing by a maintainer shows which; the Result names it.

## The human way's life cycle (owner, 5 November 2026; replaces "owed once merged")

- **Facts only, never "owed".** For a listed bounty the owner decides whom to pay and whether to; a merge decides nothing. The page states facts ("#62 by example-quill merged on 3 Nov · no payment recorded"); the owner's public record lists listed bounties with the same facts (merged or not, paid or not, to whom, by which way) and counts none as owed. Agent-posted bounties are unchanged: a merge makes them owed.
- **Only a payment moves it on:** a provider's confirmation of a one-click payment, or the owner's "I've paid" by hand. Choosing a person in the window records nothing.
- **Remove and Withdraw, never both:** nothing merged and nothing paid → Remove from the board; paid by hand → Withdraw this record (after which Remove can return if nothing is merged); paid through Stripe or PayPal → neither; a linked pull request merged and nothing paid → neither (the facts stay visible).
- **Your page:** the owner's tab: Waiting for solutions → Solutions in (a merge shown as a fact: "merged · no payment recorded · you choose whom to pay") → Paid; never Payment due. The solver's tab: In progress (open, or merged with no payment: "the owner chooses whom to pay") → Paid, or Not merged ("Another solution was paid", or closed without a merge); never Payment due, and never in "Owed to you".
