## Why

MEMORY-SPEC.md's requirement R4 is the open one: every project fact must reach every machine and every later agent. K28 studied the tools built for exactly this (git-bug: each entity a chain of commits on its own ref; Beads: a database synced through `refs/dolt/data` on the project's remote) and designed ours as git-bug's shape, simplified: **one ref per bounty, `refs/box-bounty/<id>`, each event one commit holding one small JSON event**, fetched and pushed through the project's existing remote, outside the project's files. Measured with local Git: an event pushed in about 0.3 s and fetched in about 0.5 s; a first fetch of 1,000 bounties in 3 to 6 s; 1.54 MiB on the remote for 1,000 bounties; **nothing** in an ordinary clone, in `git grep`, or in `git log -p` of the branches. Not yet shown: real GitHub (step 0 does it).

The agents' test: the agent with the chains answered the record's questions 6 right, 2 partly; the agent with the public issues alone 3 right, 2 partly, 3 wrong. Its two lessons are built in below: the larger job's standing at handoff is its own field, and payment is its own event.

## The events (schema `v: 1`)

Each event commit's tree holds one blob `event.json`: `{ "v": 1, "type": …, "at": ISO, "actor": "<GitHub login of the pushing account, display only>", …fields }`. The first commit of a chain is the `posted` event (chains start at posting: drafts stay local, the owner's decision). Merge commits hold `{ "v": 1, "type": "merge" }` and nothing else.

| Event | When, by whom | Fields (allow-list) | MEMORY-SPEC facts |
|---|---|---|---|
| `posted` | the tool, at a successful `post` | `id`, `title`, `task` (text as published), `why`, `partOf`, `followup` (the `--resume` note: the larger job and where it stood), `base` (commit), `branch`, `issue` (number, url), `published` (pushed commits, wip summary), `reward` (amount, currency), `allowedBy` (decision, level) | F-id, F-title, F-task, F-done (in task), F-why, F-tried (in task), F-followup, F-partof, F-posted, F-published, F-base, F-allowedby, F-reward |
| `solution` | the tool, at collection (`look`, `apply`, `status` refresh) | `n`, `pullRequest`, `author`, `commit`, `changed`, `added`, `deleted` (paths), `payTo` (the parsed fact's kind only, never the link text) | F-solutions, F-author, F-payee (kind) |
| `merged` | the tool, at `apply` or merge recognition | `n`, `mergeCommit`, `unasked` (true when the owner was not asked) | F-outcome, F-mergecommit, F-unasked, F-outcome-at |
| `closed` | the tool, at `close` | `kind` (`rejected` or `withdrawn`), `reason` (the `--reason` text, if any), `unasked` (for a close-up on GitHub done without asking) | F-outcome, F-closereason, F-outcome-at, F-unasked |
| `paid` | BT36's `config set paid` (defined here, written there) | `amount` (copied from the bound reward), `by: "owner"`, `withdrawn` (true to retract) | F-paid |

**Never in a chain** (machine or owner state, MEMORY-SPEC tiers): `folder`, `resume.branch/commit/changed` (F-localstate), `seenAt` (F-seen), `waiting` (F-wait), `scanFindings` (F-scan), `githubApproval`, `conflicts`, the GitHub refresh caches, rejected solutions' report and description text, the hook's told-once state (F-told), the owner's decision mode and promised total (F-decision-mode, F-promised: owner settings). Solvers' questions (F-questions) are read live from GitHub, not copied.

**Build every event by allow-list projection** (copy only the listed fields), in one module `packages/box-bounty/chain.ts`, never by removing known-local fields.

## The design (K28 step 3, made exact)

- **Writing:** at each milestone, after the local record is written, the tool builds the event, runs the **secret scan** over its text fields (`title`, `task`, `why`, `partOf`, `followup`, `reason`) exactly as the pre-publish scan does (a hit holds it, as a publish hit does), commits it onto the local `refs/box-bounty/<id>` (with `git hash-object`, `git mktree`, `git commit-tree`, `git update-ref`; never touching the working tree, the index or any branch), and pushes the ref (`git push origin refs/box-bounty/<id>`). On a non-fast-forward rejection: fetch, write an empty `merge` commit with both tips as parents, push again; at most three tries, then the push waits for the next command and the tool says once `shared bounty memory not pushed yet (reason); it will be retried`.
- **Reading:** only `box bounty`, `status`, `find`, `status --json` and `hook start` fetch, and only if the last successful fetch is more than 60 seconds old: `git fetch origin "+refs/box-bounty/*:refs/remotes/origin/box-bounty/*"`. Then, for each remote chain whose tip changed since the last import, walk its commits (git-bug's ordering: parents before children; ties by commit id), validate each event (schema, allow-list, sizes: no field above 8,000 characters), and upsert the bounty's shared row into BT31's `box.db` (a `shared` table, plus its `search_text` for `find`). A bounty known locally uses the local record; one known only from chains is shown read-only, and `look`, `apply`, `close` on it refuse `shared-only` ("this bounty was posted from another machine; its issue is <url>; act on it from that machine, or on GitHub").
- **Offline or failing:** answer from the cache; say once per spell `shared bounty memory not refreshed (reason); showing what this machine last saw`.
- **Bounds:** BT28 and BT29's overview bounds apply to the merged set (local plus shared); the unasked block and the hook's start line keep K25's sizes.
- **Recovery:** if a remote chain ref is missing but this machine has it, the next push restores it and the tool says so once. A lost `box.db` is rebuilt from the chains (BT31's store becomes a cache for shared facts; local facts are lost with it, as MEMORY-SPEC says).
- **Merge-commit link** (decision 6).
