# BT32: every agent on the project shares the bounty memory; machine detail stays local

Milestone: BT · Station: packaging · Base: master at dispatch, after BT31 · Branch: `wave/BT32` · Timebox: 180 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 17 October 2026 from K26's memory model (`kitchen/reviews/K26-shared-memory.md`, steps 1, 2 and 5) and K27's shared store (`kitchen/reviews/K27-storage.md`, steps 3 and 6), and the owner's decisions of that day: the shared part is public for now, committed with the code; a private online store (Turso) comes later as a plug-in destination. The third of three waves. Detailed for a cook without deep reasoning.

## Why

K26 placed every record field in one of three tiers (anyone; the project's agents on any machine; this machine only) and proved with three fresh agents that an agent holding only the shared part continued a half-done job as well as one holding the full record, while an agent with only the public issue left the larger job half done. Today, after BT31, everything a bounty knows sits in one machine's database: a second machine, or a later agent from a fresh clone, knows nothing.

## Outcome

When a bounty is posted, and at each later milestone, the tool appends its shared part to a committed file, `.box/bounties/shared.jsonl`; any machine's tool imports that file into its local database and shows the same bounties, purposes, whys, larger jobs and outcomes; drafts and machine detail never enter it; and two branches that both add bounties merge without conflict.

## Scope

- Write: `packages/box-bounty/**` (`store.ts`, a new `shared.ts`, `record.ts`, `create.ts`, `render.ts`, the scan's callers), `tests/box/bounty/**` (a new `bt32.test.ts`), `.gitattributes` writing by the tool (below), `docs/box-v4/BOUNTY.md`, PLAN.md is the CTO's.
- Do not touch: what is published on GitHub (the issue text is unchanged); the hard stops; the database schema of BT31 beyond adding a `shared` table and an import marker.

## The design, exact

1. **The shared field set** is K26's step 5 list, copied into one constant `SHARED_FIELDS` in `shared.ts` with a comment citing K26: identity and milestones (`id`, `title`, `stage`, `createdAt`, `kind`, `schemaVersion`); the knowledge (`why`, `partOf`, `job`, `content.task`, `resume.note`, `noteSource`, and `content.note.text` only when `noteSource` is `authored`; a generated note becomes K26's one-line summary); the shared event fields (`stage`, `at`, `destination`, `merge`, `attempt`) for events at or after `posted` only; the merged attempt's public facts (`n`, `pullRequest`, `author`, `commit`, `changed`, `added`, `deleted`, `payTo`) at the `applied` milestone only; `allowedBy`; `reward`; and the `github` publication facts (`repository`, `account`, `branch`, `commit`, `title`, `body`, `issue`, `state`, `kind`, `base`, `pushed`, `wipCommit`, `wip`, `pay`, `closedNote`, `scanBinary`). **Everything else is local.** Write `sharedPart(record)` as an allow-list projection (copy only listed paths), never as a removal of known-local fields.
2. **When it is written.** Only at milestones: the successful `post` (the first line for the bounty), an applied solution, a close, and a change of `partOf`. Never on a read, never for a draft, never for a record whose stage precedes `posted`. Each write appends one line: `{"v":1,"id":…,"at":…,"shared":{…}}`. The newest line per `id` wins on import.
3. **Where.** `.box/bounties/shared.jsonl`, committed by the agent's or owner's normal Git flow (the tool does not commit or push). The tool writes, once, a `.gitattributes` line `.box/bounties/shared.jsonl merge=union` (append to the repository's `.gitattributes`, creating it if absent, between `# box-bounty` markers, the same marker rule as the instruction block). **Why:** K27 said conflicts "resolve line-wise", but Git conflicts whenever two branches both add lines at the end of the same file, which is exactly what this file does; the `union` merge driver keeps both sides' lines.
4. **Import.** On open, `store.ts` reads `shared.jsonl` if its size or modification time changed since the last import (store both in `meta`), and upserts each `id`'s newest shared part into a `shared` table. A bounty known only from the shared file (another machine's) appears in `status`, `box bounty`, `find`, `status --json`, the instruction block's open line and `OPEN`, read-only: `look`, `apply` and `close` on it refuse by name, `shared-only`: "this bounty was created on another machine; its issue is <url>; you can read it here, and act on it from the machine that created it, or on GitHub". A bounty known both locally and from the file uses the local record.
5. **The secret scan covers the newly shared fields** before any line is appended: `why`, `partOf`, `resume.note`, `content.note.text` (authored). Same scanner, same `hits` shape. A hit holds the append exactly as a publish hit holds a post today (the owner settles it in `config`); the Result names the code path used.
6. **The once-told line at `create`**, K26's exact wording, said once per repository through the BT17 `said` mechanism, within `create`'s output budget: `note: the task, --why, --resume and --part-of are shared with everyone who can read this repository — write them like a commit message`.
7. **The five tracked full records in this repository** stay as they are (K26: the split is not retroactive; `bt23.test.ts` keeps reading them through BT31's JSON import).
8. **The destination is pluggable.** `shared.ts` exposes `appendShared(repoRoot, line)` and `readShared(repoRoot)` behind one small interface, with the file as the only implementation now, so a private store (K27's Turso fallback) can be added later without touching callers. Do not build the Turso adapter.

## Tests (`tests/box/bounty/bt32.test.ts`, K26's five plus the merge and scan cases)

| # | Case | Expect |
|---|---|---|
| 1 | `create` a draft | no `shared.jsonl` line; the once-told line printed once |
| 2 | `post` it | exactly one line; its `shared` object has exactly the allow-listed paths; assert by name that `folder`, `resume.branch`, `resume.commit`, `resume.changed`, `scanFindings`, `waiting`, `conflicts`, `githubApproval` and any rejected attempt's `report`/`description` are absent |
| 3 | `status`, `find`, `hook start`, `status --json` | `shared.jsonl` bytes unchanged |
| 4 | A second clone with an empty `.box/local/` and the committed `shared.jsonl` | `status`, `find "<word in why>"` and `status --json` show the bounty with stage, why, partOf and task; `look`/`apply`/`close` refuse `shared-only` |
| 5 | The five tracked records | load and render as before (`bt23.test.ts` green) |
| 6 | Two branches each post a different bounty; merge them | no conflict; both lines present; both bounties visible |
| 7 | A why containing a token-shaped secret | the append is held as a publish hit is; no line written |
| 8 | Apply a solution; close another bounty | one new line each; the applied one carries the merged attempt's public facts only |
