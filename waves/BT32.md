**Brief.** Rewritten by the CTO on 17 October 2026, before dispatch, at the owner's direction: the shared memory lives on the GitHub issue, fetched when needed, instead of a file committed to the project. Built on K26's memory model (`kitchen/reviews/K26-shared-memory.md`) and BT31's local database. Detailed for a cook without deep reasoning.

## Why

K26 placed every record field in one of three tiers (anyone; the project's agents on any machine; this machine only) and showed with fresh agents that an agent holding the shared part continued a half-done job as well as one holding the full record, while one with only today's public issue left the larger job half done. The first version of this brief committed the shared part to a file in the repository (`shared.jsonl`). **The owner rejected that on 17 October 2026:** a file inside the project leaks into agents' ordinary work (search results, `git diff`, `git log -p`, pull-request reviews), grows forever in every clone, and is a second public copy of facts the issue already holds. The established pattern is the opposite: memory in an online system of record, fetched only when needed, cached locally. We already have one, free, in every user's own repository: **the bounty's GitHub issue**, through the `gh` sign-in the tool already requires.

## Outcome

When a bounty is posted, its shared part (K26's tiers anyone + project agents) goes onto its GitHub issue in a machine-readable memory block. Any machine's tool fetches the project's bounty issues incrementally, at most once a minute and only for commands that show bounties, caches them in its local database (BT31), and shows the same bounties, purposes, whys, larger jobs and outcomes. Nothing is committed to the repository; drafts and machine detail never leave the machine.

## Decisions built into this brief

1. **No file in the repository.** No `shared.jsonl`, no `.gitattributes` line. Remove nothing BT31 built.
2. **A separate memory block, not the published format.** The issue already carries the `box-bounty-format` block (BT10's public, versioned contract, `packages/box-bounty/format.ts`, strict key check). **Do not change it.** The memory goes in a second block, `<!-- box-bounty-memory {json} -->`, placed after the format block, with its own `v: 1`.
3. **Written once, at post.** The issue body is written at `post` and, by BT11a's rule, only `state` changes afterwards. The memory block is written at post and never rewritten. Later milestones (a solution merged, closed) are already recorded on the issue as the tool's marked comments (`close.ts`, `<!-- box-bounty:<id>:<command> -->`) and by the format block's `state`; the reader takes the outcome from those. A `partOf` change after posting is not published (say so in BOUNTY.md).
4. **Trust only the project's own accounts.** Anyone can open an issue with the `box-bounty` label and a forged block. The reader imports an issue only when its `author_association` (present on every issue in GitHub's REST answer) is `OWNER`, `MEMBER` or `COLLABORATOR`, and reads tool comments only from such authors. Everything else is ignored, never shown as the tool's own words.
5. **Fetch only when needed.** Only `box bounty`, `status`, `find`, `status --json` and `hook start` fetch; `create`, `help`, `describe`, `config` and the rest never do. Each fetch is incremental (GitHub's `since` parameter) and happens at most once a minute per checkout.

## The design, exact

1. **What the memory block holds** (one constant, `MEMORY_FIELDS` in a new `packages/box-bounty/memory.ts`, citing K26 step 5): `why`; `partOf`; `resumeNote` (the shared `--resume` text: the larger job and where it stood); `tried` (the authored note's text, or for a generated note K26's one-line summary of which paths had uncommitted edits, path names only). Build it by **allow-list projection** from the record; never by removing known-local fields. The task, title, id, reward, branch and commit are already in the issue body and the format block; the reader takes them from there.
2. **Size and safety.** Each field goes through `publicText` like the rest of the body. Cap `resumeNote` and `tried` at 4,000 characters each, ending with `… (shortened; the full text stays on the machine that posted it)`. The **pre-publish secret scan covers all four fields** before the post goes out, with the same hold-and-settle behaviour as a hit in the task text today; name the code path in the Result.
3. **The once-told line at `create`**, said once per repository through the BT17 `said` mechanism: `note: --why, --resume and --part-of are published on the bounty's GitHub issue when it is posted — write them like a commit message`.
4. **Reading (pull).** In `store.ts` (BT31), one function `syncFromGitHub(repoRoot)`:
   - skips if the last successful sync (in `meta`) is less than 60 seconds old;
   - calls `gh api "repos/<owner/name>/issues?labels=box-bounty&state=all&since=<last sync time>&per_page=100"`, following pages only while results are full (a first sync on a new machine may take several pages: say how many for 1,000 issues);
   - for each trusted issue (decision 4): reads the format block (`readFormat`), the memory block, and the tool's marked comments for the outcome (fetch an issue's comments only when its `comments` count changed since the cached copy);
   - upserts one row per bounty into a `shared` table in `box.db` (`id`, `issue_number`, `updated_at`, `json`), and indexes it in the FTS table so `find` searches it;
   - on failure (offline, rate limit, not signed in): keeps the cache, and says once per spell `shared bounty memory not refreshed (reason); showing what this machine last saw`, then nothing until it succeeds again (BT17's said-once rule).
5. **Showing.** A bounty known only from GitHub (another machine's) appears in `status`, `box bounty`, `find`, `status --json`, `hook start` and the instruction block's open line, read-only: `look`, `apply` and `close` on it refuse by name, `shared-only`: "this bounty was posted from another machine; its issue is <url>. Act on it from that machine, or on GitHub." A bounty known both locally and from GitHub uses the local record. BT28's bounds (open listed, ended as count plus five) apply to the merged set.
6. **The GitHub stand-ins.** All three stand-ins (`tests/box/bounty/github-fixture.ts`, `tests/box/bounty/bt7-ux-fixture.mjs`, `kitchen/demo/gh-standin.cjs`) answer the issues list with `labels`, `state`, `since` and `per_page`, and return `author_association` and `comments` on each issue, in GitHub's real shape. K22's parity test (`tests/kitchen/k19-github-standin.test.ts`) must pass, with the new endpoint added to it.
7. **K14 start budgets.** Fetching adds at most one `gh` start (two when comments are read) to the five fetching commands, and none to the others. Rebaseline only those legs, by exactly the measured amount, with the reason beside each number; anything else is a regression.

| 7 | A why containing a token-shaped secret | the post is held as a publish hit is; nothing published |

| 9 | `create`, `help`, `describe`, `config` | no `gh` call for fetching |
| 10 | The repository | nothing new under `.box/bounties/` is committed or created for sharing; `git status` clean of tool files |
