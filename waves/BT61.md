# BT61: a program gets every answer as data, refusals included

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT61` · Timebox: 240 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-found-at-the-moment, D-2026-10-14-tool-convention
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K55](K55.md). Seen on the packed build that day:

- `box bounty look 3 --json`, refused: nothing on standard output, a sentence on standard error, exit 3. A program has to parse the sentence to learn which refusal it was and what to do.
- `box bounty create --json`: refused, "`--json` is not available on box bounty create yet". The id of a new bounty, the number of a posted issue and the result of an `apply` can only be read out of prose.
- `--json` exists on `status`, `look`, `config` and `discover` only (BT19, owner, 15 October 2026).

Tools built for agents that are in wide use give machine output on every command and make an error the same kind of document as a success (Arcjet's CLI, June 2026; Beads' `--json` throughout). Long-running agents script their tools; this is for them.

## Outcome

Every bounty command takes `--json` and prints exactly one JSON document on standard output and nothing else there. A refusal or a usage error under `--json` is also one document, with the refusal's existing name, its sentence, and its next step as separate fields. Exit codes do not change. Without `--json`, not one character of any command's output changes.

2. **Freeze the text before touching anything.** Write the byte-identity test (row 1): for every command, run it on a fixed fixture without `--json` and store standard output, standard error and the exit code in a snapshot file. It passes now. It must pass, untouched, at the end.
3. **Tests first** for the rest of the table; see them fail.
4. **The refusal document,** `json.ts`: `refusalDocument(command, error, exitCode)` returning

   ```json
   { "schema": "box-bounty/refusal@1", "command": "<name>", "refused": "<reason>", "message": "<text before '; next: '>", "next": "<text after it, or null>", "exitCode": 3 }
   ```

   Split on the **last** `; next: ` in the message. The message and next are plain strings; `JSON.stringify` does the escaping. A usage error is the same document with `"refused": "usage"` and `exitCode` 2.
5. **Print it,** `bounty.ts`, in the `catch`: work out once, near the top of `runBounty`, whether the raw arguments contain `--json` (do not depend on parsing having succeeded: a usage error happens before it). If so: write the refusal document on standard output with `guardOutput`, write nothing on standard error, exit with the same code as today. If not: today's lines, unchanged. The four reasons that exit 0 with a message (`owner-allow-needed`, `owner-answer-needed`, `publish-held`, `merge-held`) become, under `--json`, the same document with `exitCode` 0.
6. **Every command takes `--json`.** In `args.ts` add `'--json'` to the `switches` of every entry of `BOUNTY_COMMANDS` that lacks it, with help text in the existing form (`print one JSON document (schema box-bounty/<command>@1) instead of text`). Then delete the `json-not-supported` throw at line 373, and the two other throws of that name in `bounty.ts` (lines 306 and 423, `--since` and `--export` with `--json`) become ordinary usage errors or get documents: decide each in the plan. Add `json-not-supported` to the removed-name guard (search `command-removed` and the test that guards removed refusal names).
7. **A document per command,** one at a time, in this order (simplest first): `describe`, `help`, `find`, `create`, `allow`, `deny`, `hook`, `setup`, `close`, `post --preview`, `post`, `apply`, `take`, `submit`. For each:

## Traps

- Output under `--json` is exactly one line of JSON and a newline. No banner, no notice, no "merged solution" line: `noticeMergedSolutions` prints through a listener; under `--json` its lines go into the document (the existing documents already take a `notice` function: do the same) and never to standard output.
- Do not change any existing document's fields: additions only. `status`, `look`, `config`, `find` and `discover` keep their shape.
- Do not make JSON the default when standard output is not a terminal.
- **Changed expectations:** tests that assert `json-not-supported` on `create` change to the document; list them by file and line (search the name in `tests/`). Nothing else changes.
- If [BT62](BT62.md) merged first, its record changes here on purpose: update it with its one command and show the diff in the Result.

## Lenses

- [x] **Security:** a refusal's message can hold a path or a name a stranger chose. Under `--json` it must be a JSON string and nothing more: try a name with a quote, a newline, a control character and a closing brace, and show the document still parses and the field holds the same characters.
- [x] **User experience:** a fresh session asked to post a bounty and report its issue number from a script uses `--json` and reads the number from a field, not from a sentence.

## Notes

- Follows `gh` and the tools read in K55: one document on standard output, exit code as the verdict, no decoration.
- Not in this wave: printing JSON by default when standard output is not a terminal. Agents read our plain text well and it was designed for them (BT17); a silent change of format would break every skill written against it. `--json` stays something a caller asks for.
- After the first release (it adds, it removes nothing), so it does not hold the publish.
