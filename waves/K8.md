# K8: run the full verify off this machine on every push

Milestone: K · Station: evidence · Base: `bd149ae` · Branch: `wave/K8` · Timebox: 4 hours

Owner approval on record: 6 October 2026 — GitHub Actions on the private repository, free tier only.

## Outcome

Pushing code to master runs `verify` on a GitHub-hosted Linux runner and uploads the logs; a doc-only push costs nothing. The head chef can read the latest result with `gh` at every kickoff, and a red run on master blocks new waves until green.

## Scope

- Write: `.github/workflows/verify.yml`, `pnpm-workspace.yaml`, `scripts/verify.mjs` (only if the runner needs a flag/behaviour — prefer none), `README.md` (one badge/status line if it earns its place — optional), `tests/kitchen/**` only if a test is genuinely needed (workflow YAML checks may be better as a step in the wave's own evidence than a suite)
- Read for context: `scripts/toolchain.json` (pinned versions), `scripts/verify.mjs`, `pnpm-workspace.yaml` (`allowBuilds` has the Windows embedded-postgres entry only — the Linux package is the point), `.node-version`
- Do not touch: secrets (none allowed), other CI config (none exists), `scripts/suite.mjs`, test content

## Design constraints

- Workflow `.github/workflows/verify.yml`: `on.push.branches: [master]` with a paths filter so doc/kitchen/wave-only pushes don't run it (paths-ignore: `docs/**`, `waves/**`, `kitchen/**`, `*.md`, `templates/**` — decide the honest inverse list and comment it); `concurrency` group cancel-in-progress so a newer push kills a stale run; `timeout-minutes: 10`; `permissions: contents: read` and nothing else; artifact upload of `.kitchen/runs` with `retention-days: 3`.
- Ubuntu runner, Node from `.node-version`/`toolchain.json`, pnpm pinned to 10.34.5 (corepack or pinned action — prefer corepack to match local), `pnpm install --frozen-lockfile`.
- `pnpm-workspace.yaml` gains the `@embedded-postgres/linux-x64` (check the exact package name) `allowBuilds` entry — the Windows entry stays.
- `actions/checkout` needs `fetch-depth: 0` (verify's scoped-check merge-base and run history read git).
- Pin actions to released versions (checkout v4/v5, setup-node, upload-artifact) — no `latest` tags, nothing published in the last week.
- **Suite list is a real decision:** `verify.mjs --full` runs every suite including `test:containers` (needs Docker + the frozen M-series image, almost certainly unavailable) and `test:e2e` (Playwright/Chromium). Decide what the CI job honestly runs — if `--full` can't be green on the runner, run an explicit suite list instead and say so in the wave file and in a comment in the workflow. Never silently narrow `--full`'s meaning for CI.
- No secrets anywhere. No deploys, no schedules beyond what stays inside the free allowance.
- Scratch-branch acceptance: to prove a broken run fails, temporarily add a scratch branch (`kitchen-k8-*`) to `on.push.branches`, push the deliberately-broken commit, watch it go red, then remove the branch trigger before merge and delete the scratch branch. The merged workflow is master-only.

## Done when

- `node scripts/verify.mjs test:kitchen` exits 0 on the final commit (workflow itself is exercised live, below).
- A real push to master (this wave's own merge counts) produces a green run; the wave file records the actual minutes it used.
- The deliberately-broken scratch-branch push produces a red run (evidence: `gh run view` output quoted).
- A doc-only push starts no run; a second code push while a run is in progress cancels the first (evidence quoted or, if flaky to arrange, the concurrency config reviewed and the claim scoped).
- `gh run list`/`gh run view` on the repo works — the kickoff read-path exists.
- Wave file records: workflow triggers, permissions, minutes used per run, and the suite-list decision with its reason.
