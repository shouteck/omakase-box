# K25: the tool's memory for agents, measured and compared, and what should change

Milestone: K (kitchen) · Station: evidence (also packaging) · Base: master at dispatch · Branch: `wave/K25` · Timebox: 180 minutes; at expiry the cook stops and reports what it has

**Brief.** Written by the CTO on 16 October 2026 at the owner's request: "agents require context and memory, which is very important for our tool… we are talking agent memory architecture here", and "it needs to be scalable, because we do not want to cognitively load the agents with our information." An investigation: **it changes no product code and no test.** Its product is a report the owner and the head chef decide from, a measurement script, and at most five proposed waves. Detailed for a cook without deep reasoning: fixed steps with time budgets, the exact measurements, and the questions the report must answer.

## Why

The tool is part of an agent's memory. Over weeks, an agent (or a different agent on another host or machine) must be able to know what bounties were created, what each was for, how they relate to each other and to the larger job, and how to pick up the work a bounty interrupted, **without that knowledge costing it attention while it does other work.**

Today's approach, from PLAN.md's rule "memory without demand", in layers:

1. **The instruction-file block** (`<!-- box-bounty -->` in AGENTS.md, CLAUDE.md and each host's file; `wording.ts` `rulesBlockInterior`): four fixed lines, plus one line when a bounty is open or has a new solution. Rewritten on every record change.
2. **The hook** (`hook.ts`, slots `start`, `pause`, `finish`, off until the owner enables it): the open bounties at session start, then one line per new event, each said once.
3. **The record**, `.box/bounties/<id>.json`, the source of truth: task, why, note, the saved job (`resume`: branch, commit, changed files, the `--resume` note), stages and dated events, solutions with facts, waits, scan findings, the GitHub link.
4. **The index**, `.box/bounties/OPEN`: one line.
5. **On-request views:** `box bounty`, `status`, `status --since`, `look`, and `--json` on `status`, `look`, `config`.
6. **The public copy:** the GitHub issue and its machine-readable block.
7. **The owner's side:** `settings.json` and `state.json`.

The CTO's reading found four thin places, to be confirmed or refuted here:

- **Relationships:** each bounty stands alone; nothing records that two bounties belong to one larger job or that one depends on another (the retired `--job` did part of this).
- **Handover across machines:** the tool never says whether `.box/bounties/` is committed. If it is not, another clone sees only the GitHub issues: no saved job, no note, no solution facts.
- **Recall:** ended bounties stay as records, but nothing finds them by purpose ("have we asked for help on the parser before, and what came of it?"); `status --since` filters by time only.
- **Growth:** the block and the hook are small by design, but `box bounty` and `status` list every record; with many ended bounties the overview grows without bound.

## Outcome

A report that says, with measurements, how much the tool puts in front of an agent as the number of bounties grows; how established agent-memory tools handle the same problems; whether each of the four thin places is real; and at most five proposed waves, each keeping what an agent sees **unasked** constant however many bounties exist.

## The scalability rule this wave holds every proposal to

Three tiers, after the "small core always loaded, the rest searched on demand" split that agent-memory systems use:

| Tier | What | Budget, at any number of bounties |
|---|---|---|
| **Unasked** | the instruction-file block; the hook's start line and event lines | constant: the same size at 1 bounty and at 1,000 |
| **Overview** | `box bounty`, bare `status` | bounded: all open bounties (they need attention), ended ones only as a count plus the few most recent, with a command for the rest |
| **On request** | `status <id>`, `look`, a search, `--json` | whatever was asked for, and nothing else |

A proposal that adds to the unasked tier must say exactly what it adds and show it stays constant. A proposal that adds a command must pass the product rule "only what the tool is needed for": an agent could not do the same with Git, `gh` and its editor without losing something only the tool guarantees.

## Method: five steps, in order, with a time budget each

Write each step's output into the report as you go, so a timebox stop still leaves something usable.

**Step 1: the map of what an agent sees (25 minutes).** For each layer above: what triggers it, what text it shows, which code produces it (file and function), and which of the four needs it serves (what was created; its purpose; how bounties relate; handover). One table.

**Step 2: measure growth (50 minutes).** Write `kitchen/memory/measure.mjs`:
- It builds, in a scratch repository with scratch settings, synthetic bounty records at N = 1, 10, 100 and 1,000, in two mixes: all open, and 5 open plus the rest ended (applied or closed). Build records with the tool's own `writeNewRecord` and `transitionTo` (import from the built package), or by writing record files in today's shape, as `tests/box/bounty/` fixtures do; give each a realistic task title, why and `--resume` note of about 40 words.
- For each N and mix it runs, through the built CLI: the instruction-block sync (then reads the block), `box bounty hook start` (with the hook enabled in scratch), `box bounty`, `box bounty status`, `box bounty status --json`, `box bounty status <one id>`.
- It records for each: lines, characters, and an approximate token count (characters ÷ 4, stated as an estimate), plus wall time.
- Output: one table per mix, N across the columns. The report marks every surface whose size grows with N in the unasked or overview tier.

**Step 3: how others do it (45 minutes).** Read the current public documentation (not memory; cite each with its link and the date read) of at least these, and add others you find that solve memory for coding agents:
- **Claude Code**: CLAUDE.md and its memory files and imports; how it keeps them small.
- **AGENTS.md** (the cross-host convention) and how hosts load it.
- **Beads** (Steve Yegge's git-backed issue tracker for coding agents): how issues are stored in the repository, how agents query "what is ready", how dependencies are recorded, and how it keeps the agent's view small.
- **Letta (formerly MemGPT)**: core memory versus archival memory, and who decides what moves between them.
- **Mem0** and **Zep**: what they store and how it is retrieved; whether their approach fits tool state (not conversation) at all.
- **GitHub's own surfaces** an agent already reads (issues, labels, linked issues, sub-issues) and whether they could carry relationships between bounties instead of the tool.

For each, one row: where memory lives; what is always loaded and how big; how the rest is found; how relationships are recorded; how it travels between machines; what it costs the agent. Then three to five lessons that apply to us, each tied to one of the four needs.

**Step 4: the four thin places, decided (35 minutes).** For each: confirmed, refuted, or partly, with evidence (step 1's map, step 2's numbers, a command run). And for each confirmed one, the options seen in step 3, with what each would add to each tier. In particular, answer:
- **Committing `.box/bounties/`:** what a committed record exposes (it holds the agent's note, the saved job, and since BT19 solvers' pull-request descriptions), what it gains (handover across clones), whether the GitHub issue block already carries enough for handover, and what established tools do (Beads commits its store). Recommend one of: commit by default, never commit (ignore it), or let the tool say which and leave it to the owner. A change here may touch what is public, so the proposal names the hard stop it must not weaken.
- **Relationships:** whether the agent's own `--resume` note already carries enough, whether a field linking bounties is needed, or whether GitHub's linked issues and sub-issues should carry it.

**Step 5: proposals and the owner's page (25 minutes).** At most five proposed waves, each one paragraph: the need it serves, what it adds to each tier (with step 2's numbers before and the expected after), the product rule it passes, and its dependencies, in order. Then the owner's page, written last.
