# BT36: the owner can record that a solver was paid

Not in any queue; do not dispatch. Its tests and the `config set paid` proposal carry into that wave.

Milestone: BT · Station: packaging · Base: master at dispatch · Branch: `wave/BT36` · Timebox: 90 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 18 October 2026 from the roadmap's gap G5 (PLAN.md: "nothing records that a solver was paid"; stage **pay**; actors: the owner, and a later agent asking "was anyone owed payment?"). **One design choice in it needs the owner's confirmation in the dispatch card: how the fact is recorded (decision 1).** Detailed for a cook without deep reasoning. The tool never moves or verifies money (PLAN.md: not in this plan).

## Why

When a solution with a reward above $0 is merged, the tool tells the owner once whom to pay, how much and through which link (BT11b, `pay.ts`). After that the record says nothing: a later agent, or the owner a month later, cannot tell whether the solver was paid. The memory of the delegation is incomplete at its last step.

## Outcome

The owner, or their agent on their word, records that a merged bounty's solver was paid; the fact sits on the record with when and how much; `status`, `status --json` and the shared memory show `paid` or `payment owed`; and nothing about it is ever verified, moved or enforced by the tool.

## Decisions built into this brief

1. **How the fact is recorded: through `config`, the owner's existing word for settings and facts** (the owner's surface stays `allow`, `deny`, `config`; no new command): `box bounty config set paid <bounty-id>` records it; `box bounty config set paid <bounty-id> no` withdraws a mistaken record. **The owner confirms this choice at dispatch**, or names another (for example a `--paid` option on a command), and the brief is adjusted before cooking.
2. **Only where money is owed:** a merged (`applied`) bounty whose bound reward is above $0. Anything else refuses by name: `paid-nothing-owed` ("<id> owes nothing: its reward is $0" or "it was not merged").
3. **It is the owner's statement, recorded as such:** the event is `{ stage: 'paid', at, amount, by: 'owner' }` with the amount copied from the bound reward (`boundAmount`), never typed. It ends nothing and changes no stage.
4. **Shared.** The paid fact is part of the outcome, so it is in the shared tier (K26) and travels with BT32's shared memory.

## Shown

- In `status` on a merged bounty with a reward: `payment: owed $<n> to <solver> (<link state>)` until recorded, then `paid $<n> on <date>`.
- `status --json`: `payment: { owed: n, solver, paidAt: null | ISO }`.
- `box bounty` overview: one line counting owed payments, `<k> payment(s) owed — box bounty status shows whom`, only when k > 0 (a fact needing attention, BT17).

## Tests (`tests/box/bounty/bt36.test.ts`)

| # | Case | Expect |
|---|---|---|
| 1 | Merged, reward $5 | `payment: owed $5 to <solver>`; overview line `1 payment(s) owed` |
| 2 | `config set paid <id>` | event recorded with amount 5 and `by: 'owner'`; `paid $5 on <date>`; overview line gone |
| 3 | `config set paid <id> no` | the event withdrawn (a second event marks the withdrawal; history kept); owed again |
| 4 | Reward $0, or not merged | refuses `paid-nothing-owed`; record unchanged |
| 5 | `status --json` | the `payment` object as specified |
| 6 | The shared part (BT32) | carries the paid fact; nothing else of the owner's settings |
| 7 | GitHub | no call made by `config set paid` |
