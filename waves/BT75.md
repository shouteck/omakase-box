# BT75: every fact says where it lives, and a second clone proves it

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT75` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short. Feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `create` with the owner, who asked for a well-made shared and local memory model and for no fresh-agent testing ("All three").

**Why.** A bounty's memory has two halves:
- **shared:** the chain, `refs/box-bounty-records/<id>`, pushed to the project's GitHub remote, so public on a public repository;
- **local:** the store on this machine.

Which fact goes where is decided in `chain.ts` (`sharePosted` and its siblings) and described twice in `docs/box-v4/MEMORY-SPEC.md`: the facts table in section 3 and the event table in section 6. Nothing checks that the three agree, and they already drift:
- section 3 calls F-why's tier "project", a word that hides that it is public on a public repository (BT73 fixes the tool's own sentence; this wave fixes the spec);
- F-done and F-tried are marked missing as facts of their own.

The agent's question at hand-off (M3, M9: "what must I write so a later reader understands", "what was I doing") is answered only if the agent knows which of its words a later agent on another machine will see.

**The check is deterministic** (owner, 23 November 2026): a table, a test that reads the table, and a second clone. No fresh-agent run.

## Outcome

1. In MEMORY-SPEC section 3, every fact has one of three places, in a new column **Lives**:
   - `shared`: on the chain; public on a public repository;
   - `this machine`: never leaves it;
   - `GitHub`: read live from the issue or pull request, not stored.

   It also names the event field that carries it, or `—`. The tier word "project" is gone from the table.
2. A test reads that table and compares it with what the chain really carries: the fields of the events a real journey writes, read back from the bare remote. Any fact marked `shared` that no event carries, or any event field no fact names, fails the test by name.
3. A second-clone test runs a journey on machine A with a unique marker in every agent-written field: title, task, `--why`, `--part-of`, the `--resume` note, and a changed-file name in the local state. It then clones the remote to machine B, which has no local store, and runs `status` and `look` there. Two results:
   - each `shared` marker arrives on B exactly as written;
   - each `this machine` marker appears nowhere: not in any ref or object of the remote, and not in anything B prints or stores.

## Steps, in order

Written so any model can cook it.

1. **The table.** Add the two columns to section 3. Fill **Lives** from the code, not from the old Tier column: read each `share*` function in `chain.ts` and each field it writes. Keep the Tier column's other words (owner, machine) where they say who may read; drop "project". Put F-done and F-tried as `—` (missing), unchanged.
2. **The parser,** `memory-table.ts`: read section 3 from the file, return `{ fact, lives, fields[] }[]`; refuse a row with an unknown `lives` value.
3. **Tests first** (table below), seen failing, then passing once the table is filled.
   - For the chain's real fields, run `postedFixture`, then a solution, `apply` and a `close` on a second bounty.
   - Read every event blob from `ctx.bare` (`git for-each-ref refs/box-bounty-records`, then each commit's `event.json`), and collect the key paths (`issue.number`, `published.pushed`).
   - Never read them from the code.
4. **The second clone:** reuse `secondMachine` from `bt32.test.ts` (move it to a shared helper if both need it) with its own owner settings as `bt52.test.ts` does.
5. **Section 6:** replace the repeated field list with a link to section 3's **Field** column, so there is one list.
6. **Verify,** push, hosted run, Result, merge.

## Stops

- If the test shows a fact the spec calls private is on the chain, or the reverse, do not move the field. Record it and bring the owner one recommendation. Moving a fact between public and private is product direction.
- A shared hand-off note for what was tried (F-tried) and what done means (F-done) is the obvious next step. It would be a new `create` option, so it is the owner's decision, not this wave's. The Result proposes it in one line.

## Traps

- A marker must be unique per field (`MARK_WHY_<random>`), or a hit in one field hides a leak of another.
- Older events may carry `followup` (MEMORY-SPEC section 6). The table names it as a read-only legacy field so test 1 does not fail on history this wave did not write.
- B must have its own owner settings folder (`BOX_OWNER_HOME` as in `bt52.test.ts`) and no copy of A's store, or a local marker reaches B through the file system, not the remote.
