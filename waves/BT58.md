# BT58: the shared record's refs cannot be taken for the bounty branch

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT58` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k48-answers
Horizon: long by concept: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md). Found on the real sandbox by [BT52](BT52.md), in BACKLOG since. A bounty has two things on GitHub with almost the same name:

- its **branch**, where solutions go: `refs/heads/box-bounty/<id>`;
- its **shared record**, the event chain: `refs/box-bounty/<id>`, fetched into `refs/remotes/origin/box-bounty/<id>`.

Git resolves a short name to `refs/<name>` before `refs/heads/<name>`. So `git fetch origin box-bounty/<id>` returns the record, a commit holding only `event.json`, and a pull request made from it has "no history in common". A clone's `origin/box-bounty/<id>` can show the same wrong commit; BT52's fresh agent read it as the code to start from.

**Why now:** the owner publishes to npm after BT54, BT56 and BT53. Every bounty posted after that carries whatever name ships. Today the only chains are in the sandbox.

## Outcome

A new bounty's shared record lives under a name no short branch name can resolve to, and its tracking ref no longer sits where a branch's would. Existing chains keep working: read where they are, never rewritten or deleted by the tool.

## Plan

Started 12 November 2026 at 16:40 UTC (timebox: 180 minutes, so stop at 19:40).

**Why the fault happens, from Git's documentation.** `git help revisions` (Git for Windows' `gitrevisions.html`, "<refname>") says a short name is tried as `<refname>` itself, then `refs/<refname>`, `refs/tags/<refname>`, `refs/heads/<refname>`, `refs/remotes/<refname>`, `refs/remotes/<refname>/HEAD`, first match wins. So `box-bounty/<id>` finds the record at `refs/box-bounty/<id>` before the branch at `refs/heads/box-bounty/<id>`; `git fetch origin box-bounty/<id>` matches remote refs by the same rules. For the tracking side, `origin/box-bounty/<id>` resolves through `refs/remotes/origin/box-bounty/<id>`, which is both the record's tracking ref (today's `CHAIN_REMOTE_NS`) and where a clone's default fetch puts the branch.

**The new names (confirmed against that order).** Record `refs/box-bounty-records/<id>`; its tracking ref `refs/box-bounty-records-origin/<id>`. A short name reaches them only if someone types `box-bounty-records/<id>` or `box-bounty-records-origin/<id>`, names nothing in the product mentions to a solver. `box-bounty/<id>` now falls through `refs/box-bounty/<id>` (absent) and `refs/tags` to `refs/heads/box-bounty/<id>`, the branch. The tracking ref leaves `refs/remotes/` altogether, so `origin/box-bounty/<id>` can only be the branch's. Git accepts both names in one repository because they share no path component with `refs/heads/box-bounty/` (`git update-ref` of both, tested in row 4).

**Which name a bounty uses: a choice stored per bounty, zero Git starts.** The brief's step 4 decides by looking for an old ref; that costs one or two Git starts on every chain command, and `k14-start-budget` counts those. The same fact is already in the store: every bounty with an old chain on this machine has `chain_authored:`, `chain_pending:`, `chain_pushed:` or `chain_tip:` (BT32). So: a new store key `chain_ns:<id>` = `old` | `new`, decided once: an id that already has any of those four keys is `old` (written by master's code); an id with none is `new` (a post from now on, or a remote chain first seen at the new name); a remote chain first seen at the old name only is `old`; **at both names, old** (row 6). Once stored it never changes. `chainRef(root, id)` and `remoteRef(root, id)` read it. **An old chain stays under the old name and is continued there; nothing is moved, deleted or force-pushed.** (Deviation from the brief's wording, same outcome, stated in the Result.)

**What changes in `chain.ts`.** Constants: `CHAIN_NS`/`CHAIN_REMOTE_NS` take the new values; `CHAIN_NS_OLD`/`CHAIN_REMOTE_NS_OLD` keep today's. `syncChains` fetches both pairs in one call (two refspecs, one start; `--prune` only on those four destinations, never `refs/heads`). `adoptAndImport` lists the remote pair in one `for-each-ref` call (both namespaces as patterns) and the local pair in one: the same two starts as today. Old-namespace remote tips count only if their commit carries `event.json` (the old tracking namespace is also where a clone keeps the bounty branch's tracking ref, so an unchecked tip there is the branch, not a chain: found by reading `adoptAndImport`, where `local === undefined` adopts the remote tip as the local chain). `fetchOne`, `pushOnce`, `commitEvent`, `mergeRemoteTip`, `retryPending` take the namespace from the stored choice.

**Not the chain, unchanged** (confirm by search that no push refspec names them): `refName` and `attemptRefName` in `record.ts`, `publicationRef` in `gh.ts`: local-only pins, never pushed; a name with a suffix cannot equal `box-bounty/<id>`.

**The board.** `refresh.ts` `readEvents` reads the new name first and the old name only on a 404. No schema change: a column would be a migration on the live board, which is the owner's to apply. Cost, stated: a bounty with an old-name chain pays two reads per events step instead of one; every chain posted after this wave pays one. Legacy bounties are finite and close. Row 7 asserts both counts. `feed.ts` legend words and the stand-in (`standin.ts` line 150) take both names.

**Published text:** `FIRST-FIVE-MINUTES.md`, `BOUNTY-FORMAT.md`, `CONTRACTS.md` C3 and the line at 147, `MEMORY-SPEC.md`, `PLATFORM-UX.md`, `feed.ts`: new name, with once "bounties posted before version 0.2.0 use `refs/box-bounty/<id>`".

**Every mention, classified** (search `grep -rn "refs/box-bounty\|CHAIN_NS\|CHAIN_REMOTE_NS\|box-bounty/\*" packages docs/box-v4 FIRST-FIVE-MINUTES.md tests`): chain (changes) `chain.ts` 42 to 45, 153, 177 to 217, 400, 512, 518, 577 to 592, 632, 634, 646; export `index.ts` 108; local pin (stays) `record.ts` 354, 355, `gh.ts` 92, `render.ts` 533; board reader (reads both) `refresh.ts` 247, stand-in `standin.ts` 150; published text (updates) the docs above; tests that assert a new bounty's chain name (change the string): the files listed in the Result after the run.

**Order:** (1) tests first, rows 1 and 2 red on master; (2) constants and the choice; (3) fetch, listing, adoption; (4) run bt32 with only names changed; (5) board and stand-in; (6) docs; (7) sandbox run; (8) hosted run, Result, merge.

**Plan, changed while cooking (12 November 2026).** (1) An old chain's tracking copy moved: the brief left it at `refs/remotes/origin/box-bounty/<id>`, which is also where a clone keeps the bounty branch; the tool's `--prune` fetch there would delete a clone's branch tracking refs and its fetch overwrote them with the record (row 3 failed on master for exactly this). Old chains' tracking copies now go to `refs/box-bounty-records-origin-old/<id>`, a namespace of their own; the remote name is unchanged, the chain is read where it is. (2) Because of (1) the planned check "an old-namespace tip counts only if it carries `event.json`" is not needed and was not built.
