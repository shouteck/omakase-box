**Brief.** Written by the CTO on 10 November 2026 from the owner's decisions that day: the product has one name, omakase-box, and the command follows it. Read on npm the same day: Box, the storage company, publishes its official command-line tool as `@box/cli` with the command `box`, described as shipping official agent skills; a second package named `box` installs the same command. On a machine with either, `box bounty` runs Box's tool or ours, whichever was installed last, and an agent's model has read far more about theirs. "bounty" is also a leftover: since the older platform was retired, the tool does nothing else.

**Why now:** only 0.1.3 is public. After the next release every skill, instruction file and script written against `box bounty` sits on machines we cannot update.

## Outcome

An agent types `omakase-box post`, `omakase-box status`, `omakase-box discover`, `omakase-box setup`: the command is the product's name and the word "bounty" is gone from it. Everything the tool prints, the skill, the instruction block, the guide and the site say the new command. For one release `box bounty <command>` still works and says once per machine that the name changed (owner, 10 November 2026), unless the install check below shows the old name cannot ship safely.

## Stopped at step 1 (11 November 2026, about 23:45 UTC): the install fact

Windows 10, npm 11.6.1, Node 24.11.0, `@box/cli` 4.10.1 (its `bin` is `{ box: 'bin/run' }`), every case in its own scratch prefix, `--ignore-scripts`, Box's code never run. Our tarball is today's package (`omakase-box` 0.1.3, built by `pack.mjs`) with only `bin` changed. Scratch folder removed afterwards (83,668 items, no links).

| Case | What npm did | Result |
|---|---|---|
| `@box/cli`, then ours with `bin: { box }` (what 0.1.3 shipped) | `EEXIST: file already exists` on `box.cmd`; nothing of ours installed | **our install fails**; Box's `box` untouched |
| `@box/cli`, then ours with `bin: { omakase-box, box }` | `EEXIST` on `box`; **nothing installed, not even `omakase-box`** (all or nothing) | **our install fails** |
| `@box/cli`, then ours with `bin: { omakase-box }` | `added 1 package` | works; `box` still runs Box's tool, `omakase-box` runs ours |
| ours with `bin: { box }`, then `@box/cli` | `EEXIST` on `box.ps1`; Box's package rolled back (left a partial `@box` folder) | **Box's install fails**; `box` stays ours |
| ours with `bin: { omakase-box, box }`, then `@box/cli` | same | **Box's install fails** |

So npm neither overwrites nor warns: it refuses, whichever came first, unless `--force` is given, and `setup` and the guide never give it. This is the cross-platform behaviour of npm's bin linking, but it was **not run on Linux**: Docker's daemon is off here and WSL holds only `docker-desktop`; neither was started. macOS: not run.

**What this means.** Keeping `box` in the manifest makes `npm install -g omakase-box` fail on any machine that already has Box's own tool, which is the machine Box's agent skills are built for, and (the other way round) our package then blocks Box's. The same is already true of the published 0.1.3. The brief's stop rule applies: the old name is not shipped, and that is the owner's decision to confirm. Everything else in the brief stands without it: the rename, `omakase-box bounty <x>` accepted silently, the old skill marker recognised so `setup` replaces an old skill, one real run on the sandbox.

**What drops if the owner confirms:** `box bounty <x>` and `box setup` through our package after the release (a machine upgrading from 0.1.x loses the `box` shim, and gets Box's if it has theirs), the once-per-machine notice (step 5, tests 2 to 4), and `bin.box`. **What it costs:** a script or skill written against `box bounty` fails with "not found", or runs Box's tool, once the owner publishes; 0.1.3 stays public as it is.
