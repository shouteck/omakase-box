## Why

From `.kitchen/runs`, the last five completed runs total 111–156 s; `test:kitchen` is 99–124 s of each (88–90%), while `check` and `build` are 5–6 s and usually reused. The suite is 17 files and 136 tests, one worker, **117.2 s wall** in an isolated run. Its own per-file times:

| File | Seconds | Share | What it tests |
|---|---|---|---|
| `k16-record.test.ts` | 34.2 | 29% | the demo recorder, with Chromium |
| `verify-reuse.test.ts` | 29.0 | 25% | verify's own reuse rules |
| `k19-github-standin.test.ts` | 10.6 | 9% | the GitHub stand-in |
| `kitchen-stats.test.ts` | 7.1 | 6% | stats and wave reads |
| `k37-load-stats.test.ts` | 5.5 | 5% | host load |
| `k12-bounty-parallel.test.ts` | 4.5 | 4% | the 3-worker audit |
| six more files | 15.5 | 13% | brief check, rulebook, evidence |
| five small files | 2.7 | 2% | guards and refusals |
| vitest start/teardown | 8.1 | 7% | process and module setup |

Two files are 54% of the suite — the demo/browser test and the meta-test of verify itself — and they are the two that almost no product change needs.

The cause is structural. `changedPaths()` includes the wave's own `waves/<id>.md`; `isKitchenRead` treats `waves/*.md` as read by kitchen tests; `kitchenSuiteReason` therefore forces `test:kitchen`; and `stepReadsPath('test:kitchen', 'waves/<id>.md')` is `true`, so ancestor reuse never skips it. Confirmed by probe:

```
kitchenSuiteReason(['waves/K43.md']) -> the change touches a file a kitchen test reads
stepReadsPath('test:kitchen','waves/K43.md') -> true
```

So a docs-only wave and a product wave pay the same 100 s, and the suite is mostly kitchen self-tests (verify reuse, brief check, rulebook, stats) plus one demo/browser test. A product change needs the demo/CLI tests, not the verify-reuse tests.

## Outcome

A wave-only diff runs only the kitchen tests that read wave files. A package-only diff runs the demo/CLI kitchen tests. An unmapped path runs all of them (fail closed), and `--full` still runs all. The summary names the selected files and the reason, so the pass can see what was and was not covered.

## The change

1. **Declare each kitchen test's inputs.** A header comment in each `tests/kitchen/*.test.ts` (`// reads: <prefixes>`), or one central table; either is fine. A guard test enumerates the directory and fails when a file declares nothing (the BT22 lesson: a list from memory misses one).
2. **`suite.mjs`:** add `kitchenTestFilesForPaths(paths)` returning a sorted file list, with `kitchenSuiteReason` kept as the explanation. `waves/*.md` maps to the file(s) that actually read them (`kitchen-stats.test.ts` is the known one; confirm the rest by declaration, not by guess). Unmapped means all.
3. **`verify.mjs`:** pass the selected files to `suite.mjs` (it already accepts file targets), record `kitchenSelected` and the reason in `summary.json`, and fail closed on an empty or unknown selection.
4. **Reuse must respect the selection.** `reusableStep` is keyed by step name; a PASS from a narrow selection must not stand in for a wider one. Record the selected set on the step and require it to cover this invocation's set, the way `check` requires its `suites`. A wider recorded selection may stand in for a narrower one; state the rule and test both directions.
5. **Label the run honestly.** A selected `test:kitchen` is still acceptance for the files it ran, but not for the others. Do not reuse the "inner loop, never suite acceptance" wording that a human-scoped run gets; the summary must say "selected: N of M kitchen files, reason".
6. **Measure.** Before/after totals for three representative diffs — wave-only (`waves/K45.md`), package-only (`packages/box-bounty/look.ts`), scripts-only (`scripts/verify.mjs`) — three runs each, medians and spread.
