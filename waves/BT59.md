# BT59: the tool works with a GitHub token alone; `gh` is one way to sign in, not a requirement

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT59` · Timebox: 300 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k49-answers, D-2026-11-10-found-at-the-moment, D-2026-11-01-agent-only-direction
Horizon: long: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K49](K49.md)'s question 3 and the owner's answer: do it if it is an order of magnitude smaller than the project. Measured that day: **it is.** Every call the tool makes to GitHub's API goes through one function, `gh()` in `packages/box-bounty/gh.ts` (352 lines), as `gh api`, plus `gh auth status` and `gh version`. No other file starts `gh`. Pushes and fetches use plain Git over HTTPS with Git's own sign-in (`remoteGit`). The project is about 15,800 lines of source and 19,500 of tests; this is one transport of a few hundred lines and its tests.

**Why:** long-running agents in cloud sandboxes are usually given a GitHub token and no `gh` program. Today the tool refuses them (`github-cli-missing`). This replaces the 12 October decision that `gh` is required.

## Outcome

With `gh` installed and signed in, nothing changes. Without it, a token in the environment (`GH_TOKEN`, then `GITHUB_TOKEN`, the names `gh` itself reads) is enough for every command on both sides. The mechanism: a second transport behind `gh()` that makes the same request over HTTPS to `api.github.com` and hands back the same status, headers and body, so every caller is untouched. The limit: GitHub.com only, as today.

- Do not touch: any caller of `api()` or `pages()`; what any command prints when `gh` is present; the board

## Done when

- Accepted as the rulebook then says ([K50](K50.md) if merged), with `test:box-bounty` and `test:kitchen`.
- **Order of choice, tested:** `gh` present and signed in is used, exactly as today; else a token in the environment; else one named refusal that states both ways in and changes nothing. A token present with `gh` present but signed out uses the token.
- **Same answers:** one test drives the same journey (post, status, look, apply, close, discover, take, submit) through both transports against stand-ins and compares what the tool prints and records. The existing suites, which swap the `gh` program, pass with no expectation changed.
- **The token is never where it can be read:** not in any process's arguments, not in a refusal, a log, a record, the settings, the shared chain or `--json`; the child that makes the request gets the token and nothing else of the environment. Tests search each of those places for a marker token after a full journey, and one test first shows the search finds a token planted there.
- **Git gets the token for a push or fetch without it touching arguments or Git's config:** state the mechanism in the plan with Git's documentation cited, and test that `ps`-visible arguments and `.git/config` never hold it. If Git is already signed in, the tool adds nothing.
- Redirects are refused and only `api.github.com` and `github.com` are ever sent the token; a test with a stand-in that redirects to another host shows the token is not sent there.
- The sentence "it never sees, stores or asks for a credential" is rewritten to what is true, in the guide and anywhere a search finds it: with `gh`, the tool never sees the sign-in; with a token, it reads it from the environment, sends it only to GitHub, and never stores or prints it.
- One real run on the sandbox (`kitchen/sandbox.md`) with `gh` taken off the path and a token in the environment: post, take, submit, apply, close. The token is the sandbox account's own, from `gh auth token` piped into the environment of that one process, never printed or written. Everything left on the sandbox listed by name.
- The rate-limit and failure messages (BT50) are the same sentences on both transports.

## Lenses

- [x] **Security:** this wave makes the tool hold a credential for the first time. Attack it: a hostile repository's Git config that redirects `github.com`; a `GH_HOST` or proxy variable pointing elsewhere; a stand-in that echoes request headers into an error body the tool might print; a solver-controlled string reaching a URL path; a token with a newline. Say what each did.
- [x] **User experience:** a fresh session in a folder with a token and no `gh` runs `box bounty` and reaches a posted bounty on the sandbox without being told how to sign in.
