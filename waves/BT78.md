# BT78: the secret scan uses gitleaks' published rules, not a hand-made list

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT78` · Timebox: 240 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: long: a converter, a pinned data file, a sample generator and a measurement; starts with `/plan`. Feature playbook; principles: build-the-lever, prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 23 November 2026 from the walkthrough of `post`. The owner asked for it ("Brief both") after asking whether the pre-post checks follow established tools or are hand-wavy.

**Why.** The pre-publish scan (`packages/box-bounty/scan.ts`, `SECRET_RULES`) has 11 named token patterns and one general "name = random value" pattern, chosen by hand in BT8:
- private keys;
- GitHub, GitLab, AWS, Slack, OpenAI, Stripe and Google tokens;
- JWTs;
- database URLs with passwords.

It misses common publish and service tokens, for example npm, PyPI, Hugging Face, SendGrid and Twilio.

The established answer is **gitleaks**' rule file (`config/gitleaks.toml`, MIT licence), maintained by that project for many providers and tested by it. Each rule has:
- an id;
- a regex;
- optional keywords (a cheap prefilter);
- an optional entropy floor;
- allowlists.

Guessing which providers matter is the hand-wavy part. Adopting a maintained list as data is the standard.

The tool stays offline for this: the rules are a **pinned copy** in the package, updated by a script and a wave, never fetched at run time.

## Outcome

1. `packages/box-bounty/secret-rules.json`, generated by `scripts/gitleaks-rules.mjs` from a pinned gitleaks release (version and file hash recorded in the JSON), holds every rule that converts cleanly to a JavaScript regex. It carries each rule's id, pattern, keywords and entropy floor. The rules the converter cannot take are listed in the JSON's `skipped` with the reason.
2. The scan runs those rules, plus the tool's own two that gitleaks does not have in this form (`assigned-secret`, `passworded-connection-string`, kept), plus `private-key-block`, if gitleaks' private-key rule does not cover it. A hit reports the gitleaks rule id (`npm-access-token`); the file and line are named, never the value, as today.
3. Every adopted rule is proven to fire. A test builds a matching sample for each rule **at run time** from its regex (no secret-shaped literal in any committed file, `secret-literals.test.ts`) and checks the scan holds it. A rule no sample can be built for is listed, never silently passed.
4. The cost is measured and stated:
   - holds before and after on this repository's tracked files and on its whole history (`git log -p`);
   - scan time on the largest first-published diff in the test suite.

   Each new hit in this repository is named (rule, file, line) in the Result, never its value. False alarms are what the owner pays for in holds.
5. `NOTICE` in the published package credits gitleaks and carries its MIT licence text; BOUNTY.md names the source and version instead of "a small stated list".

## Steps, in order

Written so any model can cook it. Start with `/plan`; keep the plan in this file.

1. **Read the pinned file.** Pick the latest gitleaks release at least two weeks old; record its tag and the file's SHA-256. Read what `keywords`, `entropy`, `secretGroup`, `allowlists` and `path` mean there.
2. **The converter,** `scripts/gitleaks-rules.mjs`.
   - It reads the TOML from a path or the pinned URL (the network only here, never in the tool) and translates Go RE2 syntax to JavaScript.
   - It skips rules that match on `path` alone; those are file names, which never-ship covers.
   - It writes the JSON sorted by id and has a `--check` mode.
3. **Tests first** (the table below), seen failing.
4. **The scan:** load the JSON once; for each line, run the keyword prefilter, then the regex, then the entropy floor and the rule's allowlist; keep one hit per line.
5. **Measure** (Outcome 4) and fix any test file the wider rules now catch.
6. **Package,** NOTICE, docs; verify, push, hosted run, Result, merge.

## Traps

- **Node 22.13 is the floor** (`engines` in the published package). Its regular expressions do not support inline modifiers such as `(?i)` in the middle of a pattern, which gitleaks uses. Translate them, using the `i` flag for a whole-pattern `(?i)` and an expanded class for a partial one, or skip the rule and list it. Never let a pattern fail to compile at run time.
- Go's `\z`, `(?s)` and named groups `(?P<name>…)` differ in JavaScript; the converter handles each or skips.
- Many more patterns means slower scans on large diffs. The keyword prefilter is what keeps gitleaks fast; keep it.
- A generated sample is a secret-shaped string: build it in memory only, never write it to a file that is committed, and never print it in a failure message (print the rule id).
- GitHub push protection is on in the sandbox. A test or fixture that pushes a generated sample to the real sandbox would be refused by GitHub: keep these tests local.

## Notes

- Follows gitleaks (MIT), which GitHub's own secret scanning and TruffleHog parallel. Its rule file is the widely reused open list.
- Validity checks (calling the provider to ask whether a token is live) are out of scope: the tool never sends a found secret anywhere.
