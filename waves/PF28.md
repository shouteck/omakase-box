# PF28: no bounty can stall the board's reading

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF28` · Timebox: 150 minutes; at expiry, report partial findings and stop
Owner decisions: the owner's "Yes, fix the board" (3 November 2026), on PF25's finding
Horizon: short. Bug-fix playbook; principles: prove-it-works, model-the-domain

**Brief.** Written by the CTO on 3 November 2026, after PF25's sandbox run. The live board never stored draft #60: an hour later it still counted 0 attempts and 0 pull requests.

## The cause, reproduced

The Worker allows each run 2 GitHub reads (`tickReads: 2`, PF8, for CPU). The refresh reads due bounties stalest first, and marks a bounty read only when its whole read finishes: pull requests, then a compare for each merged head not yet seen on the default branch, then the event chain.

The sandbox's squash-merged bounties need 3 or more reads: pull requests, a compare (`on_default` 0 is checked again each time, because the bounty branch may reach the default branch later), then events. Each run spends both reads on the same bounty and stops; its read time never moves, so it stays first in line for ever. Nothing behind it is read.

A scratch test with the live settings, 25 closed bounties and one squash-merged one, stored no pull request for a new bounty in 90 minutes; without the squash-merged one, the first run stored it. A bounty with a new event commit jams the same way (pull list plus commit list already spend both reads).

A notice's look (`lookNow`) reads the repository and the issue first, so at 2 reads it never reaches the pull requests either.

## Outcome

Whatever GitHub holds, every open bounty's pull requests are read again within the board's stated refresh, and a notice shows a new pull request at once.

## Build

1. **A turn is spent when it starts.** Each step marks its read time before it reads. A step cut off by the budget keeps what it stored and stays due, behind every other due step. A step stopped before its first read keeps its place.
2. **Two steps with their own freshness.** Pull requests by `details_read_at`; the event chain by a new `events_read_at`. Each step's fixed cost is one list read and each further read is stored, so at 2 reads a run each turn makes progress. The pull-request step is done once its list is stored; the compares after it are best effort, so a head never seen on the default branch is not compared every run. Migration `migrations/pf28.sql`; `schema.sql` gains the column.
3. **A notice reads a held bounty's pull requests next.** The repository is still read first (the private rule; the board's token may see a repository that just turned private). For a bounty the board already holds at that address, the pull requests come next and the issue after, so a look at 2 reads stores a new pull request. What the look could not finish still goes first in the next run.
4. **Nothing else changes:** caps, cadence, the public answers.
