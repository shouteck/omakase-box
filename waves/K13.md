# K13: the bounty tool runs on Bun

Milestone: K (kitchen and toolchain) · Station: packaging · Base: master at dispatch, after K12 · Branch: `wave/K13` · Timebox: 120 minutes, with a stop-or-go point at 40; at either, the cook stops and reports where it is

**Pre-brief.** Written by the CTO on 12 October 2026. The owner's decision of that day: move to Bun after K12 **if the move is quick**, without a separate experiment first. This wave is built so that "is it quick" is answered early and honestly: a first step that changes nothing, and a stop if the answer is no. It cooks only when named.

## Outcome

The bounty tool is run by Bun, in its tests and when used: each `box bounty` command starts faster, the test suites take less time, and every behaviour is as it was. If Bun cannot do that on this Windows host without changing what a test expects, nothing is changed and the owner has the reasons.

## What this wave does not change

One new thing only (KITCHEN.md, "Never stack unknowns"): the runtime. Not the test framework's assertions, not product behaviour, not the commands, not how the tool is installed (BT12), not the other packages in this repository, which stay on Node. `scripts/verify.mjs` stays the acceptance command.

## Scope

- Write: `scripts/toolchain.json` and the scripts that read it, `scripts/suite.mjs`, `scripts/workspace.mjs` and `package.json` scripts only where they launch the bounty tool or its suites, `packages/box-cli/**` and `packages/box-bounty/**` only for runtime differences, `tests/box/bounty/**` and `tests/box/package/**` only where they launch a program, `.github/workflows/**`, `docs/box-v4/BOUNTY.md`.
- Read for context: `waves/K12.md` Result (where the time goes after it, and Git starts per command); `kitchen/stations/packaging.md`, the lines on Windows launch of `.cmd` files, junctions and path dialects; PLAN.md, the rule on required programs.
- Do not touch: any test's expected outcome or timeout; product behaviour; `.execution/`, `docs/legacy/`; global settings on this machine.

## Done when

**Step 1, stop or go (by minute 40, nothing committed to product or tests)**

- Bun is added as a pinned development dependency of this repository, the way the toolchain file pins Node and pnpm: an exact version, fetched by the repository's own installer, nothing installed machine-wide.
- The bounty and package suites are run with the runtime switched to Bun and nothing else changed. The report lists every failure by cause: a difference in how Bun starts a process on Windows, a Node interface Bun lacks or does differently, the test runner, something else.
- Measured on the same commit, three runs each, with the spread: the start time of one `box bounty` command that does no Git work, one that does, and both suites, on Node and on Bun.
- **Go only if** every failure is understood and can be fixed in the write scope without changing what any test expects, and the suites are faster by a margin outside the spread. **Otherwise stop:** the Result says the move is not quick, why, and what would have to be true first. Stopping is a finding, not a failure of the wave.

**Step 2, the move (only on go)**

- `node scripts/verify.mjs --full` exits 0 on the final commit, with the bounty and package suites running the tool on Bun. No expected outcome and no timeout changed; `git diff master -- tests/` shows only how programs are launched.
- The Windows-only behaviours are each proved again on Bun by their existing tests: launching `.cmd` and `.bat` files, junction handling, case-insensitive paths, reserved names, the executable-lookup control used by the missing-program tests.
- The stand-in `gh` in the tests starts with one process per call, not two.
- The off-machine Linux run passes with Bun pinned to the same version.
- The tool states its runtime honestly wherever it states requirements: PLAN.md's "the tool itself runs on Node" is the head chef's to change at close; `docs/box-v4/BOUNTY.md` is the cook's.
- Before and after, same commit and host, three runs each: both suites, a full verify, and the two command start times. The gain is stated with its spread and as measured on an idle machine.
- One way back: the Result names the single commit to revert to return to Node.

## Review lenses

- [x] **Security:** the runtime sits under every guarantee the tool makes. The pass reruns, on Bun, the attacks that depend on how a process is started or a path is resolved: a hostile solution path, a junction at a destination, executable lookup with a stand-in on the path, arguments with spaces, quotes and trailing backslashes through a `.cmd` file. It checks that pinning Bun fetched exactly the pinned version and that nothing runs from outside the repository's own tool folder.
- [ ] **User experience:** not applicable; output is unchanged, and a test proves it byte for byte on three commands.
- [x] **Measurement fairness:** both runtimes were measured the same way on the same commit and host, every run is counted, and a gain that needs an idle machine is stated as that.

## Notes for the worker

- Refactoring playbook, with prove-it-works: the suites passing on Bun on this host is the proof, not a compatibility table.
- Popularity is not evidence for this code. It starts thousands of processes and depends on Windows path behaviour; those are the places to look first.
- Git process starts are most of the time and Bun does not change them. Do not promise more than the measurement shows.
- If the test runner itself has to change to run on Bun, that is a second new thing: stop at step 1 and say so.
- Report at minute 40 and at the timebox. Do not run on.
- Not in this wave: compiling the tool to a single file, dropping Node for people who install it (BT12), rewriting anything in another language.
