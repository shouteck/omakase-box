**Brief.** Written by the CTO on 10 November 2026 from [K53](K53.md). Read on the live board that day, as a program without JavaScript reads it:

| Page | Text in the page's main part |
|---|---|
| A bounty's page (`/b/<id>/`) | "Reading the board." and nothing else |
| The board (`/board/`) | its heading and "Reading the board" |
| The numbers (`/numbers/`) | its heading and one sentence |
| Front page, How it works, For agents | complete |

Every posted issue links to the first kind. An agent that follows the link with an ordinary fetch, a search engine, or a registry's preview gets an empty page. The JSON feed and MCP hold the same facts, but only for a reader that already knows to ask for them.

## Outcome

The first answer for a bounty's page, the board and the numbers page already contains what the page shows: the task, the reward and payment facts, the attempts, how to answer; the list of open bounties; the numbers. A browser with JavaScript then behaves exactly as today. The pages look the same.

## Steps, in order

Written so any model can cook it. Facts as read on 10 November 2026:

- `packages/box-platform/components/Board.jsx`, `BountyView.jsx` and `Numbers.jsx` are client components: each renders "Reading the board." (or the numbers' equivalent) and then fetches `/api/board`, `/api/b/<id>` or `/numbers.json`.
- `src/api.ts` near line 157: any `/b/<something>/` is answered with the one built shell `out/b/index.html`. `/board/` and `/numbers/` are static files the Worker never sees (`wrangler.toml` `run_worker_first` does not list them).
- The facts already exist as functions: `bountyDetail` (`src/feed.ts` line 236), the board's `board()` in `src/api.ts`, and the numbers' cached reader.

**The design the CTO recommends, for the plan to confirm by measuring:** the Worker fills the built page before sending it. It fetches the built HTML from `env.ASSETS`, and inserts two things: the facts as plain HTML inside the page's main element (so a reader with no script sees them), and the same facts as JSON in a `<script type="application/json" id="first-facts">` (so the client component starts from them and does not show "Reading the board"). The approved markup and looks are reused; no second way of drawing a page is invented. Build a different candidate only if this one fails the measurement.

1. **Order with the design waves:** [PF41](PF41.md) changes only what the board shows when it is empty. If it has merged, the board's first answer for an empty board carries its message and two links, not the sample row. If it has not, render today's empty box. Neither blocks this wave.
2. **Tests first:** the table below, rows 1 to 4, seen failing on master's build.
3. **Measure before building.** In a scratch file (not committed) write the fill function for the bounty page only, and time it on the local board for a bounty with 1, 25 and 100 pull requests: CPU milliseconds for the Worker's part (use `performance.now()` around the fill, 100 runs each, median and slowest), and bytes sent. The free plan allows 10 ms of CPU per request; the database waits do not count as CPU. Write the numbers in this file. **If the median is over 5 ms or the slowest over 10 ms, stop and report**; do not ship a page Cloudflare may cut off. A local run is not Cloudflare's CPU: say so, and plan the `exceededCpu` check after deploy.
4. **The plain HTML of the facts.** One module, `packages/box-platform/src/first-html.ts`, with three functions that take the same objects the JSON answers return and give a string:
   - a bounty: title, state sentence, the task, the reward and payment lines, each attempt, the steps to answer;
   - the board: for each open bounty on this page its title (a link to `/b/<id>/`), reward, repository;
   - the numbers: each number with its label.
   **Every value from a person goes through one `escapeHtml` function** (`&`, `<`, `>`, `"`, `'`) with no exception; build strings only through a tagged helper that escapes every interpolated value, so a missed escape is impossible rather than unlikely. This HTML sits in an element the client component replaces when it starts.
5. **The JSON for the client.** `JSON.stringify(facts)` with `<` written as `<`, placed in the `application/json` script. In each of the three components, read `document.getElementById('first-facts')` on first render: if present, start from it and skip the first fetch; if absent, behave exactly as today.
6. **Route the three addresses through the Worker.** `wrangler.toml` `run_worker_first` gains `/board/*`, `/board`, `/numbers/*`, `/numbers`. In `src/api.ts`: for `/b/<id>/` call `bountyDetail`; for `/board/` the board's first page with the address's own filters; for `/numbers/` the cached numbers; then fill and return. Use `HTMLRewriter` (built into Workers) or one string replace on a marker comment the build leaves in the page; pick whichever measured cheaper in step 3.
7. **A missing bounty** now answers 404 with the existing "Not on the board" words in the HTML and a link to `/board/`. Say in the Result that this replaces the "same shell for every id" choice, and why that is acceptable (`/bounties/<id>.json` already answers 404 for the same id; a private repository's bounty is already indistinguishable from a missing one there: confirm that with the existing private-repository test at `pages.test.ts:880` and keep it green).
8. **Cache headers:** `/b/<id>/`, `/board/` and `/numbers/` answer `cache-control: public, max-age=60` at most, and never when the request carries the session cookie's name (then `no-store`). Nothing personal is in the filled page: the fill uses only the public facts functions, never anything from `account.ts`.
9. **With scripts on, nothing changes:** walk filters and search on the board, the payment window from a bounty's page, and every link, in a real browser.
10. **The looks:** full-page before and after of the three pages at 1440 and 390, signed out; show the owner and quote the approval even if identical.
11. **The attacks** in the Security lens. **Verify, merge;** after the owner's deploy read `exceededCpu` over at least 30 page requests.

## Traps

- **Changed expectations:** a test may assert that `/b/<anything>/` returns the same bytes for every id, or that the shell says nothing about existence (search `tests/platform` for `same shell`). The design changes that on purpose (step 7): change that assertion to the new behaviour and name the file and line. Nothing else changes.
- React will complain if the server-filled HTML inside its root differs from what it renders first. Put the plain HTML in an element **outside** the component's root, or one the component removes in an effect; do not try to make React hydrate hand-built markup.
- The task text can be long (`capTask` already limits it). Use the capped text, as the JSON does.
- Do not render Your page, sign-in or profile pages this way.
- Do not add a second query path: every fact comes from the function that feeds the JSON.
- If [PF38](PF38.md) has merged, the `application/json` script is not executed and needs no hash; the page's real inline scripts are unchanged.

## Lenses

- [x] **Security:** a stranger's text now arrives in the first HTML. Attack it with markup, a closing tag for the surrounding element, an event-handler attribute, a `javascript:` link, and bidi and control characters. If [PF38](PF38.md) has merged, show the policy also blocks what escaping should already have stopped.
- [x] **User experience:** a fresh session given only a bounty's page address and an ordinary fetch tool says what the bounty is, what it pays and how to answer, without being told about the feed.
