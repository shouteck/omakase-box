# PF39: a bounty's page, the board and the numbers read complete without JavaScript

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF39` · Timebox: 300 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-found-at-the-moment, D-2026-11-02-site-looks-need-approval, D-2026-11-01-agent-only-direction
Horizon: long, with a design unknown: start with `/plan` and keep the plan in this file. The plan may call for a prototype wave first (KITCHEN.md, "Design decisions with no precedent").

**Brief.** Written by the CTO on 10 November 2026 from [K53](K53.md). Read on the live board that day, as a program without JavaScript reads it:

| Page | Text in the page's main part |
|---|---|
| A bounty's page (`/b/<id>/`) | "Reading the board." and nothing else |
| The board (`/board/`) | its heading and "Reading the board" |
| The numbers (`/numbers/`) | its heading and one sentence |
| Front page, How it works, For agents | complete |

Every posted issue links to the first kind. An agent that follows the link with an ordinary fetch, a search engine, or a registry's preview gets an empty page. The JSON feed and MCP hold the same facts, but only for a reader that already knows to ask for them.

## Outcome

The first answer for a bounty's page, the board and the numbers page already contains what the page shows: the task, the reward and payment facts, the attempts, how to answer; the list of open bounties; the numbers. A browser with JavaScript then behaves exactly as today. The pages look the same.

## Scope

- Write: `packages/box-platform/src/` (where the Worker answers these three addresses), `app/b/`, `app/board/`, `app/numbers/` and their components as the chosen design needs, `wrangler.toml` (`run_worker_first`), `tests/platform/pages.test.ts`
- Read for context: `src/feed.ts` (`bountyDetail`, `findBounties`, `numbersCached`: the same facts the JSON gives; render from these, not from a second query path), `src/api.ts:157` (today every `/b/<id>/` gets one shell on purpose, "so the shell says nothing about whether it exists": the new design must decide what a missing bounty answers), [PF8](PF8.md) (the 10 ms CPU limit), [PF10](PF10.md), [PF31](PF31.md), `untrusted` handling of posters' text
- Do not touch: the signed-in pages (Your page stays as it is: it is personal and not for a crawler), the JSON feed and its schema, the looks

## Done when

- Accepted as the rulebook then says ([K50](K50.md) if merged), with `test:platform` and `test:kitchen`.
- **The design is chosen in the plan from a measurement, not by preference.** Candidates: the Worker fills the built page with the facts before sending it; the Worker renders these three pages itself from a small template; the framework renders them at request time. For each: CPU per request against the 10 ms limit (measured on a local board at 1, 25 and 100 bounties, with what a local run cannot show said plainly), bytes sent, and how much of the approved markup is reused. If none fits in the limit, stop and report: do not ship a page that Cloudflare will cut off.
- A test fetches each of the three pages from the built board as text, with no script run, and finds: for a bounty, its title, task, reward, payment line, each attempt and the answer steps; for the board, every open bounty's title and reward on that page; for the numbers, every number `/numbers.json` gives. Seen failing on master's build first.
- **One source of facts:** a test compares what the page says with what the JSON says for the same bounty and fails on any difference.
- **A poster's or solver's text is still only text:** the existing escaping tests run against the new first answer; a title or task holding markup, a script tag and a link appears as characters. Tried with the hostile strings the reading-boundary tests already use.
- A missing bounty answers 404 with a page that says so and names the board; say in the Result that this changes the earlier "same shell for every id" choice and why that is acceptable (the JSON detail already answers 404).
- **The looks do not change:** full-page before-and-after screenshots of the three pages, signed out, at desktop and phone width; the owner's approval quoted before merge, even if they are identical.
- With JavaScript on, every action on these pages works as before, checked in a real browser: filters and search on the board, the payment window from a bounty's page, the links.
- Cache headers are stated and tested: a bounty's page is never served stale past the board's own freshness (15 minutes), and nothing personal is ever in a cached answer.
- Deploying is the owner's word; `exceededCpu` before and after, read over at least 30 page requests.

## Lenses

- [x] **Security:** a stranger's text now arrives in the first HTML. Attack it with markup, a closing tag for the surrounding element, an event-handler attribute, a `javascript:` link, and bidi and control characters. If [PF38](PF38.md) has merged, show the policy also blocks what escaping should already have stopped.
- [x] **User experience:** a fresh session given only a bounty's page address and an ordinary fetch tool says what the bounty is, what it pays and how to answer, without being told about the feed.
