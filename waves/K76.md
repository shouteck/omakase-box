# K76: the hosted run picks its jobs from what the push changed

Milestone: K (kitchen) · Station: evidence · Base: `master at dispatch` · Branch: `wave/K76` · Timebox: 120 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Feature playbook; principles: build-the-lever, prove-it-works, subtract-before-you-add.

**Brief.** Written by the CTO on 24 November 2026 at the owner's request ("Yes, brief it"). The owner noticed the kitchen waits for hosted runs on pushes that cannot change their outcome, for example BT80's Result (one Markdown file).

**Why.** `.github/workflows/verify.yml` already skips a push that touches only inert files (its `paths` list mirrors `INERT` in `scripts/suite.mjs`). But it re-includes every file a kitchen test reads: `waves/*.md`, `STATUS.md`, `kitchen/stations/*.md`, `kitchen/reviews/guard-breaks.json`, `docs/box-v4/CONTRACTS.md` and others. A push that touches any of them starts **every** job: the bounty suite (8 shards on three systems), the platform suite, the install test, the kitchen suite and the audit. Only the kitchen suite (and the audit) can read those files.

KITCHEN.md (Verification, K57) then requires the Result's own push to be green before the merge, so every wave waits once more for a full run. On 24 November 2026 that was three waits (BT72, BT77, BT80). The run on the Result push `a628828f` (45362125844) ran 18 jobs; the bounty shards on Windows took 332 to 485 s each, against 224 s for the Windows kitchen job. Each STATUS push on master also runs everything; one (45356666879) failed only because three macOS jobs were cancelled waiting for a runner.

`scripts/verify.mjs` already knows the answer locally: a step is `reused` when every path between a passing ancestor and HEAD is one the step does not read (K23, `stepReadsPath`). The hosted run does not use that rule.

## Outcome

1. A first job, `select`, reads the push's changed paths (`github.event.before..github.sha`, the two-dot diff GitHub's own path filter uses) and classifies them with the same rule `verify.mjs` and `suite.mjs` use. It outputs `full: true` when any changed path is read by the bounty suite, the platform suite or the install test, and `full: false` when every changed path is read only by the kitchen suite.
2. With `full: false`, the `bounty`, `platform` and `install-node22` jobs are skipped by an `if:`. `kitchen` (all three systems) and `audit` always run. With `full: true`, nothing changes from today.
3. `select` falls back to `full: true` whenever it cannot be sure: a new branch (`before` is all zeros), a `before` that is not an ancestor of `after` (a forced push), an unreadable diff, or more than 1,000 commits. It prints the changed paths and the reason for its answer.
4. KITCHEN.md's Verification section and `kitchen/roles/cto.md` step 6 say what accepts a push that ran kitchen only: its `kitchen` and `audit` jobs green, its other jobs `skipped`, **and** a full green run on the nearest ancestor commit whose diff to it is kitchen-only. Red, cancelled or missing is still not a pass.
5. Measured on the wave itself: the wall time of a kitchen-only run (a commit touching only the wave file), quoted with its run id, against the full run on the same branch.

## Steps, in order

Written so any model can cook it.

1. **Read** the files under "Read for context". Write down in this file, under `## Plan`, which existing function or set decides "a kitchen test reads this path" and which decides "the bounty suite reads this path", with file and line. If none decides the second, the rule is: every path that is not inert and not a kitchen-only read is read by the full run.
2. **Tests first:** the table above, against a stub `ci-select.mjs` that always answers `full: true`. See rows 1, 2 and 12 fail.
3. **`ci-select.mjs <before> <after>`:** run `git diff --name-only -z <before> <after>` (two-dot, as GitHub's path filter); apply the fallbacks of Outcome 3 first; then `full = changed.some(path => !kitchenOnly(path))`, where `kitchenOnly` is built from `suite.mjs`'s own sets. Print one line per changed path with its class, then `full=<true|false> (<reason>)`. In CI, write `full=<value>` to `$GITHUB_OUTPUT`. Exit 0 in every case; a failure to decide is `full=true`, never an error.
4. **The workflow:** a `select` job on `ubuntu-24.04` with `fetch-depth: 0` (it needs `before`), running `node scripts/ci-select.mjs ${{ github.event.before }} ${{ github.sha }}`. `bounty`, `platform` and `install-node22` get `needs: select` and `if: needs.select.outputs.full == 'true'`. `kitchen` and `audit` do not depend on it.
5. **The rule text:** KITCHEN.md Verification and `cto.md` step 6, as Outcome 4. Replace words; the pair is at its size limit.
6. **Verify:** `node scripts/verify.mjs test:kitchen` locally, push, read the full run, then push the wave-file-only commit and read the kitchen-only run. Result, merge.

## Traps

- **The wrong direction is the only dangerous one.** Skipping a job that should run hides a failure; running one that could be skipped costs minutes. Every uncertain case answers `full: true` (Outcome 3, rows 8 to 11).
- **Do not copy the path lists.** `verify.yml`'s `paths` already mirrors `INERT` by hand. `ci-select.mjs` reads `suite.mjs`'s sets, so the two cannot drift. Leave the workflow's `paths` list alone in this wave.
- **A skipped job is not a green job.** GitHub marks a job skipped by `if:` as `skipped`. The acceptance rule must name that state and require the ancestor's full green run, or "every job is success" (cto.md step 6) reads a kitchen-only run as incomplete and the kitchen waits anyway.
- **`github.event.before` on the first push of a branch** is forty zeros; on a forced push it may be a commit the new history does not contain. Both are rows in the table.
- **The workflow change itself** must get a full run: `.github/` and `scripts/` are never kitchen-only (rows 6 and 7).
- GitHub's docs (read on 24 November 2026, `docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions`, "Git diff comparisons"): a push to an existing branch "compares the head and base SHAs directly with each other"; a push of more than 1,000 commits always runs. Re-read the page on the day and quote it in the Result. The pages on skipped jobs and required checks moved (404 on 24 November); find their current addresses before relying on them. This repository has no required status checks, so the kitchen's own reading of the run is the gate.
