# K75: the walkthrough's deterministic half: one script for the agenda, and a scanner for each class of fault found

Milestone: K (kitchen) · Station: evidence · Base: `master at dispatch` · Branch: `wave/K75` · Timebox: 240 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: medium. Feature playbook; principles: encode-lessons-in-structure, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026. The owner asked for walkthroughs at fixed points, early and often, and for them to be deterministic ("how do you make the walkthrough deterministic?"). The practice is [WALKTHROUGH.md](../docs/box-v4/WALKTHROUGH.md). This wave builds its deterministic half.

**Why.** The walkthrough of 23 and 24 November 2026 found faults of a few recurring kinds, each found by reading. Reading again next time finds them only if someone thinks to look. A parser check finds them every time, in every hosted run. `exit-sites.ts` (BT82) and `refusal-sites.ts` already show the pattern.

## Outcome

1. **`node scripts/walkthrough.mjs`** prints the agenda in a fixed order:
   - **Scope:** files changed since the newest `walkthrough/*` tag, grouped by component (`packages/box-bounty`, `packages/box-cli/src`, `packages/box-platform/src`, `.github/workflows`).
   - **Coverage:** every product file, placed in the register in `docs/box-v4/WALKTHROUGH.md` by a new `register.json` beside it (file → table or `not pinned`). A file in neither exits non-zero, naming it.
   - **The invariants:** each register row's test is run, with its result.
   - **The scanners' results** (Outcome 2).
   - **The checklist** for each component in scope, printed as headings ready to answer.

   `--references` re-reads every source recorded in the register's tables (addresses with dates) and lists the ones whose content changed, by hash of the fetched text. It is never part of the ordinary suite.
2. **Scanners for this walkthrough's fault classes,** each in `tests/kitchen/scanners/`, run in the ordinary suite, each with the walkthrough finding it comes from. A scanner whose rule a pending wave will establish starts in "report" mode (it prints, does not fail), and the wave that lands the rule switches it to "fail". The Result lists each mode.
   - **Writes outside the door** (BT82, BT83): `exit-sites.ts`, already built.
   - **A permission decided by login name** (PF61): a `same(` call, or a login comparison, inside a function that decides a role or an access in `packages/box-platform/src`.
   - **Stranger text in unasked output** (BT93, BT92): a field the `foreignFields` lists name, reaching the hook's envelope or any `additionalContext`.
   - **A Git call missing a defence** (BT97): read from `GIT-DEFENCES.md` once it exists.
   - **A read that writes outward** (BT100): a call to any exit reachable from a read-only command's entry (`look`, `status`, `find`, `describe`, `discover`), by the import and call graph the exit walk already builds.
   - **A record write without a revision check** (BT96): a `persistRecord` or `writeStored` call outside the store's own compare-and-swap.
   - **Board settings that change the tool's flow** (D-2026-11-24-card-is-the-only-board-setting): a board table or column read by a tool-facing answer, other than the public facts the register lists.
3. **The first walkthrough is recorded:** the walkthrough file WT-2026-11-24 (in `waves/`) lists the session's findings by component, and where each went (a brief, a fold, a backlog line). The tag `walkthrough/2026-11-24` is put on the master commit the walkthrough read: the product code did not change during the session, so it is the last commit before this wave that touched a product file. The Result names it.

## Scope

- Write: `scripts/walkthrough.mjs` (new), `docs/box-v4/register.json` (new), `docs/box-v4/WALKTHROUGH.md` (the register's table generated from `register.json`, or checked against it), `tests/kitchen/scanners/*.test.ts` (new), `tests/kitchen/walkthrough.test.ts` (the script's coverage check on a scratch tree), the walkthrough file WT-2026-11-24 in `waves/` (new)
- Read for context: `tests/box/bounty/exit-sites.ts`, `tests/box/bounty/refusal-sites.ts`, `scripts/proof-map.mjs`, `scripts/gitleaks-rules.mjs` (once BT78 lands), the briefs named in Outcome 2
- Do not touch: product code (the scanners read it; the waves fix it)

## Done when

- The hosted run on the final commit is green on Linux, Windows and macOS, quoted with its run id; the suite the change affects: `test:kitchen`.
- `walkthrough.mjs` run on master prints the agenda, quoted in the Result. A product file added to a scratch copy without a register entry fails it, naming the file.
- **Each scanner is shown to bite** on a scratch planted fault, quoted. Its mode (report or fail) is listed with the wave that will switch it.
- The walkthrough file WT-2026-11-24 exists, and the tag is pushed.

## Steps, in order

1. **`register.json`** from the register table; the coverage check, tests first.
2. **The agenda script;** `--references`.
3. **The scanners,** one at a time, each with its planted fault.
4. **The first walkthrough's record** and its tag.
5. **Verify,** push, hosted run, Result, merge.

## Traps

- **A scanner that fails on code a pending wave fixes would block every wave until then.** That is why "report" mode exists. Never weaken a scanner to make it pass.
- **Coverage is per file, not per line.** A file pinned by one table may still hold unpinned behaviour, which the checklist is for.
