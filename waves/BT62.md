## Outcome

One recorded description of what an agent can depend on: every command, every option with whether it takes a value, every exit code, every refusal name, and every field of every `--json` document with its type. A test compares the built tool with the record and fails on any difference, naming it and saying whether it adds, removes or changes. Updating the record is one command; its diff in a commit is how a surface change is seen and judged.

## Scope

- Write: a script that derives the surface from the built tool, the record it writes (one readable file under `docs/box-v4/` or `tests/box/bounty/`), a new `tests/box/bounty/bt62.test.ts`, `docs/box-v4/KITCHEN.md` or the wave template (one line: a wave that changes the record says so in its brief and Result), `scripts/surface.mjs`, `docs/box-v4/SURFACE.txt`, `templates/wave.md` (one line)
- Read for context: `packages/box-bounty/args.ts` (the one option table, BT18), `json.ts` and its schema names, `errors.ts` and the refusal walk [BT40](BT40.md) built, `tests/box/bounty/k14-start-budget.test.ts`, `json-agreement.test.ts`, the removed-name guard, [BT61](BT61.md) (merged: every command's document and the refusal document), `docs/box-v4/CONTRACTS.md` (its refusal sections), [K51b's map](../kitchen/reviews/K51b-test-map.md)
- Do not touch: any command, option, field, refusal or exit code; this wave records, it changes nothing

## Steps, in order

Written so any model can cook it. This wave changes no behaviour: if a product file under `packages/` needs editing, stop and ask.

1. **Find what already pins the surface.** Search `tests/box/bounty` for tests that list commands, options, refusal names or JSON fields: start with `bt18.test.ts` (the option table), `bt40.test.ts` (the refusal walk), `json-agreement.test.ts` and `bt26.test.ts` (documents), and the removed-name guard. Write each down with what it pins.
2. **The record's shape,** one text file, `docs/box-v4/SURFACE.txt`, sorted, one item per line, in four parts:

   ```
   command status
   option status --full switch
   option status --since value
   exit 0 ok
   exit 1 failed
   exit 2 usage
   exit 3 refused
   refusal reward-required
   field box-bounty/status@1 bounties[].id string
   field box-bounty/status@1 bounties[].reward number optional
   ```

3. **The script,** `scripts/surface.mjs`, with two modes: no argument prints the surface it derives; `--write` writes the file.
   - **Commands and options:** import `BOUNTY_COMMANDS` from the built `packages/box-bounty` (the same table the parser uses, `args.ts` line 107). For each entry: its name; each key of `values` as `value`; each key of `switches` as `switch`; `positionals`.
   - **Exit codes:** fixed, read from `packages/box-cli/src/bounty.ts`'s `catch` block; write the four lines by hand in the script with a comment naming that block, and add a test that the block still has exactly those `process.exit` codes.
   - **Refusal names:** every string literal that is the first argument of `new BountyRefused(` or `invalid(` in `packages/box-bounty` and `packages/box-cli/src`, found with the same walk `bt40.test.ts` uses (reuse its helper; do not write a second regular expression that can disagree).
   - **JSON fields:** run the tool with `--json` on fixtures and walk each printed document: for every path, its type (`string`, `number`, `boolean`, `null`, `object`, `array`), with array elements written as `[]`. Run every fixture that the agreement test uses; a path present in some runs and absent in others is `optional`. A value written by a stranger is still just `string`.
4. **The test,** `tests/box/bounty/bt62.test.ts`: derive the surface, read the file, compare as sets. On a difference it fails with one line per item: `added: …` or `removed: …` (a changed type shows as one of each), and ends with `update the record on purpose: node scripts/surface.mjs --write`.
5. **Show it bites.** For each of the seven changes in Done when, make the change in a scratch edit, run the test, copy the failure line into the Result, and undo the edit. Do them one at a time. `git status` is clean before the next.
6. **Write the first record** with `--write` and commit it with the test.
7. **Time it:** three runs of the test alone; if over five seconds, find which part (it will be the fixture runs) and reuse output the agreement test already produces.
8. **One line for the kitchen,** in `templates/wave.md` under Done when: "if the wave changes `docs/box-v4/SURFACE.txt`, the brief says so and the Result shows the diff".
9. **Verify and merge.**

## Traps

- The record is derived. If you find yourself typing a command or a field name into `SURFACE.txt`, the script is missing a source.
- A field that only a rare state produces will be missing if no fixture reaches that state. List the states you could not reach in the Result; do not mark the record complete.
- Do not publish the file as a promise: no page, README or help text links it as "stable". The version stays under 1.0.
- If an existing test pins the same thing as the new record (step 1), keep the stricter one; do not delete a test in this wave unless the new one fails on every break the old one does, shown once.

## Lenses

- [x] **Measurement fairness:** the Result gives the counts on the day (commands, options, refusal names, documents, fields) and says which parts of the surface the record cannot see, such as the wording of plain-text output, which stays under BT17's budget tests and is not frozen.

## Notes

- Follows the practice of tools that keep an API report in the repository and review its diff (the "frozen contract, additive only" of the CLI read in K55 is the 1.0 form of the same idea).
- When 1.0 is declared, later, the same test gets one rule added: a removal or a change fails outright, and only additions may update the record. That is the owner's decision and a separate wave.
- No dependency on the release. Runs before BT59, and the next release carries both, so the first published record is the baseline.
