# BT62: the tool's surface is on record, so it changes only on purpose

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT62` · Timebox: 120 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k55-answers, D-2026-10-14-tool-convention
Horizon: short

**Brief.** Written by the CTO on 10 November 2026 from [K55](K55.md)'s question 3 and the owner's answer: stay below 1.0 through launch and first real use, and add now the test that records the surface. Skills, instruction files and scripts are written against the exact commands of the day and sit on machines we cannot update; a rename breaks them silently. Before 1.0 we still want the freedom to fix a wrong name. So nothing is frozen by this wave: a change stays allowed, but it has to be made knowingly.

## Outcome

One recorded description of what an agent can depend on: every command, every option with whether it takes a value, every exit code, every refusal name, and every field of every `--json` document with its type. A test compares the built tool with the record and fails on any difference, naming it and saying whether it adds, removes or changes. Updating the record is one command; its diff in a commit is how a surface change is seen and judged.

## Scope

- Write: a script that derives the surface from the built tool, the record it writes (one readable file under `docs/box-v4/` or `tests/box/bounty/`), a new `tests/box/bounty/bt62.test.ts`, `docs/box-v4/KITCHEN.md` or the wave template (one line: a wave that changes the record says so in its brief and Result)
- Read for context: `packages/box-bounty/args.ts` (the one option table, BT18), `json.ts` and its schema names, `errors.ts` and the refusal walk [BT40](BT40.md) built, `tests/box/bounty/k14-start-budget.test.ts`, `json-agreement.test.ts`, the removed-name guard, [BT61](BT61.md) (which adds documents: whichever of the two merges second updates the record)
- Do not touch: any command, option, field, refusal or exit code; this wave records, it changes nothing

## Done when

- Accepted as the rulebook then says ([K50](K50.md) if merged), with `test:box-bounty` and `test:kitchen`.
- **Read first what already pins part of this,** by search, and list it in the Result: tests that pin the option table, the refusal names, the JSON documents. The new record replaces a duplicate where one exists and never loosens an existing check.
- **The record is derived, not typed:** commands and options from the option table the parser itself uses; refusal names from the same walk BT40 used; JSON fields from the documents the tool actually prints on fixtures that reach every branch that adds a field. A field only some states produce is recorded as optional, and the Result says how each was reached.
- **It bites, each shown once on a scratch change:** an option renamed; an option removed; a JSON field renamed; a field's type changed; a refusal renamed; an exit code changed; and an addition (a new option), which also fails until the record is updated, so additions are seen too.
- The failure message names the exact item and the one command that updates the record, and distinguishes "added" from "removed or changed".
- The record reads plainly to a person: one line per item, sorted, no generated noise, so a commit's diff shows a surface change at a glance.
- The test costs under a few seconds; its time is stated from three runs.
- The record is not published as a promise: no page or help text says the surface is frozen. The version stays below 1.0.

## Lenses

- [x] **Measurement fairness:** the Result gives the counts on the day (commands, options, refusal names, documents, fields) and says which parts of the surface the record cannot see, such as the wording of plain-text output, which stays under BT17's budget tests and is not frozen.

## Notes

- Follows the practice of tools that keep an API report in the repository and review its diff (the "frozen contract, additive only" of the CLI read in K55 is the 1.0 form of the same idea).
- When 1.0 is declared, later, the same test gets one rule added: a removal or a change fails outright, and only additions may update the record. That is the owner's decision and a separate wave.
- No dependency on the release; any time.
