**The format**

- Every bounty issue carries, besides the text a person reads, one block a program can read without guessing. Its fields: the format's version; the bounty's identifier; the repository; the commit to work from; the branch to send pull requests to; whether that branch carries the poster's work on top of the commit; when it was created; its state; the reward, as an amount and a currency; and the terms, as one fixed value meaning that the merged solution earns all of it. It sits where a person is not bothered by it and where editing the visible text cannot desynchronise it by accident.
- **The reward field is taken from the owner's standing rules** (BT8), where 0 is the only value accepted in this wave. No command lets an agent set it.
- The fixed label from BT6 is the way in: the page gives the one search that finds every open bounty made with this tool, on any repository.
- The block is written by the tool and only the tool. `status` reads it back for open bounties; `status <id> --full` reads it back for ended bounties and says, as a fact, if someone has edited it so that it no longer matches the record. Compact ended status explicitly labels its last observation and names the full command for a current comparison. A failed current read is reported as unavailable, never as a fresh match. The block is never trusted over the record.
- The state in the block follows the bounty: open, closed with a solution merged (naming the pull request and the commit), closed with none. A test walks a bounty through each and reads the block back.
- **The format is versioned and kept stable.** A test pins the exact field names and shapes; changing one means changing the version and the page, on purpose.
- Bounties posted before this wave are still read; the tool says they carry no block.

**The public page** (`docs/box-v4/BOUNTY-FORMAT.md`)

- Written for a stranger building on it: a site, a solver agent, a person. One screen. What a bounty is, how to find them all, each field with one line and an example, how to answer one (fork, branch from the bounty branch, pull request against it), and what the poster's tool does with an answer (lists it, lets the poster look and choose, runs nothing).
- It says plainly what is not promised: that anyone is watching, that an answer will be used, any payment.
- No verdict words, nothing that reads as marketing.

**Proved by a reader that is not ours**

- A small program written for the test, using only the public page and GitHub's public search, with none of this repository's code, lists the open bounties on a repository and prints each one's fields. It lives with the tests as the worked example the page links to.

**The whole journey, once**

One real bounty on `shouteck/omakase-box`, from the main checkout with the merged tool, through every step in `PLAN.md`'s journey that is built, and nothing skipped:

0. **A real first-time setup, with the owner as the owner** (owner, 13 October 2026). The journey starts on a repository the owner has never allowed, with nothing written for it: an agent tries to post, the bounty waits, the agent tells the owner in its own words, and the owner answers. What the owner understood they were agreeing to is written down before they see the tool's own text, and compared with it. This comes before any reward exists (BT11).
1. A small real task chosen from STATUS or the backlog.
2. Created with the task, what was tried, the one line of why, and the line on what the agent was in the middle of (BT7), with a small uncommitted change the task needs.
3. **The owner sees the exact issue text, and the exact list of what becomes public, and says "go"** before it is posted. This repository's own rules stay the owner's; the kitchen does not grant itself authority to post without asking.
4. Posted: issue, bounty branch, label, the block. The content scan (BT8) has run on what was newly published and its result is in the record. The outside reader from the test finds the bounty and prints its fields.
5. **The kitchen is the solver.** Two blind solvers, each in an empty folder outside every checkout and given only the issue's address, each open a pull request using the account signed in on this machine. One of them also leaves a question as a comment on the issue. Before they finish, the head chef changes a line on master that one of them also changes, so that solution clashes.
6. A collecting session, new and told nothing, learns of the bounty the way a real one would (the rules-file line, and the hook if the owner has it on here; say which), sees both solutions and the comment count, reads the question, looks at each solution as its solver made it, chooses the one that clashes, is refused by `apply` with the facts, and merges it with its own Git. The tool, on the session's next command, recognises the merge and closes the bounty.
7. It says what job it would go back to, from the record.
8. The solver's pull request and the issue are read back from GitHub and described as a solver would see them: which solution was merged, and that the bounty is closed.
9. Nothing was closed by hand: the block reads closed with that solution merged, and the branch is gone.

The Result gives, for each numbered step 0 through 9, what happened, and lists by exact name anything left on GitHub. No money, no bounty site, no message to anyone beyond the approved issues, their pull requests and the specified question, nothing overnight.

## Review lenses

- [x] **Security:** the block is read by programs and written near text strangers can influence. The reviewer tries to make a reader mis-parse it (a task or title containing the block's own delimiters, a second forged block in the issue body or in a comment by another account, an edited block), and checks our own `status` never trusts a block over the record. It confirms the block and the page reveal nothing the listing did not already say, and no never-ship name.
- [x] **User experience:** two readers. A fresh agent given only the public page and the address of a repository with two open bounties writes, unaided, a few lines that list them and say how it would answer one; the reviewer reports what the page left unclear. And the collecting session in step 6 is the user-experience check on the whole product: the reviewer reads its transcript and reports every hesitation, every command it ran that the output had not named, and anything it got wrong.
- [ ] **Measurement fairness:** not applicable.
