# BT10: the open bounty format, and the whole journey run once

Milestone: BT · Station: packaging (also evidence) · Base: master at the time this cooks, after BT9 is merged · Branch: `wave/BT10` · Timebox: 150 minutes; at expiry, report partial findings and stop

**Brief, written ahead.** By the CTO on 11 October 2026, while BT6's second run was cooking, for the way BT6a posts a bounty: an issue on the real history, with an ordinary bounty branch. The outcome is settled with the owner. Field names and commands follow the design discussion; the head chef checks them against the Results of BT6a to BT9 before dispatching, corrects names only, and says in the pre-cook card what changed.

Two decisions frame this wave: **we do not interface with bounty sites; they can interface with us**, and **every bounty in this wave states a reward of $0** (a stated amount arrives in BT11).

## Outcome

1. A bounty posted by this tool can be found and read by a program that has never heard of us: one search finds every bounty, and each issue carries the same named fields in the same place. A short public page says what they are.
2. The whole journey, with everything BT6 to BT9 built, is run once for real on `shouteck/omakase-box`, solved by the kitchen, and closed.

**The format**

- Every bounty issue carries, besides the text a person reads, one block a program can read without guessing. Its fields: the format's version; the bounty's identifier; the repository; the commit to work from; the branch to send pull requests to; whether that branch carries the poster's work on top of the commit; when it was created; its state; and the reward, as an amount and a currency. It sits where a person is not bothered by it and where editing the visible text cannot desynchronise it by accident.
- **The reward field is taken from the owner's standing rules** (BT8), where 0 is the only value accepted in this wave. No command lets an agent set it.
- The fixed label from BT6 is the way in: the page gives the one search that finds every open bounty made with this tool, on any repository.
- The block is written by the tool and only the tool. `status` reads it back and says, as a fact, if someone has edited it so that it no longer matches the record. It is never trusted over the record.
- The state in the block follows the bounty: open, withdrawn, closed with a solution used, closed with none. A test walks a bounty through each and reads the block back.
- **The format is versioned and kept stable.** A test pins the exact field names and shapes; changing one means changing the version and the page, on purpose.
- Bounties posted before this wave are still read; the tool says they carry no block.

**The public page** (`docs/box-v4/BOUNTY-FORMAT.md`)

- Written for a stranger building on it: a site, a solver agent, a person. One screen. What a bounty is, how to find them all, each field with one line and an example, how to answer one (fork, branch from the bounty branch, pull request against it), and what the poster's tool does with an answer (lists it, lets the poster look and choose, runs nothing).
- It says plainly what is not promised: that anyone is watching, that an answer will be used, any payment.
- No verdict words, nothing that reads as marketing.

**Proved by a reader that is not ours**

- A small program written for the test, using only the public page and GitHub's public search, with none of this repository's code, lists the open bounties on a repository and prints each one's fields. It lives with the tests as the worked example the page links to.

**The whole journey, once**

One real bounty on `shouteck/omakase-box`, from the main checkout with the merged tool, through every step in `PLAN.md`'s journey that is built, and nothing skipped:

1. A small real task chosen from STATUS or the backlog.
2. Created with the task, what was tried, the one line of why, and the line on what the agent was in the middle of (BT7), with a small uncommitted change the task needs.
3. **The owner sees the exact issue text, and the exact list of what becomes public, and says "go"** before it is posted. This repository's own rules stay the owner's; the kitchen does not grant itself authority to post without asking.
4. Posted: issue, bounty branch, label, the block. The content scan (BT8) has run on what was newly published and its result is in the record. The outside reader from the test finds the bounty and prints its fields.
5. **The kitchen is the solver.** Two blind solvers, each in an empty folder outside every checkout and given only the issue's address, each open a pull request using the account signed in on this machine. One of them also leaves a question as a comment on the issue. Before they finish, the head chef changes a line on master that one of them also changes, so that solution clashes.
6. A collecting session, new and told nothing, learns of the bounty the way a real one would (the rules-file line, and the hook if the owner has it on here; say which), sees both solutions and the comment count, reads the question, looks at each solution as its solver made it, chooses the one that clashes, resolves the clash, and finishes.
7. It says what job it would go back to, from the record.
8. `undo`, then the merge again, to show the way back works on the real thing.
9. Closed with the tool's own commands; the block reads closed; the branch is gone.

The Result gives, for each of the nine steps, what happened, and lists by exact name anything left on GitHub. No money, no bounty site, no message to anyone beyond the issue and its pull requests, nothing overnight.

## Review lenses

- [x] **Security:** the block is read by programs and written near text strangers can influence. The reviewer tries to make a reader mis-parse it (a task or title containing the block's own delimiters, a second forged block in the issue body or in a comment by another account, an edited block), and checks our own `status` never trusts a block over the record. It confirms the block and the page reveal nothing the listing did not already say, and no never-ship name.
- [x] **User experience:** two readers. A fresh agent given only the public page and the address of a repository with two open bounties writes, unaided, a few lines that list them and say how it would answer one; the reviewer reports what the page left unclear. And the collecting session in step 6 is the user-experience check on the whole product: the reviewer reads its transcript and reports every hesitation, every command it ran that the output had not named, and anything it got wrong.
- [ ] **Measurement fairness:** not applicable.

## Notes for the worker

- Feature playbook. The format is an interface other people will build on: decide it once, small, and write the page before the code.
- Fewer fields is better. Every field is a promise to keep it. If a field is only useful to us, it belongs in the record, not the block.
- Do not invent a new syntax; use a common, boring one that every language can parse.
- A stranger's reader must never need our code, our record or an account with us.
- Leave room, by version, for the two things BT11 adds to the block: a reward above $0 and the instruction to supply a payment link. Do not add them here.
- Out of scope: any reward other than $0; any payment; any bounty site; a site or board of our own; a second hosting service.
- Everything the wave creates in the temp folder or on the remote is named for the wave or the bounty and removed at close.
