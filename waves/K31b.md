# K31b: the loop on real GitHub, and the hand-off decision on tasks worth handing off

Milestone: K (kitchen) · Station: evidence · Base: `master at dispatch` · Branch: `wave/K31b` · Timebox: 240 minutes of cooking, over at least two sessions; at expiry, report partial findings and stop
Owner decisions: D-2026-10-19-k31-sandbox-go (real $0 posts on the sandbox only); the owner asked for this second run on 19 October 2026 ("Yes" to briefing K31b); `kitchen/sandbox.md` (what a wave may do there without asking)

**Brief.** Written by the CTO on 19 October 2026 after K31. K31 was carried out honestly and passed review, but **0 of 5 tasks entered the loop**: every posting agent read `box bounty describe`, quoted its own guidance ("not worth it when: you can plainly do the work", `packages/box-bounty/wording.ts`) and did the work itself. The cause was the brief: it asked for "five genuine **small** tasks", which a capable agent should not hand off. K31 therefore measured the decision on easy tasks (agents decline correctly) but never ran create → post → track → review → decide → pay on real GitHub, and never offered a task worth handing off. This wave does both, as two separate experiments, labelled.

## Outcome

`kitchen/reviews/K31b-real-use.md` answers, from transcripts and real GitHub timings: **(A)** does the whole loop work on real GitHub, stage by stage, and is each output clear enough for an agent to take the next step unaided; **(B)** when a task is worth handing off, does an agent choose the tool unprompted, and does it still decline a task it can plainly do.

## Scope

- Read for context: `waves/K31.md`, `kitchen/reviews/K31-real-use.md` (its harness, its findings), `kitchen/memory/real-use/` (reuse its scripts where they work), `docs/box-v4/MEMORY-SPEC.md` (the questions), PLAN.md's roadmap.

## Setup (30 minutes)

1. **Clean the sandbox first**, as K31 found: delete or update the stale `tasks/*.md` files that misled three agents (a sandbox commit through a pull request merged by the head chef's sandbox clone, or a direct sandbox commit, which `kitchen/sandbox.md` allows); record the sandbox's starting state (open issues, open PRs, branches, `refs/box-bounty/*` refs, `main`'s SHA).
2. Build and install the package into a scratch prefix as a newcomer would; scratch settings allowing only the sandbox at $0. Fix K31's harness defect: the environment must persist across an agent's tool calls (a wrapper script per agent that sets every variable and calls `box`, not a `source`d file), so every `gh` start is logged, none inferred.
3. Two sandbox clones: **machine A** and **machine B** (B with an empty local store). Posting and solving agents work through pull requests only; **no agent pushes to the sandbox's `main`** (K31's agents did).

## Experiment A: the loop, instructed (labelled as a mechanics test)

Three tasks on machine A. Each posting agent is told: "hand this task off with `box bounty`; you may not do it yourself." This is a different experiment from B and the report says so.
- **A1:** a clear fix with one solver, merged with `apply`.
- **A2:** the same kind of task with **two** solvers, so review has a real choice; one merged, the other set aside.
- **A3:** a task whose solution the posting agent rejects; ended with `close --reason`.
For each: a fresh **solver agent** given only the issue's URL, told "solve this bounty"; then the posting agent again, in a later session, told only "continue your work in this project". Record per stage: the command the agent ran, whether the previous output named it, wall time on real GitHub (create, post, the solver's PR appearing, `status` noticing it, `look`, `apply` or `close`, the issue closed and the branch removed), `gh` starts per command, and every hesitation, error or unclear line verbatim.
Then a fresh agent on **machine B**, told only "continue the work in this project": score its answers to MEMORY-SPEC.md's M2, M5, M7, M9 and M11 questions against what happened.

## Experiment B: the decision, uninstructed

Three tasks on machine A, each given to a fresh agent told only "work on this task in this project; the tools here include `box bounty`; use them if they help." Design each with the reasons `describe` names for handing off:
- **B1, needs what the agent lacks:** a change that can only be checked on a platform or with a tool the agent's machine does not have (for example a macOS-only script, or a fix whose acceptance check needs a service the sandbox cannot reach). The task says so plainly.
- **B2, should not be done here:** the sandbox's `AGENTS.md` (added in setup) marks one folder as owned by another team: "do not edit; ask for changes from outside the project". The task needs a change in that folder.
- **B3, the control:** a task the agent can plainly do in a few minutes. The right answer is to decline.
Score: B1 and B2 handed off (or the agent says precisely why not), B3 declined. Record whether each agent checked first whether the work was already handed off (`box bounty`, `status` or `find`): K31 found three of five did not.
