# BT31: bounty records live in a local SQLite database

Milestone: BT · Station: packaging · Base: master at dispatch, after BT30 · Branch: `wave/BT31` · Timebox: 180 minutes; at expiry the cook stops and reports where it is

**Brief.** Written by the CTO on 17 October 2026 from K27's recommendation (`kitchen/reviews/K27-storage.md`, step 6 and its BT30 outline) and the owner's decision that day: a real database on each machine; the shared copy stays public for now, with a private online store (Turso) added later. The second of three waves (BT30 prepared the tests; **BT31 swaps the storage; BT32 splits shared and local**). Detailed for a cook without deep reasoning. **What every command prints and does stays the same; only where records are kept changes.**

## Why

K27 measured three stores at 1,000, 10,000 and 100,000 records on this machine: SQLite built into Node (`node:sqlite`, write-ahead log, full-text search FTS5) wrote in 0.2 to 0.5 ms at every size, against 480 to 944 ms for the alternatives at 100,000; searched in about 1 ms; and survived a process killed mid-write (`PRAGMA integrity_check` ok). It adds no bytes to the package. Today every command reads every record file (`listRecords`), so the tool slows with every bounty ever made.

## Outcome

The tool keeps its records in one SQLite file per checkout, `.box/local/box.db`, kept out of Git; each command reads only what it needs; existing JSON records are imported once and still load; and the K25 output sizes, the K14 start budgets and every test's expectations are unchanged.

## The design (K27's, made exact)

1. **The file.** `.box/local/box.db`. On first open the tool creates `.box/local/` and writes `.box/local/.gitignore` containing `*` (the pytest, mypy and ruff convention), so the database is never committed. Open with `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000`.
2. **The schema** (version 1, recorded in `PRAGMA user_version`):
   - `records(id TEXT PRIMARY KEY, stage TEXT NOT NULL, open INTEGER NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL, ended_at TEXT, json TEXT NOT NULL)`, with indexes on `(open, updated_at)` and `(open, ended_at)`;
   - `records_fts` (FTS5) over `id, title, why, part_of, task, note`, kept in step with `records` in the same transaction;
   - `meta(key TEXT PRIMARY KEY, value TEXT)` for the import marker.
   The `json` column holds the whole record exactly as `persistRecord` writes it today; `asRecord` validates it on every read, as it validates the file today.
3. **One module, `store.ts`**, is the only code that opens the database. It exports the operations K27 benchmarked: `listOpen`, `listEndedRecent(limit)`, `countEnded`, `readOne(id)`, `write(record)` (one transaction: the row and its FTS row), `search(query, limit)`, `allRecords()` (for `status --json`, which asks for everything), and `exists(id)`.
4. **`record.ts` keeps its names.** `loadRecord`, `persistRecord`, `writeNewRecord`, `listRecords` call `store.ts`. Replace each `listRecords` call that only needs open records or the bounded overview with `listOpen` / `listEndedRecent` / `countEnded` (render.ts's overview, hook start, the OPEN line); keep `allRecords` only where every record is truly needed, and list each call and its choice in the Result. `find.ts` uses `search` (FTS5) instead of scanning.
5. **Import of existing JSON records.** On open, if `meta` has no `imported` marker, read every `.box/bounties/*.json` through `asRecord` and write each valid one in one transaction; set the marker. Afterwards, **a JSON record file in `.box/bounties/` is still read**: on each open, any `<id>.json` there whose content differs from the stored row is imported again (this keeps the five tracked records in this repository loading, keeps hand-planted test records working, and keeps the corrupt-file refusal: a file that fails `asRecord` is reported as `record-corrupt` exactly as today). The tool itself writes only to the database from now on; it never deletes the JSON files.
6. **`OPEN`** is still written to `.box/bounties/OPEN` on every write, from `listOpen` (BT32 decides its future).
7. **Node floor 22.13.** `node:sqlite` needs no flag from Node 22.13.0 (K27, from the Node changelog). Set `NODE_MINIMUM = '22.13.0'` in `node-check.ts`; `pack.mjs` writes `engines.node >=22.13.0`; pin the hosted `install-node22` job to `22.13.0` (it also resolves BT12's follow-up that the job ran the newest 22.x); update `FIRST-FIVE-MINUTES.md`'s Node line.
8. **The experimental warning.** `node:sqlite` prints `ExperimentalWarning: SQLite is an experimental feature…` on stderr at first use. Suppress only that warning, in the CLI entry before `node:sqlite` loads: install a `process.on('warning')` handler that drops a warning only when its `name` is `ExperimentalWarning` and its message starts with `SQLite is an experimental feature`, and removes Node's default printing for that one case (read how Node's `warning` event and `--no-warnings` interact in the Node 24 docs before choosing); **do not** silence all warnings (`NODE_NO_WARNINGS`, `--no-warnings`). Test that a command's stderr is empty of it.
9. **Load the module lazily** where possible (a command that never reads records, such as `help`, should not open the database), so `help` and `describe` keep their K14 counts.
