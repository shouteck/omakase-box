# BT56: a stranger's pull request cannot claim the owner's own commit

Milestone: PF (the platform) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT56` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: none
Horizon: long by concept: start with `/plan` and keep the plan in this file

**Brief.** Written by the CTO on 10 November 2026 from [K48](K48.md). Found by [BT44](BT44.md)'s pass, narrowed by [BT51](BT51.md), still open in BACKLOG. Bug-fix playbook: reproduce first.

## The fault

`merged.ts` ends a bounty when the head of a pull request the tool has seen is part of the branch the bounty was created on, descends from the posted commit and is new to it. A commit the **owner** pushed after posting passes all three. So a stranger opens a pull request whose head is that commit; the next bounty command closes the bounty as solved by them, and with a reward the pay message can name them. Since BT51 the closing step does not move the bounty branch for such a head, so GitHub does not mark the pull request merged and the board credits nobody: pay on merge is not exposed. A payment by hand from the pay message is, and the bounty ends with the work not done.

## Outcome

A bounty ends as merged only for a commit that came from a solution. The mechanism: when the tool first records a pull request's head, it also records whether that commit was already on the branch; a head that was already there is never a merge candidate. The limit, stated in `help` or CONTRACTS: a pull request merged by hand on GitHub before any bounty command saw it is recognised only if GitHub itself says it is merged; ancestry alone is no longer enough for a head first seen on the branch.

## Steps, in order

Written so any model can cook it. Lines are as read on 10 November 2026.

**How the code decides today** (`packages/box-bounty/merged.ts`): `candidatesOf` (line 98) lists every collected attempt's commit and every `seenPullRequests` entry's commit. `checkOne` (line 114) keeps a candidate when it is on the branch the bounty was created on, descends from the posted commit, and is not part of the posted commit's history (lines 153 to 159). A commit the owner pushed after posting passes all three. That is the fault.

**The fix in one sentence:** when the tool first records a pull request's head, it also records whether that commit was already on the creating branch at that moment; a commit recorded that way is never a candidate.

1. **Reproduce first.** New file `tests/box/bounty/bt56.test.ts`. Copy the setup of `tests/box/bounty/bt44.test.ts` (it already builds a posted bounty with the stand-in GitHub). Write row 1 of the table and see it fail on master's code: the bounty closes as merged.
2. **The new field.** In `packages/box-bounty/gh.ts` line 29 the entry type of `seenPullRequests` gains `readonly onBranch?: true` ("this commit was already on the branch the bounty was created on when this machine first recorded it"). Give `availablePullRequests`' entry type the same field. It is only ever `true` or absent, so an old record needs no conversion.
3. **Let it load.** `packages/box-bounty/record.ts` near line 570 validates both lists entry by entry. Add: `if (pr.onBranch !== undefined && pr.onBranch !== true) return null;`.
4. **One helper,** in `packages/box-bounty/collect.ts`: `alreadyOnBranch(root, record, commit): boolean`.
   - the branch is `record.resume?.kind === 'recorded' ? record.resume.branch : null`; if it is null or `(detached HEAD)`, return false;
   - run `gitOutcome(root, ['merge-base', '--is-ancestor', commit, `refs/heads/${branch}`])`; return `status === 0`. Any other status (not an ancestor, or the commit is not in this clone) is false.
5. **Set it where an entry is first made.** There are three places in `collect.ts`; in each, call the helper only when the entry is new, never for one already recorded (the call costs one Git start):
   - near line 52 (the unchanged-listing path): the object pushed into `seenPullRequests`;
   - near lines 75 to 78 (the full listing): the `fact` object, which goes into both `available` and `seenPullRequests`;
   - near line 276 (a pull request collected by number): the object pushed into `seenPullRequests`.
   For an entry that already exists in `seenPullRequests` or `availablePullRequests`, carry its stored `onBranch` over unchanged: the answer is fixed at first sight and never recomputed.
   `json.ts` line 332 and `render.ts` line 507 copy entries from `availablePullRequests` into `seenPullRequests`; because step 5 put the field on the available entry, the copy carries it. Confirm with a test (row 7).
6. **Use it.** In `merged.ts` `candidatesOf`: first build `const onBranchAtFirstSight = new Set((record.github?.seenPullRequests ?? []).filter(pr => pr.onBranch === true).map(pr => pr.commit));` and skip any commit in that set, in **both** loops (attempts and pull requests). An attempt collected from such a pull request is skipped too.
7. **Say it as a fact.** Where `status` lists a seen pull request (`render.ts` near line 474), an entry with `onBranch` prints, in place of "seen and not decided": `pull request #N: its commit was already on <branch> when first seen here; it adds nothing and is not counted as a merge`. No verdict about the author. Under `--json` the same entry gains `onBranch: true` (`json.ts` near line 109).
8. **The case this can lose.** A solver's pull request that the owner merged into the creating branch by hand **before any bounty command on this machine listed it** is, at first sight, already on the branch, and is now not recognised. Decide in the plan between:
   - **(recommended) say so and offer the step:** the fact line above, followed by `next: if this is the merged solution, close the bounty: <the close command>`; and one clause in CONTRACTS.md stating the limit;
   - or ask GitHub whether that pull request is merged. Read first, on the sandbox, what GitHub's `pulls/<n>` says for a pull request whose base is the bounty branch and whose head was merged into another branch: if `merged` is false there, this route cannot work, and say so.
   Test whichever is chosen (row 6).
9. **Every reader, by search.** Run `grep -n seenPullRequests packages/box-bounty packages/box-cli/src` and list each hit in the Result as: writes an entry, reads `at`/`author`/`payTo`, or treats as a candidate. On 10 November only `merged.ts` line 106 treats one as a candidate.
10. **CONTRACTS.md:** the merged-recognition guarantee gains the rule and its limit. **Verify and merge.**

## Plan

Agreed in plan mode on 11 November 2026 (started 12:53 UTC; bug-fix playbook; principles to read before citing: fix-root-causes, sequence-verifiable-units).

- **Field:** `onBranch?: true` on both entry types (`gh.ts`), validated in `record.ts`; only `true` or absent, so old records need no conversion.
- **One helper** `alreadyOnBranch` in `collect.ts` (`merge-base --is-ancestor <commit> refs/heads/<branch>`; anything but status 0 is false) and one `firstSightFlag`: an entry already recorded keeps its stored flag, a new one is computed once. Used at the construction sites in `collect.ts` (lines about 49, 52, 75 to 80, 276); the copies in `json.ts` and `render.ts` spread whole entries and carry it.
- **Use:** `merged.ts` `candidatesOf` skips the commits of flagged entries in both loops.
- **Fact:** the listing line and the seen-only line say `already on <branch> when first seen here; it adds nothing and is not counted as a merge; if this is the merged solution, close the bounty: <the close command>`; `--json` gains `onBranch: true` only when set.
- **The case this loses (decided):** a pull request the owner hand-merged before any command listed it is not recognised; the tool says so and offers the close; CONTRACTS.md states the limit. GitHub's merged fact cannot carry it (head merged into main, base the bounty branch: `merged: false`).
- **A second limit, found while planning:** per machine and per first sight; a commit the owner makes on another machine and that reaches this branch only by a later `git pull` is not on the branch at first sight here, so such a head is still recognised when pulled. Only authorship could tell it from a solver's head landing by hand, which the brief rules out.
- Order: tests first (row 1 red on master), then the field, helper and `merged.ts`, then the fact line and `--json`, the reader search, the two-machine check, CONTRACTS.md, the hosted run, Result.
