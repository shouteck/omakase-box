# BT95: recognising a merge costs what the bounty added, not the whole history, and a merge on the wrong branch is named

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT95` · Timebox: 150 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: none
Horizon: short. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of `merged.ts` with the owner ("yes").

**Why.** `noticeMergedSolutions` (`packages/box-bounty/merged.ts`) runs first in every command that reads a record, once per process, and in the hook at every prompt. For each open bounty, it asks Git whether a known solution commit has reached the branch the bounty was created on. The check is careful:
- ancestry only;
- new work on top of the posted base only (BT44);
- squash and rebase merges through GitHub's `merge_commit_sha`, with the repository, branch and head checked (BT51);
- the first merged wins.

Two faults:
1. **It walks the branch's whole history.** `checkOne` runs `git rev-list --parents refs/heads/<branch>`, every commit back to the repository's first, once per open bounty per command. `closeOne` runs `git rev-list --first-parent refs/heads/<branch>` the same way when something lands. Every candidate must descend from the bounty's base anyway, so everything older is read and thrown away. In a repository with hundreds of thousands of commits, that is seconds and megabytes on each command and each prompt.
2. **A merge onto another branch is silent.** A solution merged into `main` when the bounty was created on `feature-x` is "simply absent from the set and is never mentioned" (the code's own comment). The bounty stays open, no decision comment goes out, and no pay message is given. Only a branch that is gone is named today.

## Outcome

1. **The walk stops at the base.**
   - When the record names a base (the publication's commit for a history post, else `baseCommitOf`), `checkOne` reads `rev-list --parents <base>..refs/heads/<branch>`, and the base is added to the parent map as the boundary.
   - `closeOne`'s first-parent chain reads `<base>..refs/heads/<branch>` plus the base.
   - `checkRewritten`'s tip-to-base checks run on the same map.
   - A record with no base keeps today's full read, said in a comment as the one case left.
   - Every decision is unchanged: the same candidates qualify, the same one wins, and the same landing commit is named.
2. **A solution found on another branch is named, never acted on.**
   - In `status` (the overview and `status <id>`), when an open bounty has candidates and none has landed on its creation branch, one `git for-each-ref --format=%(refname:short) refs/heads --contains <commit>…` (one Git start per such bounty) finds the local branches holding any candidate.
   - A hit prints one fact: "`<id>` — solution `<n>` is on `<other>`, not on `<branch>`, the branch this bounty was created on; it is not counted as landed. To close the bounty, merge it into `<branch>`, or omakase-box close `<id>`".
   - The other commands do not run this read, so their cost does not grow.
   - The bounty is never closed from another branch: guessing the branch could close bounties wrongly.

## Traps

- **`reachesThrough` stops when it meets `older`.** With the base as a boundary entry with no parents, every walk from a candidate still meets it. Check the BT44 tests catch an off-by-one at the boundary.
- **A history post's base is the publication's commit,** not the record's snapshot base. Use the same choice `checkOne` uses today.
- **`--contains` with several commits lists branches holding any of them.** Find which candidate is where with the parent map already read, not extra Git starts.
