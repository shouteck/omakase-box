# BT82 (prototype): one door out, one door in

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT82` (the record only; each attempt on its own throwaway branch) · Timebox: 300 minutes (two attempts and a comparison; no hosted acceptance run is needed for throwaway code); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: long: a design with no precedent here (KITCHEN.md, "Design decisions with no precedent"); starts with `/plan`. Prototype playbook; principles: boundary-discipline, type-system-discipline, redesign-from-first-principles, subtract-before-you-add, prove-it-works.

**Brief.** Written by the CTO on 23 November 2026 after the walkthrough of the owner's whole journey (create, post, status, look, apply, close). The owner asked for it ("Yes, brief it").

**Why.** Data leaves the machine in about 18 places across 6 files:
- **Git pushes:** `post.ts`, `close.ts` (4), `take.ts`;
- **GitHub writes** through `api(...)` with a body or a method: issues, comments, labels, issue edits, forks, in `post.ts`, `close.ts`, `gh.ts`, `take.ts`;
- **The shared-memory push** in `chain.ts`;
- **The board send** in `board.ts`.

Each place carries its own guards: never-ship, the secret scan, the owner's authority. Only `post`'s push goes through the shared last check (`checkOutbound`, `publish-sink.ts`, BT69).

Four of the faults found on 23 November are one fault, **a path that guards itself and forgot something**:
- [BT73](BT73.md): no proof over all exits;
- [BT80](BT80.md): `apply` uses the never-ship rules from collection time;
- [BT81](BT81.md): the close reason reaches GitHub unscanned;
- BT69 before them: `post` needed a check at the actual push.

The kitchen's history says per-site guarding does not settle: BT43 found one more site on each of five passes; BT22's list from memory missed a caller.

The established answer is **complete mediation** (Saltzer and Schroeder; a reference monitor): one checkpoint every exit passes, which cannot be skipped. For this tool that means:
- **One door out:** the only code allowed to write outward. At the moment of sending, under the rules in force then, it applies never-ship to what is actually sent, the secret scan to every text that leaves, and a check that the owner's authority was granted.
- **One door in:** solver content enters only through collection and is checked again at the merge.

This is a design question with two plausible shapes. By the kitchen's rule it is tried as throwaway code first, then the real brief is written from the winner.

## Outcome

This wave ships no product code. It leaves three things on master:

1. **The exit inventory,** mechanical: `tests/box/bounty/exit-sites.ts`, a parser walk like `refusal-sites.ts`. It lists every call in `packages/box-bounty` and `packages/box-cli/src` that can send outward (`remoteGit` with `push`, `gitOutcome` with `push`, `api` with a body or a method other than GET, `fetch` with a body, `gh` subprocesses that write). It has a test asserting the count, so it cannot pass by finding nothing. It lands as a test of the current code: the list is the truth, whatever the design.
2. **The comparison,** a notes file beside this brief, named BT82-notes: the two attempts below, each on the same two exits, each measured against the same checks (table below), with the winner and why.
3. **The real brief,** the next brief, BT83, written from the winner: steps, a tests-first table, the order in which the 18 exits move behind the door, and which of BT73, BT79, BT80 and BT81 it absorbs, shrinks or leaves as they are. It awaits the owner's go.

## The two attempts

Both use the same two exits, the ones with known gaps: `post`'s issue creation (`post.ts`) and `close`'s decision comments (`close.ts`, `syncGitHubDecision`). Each goes on its own throwaway branch, `proto/BT82-a` and `proto/BT82-b`.

- **A: a door module with a permission value.**
  - `outbound.ts` exports the only functions that write outward: `pushRef`, `createIssue`, `comment`, `editIssue` and so on.
  - Each takes a `Granted` value that only the owner check (`gate.ts`) can construct (a branded type; no other module can make one), plus the bytes or text to send.
  - Each runs never-ship and the scan itself, under the rules read at that moment.
  - The low-level `api` and `remoteGit` write paths are no longer exported.
- **B: one plan, one executor.**
  - Commands no longer write; they return a list of intended effects: `{ kind: 'comment', issue, body }`, `{ kind: 'push', ref, commit }`.
  - One executor checks the whole list (authority, never-ship, scan) and then performs it in order, recording progress for retries.
  - This is closer to `terraform plan` then `apply`, and makes "a refused command changes nothing" true by construction.
