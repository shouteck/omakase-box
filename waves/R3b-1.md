# R3b-1: screen recently fixed issues on a public project into replayable cases

Milestone: R (R3b, wave 1 of 2) · Station: evidence (also packaging) · Base: `8d099d6` · Branch: `wave/R3b-1` · Timebox: 120 minutes; at expiry, report partial findings and stop

## Outcome

A shortlist of replayable cases from one well-known public project: for each, the commit just before a fix, the fix itself, and the maintainers' own test from that fix, with recorded evidence that the test fails on the code before the fix for the right reason and passes after it, and that the neighbouring tests pass on both. Plus the screening counts: how many fixed issues were looked at and why each was kept or dropped.

No Box is made in this wave. Wave 2 takes one or two of these cases through the product. This wave exists so that wave 2 starts from cases known to be solvable, which R3 did not have.

## Safety, which does not bend

- **Nothing goes to the other project.** No issue, comment, pull request, star, fork, message or push. Read-only queries and a clone only.
- **Their code never runs on this machine directly.** Cloning, installing, building and testing all happen inside containers. The host only runs `git`/`gh` read-only queries and `docker` control commands.
- **Containers:** start from the pinned Node image already on this machine (`node:24.11.0-bookworm-slim@sha256:76d0ed0e...`, see R3's Dockerfile). No piping a download into a shell. Run as a non-root user where the image allows, with a memory limit, no host credentials, no Docker socket, no privileged mode, and no mount of this repository or the user's home. Use named volumes or a dedicated scratch folder under the system temp folder named `kitchen-r3b-...`.
- **Network:** on only for the clone and for dependency installation. Every test run uses `--network none`.
- **Installs:** install scripts disabled on every install (`--ignore-scripts` or the tool's equivalent), from the project's committed lockfile, unchanged.
- **Everything created is named `kitchen-r3b-...`** (containers, volumes, images, folders) and removed at the end. Record what was created.

## Screening

1. With `gh` read-only, list the most recent merged pull requests that fix a bug (closing an issue or labelled as a fix) and change both source and test files. Take the first **eight** in order, most recent first. Record the query, the time, and the raw list. Do not skip any; a dropped candidate is recorded with its reason.
2. For each, record: the issue and its text (kept verbatim, with its URL), the pull request, the commit just before the fix (base), the fix commit, the test files the fix added or changed, and the source files it changed.
3. In a container, for each candidate:
   - at the base, with only the fix's test files copied in: run those tests. Record the exit code and the failing output.
   - at the fix: run the same tests. Record the exit code.
   - at the base, unchanged: run the test files that sit beside the changed source and were not touched by the fix (the guards). Record the exit code.
4. A candidate **qualifies** when: the fix's test fails at the base with an assertion about the behaviour (not a load error, missing export or syntax error), passes at the fix, and the guards pass at the base. Read each failure and say in one line why it is or is not the right reason. A candidate whose fix landed after June 2026 is preferred for wave 2, because a solver is less likely to have seen it; record each fix date.
5. Take exit codes from the process, never from printed text. Use the recorder if it fits.
