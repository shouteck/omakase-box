# BT91: the tool is found where each agent actually looks, whichever channel brought it

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT91` · Timebox: 360 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: medium. Bug fix and feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of `setup`. The owner: making the tool always present where agents reach for it has many references to learn from, "so we cannot mess this up" ("yes").

**Why.** The shape is the established one. Playwright recommends it for coding agents: a CLI on the machine, plus a skill that loads on demand, with MCP kept for special cases. Ours has every layer:
- the CLI (`npm i -g`);
- a skill in the Agent Skills format (`SKILL.md`, an open standard now at the Agentic AI Foundation);
- an optional block in the project's instruction files (AGENTS.md and its siblings, BT41);
- the board's read-only `/mcp`.

Four things are wrong or behind:

1. **The skill lands in folders some agents do not read.** `SKILL_TARGETS` (`packages/box-bounty/instructions.ts`) writes `~/.claude/skills/` for Claude Code, and `~/.agents/skills/` for "Codex, Cursor and Gemini CLI". The table kept by the standard installer, Vercel's `skills` CLI (`docs/agents.md` in `vercel-labs/skills`, read on 24 November 2026), gives these global folders:

   | Agent | Global folder there | Ours |
   |---|---|---|
   | Claude Code | `~/.claude/skills/` | ✅ |
   | Codex | `~/.agents/skills/` | ✅ |
   | Cursor | `~/.cursor/skills/` | ❌ |
   | Gemini CLI | `~/.gemini/skills/` | ❌ |
   | GitHub Copilot | `~/.copilot/skills/` | missing |
   | OpenCode | `~/.config/opencode/skills/` | missing |
   | Windsurf | `~/.codeium/windsurf/skills/` | missing |

   So `setup` can tell a Cursor or Gemini user "your next agent session finds the tool" when it may not.
2. **Nothing travels with the repository.** The skill is written only under the home folder. A cloud agent starts from a fresh clone with an empty home and never sees it. The standard installer installs into the project (`.agents/skills/`) by default, and globally only with `-g`.
3. **The folder table is written by hand,** and it has drifted already.
4. **A skill can outlive the tool that wrote it.** The skill carries `version: "0.4.3"` and is refreshed only when `setup` runs again. Nothing compares it with the running tool, so after an upgrade agents may read old instructions.

**And the other channels** (added 24 November 2026, owner: "yes"). Agents do not only arrive through `setup`. The channels drafted in `docs/box-v4/launch/listings/` each deliver one piece:

| Channel | What arrives |
|---|---|
| npm and `omakase-box setup` | the CLI and the skill |
| skills.sh (`npx skills add`), the Claude Code plugin marketplace, ClawHub | the skill only; the skill says to install the CLI when needed |
| the Official MCP Registry, Glama, Smithery, PulseMCP, mcp.so | read-only discovery from the board |
| Monid | a read-only connector to the board's JSON (LAUNCH.md: optional, no posting) |

The channel files already come from one source, and their versions are kept equal: `scripts/launch-skill.mjs --check` for the published skill, `scripts/check-release-versions.mjs` for the plugin, registry and npm versions, all 0.4.3 today. Three gaps remain:

5. **Two installers fight over one folder.** The published skill carries our marker ("written by omakase-box setup"), so `setup` treats a copy installed by skills.sh or the plugin marketplace as its own. It overwrites that copy, where the skills installer keeps a lock file with a fingerprint of each skill, and `setup --remove` deletes it. An agent can also end up with two copies at different versions, one from the plugin and one from `setup`.
6. **An agent arriving through MCP or Monid is never pointed to the tool.** The board's `how_to_answer` (`packages/box-platform/src/feed.ts`) gives only the manual Git steps. `omakase-box take`, which gives the safe workspace and the draft others can see, is in the issue body but not on the board.
7. **No single list says what each channel delivers,** or how an agent arriving there reaches the next step.

**How established tools handle "installed several ways"** (researched 24 November 2026 on the owner's request; the owner said "yes" to following them):
- **`claude doctor`** finds every installation, warns "Multiple installations found", and its docs say to keep one. The lesson from its own bugs: a saved install method went stale after a migration and misreported, so check the real files and trust a record only while it matches them. ([troubleshoot install](https://code.claude.com/docs/en/troubleshoot-install); [issue 27910](https://claudeissues.com/issue/27910-doctor-installmethod-stuck-on-local-after-migrating-to-native-install-causes-rec))
- **Homebrew** writes an install receipt beside what it installed: how, when, which version. ([Formula Cookbook](https://docs.brew.sh/Formula-Cookbook))
- **The skills CLI** keeps lock files with a fingerprint of each skill folder: `./skills-lock.json` in a project, `~/.agents/.skill-lock.json` globally. ([lock files](https://www.mintlify.com/vercel-labs/skills/advanced/lock-files))
- **update-notifier** names the upgrade command for the install it detects, and gets pnpm wrong. Name the command for the channel found, or say "upgrade it the way you installed it", never a guess. ([update-notifier](https://Www.github.com/yeoman/update-notifier))
- **`brew doctor`, `flutter doctor`, `claude doctor`** each give one report of what is installed, where, and one fix per problem.

## Outcome

1. **Every agent's folder is right, and checked against that vendor's own documentation.**
   - The table moves to a pinned data file, `packages/box-bounty/skill-targets.json`, giving for each agent: its name, the folder whose presence means it is installed, its global skills folder, its project skills folder, and the source address with the date read.
   - A row is changed only where the vendor's own docs confirm it.
   - Where the vendor's docs and the installer's table disagree, the vendor's docs win, and the Result says which rows differed.
   - Copilot, OpenCode and Windsurf are added when their docs confirm a folder.
2. **`setup --project`**, the owner's choice (off by default, like the instruction block), writes the same skill into the repository's project skills folders: `.agents/skills/omakase-box/` and `.claude/skills/omakase-box/`, plus any other folder the table names. A fresh clone and a cloud agent then find the tool.
   - It says, before writing, that these files land in the repository and are public on a public repository, and that the owner commits them.
   - It uses the project path walk that already guards the instruction block (`walkProjectPath`: no links, junctions or paths that leave the root).
   - `setup --project --remove` takes away only files carrying our marker.
3. **The table is held to the standard.** `node scripts/skill-targets.mjs --check` fetches the installer's published table and lists every difference from ours, as BT78's `gitleaks-rules.mjs --check` does for the scan rules.
   - It runs before each release, by hand, named in the release steps.
   - It is never part of the ordinary suite, which stays offline.
4. **A stale skill is named once.** When the installed skill's `version` (home or project) is older than the running tool, bare `omakase-box` and `describe` say once: "the omakase-box skill at `<path>` is from `<old>`; this is `<new>`; run omakase-box setup (or setup --project) to refresh it". Once per version, recorded like the tool's other once-only lines (`saidOnce`).
5. **Receipts, checked against the files.**
   - Every file `setup` writes is recorded in the tool's own state (`state.json`, which carries no authority, BT22): path, fingerprint (SHA-256 of the bytes), version, time.
   - A copy is `setup`'s to refresh or remove only while a receipt names it **and** its bytes still match the fingerprint.
   - A receipted file that has changed is no longer ours, and `setup` says so rather than overwriting it.
   - Copies written before receipts existed (byte-for-byte our text, in a folder `setup` used to write) are adopted once, with a receipt, and the Result lists the rule.
6. **One copy per agent, whatever channel installed it.**
   - `setup` recognizes a skill put there by another channel: a skills-installer lock entry, a plugin's skill folder, or a copy whose content is not byte-for-byte ours. It leaves that copy alone, says where it is and which channel it seems to come from, and writes no second one for that agent.
   - A skill named in either skills-CLI lock file, or sitting inside a plugin's folder, is that manager's, and is never changed or removed.
   - `setup --remove` removes only receipted copies whose bytes still match (Outcome 5), not anything recognized by the marker alone.
   - The stale-version line (Outcome 4) reads every copy it finds, from any channel.
   - The marker's words become neutral ("the omakase-box skill; omakase-box setup can refresh or remove copies it wrote"), so a copy from another channel does not claim `setup` wrote it. `launch-skill.mjs` regenerates the published copy.
7. **Copies of the CLI itself.**
   - Bare `omakase-box` notices, once per set of copies, when more than one `omakase-box` is on the PATH or in npm's, pnpm's or bun's global folders, or when an npx cache copy is the one running.
   - It says which copy is running and its version, which to keep (the first on the PATH, unless it is an npx cache), and the remove command for each copy, from the channel detected by its folder: `npm uninstall -g`, `pnpm remove -g`, `bun remove -g`. When the channel is unknown it says "remove it the way you installed it", never a guessed command.
8. **One report: `omakase-box setup --check`,** like `claude doctor`. It is an option of `setup`, not a new command (the owner's rule), and it writes nothing. It lists:
   - every CLI copy: path, version, channel;
   - every skill copy: path, version, and whose it is (ours with a receipt, another manager's by lock or plugin folder, or unknown);
   - for each problem, one fix.

   `--json` gives the same as a document.
9. **The board's answer leads with the tool.** `how_to_answer` starts with "With the tool: `npm i -g omakase-box`, then `omakase-box take <id>`, which prepares a safe workspace and opens the draft others see." The manual steps follow as the way without it. The feed schema and `llms.txt` say the same, and the fields keep their names: old readers and the Monid connector keep working, as PF56's old-tool test checks.
10. **`docs/box-v4/CHANNELS.md` lists every channel:** what it delivers, where it lands, where its version comes from, and how an agent arriving there reaches the next step. A test reads it and fails when:
   - a channel file under `docs/box-v4/launch/` (skill repository, `.claude-plugin/`, `server.json`) has no row;
   - a row lacks its next step.
11. **`setup` says only what is true.** For each agent it found, it names the exact folder it wrote. "Your next agent session finds the tool" is printed only for agents whose folder is confirmed in the table. An agent found but not confirmed gets "written to `<path>`; not confirmed that `<agent>` reads it".

## Traps

- **Do not trust a saved record over the files** (Claude Code's own bug): a receipt counts only while the fingerprint matches.
- **Detecting a CLI copy reads folders and runs nothing:** no `npm ls -g`, no other copy's binary. Read `package.json` files under the known global folders.
- **Another channel's copy is not ours,** even when its text is ours: it may be tracked by that channel's own lock or update. Only what `setup` recorded writing is `setup`'s to change or remove.
- **The board change is data only:** no page's look changes here.
- **Do not run another package's installer at setup.** It would run a third party's code on the owner's machine. The table is ours, checked against theirs.
- **The project skill is committed by the owner, not by the tool.** `setup --project` writes the files and says so; it never commits or pushes.
- **Removing must cover where earlier versions wrote,** or old copies stay behind and go stale.
- **Agents' folders change.** That is why the table carries its sources and dates, and why the check script exists.
