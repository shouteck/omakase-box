# BT91: the tool is found where each agent actually looks, at home and in the repository

Milestone: BT (the bounty tool) · Station: packaging · Base: `master at dispatch` · Branch: `wave/BT91` · Timebox: 240 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: medium. Bug fix and feature playbook; principles: prove-it-works, encode-lessons-in-structure.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of `setup`. The owner: making the tool always present where agents reach for it has many references to learn from, "so we cannot mess this up" ("yes").

**Why.** The shape is the established one. Playwright recommends it for coding agents: a CLI on the machine, plus a skill that loads on demand, with MCP kept for special cases. Ours has every layer:
- the CLI (`npm i -g`);
- a skill in the Agent Skills format (`SKILL.md`, an open standard now at the Agentic AI Foundation);
- an optional block in the project's instruction files (AGENTS.md and its siblings, BT41);
- the board's read-only `/mcp`.

Four things are wrong or behind:

1. **The skill lands in folders some agents do not read.** `SKILL_TARGETS` (`packages/box-bounty/instructions.ts`) writes `~/.claude/skills/` for Claude Code, and `~/.agents/skills/` for "Codex, Cursor and Gemini CLI". The table kept by the standard installer, Vercel's `skills` CLI (`docs/agents.md` in `vercel-labs/skills`, read on 24 November 2026), gives these global folders:

   | Agent | Global folder there | Ours |
   |---|---|---|
   | Claude Code | `~/.claude/skills/` | ✅ |
   | Codex | `~/.agents/skills/` | ✅ |
   | Cursor | `~/.cursor/skills/` | ❌ |
   | Gemini CLI | `~/.gemini/skills/` | ❌ |
   | GitHub Copilot | `~/.copilot/skills/` | missing |
   | OpenCode | `~/.config/opencode/skills/` | missing |
   | Windsurf | `~/.codeium/windsurf/skills/` | missing |

   So `setup` can tell a Cursor or Gemini user "your next agent session finds the tool" when it may not.
2. **Nothing travels with the repository.** The skill is written only under the home folder. A cloud agent starts from a fresh clone with an empty home and never sees it. The standard installer installs into the project (`.agents/skills/`) by default, and globally only with `-g`.
3. **The folder table is written by hand,** and it has drifted already.
4. **A skill can outlive the tool that wrote it.** The skill carries `version: "0.4.3"` and is refreshed only when `setup` runs again. Nothing compares it with the running tool, so after an upgrade agents may read old instructions.

## Outcome

1. **Every agent's folder is right, and checked against that vendor's own documentation.**
   - The table moves to a pinned data file, `packages/box-bounty/skill-targets.json`, giving for each agent: its name, the folder whose presence means it is installed, its global skills folder, its project skills folder, and the source address with the date read.
   - A row is changed only where the vendor's own docs confirm it.
   - Where the vendor's docs and the installer's table disagree, the vendor's docs win, and the Result says which rows differed.
   - Copilot, OpenCode and Windsurf are added when their docs confirm a folder.
2. **`setup --project`**, the owner's choice (off by default, like the instruction block), writes the same skill into the repository's project skills folders: `.agents/skills/omakase-box/` and `.claude/skills/omakase-box/`, plus any other folder the table names. A fresh clone and a cloud agent then find the tool.
   - It says, before writing, that these files land in the repository and are public on a public repository, and that the owner commits them.
   - It uses the project path walk that already guards the instruction block (`walkProjectPath`: no links, junctions or paths that leave the root).
   - `setup --project --remove` takes away only files carrying our marker.
3. **The table is held to the standard.** `node scripts/skill-targets.mjs --check` fetches the installer's published table and lists every difference from ours, as BT78's `gitleaks-rules.mjs --check` does for the scan rules.
   - It runs before each release, by hand, named in the release steps.
   - It is never part of the ordinary suite, which stays offline.
4. **A stale skill is named once.** When the installed skill's `version` (home or project) is older than the running tool, bare `omakase-box` and `describe` say once: "the omakase-box skill at `<path>` is from `<old>`; this is `<new>`; run omakase-box setup (or setup --project) to refresh it". Once per version, recorded like the tool's other once-only lines (`saidOnce`).
5. **`setup` says only what is true.** For each agent it found, it names the exact folder it wrote. "Your next agent session finds the tool" is printed only for agents whose folder is confirmed in the table. An agent found but not confirmed gets "written to `<path>`; not confirmed that `<agent>` reads it".

## Scope

- Write: `packages/box-bounty/skill-targets.json` (new), `packages/box-bounty/instructions.ts` (`SKILL_TARGETS` reads it), `packages/box-bounty/setup.ts` (`--project`, the true lines, `SETUP_USAGE`), `packages/box-bounty/wording.ts` (the skill's `version` follows the package version; the stale line), `packages/box-bounty/render.ts` or `tell.ts` (where the once-only line is shown), `packages/box-bounty/args.ts` (`setup --project`), `scripts/skill-targets.mjs` (new), `docs/box-v4/BOUNTY.md` (`setup`), FIRST-FIVE-MINUTES.md (if it names setup's folders), `docs/box-v4/launch/getting-started.md`, the release steps (wherever the kitchen keeps them), `tests/box/bounty/bt91.test.ts` (new), `tests/box/bounty/SURFACE.txt` (by `surface.mjs --write`)
- Read for context: `tests/box/bounty/pf16.test.ts`, `bt65.test.ts`, `bt63.test.ts`, `pf6.test.ts` (the skill text kept identical with the published copy), `waves/BT41.md` (instructions stay off unless the owner turns them on), `waves/BT78.md` (the pinned-and-checked pattern), the vendors' own skill documentation for each row
- Do not touch: the skill's words (PF57 and BT89 change them); the instruction block; the npm install step; nothing from another package is run at setup (no `npx skills`)

  - **Folders:** a home holding `.cursor` gets the skill in Cursor's confirmed folder, and likewise `.gemini`; neither in `~/.agents/skills/` unless the table says so.
  - **`setup --project`** writes the project folders, says first that they are public on a public repository, and refuses through a linked folder (the path walk). `--project --remove` leaves a folder without our marker alone.
  - **The true line:** an agent found but not confirmed is told "not confirmed", never "finds the tool".
  - **Stale:** a skill of an older version makes bare `omakase-box` say the line once; a second run does not; a newer tool version says it again.
  - **Old installs:** a skill written by the old `~/.agents/skills/` rule for Cursor is still removed by `setup --remove`.
- `scripts/skill-targets.mjs --check` run once in the Result, its differences listed (or "none").
- `node scripts/surface.mjs --write`: the Result shows the diff (`setup --project`).

## Traps

- **Do not run another package's installer at setup.** It would run a third party's code on the owner's machine. The table is ours, checked against theirs.
- **The project skill is committed by the owner, not by the tool.** `setup --project` writes the files and says so; it never commits or pushes.
- **Removing must cover where earlier versions wrote,** or old copies stay behind and go stale.
- **Agents' folders change.** That is why the table carries its sources and dates, and why the check script exists.
