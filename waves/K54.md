# K54: a linter that fails the run on rules that find faults

Milestone: K (kitchen) · Station: evidence · Base: `master at dispatch` · Branch: `wave/K54` · Timebox: 180 minutes; at expiry, report partial findings and stop
Owner decisions: D-2026-11-10-k49-answers
Horizon: short

**Brief.** Written by the CTO on 10 November 2026 from [K53](K53.md). The repository has no linter and no formatter. The compiler is strict and catches types. Nothing catches:

- **a promise nobody waited for.** In the Worker an unawaited database write or outside call is dropped without a trace when the request ends; the tool is synchronous, so the risk is the board's;
- an export or a variable nothing uses;
- a `switch` over a set of states that misses one;
- a comparison or a condition that can never be true.

## Outcome

One lint step in verify and in the hosted run that fails on a short, stated list of fault-finding rules, over `packages/`, `tests/` and `scripts/`. It changes no formatting and no behaviour. Every finding on today's code is fixed, or listed with the reason it is not a fault.

## Scope

- Write: one linter configuration at the root, `package.json` (a `lint` script and the development dependency), `pnpm-lock.yaml`, `scripts/workspace.mjs` or `scripts/verify.mjs` only to run the step, `.github/workflows/verify.yml`, the source lines the findings require, `docs/box-v4/KITCHEN.md` (one line under Verification), `kitchen/reviews/K54-lint.md`
- Read for context: `tsconfig.json`, `scripts/verify.mjs` (how a step is declared and reused), `packages/box-platform/src/worker.ts` and `api.ts` (`defer` and `waitUntil`: the intended way to not wait), [K45](K45.md)
- Do not touch: formatting of any line (no formatter, no style rules, no import sorting); any test's expected outcome

## Done when

- Accepted as the rulebook then says ([K50](K50.md) if merged), with `test:box-bounty`, `test:platform` and `test:kitchen`.
- **The tool is chosen in the first step from what the rules need,** cited: the promise rule needs type information, so name a linter that has it, read its documentation on the day, and record its version and its run time on this tree. A development dependency only; it must respect the workspace's `minimumReleaseAge`.
- **The rule list is in the brief's Result, each with the fault it finds:** unawaited promises; a promise used where a value is expected; unused variables, imports and exports; a `switch` that does not cover its union; conditions the types say are constant; `await` of a non-promise. No rule about spacing, quotes, line length, naming or ordering. A rule that produces more than 25 findings none of which is a fault is dropped and named.
- **Each rule is shown to bite:** for each, one scratch change that breaks it and the step going red; then reverted.
- Every finding on master is listed in a notes file: fixed (with the commit), or kept with a one-line reason and a targeted suppression beside the line. A blanket suppression for a file or a folder is not allowed. A finding that is a real fault in behaviour gets a test that fails before its fix.
- The step's time is measured (three runs) and stated; if it adds more than a minute to the hosted run, say so and propose where it runs.
- The lint step is reused by verify like the others: a diff that touches no linted file does not rerun it.

## Steps, in order

Written so any model can cook it.

1. **Choose the tool, and prove it installs.** The promise rules need type information. The standard choice is ESLint with `typescript-eslint`'s type-aware rules; read both projects' current documentation on the day and cite the pages. Check the workspace's `minimumReleaseAge` (in `pnpm-workspace.yaml` or `.npmrc`) and pick the newest versions older than it. Add them as root `devDependencies` only, with `node scripts/pnpm.mjs add -D -w <packages>`. Record the versions.
2. **The configuration,** one file at the root, `eslint.config.mjs`. It turns on **only** these, each as an error, and nothing from any "recommended" or "stylistic" preset:

   | Rule | The fault it finds |
   |---|---|
   | `@typescript-eslint/no-floating-promises` | a promise nobody waited for |
   | `@typescript-eslint/no-misused-promises` | a promise used where a plain value is expected |
   | `@typescript-eslint/await-thenable` | `await` of something that is not a promise |
   | `@typescript-eslint/switch-exhaustiveness-check` | a `switch` over a set of states that misses one |
   | `@typescript-eslint/no-unnecessary-condition` | a condition the types say never changes |
   | `@typescript-eslint/no-unused-vars` (arguments starting `_` allowed) | a variable or import nothing uses |

   Files: `packages/**/*.ts`, `tests/**/*.ts`, `scripts/**/*.mjs` (the type-aware rules apply to the `.ts` files; give `.mjs` only `no-unused-vars`). Ignore `**/dist/**`, `**/out/**`, `**/node_modules/**`, `.runtime/**`, `docs/**`. Point the parser at the existing `tsconfig.json` (`projectService: true`); if a file is outside every tsconfig, list it, do not write a second tsconfig without saying so.
   Unused **exports** are not covered by these rules: say so in the Result and leave them (a separate tool would be a second unknown).
3. **First run, count only.** Add the script `"lint": "eslint ."` to the root `package.json`. Run it; write the count per rule into a notes file, `kitchen/reviews/K54-lint.md`. Time it three times.
4. **The noise rule.** A rule with more than 25 findings of which none, after reading a sample of ten, is a fault: turn it off, and name it in the notes with the sample. `no-unnecessary-condition` is the likely one. A rule is not dropped for being inconvenient when its findings are real.
5. **Fix or justify every remaining finding,** one rule at a time, a commit per rule:
   - a real fault in behaviour (most likely an unawaited write in `packages/box-platform/src/`): first a test that fails, then the fix;
   - an intentional not-waiting in the Worker: it must go through the existing `defer`/`waitUntil` helper in `worker.ts`/`api.ts`; if it does and the rule still fires, mark the line `void` with a one-line comment why;
   - anything kept: `// eslint-disable-next-line <rule> -- <reason>` on that line only. Never a file-wide or folder-wide disable.
   No line's formatting changes. If the linter's fix mode would reformat, do not use `--fix`.
6. **Each rule bites.** For each rule left on: one scratch edit that breaks it, the step red, the edit undone. Six lines in the notes.
7. **Into verify.** Read how `scripts/verify.mjs` declares a step and when it reuses a previous result; add `lint` as a step whose inputs are the linted files and the config, so a change to an unlinted file does not rerun it. Add `node scripts/pnpm.mjs run lint` to `.github/workflows/verify.yml` after the install step. If the step adds over a minute to the hosted run, say so and propose running it on Linux only.
8. **One line** in `docs/box-v4/KITCHEN.md` under Verification. **Verify and merge.**

## Traps

- Do not install Prettier, a formatter plugin, or any rule about spacing, quotes, naming or import order (the owner said "not now" to formatting on 10 November 2026).
- `tests/kitchen` holds tests that pin `package.json` scripts and the workflow file: read them before adding the script and the step; an added script is an addition, not a changed expectation, but a test that lists all scripts will need the new name, by this wave's own decision. Name it in the Result.
- The tool (`packages/box-bounty`) is synchronous by design; few promise findings are expected there. Do not make a synchronous function `async` to satisfy a rule.
- A finding that needs a design change to fix goes to BACKLOG with file and line; the code stays and the line gets a targeted disable naming the BACKLOG entry.

## Lenses

- [x] **Measurement fairness:** findings counted per rule, with how many were real faults, how many were noise, and how many were suppressed; nothing reported as "clean" that was suppressed.

## Notes

- Follows the TypeScript community's own convention: the compiler for types, a type-aware linter for the fault classes the compiler does not report.
- Formatting the tree is K53's discussion item 2 and is not part of this wave, so its diff stays small and reviewable.
- Do not stack unknowns: if a finding needs a design change to fix, list it in BACKLOG with its line and leave the code.
