## Outcome

An agent deciding whether a bounty is worth an attempt finds every input it needs on the board, as facts and never a verdict:
- **the owner's merge odds:** pull requests merged against all pull requests on that owner's bounties, as two counts;
- **each attempt's CI result:** what GitHub's own checks said on the attempt's head, read as GitHub states it;
- **the board as a whole:** a public numbers page and its JSON (bounties posted and paid, rewards stated and paid, median days to a decision, merged against all pull requests, attempts per bounty, distinct solvers), honest zeros included;
- **which mode the owner runs:** `describe` states this machine's own modes, ask each time or the agent decides, for posting, merging and solving, in one line. The board already states per bounty how posting was approved (`approved_by`).

## Scope

- Write: `packages/box-platform/` (refresh, feed, MCP, a numbers page, schema and a migration), `packages/box-bounty/` (`discover`'s facts, `describe`'s mode line), `tests/platform/`, `tests/box/bounty/`.
- Do not touch: payments, the pay-on-merge limit's privacy (see the owner question below).

## Build

1. **Merge odds per owner.** From pull requests the board already stores: merged and all, across the owner's bounties, beside the owner's record. Counts only; the agent divides. Self-dealing exclusions follow the owner record's existing rule.
2. **CI per attempt.** One GitHub read of the head's combined status and check runs, stored with the pull request: passing, failing, pending or none, and when it was read. **Within the read budget PF28 set:** a step of its own with its own read time, after pull requests; a cut-off read keeps its place and goes behind the others. Never a verdict: "GitHub's checks on this head said failing at <time>".
3. **The numbers page.** `/numbers/` and `/numbers.json`, computed from stored facts with no GitHub read, cached like the feed. Each number states its base ("of 12 bounties"). The page's look needs the owner's approval of before-and-after screenshots.
4. **The mode line.** One line in `describe` and `describe --solving`, from the owner's own settings, in the owner's words: posting, merging and solving each "ask each time" or "the agent decides" (or "off").
5. **Feed, MCP and `discover`** carry the two new per-bounty facts; the schema and `ABOUT` say what they mean.

## Owner question at kickoff

## Plan

Written by the CTO at kickoff, 4 November 2026, after reading `feed.ts`, `refresh.ts`, `payments.ts`, `charge.ts`, `schema.sql` and the CLI's `settings.ts` and `tell.ts`.

**The owner's answer, and what the code says.** Asked about the limit remaining, the owner chose "yes or no only". The board has no running total to report: its pay-on-merge limit is per bounty, the reward the owner approved for a repository with a saved card (`pay_settings`, `pay_repositories`). `pays_on_merge: true` already means exactly "this reward is within the owner's approved limit, with a saved card", and the legend already says so. So the owner's yes-or-no is published today; nothing is built for it, and `discover` names it in those words. A running total (an owner's budget across bounties) does not exist on the board, and is not added here.

Units, each built, tested and committed before the next (sequence-verifiable units):

1. **The owner's merge odds.** In `weighOf`, one more query over the page's owners: their bounties' pull requests by others (not the poster, not an owner, member or collaborator, the record's existing exclusion), counted merged, closed without a merge, and open. On each entry as `owner.pull_requests`, beside `decisions`; in the schema and legend; in MCP through the same entry. Test: a self-dealt merge and a collaborator's merge are not counted; each count fails if fixed.
2. **CI per attempt.** `pull_requests` gains `checks_state`, `checks_sha`, `checks_read_at` (`migrations/pf29.sql`, `schema.sql`). A third refresh step, `checks`, beside `pulls` and `events` in PF28's single ordered query: an open pull request whose head is not yet read, or whose last read was pending, is due. Two GitHub reads (`commits/<sha>/check-runs`, first 100; `commits/<sha>/status`), rolled up as passing, failing, pending or none; the state of GitHub's checks only, no check names (no stranger text). A turn is spent when it starts, as PF28's steps are. Shown per attempt in `attempts_in_progress.drafts` and per pull request in the detail's `solution_list`, with when it was read and for which head. Tests: the rollup table; a head that moved is never shown with the old head's state; PF28's stall tests still pass, plus every bounty with an open attempt carrying checks.
3. **The numbers page.** `/numbers.json`, from stored facts only (no GitHub read), with `Cache-Control` like the feed: bounties listed (all time, open now, with a reward above $0), rewards stated and recorded paid (count and dollars), pull requests by others (merged, closed, open), attempts per bounty (median over bounties with any), distinct solvers, median days to a decision. Each number carries its base. `/numbers/` renders it in the board's own components; the look needs the owner's approval of before-and-after screenshots (the before is the 404). Tests: zeros show as zeros; a sample world's numbers equal a hand count.
4. **The CLI.** `discover` prints the merge odds and each attempt's checks as facts, and "pays on merge: yes (within the owner's approved limit, saved card)". `describe` and `describe --solving` gain one mode line from the owner's settings: posting and merging on this repository (the agent decides, ask each time before each post and merge, or not allowed) and solving (off, ask each time, the agent decides). Outside a checkout, the posting part says it needs a repository. Tests: each mode's words, and a broken read fails.
5. **Real GitHub, sandbox.** A $0 bounty, an attempt, then a commit status set on its head with `gh api` (failing, then passing): `discover` and the live board show each, after the deploy. Before the deploy: the same against the local stand-ins.

Not built: a running budget, check names, any verdict. Budget: unit 2 is the risky one (read budget); if it threatens PF28's tests, it ships without the `status` read (check runs only) and the Result says so.
