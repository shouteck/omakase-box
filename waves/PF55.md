# PF55: the board keeps the reward bound at post, says when the issue changes it, and charges only when they agree

Milestone: platform · Station: packaging · Base: `master at dispatch` · Branch: `wave/PF55` · Timebox: 180 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-10-11-public-origin
Horizon: short to medium. Bug fix playbook; principles: fix-root-causes, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026 from the walkthrough of the board with the owner, who agreed with the finding ("I agree with your take and your recommendations"). It touches the live board's data and one page, so it carries a database migration (the owner deploys it, `packages/box-platform/DEPLOY.md`) and before-and-after screenshots for the owner's approval of the page change.

**Why.** The board takes a bounty's reward from the issue's **current** format block, on every read. `issueStatement` (`packages/box-platform/src/refresh.ts`) writes `amount = excluded.amount` each time, and no history is kept. Anyone who can edit the issue on GitHub, the poster or any collaborator, can change that number by hand after the bounty is listed:

- **A solver is misled.** A bounty listed at $100 can drop to $10 after work starts, or rise to $500 to attract solvers when the tool bound $100 (BT11a). The board shows the new figure as if it had always been so.
- **The charge follows the edited figure.** Pay on merge (`src/charge.ts`, `decide`) charges `row.amount` when it equals the owner's fixed per-repository amount (`card.limit`). If the owner approved $100 per bounty and posted one at $10, an edit to $100 makes a merge charge $100: within the owner's limit, but not what that bounty promised.
- **The true figure is already in reach.** The `posted` event on the shared memory carries `reward: { amount, currency }`, bound at post. The board reads that event (`readEvents`), but `projectEvent` keeps only a top-level `amount`, so the posted reward is dropped.

## Outcome

1. **The board keeps the posted reward.** `projectEvent` reads `reward.amount` from a `posted` event. A new column, `bounties.posted_amount`, holds it: set once, from the first valid posted event, and never overwritten. A migration, `packages/box-platform/migrations/pf55-*.sql`, adds it. A bounty without a chain, or listed from the board (PF32, PF44), has none: its approved amount is the fact there, as today.
2. **A change is stated, never hidden or judged.** When the issue's block says an amount other than `posted_amount`:
   - the bounty's detail (`/bounties/<id>.json`, MCP `get_bounty`) carries `reward.posted` and `reward.changed_at`, the first time the board saw the difference;
   - the bounty's page says, as a fact: "Posted at $X; the issue now says $Y (edited, first seen `<day>`)";
   - the feed's `reward.amount` stays the issue's figure (it is what the issue says), and the feed gains `reward.posted` when they differ.
3. **Pay on merge charges only when the issue's figure equals `posted_amount` (when present) and is at most the most the owner's card pays per bounty** ([PF59](PF59.md), D-2026-11-24-card-is-the-only-board-setting; before PF59 lands, the owner's per-repository approved amount, as today). Otherwise it settles a new state, `refused-reward-changed`, which waits for the owner like `refused-over-limit` does. The owner's own pay page names both figures, and the owner pays by hand if they choose.
4. **The tool's side needs nothing new:** `post` binds the reward and `close` keeps the block's bytes (BT11a). This wave makes the board honour that binding.

## Steps, in order

Written so any model can cook it.

1. **Tests first,** the list above, seen failing on master.
2. **The fact:**
   - `projectEvent` returns `reward` for `posted`;
   - `readEvents` sets `posted_amount` with `UPDATE bounties SET posted_amount = ? WHERE id = ? AND posted_amount IS NULL`;
   - add the column in `schema.sql` and the migration.
3. **The change seen:** in `issueStatement`, when `posted_amount` is set and the block's amount differs, record the first time in a column `amount_changed_at`, kept only while they differ.
4. **The charge:** add `posted` to `ChargeFacts`. In `decide`, before the limit check, `if (facts.posted !== null && facts.posted !== facts.amount) return settle('refused-reward-changed')`. Add the state's words.
5. **The page and the feed:** the words in Outcome 2; screenshots.
6. **Docs, DEPLOY's migration step;** verify, push, hosted run, Result. Merge after the owner approves the screenshots.

## Traps

- **"Never overwritten" is the whole point.** Any code path that sets `posted_amount` must be guarded on `IS NULL`.
- **Chain events can be written by anyone with push access** (the walkthrough of shared memory). The first valid posted event wins. A later one is ignored and logged, never trusted.
- **Free-tier CPU is 10 ms a run** (`src/worker.ts`). The new read is a field of an event the board already fetches. Add no GitHub read.
- **The live board's database is the owner's.** The migration is written and tested here; the owner applies it at deploy. Nothing in this wave touches the live database.
