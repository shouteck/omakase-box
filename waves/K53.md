### 1. The language and runtime: keep TypeScript on Node. (Reasoned, not prototyped.)

- **Speed is not the language's.** A command takes 0.2 to 0.5 s, of which Node's own start is 0.1 s and most of the rest is starting Git ([K49](K49.md)). A compiled language would save about a tenth of a second.
- **Distribution is where agents are.** Skills, MCP servers and `npx` are the channels the strategy depends on, and they are Node's. One bundled file of 607 KB with no dependency already installs like a binary.
- **The tool and the board share code** (the bounty format's reader, the payment words). One language keeps one definition.
- **A rewrite is the whole project:** about 15,800 lines of source and 19,500 of tests, for a tenth of a second.
- The compiler is set as strictly as it goes (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`); 41 escapes (`as unknown`, `any`) in about 19,600 lines of source.
- The one real runtime cost is the floor, Node 22.13, set by the built-in SQLite. That is the current long-term-support line and I would not lower it.

### 2. The tool's architecture: keep.

One process per command, synchronous, plain Git underneath, a local SQLite cache, the shared record in Git. It is simple to reason about and every failure is one named refusal. The contained fixes are already briefed (BT58 the ref name, BT59 the token). One small debt: the tool and the board import each other's files by relative path (`box-bounty` reads `box-platform/src/charge-words`, `methods`, `pay-ways`; the board reads `box-bounty/format`), and `box-bounty` has no manifest of its own. It works because the bundler follows paths; it means neither can be read, tested or published alone. Listed for discussion as a small pure move.

### 3. The board's architecture: one certain fault, one big question.

- **Certain: the pages that hold the facts are empty to a program.** Fetched without JavaScript, a bounty's page says only "Reading the board."; the board and the numbers page give their heading and nothing else. The front page, How it works and For agents are complete. The link every posted issue carries leads to the empty kind. For a product whose audience fetches pages and does not run scripts, that is the wrong way round. Briefed as PF39.
- **The big question:** the site is a full framework (Next, React, a static export, 1.2 MB of scripts) for a dozen pages whose data all arrives from the Worker anyway. Rendering the pages in the Worker itself would be smaller, faster and readable by anything. It is also a rebuild of a site the owner approved screen by screen. For discussion; PF39 fixes the fault inside the present design first.
- Workers, D1 and the reading loop: sound for today; the ceiling is PF36.

### 4. The tooling: one certain gap.

- **No linter and no formatter anywhere.** The compiler catches types; nothing catches a promise nobody waited for (a real fault class in the Worker, where an unawaited write is silently dropped when the request ends), an unused export, or a shadowed name. Briefed as K54, limited to rules that find faults.
- **Formatting is a discussion, not a brief:** 1,403 lines of the tool's source are over 120 characters, 406 over 200, and the longest line in the board is 787. A formatter would touch nearly every file once.
- The kitchen's own scripts (`verify`, `suite`, `kitchen-stats`, `brief-check`: 1,678 lines) are proportionate and tested. K50 and K51 cover the run itself.
- Releasing is by hand: the owner runs one command. Fine at this size; an idea for discussion below.

### 6. Big changes: for discussion, none briefed

1. **Rebuild the site without the framework,** rendered by the Worker. Right in principle for an agent audience; costs the approved screens being rebuilt and re-approved. Recommendation: not now. Do PF39; if it shows we are fighting the framework, bring this back with that evidence.
2. **A formatter over the whole tree.** One mechanical commit, no behaviour change, every later diff easier to read; the cost is one unreadable history line and a rebase for anything in flight. Recommendation: yes, as its own wave when nothing else is open, after K52.
3. **A shared package for what the tool and the board both use.** A pure move of three or four small files. Recommendation: yes, low priority.
4. **Publishing from the tag.** The release workflow already builds and tests the package on a tag; npm can be set to accept a publish from that workflow with no stored secret. The owner's act becomes pushing a tag. It needs a one-time setting in the owner's npm account. Recommendation: after the first hand publish has worked.
5. **A rewrite in another language:** no (section 1). Listed so the answer is on record.
