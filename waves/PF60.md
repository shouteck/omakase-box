# PF60: "paid" has one writer: the board, when one is set

Milestone: platform, with a tool part · Station: packaging · Base: `master at dispatch`, after [PF59](PF59.md) and [BT89](BT89.md) · Branch: `wave/PF60` · Timebox: 180 minutes (a hosted run takes about 25); at expiry, report partial findings and stop
Owner decisions: D-2026-11-24-board-is-the-paid-ledger, D-2026-11-24-one-fact-one-owner
Horizon: short to medium. Refactoring playbook; principles: subtract-before-you-add, prove-it-works.

**Brief.** Written by the CTO on 24 November 2026. The owner chose that "paid" has one writer, the board ("Board only (Recommended)").

**Why.** "Paid" is recorded in two places today:
- **in the tool:** `omakase-box config set paid <id>`, `recordPaid` in `packages/box-bounty/owner.ts`, which writes a `paid` event locally and on the shared memory (`sharePaid`, `chain.ts`);
- **on the board:** the bounty's page, signed in (`recordPaid` and `answerReceipt` in `packages/box-platform/src/account.ts`), beside the charges, the one-click payments, the receipts and the solver's "received" or "not received".

The board reads the tool's chain event (`readEvents`), but the tool learns of a board record only through the board's public facts. Two writers for one fact break the rule the owner set (D-2026-11-24-one-fact-one-owner): they can disagree, and each side's "owed" can be wrong. The board already holds every other money fact, so it is the ledger.

## Outcome

1. **With a board set, `config set paid <id>` writes nothing.** It answers with the one place to record it, and is not a refusal:
   > `<id>`: record the payment on the bounty's page, signed in to GitHub: `<board>/b/<id>/`. The board keeps the money record, beside any charge and the solver's confirmation. Nothing was written here.

   `config set paid <id> --withdraw` (or the spelling BT89 settles on) answers the same.
2. **With the board turned off** (`config set board ''`), `config set paid` works exactly as today, and the tool's record is the only one. One owner per setup.
3. **The tool's "owed" and "paid" read the board when one is set.** `status`, the overview, `describe` and the pay message take a bounty's paid state from the board's public fact (`readBountyFact`: `recorded`, `confirmed`, `says-not-received`, and charges), not from local events. When the board cannot be read, they say "paid state unknown: the board could not be read", never a guess.
4. **History stays readable:**
   - `paid` events already on the shared memory, written by any version, still import;
   - the board still counts them, as it does today;
   - a local record from before this wave keeps showing its own paid event, labelled "recorded in this tool before the board kept the record".
5. **Every description of recording a payment says the board,** and the tool only when no board is set: the pay message's "record it" line, BOUNTY.md, FIRST-FIVE-MINUTES.md, `describe`, the skill, `CLAIMS.md` (BT92), `OWNER-SURFACE.md` (BT89's `paid` row: owner, the board).
