## Problem

Option variadic detection used `\w`, which only recognises ASCII word characters.

As a result, Unicode placeholders such as `--tag <值...>` were treated as non-variadic options, causing parsing of multiple values to fail with an excess-argument error.

The same issue also affects placeholders whose final identifier character is a Unicode combining mark or connector punctuation, such as decomposed names and the exact reproduction discussed in #2614.

Fixes #2614.

## Solution

Use the Unicode `ID_Continue` property to recognise valid identifier-continuation characters immediately before the variadic ellipsis.

This covers:

- Unicode letters and numbers
- Combining marks
- Connector punctuation
- Existing ASCII word characters

This preserves the existing behaviour for ASCII placeholders while continuing to reject non-variadic or malformed forms such as `<value,...>`, `<...>`, and `<value....>`.

## Tests

Added one regression test alongside the existing variadic special-case tests: a placeholder ending in a decomposed Unicode combining mark (`[cafe\u0301...]`) is recognised as variadic.

The existing `[value,...]` test continues to verify that CSV-like single-argument placeholders are not treated as variadic. I also manually verified that the issue's `<值...>` example collects both values. On Node 22.19.0, the full suite passed (1,405 passed, 4 skipped), along with type, lint, and format checks.
