# B2. Bounded Open Box milestone

This is the active Box V4 plan. Read the common specification, standing orders and state protocol before work. Every task requires approval of its named work wave. The CTO coordinates; station leads dispatch scoped workers; independent reviewers bind verdicts to exact candidates. Current product code is an asset to evaluate, not automatic proof of these new criteria.

## B2.1. Persist grounded intent conversations

Owner station is product_experience. Dependencies are B1.1, B1.2. Supplement stage is 1.

### Allowed outputs

- `services/private-api/boxes/intents/**`
- `packages/planner/box-intents/**`
- `apps/private-console/boxes/intake/**`
- `tests/box/intents/**`

Shared schemas, migrations and tooling require a CTO-managed integration lease. All product writes must also be inside the approved wave scope.

### Reuse to inspect

- `services/private-api/intents/**`
- `services/private-api/requests/**`
- `packages/planner/providers/**`
- `packages/planner/retrieval/**`
- `apps/private-console/intake/**`

### Deliver

- Persistent conversation turns, repo/evidence references, facts/assumptions/unknowns and consequential internal decisions.
- Goal-first UX and typed private provider adapter using relevant pinned context; demo/local live modes remain separate.
- Connect intent revisions to Box drafts without running model tools, approving outcomes or exposing private model chat to executors.

### Acceptance

- A PM can describe a coherent full-stack or policy goal without a technical spec; conversation survives resume and references its source revision.
- Required unresolved decisions block readiness; invented facts are labeled; malformed/model timeout responses cannot approve a Box.
- Demo protocol checks are not recorded as live model or good requirement quality.

### Verify

- Required new test:box-intents runs persistence/provider/failure tests and a synthetic conversation API journey.
- Independent intent reviewer checks unknowns, stale evidence, wrong roles, prompt injection and no model-authorized execution.

New named suites are required future commands, not existing commands or passed checks. Implement them under the owning task and tooling lease before using their results. Tests must exercise behavior with independent expectations. Unavailable checks stay unavailable.

### Handoff

Use templates/box-v4/handoff.md. Save bounded evidence under `.execution/box-v4/evidence/B2.1/` and a candidate handoff to the owning lead. Root finalizes `.execution/box-v4/handoffs/B2.1.md` only after independent revision-bound acceptance and dependencies. Report limits, actual runtime/model and next-agent interface context. Do not update legacy state.

## B2.2. Approve expected behavior before implementation

Owner station is product_experience. Dependencies are B2.1. Supplement stage is 1.

### Allowed outputs

- `apps/private-console/boxes/behavior/**`
- `services/private-api/boxes/behavior/**`
- `packages/box-contracts/behavior/**`

Shared schemas, migrations and tooling require a CTO-managed integration lease. All product writes must also be inside the approved wave scope.

### Reuse to inspect

- `apps/private-console/intents/**`
- `services/private-api/db/intent-store.ts`
- `templates/workspaces/catalogue.ts`

### Deliver

- Reviewable versioned behavior artifact with examples, before/after flow, API/state/error cases and exclusions.
- Exact human approval, edit invalidation and requirement-to-evaluator links; data-only previews with safe rendering.
- Coherent UI/API feature and independent response-policy goal with immutable desired outcome.

### Acceptance

- Requester can understand and approve behavior before code exists; unresolved choices and stale approval are visible and enforced.
- A polished mockup or generated test cannot substitute for approval or acceptance; candidates never run in control-plane origin.
- Alternative implementations may satisfy the same behavior; private unpublished assumptions remain Box defects.

### Verify

- Required new test:box-behavior plus actual synthetic browser approval/stale-edit/keyboard/error journeys.
- Independent reviewer challenges conflicting examples, missing API error states and unsafe rendered evidence.

New named suites are required future commands, not existing commands or passed checks. Implement them under the owning task and tooling lease before using their results. Tests must exercise behavior with independent expectations. Unavailable checks stay unavailable.
