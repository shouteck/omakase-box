# M5: Actual isolated evaluation infrastructure

Hostile code runs only within the required disposable VM profile, with bounded results.

Read `docs/SPEC.md`, `docs/COMPOSITION.md`, `docs/ARCHITECTURE.md` and `docs/SECURITY.md` before implementing. These task cards are additive to their normative requirements. Normal execution requires accepted prerequisite handoffs. Sequential fallback may use checked implementations under START.md, while independent-review gates remain open.

The milestone passes when every task below has evidence and an independent accepted review. Sequential checked implementations alone do not complete the milestone. A mocked or unavailable mandatory runtime does not satisfy a real-runtime gate.

## M5.1: Runner protocol and safe controller

Role: `platform`. Prerequisites: M1.1, M0.2.

Write scope: `packages/runner-protocol/**`, `services/runner-controller/**`, `infra/runner/**`, `docs/runner-setup.md`. Shared changes require coordinator ownership.

### Implement

- Bounded job/result schemas, trusted command mapping, digest/replay verification and SSH/SFTP transport.
- Capability doctor, fake-development adapter and required dedicated-VM adapter.
- Implement the operator-host KVM/libvirt baseline-to-ephemeral-guest provider and explicit per-job VM lease disposal.

### Acceptance

- Untrusted commands/URLs/harness IDs cannot control host execution.
- Fake runner is explicit; missing/invalid required profile fails closed and leaves real-validation tasks blocked.

### Verify

    pnpm test:runner -- --suite protocol
    pnpm doctor --json

Commands must really run or be recorded unavailable. Implement the relevant meaningful suite if this is its first owner; an empty script is not evidence.

## M5.4: Composed services and aggregate evaluation authority

Role: `runtime_integration`. Prerequisites: M5.2, M5.3.

Write scope: `services/runner-controller/composition/**`, `infra/runner/composition/**`, `packages/evaluation/composition/**`, `tests/runner/composition/**`, `tests/security/composition/**`. Shared changes require coordinator ownership.

### Implement

- Implement fixed per-job browser/static-assets/candidate-API proxy profile, separate candidate process/container boundaries, data-only policy validation and trusted aggregate verdicts per COMPOSITION.md.
- Bind all work-unit/interface/package/harness digests to one authorized attempt; aggregate CPU/memory/process/time/storage limits and clean up every service/network/guest on cancellation.
- Run positive full-stack and policy cases plus mismatched client/API, missing unit result, forged success, privilege-changing policy and forbidden network/management access cases in the real VM profile.
- Exercise fixed proxy method/route/upstream rules, renderer isolation from CDP/SSH/signing channels, forged forwarding/Host headers and trusted application-policy application after candidate API output.

### Acceptance

- Browser checks exercise the actual candidate API through fixed internal routes; trusted supervisor/signing authority remains inaccessible to every candidate.
- Unit success with failed interface/end-to-end or missing required evidence cannot pass; one submission attempt is counted once even when it starts multiple bounded child jobs.
- Public/private composition jobs use separate fresh VMs and input bundles; pure modules stay network-none and policies never execute as scripts. Real resource/egress/disposal evidence is required.
- Run passing and failing frontend+backend+policy patches in real separate public/private VMs. A candidate response header cannot override trusted application policy; policy cannot relax evaluator controls; forged ingress context and proxy tunneling/redirect/route escape fail.
