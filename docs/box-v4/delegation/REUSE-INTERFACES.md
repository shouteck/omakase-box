## services/private-api/boxes/store/store.ts — accepted B1.1, source-only wiring

`BoxStore` class, constructed with a `pg` `Pool`. Verified methods and semantics:

- `createArtifact(actor, input)` — parses `BehaviorArtifactSchema`, `assertNoRestrictedFields`, `box.write` permission, inserts into `box_behavior_artifacts`, returns `{artifactId, contentHash}`.
- `create(actor, input, key?)` — parses `BoxVersionSchema`, requires `version === 1`, verifies the referenced artifact row exists by `(artifactId, contentHash)`, inserts `box_versions` + `box_heads`, idempotent via `box_operation_keys`. Returns `{boxId, version, contentHash}`.
- `revise(actor, input, expectedVersion, key?)` — requires `version === expectedVersion+1`, stale-version check via `head()`, author-or-owner guard, re-verifies artifact, inserts new version, moves head, returns `approvalInvalidated: true`.
- `approveBehavior(actor, boxId, expectedVersion, expectedHash, approvalId, key?)` — `box.behavior.approve` permission, **owner role only**, hash must match current head, an assigned executor on that version cannot approve (forbidden), one approval per `(boxId, version)`.
- `read(actor, boxId)` — `box.read`; returns head payload plus `approval` and `supersededApproval` flag — the stale-approval signal the agreement card needs.
- `transition(actor, boxId, expectedVersion, to)` — `to:'open'` requires an existing behavior approval for that version.
- `assign`, `openAttempt`, `submitAttempt`, `recordEvaluation` (partially read), plus `box_scoped_tokens` minting for non-human executors — accepted foundation for D2 onward, not needed by D1.2's prepare/approve/amend slice.
- Session auth: `SessionActor {id, role, sessionHash, csrfHash}` checked against `private_accounts`/`private_sessions`; `permits('private', role, action)` from `packages/contracts/auth/policy.js`.

**Absent wiring (confirmed by reading `services/private-api/src/bootstrap/server.ts`): no HTTP route installs `BoxStore`.** The store is reachable only by tests today. D1.2 must add route installation (see FIRST-IMPLEMENTATION-BRIEF.md).

## Resolved D1.2 repository registration

D1.2 makes `POST /v1/box-repositories` one registration operation using configured `sourceId:"private-shop"` and the reviewed fixture root. A new preparation-store method loads that configured source, calls `importPinnedSnapshot`, then inserts `private_intake_objects`, `private_snapshots`, `private_snapshot_provenance`, and `box_repository_registrations` in one transaction. It returns `{repoId, snapshotId, snapshotHash, fileCount, baseCommit, contextManifestHash}`. The existing `POST /v1/snapshots` route remains the generic intake seam, but Box registration does not depend on two separately committed HTTP calls.

The registry row fields are `repoId` matching `IdSchema` (for example `repo-<uuid>`), `snapshotId`, `sourceId`, `sourceRoot`, `baseCommit` (40-hex real commit), `contextManifest` JSON, `contextManifestHash`, `environmentRef` JSON, `evaluatorRef` JSON, `mergeTarget` JSON, `registeredBy`, and `registeredAt`. `contextManifest` records selected paths, excluded paths, protected paths, per-file digests, package-source mapping, runnable-closure membership, and a human-readable label such as `private-shop-before-v1`. `protected` paths record owner-only status and digest only; raw `src/private/eligibility.ts`/`src/private/scoring.ts` source is never exported to a recipient. `environmentRef` is `{reference:<IdSchema>, digest:<sha256:64-hex ImageDigestSchema>}`; `evaluatorRef` is `{reference:<IdSchema>, version:<positive int>, digest:<bare 64-hex HashSchema>}` even if the descriptor document displays it as `sha256:<64-hex>`. The row is unique on `(snapshotId, baseCommit, contextManifestHash)` so a repeated identical registration returns the existing `repoId`; differing bytes produce a new registration rather than mutating history.

This does need one additive migration, `services/private-api/db/migrations/0013_delegation_preparation.sql`, its index-13 entry in `services/private-api/db/migrations/meta/_journal.json`, and a matching Drizzle table in `services/private-api/boxes/store/schema.ts`. That is a D1.2 shared-lease prerequisite because the current delegation graph did not name the migration path. It does not change any accepted B1.1 table and does not assume a `0013_snapshot.json`: current journal convention has snapshots only for indices 0 and 1. Registration is idempotent at the data level, and any route accepting an operation key stores it in `box_operation_keys` for the returned result.

`repoId` in `BoxVersionSchema` is the `IdSchema` identifier from this registry (for example `repo-<uuid>`). `baseCommit` is the same 40-hex commit, never the label `private-shop-before-v1`. `contextManifest.reference` is the registration `repoId` because it already matches `IdSchema`, and `contextManifest.contentHash` is `contextManifestHash`. `environmentRef`, `evaluatorRef`, and `mergeTarget` are copied from the registered row; preparation cannot invent or edit them per request.

## Minimum integration paths for D1.2

1. `BehaviorArtifactSchema` for the completion agreement. D1.2 adds bounded `BoxStore.createPrepared`/`revisePrepared` methods that insert the artifact and version in one transaction and reuse `assertNoRestrictedFields` plus `idempotent`, avoiding orphan artifacts on prepare/amend replay.
2. `BoxVersionSchema` + existing `BoxStore.create`/`revise`/`approveBehavior`/`transition`/`read` semantics for create/approve/amend; the new wrappers call the same guards rather than bypassing them.
3. New route module `services/private-api/boxes/preparation/routes.ts` installed by `services/private-api/src/bootstrap/server.ts`, reusing `authHandlers`/`requirePermission`. Error mapping uses a Box-specific `safeBoxError` sibling modeled on `safeIntentError`, not the intent mapper verbatim, because Box exposes `invalid_transition`, `stale_version`, `missing_evidence`, and `forbidden_role` plus registration/parse errors without leaking internals.
4. New orchestration/store module `services/private-api/boxes/preparation/{orchestrator,types}.ts` plus the registry methods/table in `services/private-api/boxes/store/{store,schema}.ts`. The orchestrator composes `PrivateIntakeStore`, `IntentOrchestration`, and `BoxStore`; it does not duplicate intent persistence.
5. `POST /v1/box-repositories` uses `snapshot.import` because it writes owner snapshot/registry data; `POST /v1/boxes/prepare` and `POST /v1/boxes/:id/revisions` use `box.write`; `GET /v1/boxes/:id/agreement` uses `box.read`; `POST /v1/boxes/:id/behavior-approval` uses `box.behavior.approve`; and `POST /v1/boxes/:id/readiness` uses `box.write` for the approval-gated `draft -> open` transition. Existing `/v1/requests` and `/v1/intents/:id/*` remain the request/decision/readiness seams. `/v1/intents/:id/preparation` stays a planner-preparation route and is not treated as Box preparation.
6. Agreement card uses a Box-specific `BoxAgreementProjectionSchema`, modeled on `ReviewProjectionSchema` but adding `boxId`, `version`, `state`, `repoId`, `baseCommit`, `editableSurface`, `contextManifest`, environment/evaluator refs, merge target, approval binding, and `supersededApproval`.
7. Fixture registration as resolved above; `repoId`, `baseCommit`, `contextManifest`, `environmentRef`, `evaluatorRef`, and `mergeTarget` come only from the registered owner row.
8. Tests under `tests/box/delegation/` registered through the existing `scripts/suite.mjs box --suite delegation` convention, plus `tests/box/delegation/support.ts` for fresh delegation DB/API/browser setup and reviewed wave-local `fixture-manifest.json`/`register-fixture.mjs` for baseline registration; those are proposed paths, not current authorization.
9. A later owner UI/API/browser runtime needs a dedicated W004 recipe modeled on the cached `scripts/box-verification` manifest (cached Linux runner `sha256:eb4a84ec...`, cached Postgres `sha256:639ab7ce...`) rather than host candidate execution; it requires separate approval and readiness verification.

Everything else (packaging export, recipient workbench, merge queue) is D2/D3, not D1.2.
