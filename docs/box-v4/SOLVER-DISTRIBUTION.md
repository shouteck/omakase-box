# How the solver side becomes the obvious choice for agents that earn

Written on 4 November 2026 at the owner's request, as strategy, not a brief. Revised the same day after the owner answered two of its questions: no seed rewards and no spending of any amount (section 3a replaces the money stage), and no crypto for now, with two modes, guard rails by default and the full agent flow available (section 3b). It reads PLAN.md, [SOLVER-SIDE.md](SOLVER-SIDE.md) (K47), [SOLVER-CLI.md](SOLVER-CLI.md), [GTM.md](GTM.md), [DECISIONS.md](DECISIONS.md) and [PF27](../../waves/PF27.md), and outside sources read on 4 November 2026 unless dated otherwise. Nothing here is committed to PLAN.md; the roadmap rows are candidates. The frame is the owner's: agents that run for days, keep budgets and run businesses; attract agents, not people; be for earning what Monid is for spending; order and dependencies, no dates.

## The strategy in a few sentences

The money in the channel is always a poster's, never ours (owner, 4 November 2026); the strategy is to bring real owners' rewards into the channel, not to stand in for them. An earning agent has no loyalty. It goes where the expected return per attempt is highest, and it finds capabilities through three things: what its model already knows, what the registries it searches return, and what the place it already works in tells it. So the solver side becomes the obvious choice by being three things at once, in this order of difficulty: **the place with the most paid code work that settles by rule** (demand is the scarce side, and an earning channel with nothing paid in it teaches every agent that tries it to leave); **the cheapest capability to adopt** (one skill, both halves, a GitHub account it already has, no registration, no wallet, honest facts); and **a named open format that other tools emit and future models have read** (so that "paid code work on GitHub" and our format become the same idea in the model's prior). Everything we do on the solver side should move one of those three, and the first one first.

## 1. How an earning agent finds, judges and adopts a capability

Reasoned from what such agents are built on today, with the evidence beside each step.

### Finding

1. **The model's prior.** A model reaches for what it has read many times: "GitHub issue", "bounty", "pull request", "Upwork". A new capability enters the prior through volume of public text with a stable name and shape: documentation, READMEs, public issues, Q&A, other people's posts. The lag is one training cycle. Nothing we write in a chat reaches it; only what is public, repeated and consistent does. We have one asset most tools do not: every bounty is a public GitHub issue carrying the same machine block and the same "how to answer" words. At volume, that is training data for the format.
2. **Skill search.** This is the mechanism behind "how do I make money?" today. The most-installed skill on skills.sh is `find-skills` (4.2M installs on the leaderboard read 4 November 2026). Its own instructions fire when the user "asks 'how do I do X'", and it runs `npx skills find <query>` against `skills.sh/api/search`, checks the leaderboard first, and, since a change to its instructions (pull request #547 on `vercel-labs/skills`), prefers skills with 1,000 or more installs. ClawHub, OpenClaw's registry, searches "via embeddings (vector index) instead of brittle keywords" (`openclaw/clawhub` README). So the query "make money", "earn income", "get paid" meets whatever skill descriptions sit nearest it, ranked by installs. The registry is huge and top-heavy: Vercel reports one million skills and about 280 million installs in seven months, with 375 skills taking 62 % of installs (Vercel's own numbers, "State of agent skills", 2026; Vercel runs the registry).
3. **MCP registries.** Searched by name and description, less by need; GTM §5 covers them. Useful, secondary.
4. **The place the agent already works.** An agent with the tool installed reads the instruction block; a solver that reaches a bounty issue through GitHub search reads "how to answer" there. This is the channel the installed posting base gives us for free (SOLVER-SIDE §7).
5. **Another agent pointing.** Awesome-lists and "how to make money with OpenClaw" guides are what OpenClaw agents are given today (`BlockRunAI/awesome-OpenClaw-Money-Maker`; "10 Ways to Make Money with OpenClaw", 11 February 2026, listing "Autonomous Bounty Hunting" on PayAClaw and freelancing on MoltyWork). Being in those lists is a listing, so it is the owner's message to send.
6. **Not llms.txt.** Three independent log studies in 2026 agree: Ahrefs found 97 % of 38,000 llms.txt files received no request at all in May 2026, and no bot ever asked for one that did not exist; Arrivl counted 40 requests to `/llms.txt` against 195,245 to ordinary pages from OpenAI's and Anthropic's fetchers over 46 days; a14y's benchmark found no page signal made Claude fetch it, and one line in the prompt did. Agents fetch `/`, `/docs`, `/pricing`. A plain documentation page is the discovery file. Drop llms.txt from the plan as a channel; keep it only if it costs nothing.

### Judging

A loyalty-free agent prices an attempt: reward × probability of merge, minus the attempt's tokens, minus its owner's review time, minus the chance of not being paid, over the time its capital is locked. The board already states reward, `pays_on_merge`, the owner's payment record with median days to record paid, attempts in progress, the owner's median days to a decision and the poster's-own flag (PF22). What it does not state, and an agent would use first:

- **the probability of merge for this owner:** merged over all pull requests on their bounties, which the board already counts (`open_pulls`, `all_pulls`) and does not divide;
- **the CI result on each attempt** (GitHub's check status is a public fact; competitors sell sandbox verification as their whole product, TaskBounty, read 4 November 2026, and we never run code, so the poster's own CI is the honest substitute);
- **the numbers for the board as a whole:** bounties paid, median reward, median days to decision, merge rate. An agent choosing between channels compares channels, and today only we can see ours (`kitchen/launch/watch.mjs`, PF6 item 8, is internal).

Our own test says the agent prices correctly already: PF27's solver, told it needed income, "ran `discover`, found the bounty, and declined it: $0, not paid on merge, an owner who never paid, 'the tool's own rules'". That is the right behaviour and the whole problem in one line.

### Adopting

Adoption cost is the number of things a new agent must have or do before the first `discover`. Ours: the tool installed (one line), the owner's switch, a GitHub account it already has, a schedule on its own host. No registration, no API key, no wallet. For payment, a person connects Stripe once. Compare the field: PayAClaw asks for `POST /api/agents/register` and an API key; the crypto boards (handsel, live on Base mainnet since 30 July 2026; Bountic; `ai-growth-engine`) need a funded wallet; TaskBounty takes 20 % and says bank payout is "not available" self-service. We are already the cheapest to adopt for an agent whose owner is a developer with GitHub. That advantage is real and should be kept: every new step on the solver side is a step towards the field.

## 2. The market as it stands, and the one fact that orders everything

The earn side is crowded with offers and empty of paid work. GTM §4 found this in October (BasedAgents' counters at "—", agent-hires-agent boards at 1 to 12 Hacker News points). It is sharper now:

- PayAClaw's front page (read 4 November 2026): **7 tasks, 6,675 submissions.** Nearly a thousand attempts per task, on writing prompts, for prizes scored by an AI judge.
- "Make money with OpenClaw" is a genre with kits and lists; one honest kit reports "$0 earned and 4 products live" on day two (César Lars, itch.io, 2026).
- The boards that pay on merge for real code are crypto-settled hackathon projects with a handful of bounties each; the one with a verification sandbox is a marketplace taking a fifth.
- OpenClaw itself is the runtime most of these agents run on: about 394,000 GitHub stars and 2.6M npm downloads a week (AgentStackWatch, 3 November 2026; GitHub's own blog called it "the fastest-growing project in GitHub history", 27 August 2026). It has skills, a registry, cron, and a culture of agents launched with a goal.

So supply is not the scarce side and never will be; an idle agent costs cents to point at a task. **Paid work is scarce**, and it is scarce on every board. The board with the most real, paid-on-merge code work wins the solver side by default, because loyalty-free agents and the skills that route them go where the money is. This reorders the question: "how do we become the obvious choice for earning agents" is answered mostly by "how do we become the place with the most paid code work", which is a demand question, and our plan after launch has no demand stage at all.

## 3. What our plan and strategy lack

1. **A demand stage after launch.** PF6 ends with "the owner deploys, publishes, lists and posts" and then there is nothing. GTM §9 step 1 recommended the kitchen's own bounties with small real rewards; the owner declined seed rewards on 21 October and again on 4 November ("I also do not have much capital"), and asked for the benefits of seeding without spending any amount. Section 3a is that answer. The need stands: paid work must exist before anything asks a solver to look, or the solver side launches empty and every agent that tries it learns to leave. The money is other people's, by design.
2. **A solver-side distribution plan that matches how discovery works.** PF6 lists the skill marketplaces, but as a channel for the tool, not as a search-ranked answer to "earn". The solving half needs its own skill entry, worded for the income query space, on skills.sh and ClawHub, with install count treated as the ranking lever it is, and a proof that `npx skills find "make money"` and `openclaw skills search "earn"` return it. PF6's "proof by need" is the right test; it is not yet aimed at these two registries.
3. **The format as a standard, not a page.** `box-bounty-format` has a public page (BT10). It is not a named, versioned, separately published specification with a conformance checker and a guide for other tools that want to emit it. "Become a protocol rather than a destination" is right, and nothing in the plan does it.
4. **Public numbers.** K44's measures M0 to M5 are collected by a kitchen script. An agent choosing a channel, and a person writing about one, need them at a public address: bounties paid, median reward, time to decision, merge rate, attempts per bounty. Facts, never a verdict, in the board's own register.
5. **A fact for the probability of merge.** Merge rate per owner and CI status per attempt (section 1). Small, and the biggest missing input to a rational solver.
6. **Fleet identity.** Pay on merge pays a signed-in GitHub user; an App `[bot]` cannot sign in (D-2026-11-03-solver-in-the-tool, "a known limit"). A business running ten agents under ten Apps earns nothing. GitHub states an App's owner; paying the App's owning account when that account has signed in is a GitHub fact, not a claim in a solver's text, and so stays inside the owner's rule against bot-claiming. Not in the plan.
7. **A stop for the flood we are inviting.** PayAClaw shows what arrives when supply meets a visible reward. Attempts visible (PF25) lets a solver walk away; nothing lets a poster bound attempts. Gap G4 ("no triage when many solutions arrive") is still "only if real use shows it". Real use elsewhere has shown it.
8. **Measures for the solver side itself.** M0 to M5 count posting and payment. Nothing counts `discover` calls, distinct solvers, takes, and takes that reach merged. Without them we cannot tell an empty channel from an unfound one.
9. **An earning route an agent can set up alone** is named as "the next solver-side wave" in D-2026-11-03-solver-side-by-need and absent from the roadmap. Stripe needs a person; every competitor that claims autonomy uses USDC. The owner's answer of 4 November: no crypto for now, and two modes. Section 3b says what that means for the roadmap.

## 3a. The benefits of seed rewards, at $0

Seed rewards were never the goal; they were the cheapest known way to buy four things. Each can be had another way, and the owner's constraint forces the better design: **the money in the channel is always a poster's, never ours.** A board that seeds its own rewards is a marketplace pretending; a board where every reward is a real owner's budget is the thing itself.

| What seeding buys | How to get it without spending |
|---|---|
| **`discover` returns something an agent takes** | Two sources of real rewards that cost us nothing. (a) **Owners who already fund issues.** Projects that run Algora bounties, GitHub Sponsors budgets or "help wanted" with a reward already have the money; what they lack is a way for agents to find and take it by rule. Make posting in our format a one-step act for them (a label and a GitHub Action, or the tool's `post` on an existing issue), and list any issue in the format (decision 2). (b) **Friendly projects whose owners run agents**, invited by the owner (GTM §9 step 2), with pay on merge on and their own limit. Both are the owner's messages, not the kitchen's; both are $0. |
| **A first merge rate, time to decision, attempts per bounty** | None of these needs money. The kitchen's own real $0 bounties, posted by its agents for real reasons (a macOS check, a side task), produce them. S2's numbers page shows them beside "rewards paid: $0", which is honest and still more than any competitor shows. |
| **Solvers learn the channel settles** | Pay on merge is the proof, and it is proven by the first real payment from any owner, not by ours. Until then, the fact the board states is the mechanism itself: "pay on merge is on for this repository; limit remaining $X". That is what the solver-trust agents asked for ("the owner putting the money somewhere I can see it first", GTM §4), and a saved card with a limit is as near as a board that holds no money can get. |
| **A reason for a cold agent to take work at all** | There is one value a $0 merge carries and we have not said so: **a counted merge on the payee's record.** GTM §4's posters trusted a solver with a record over one without. So the solving half of `describe` should say, as a fact: "A merged solution counts on your record whatever the reward; the record is what owners with rewards read. Taking $0 work to build one is a choice; the tool does not advise it either way." Our current advice tells an agent that needs income to decline $0, which is right; it says nothing to an agent that needs a record. Both are facts the agent can price. |

Two further $0 levers belong later, once there is a reason to build them:

- **Pledges on a bounty, charged on merge.** Anyone signed in with a saved card may add to a bounty's reward; each pledge is its own direct charge to the payee on merge, under its pledger's own limit, and the board still holds nothing. This is how Bountysource and Algora's tips funded issues, without the escrow that broke Bountysource. It turns every reader of a bounty into a possible funder and costs the platform nothing. Candidate stage S7b below; it waits for one real request.
- **Rewards the poster's own agent sets within the owner's limit.** PLAN's backlog has "an agent pricing bounties itself (owner: too early)". For a business agent that keeps a budget, the reward is a line item it decides; the owner's limit is the guard rail. Still too early, and it is the end state of "the money is the poster's".

**The honest cost of $0 seeding.** The first weeks will show mostly $0 bounties, agents that read the facts and decline, and numbers that say so. That is the right picture to publish: the measure that matters becomes **bounties with a reward above $0 posted by owners other than us** (the demand measure M1 already counts owner-prompted posts; this adds "with money"), and the stop signal is none after the friendly projects and the format route have been offered. Seeding would have hidden that signal for as long as our money lasted.

## 3b. Two modes, and what "no crypto for now" means

The owner's frame: guard rails by default, where people and agents work together; and the full agent flow, end to end, available to those who choose it. Reading the product as it stands against that:

- **Per identity, once:** a person installs the tool, allows posting and solving, saves a card and a limit, and connects a way to be paid. These are the guard rails, and they are already standing rules: answered once, in force for every bounty after.
- **Per bounty:** with "the agent decides" set on both sides, nothing asks a person. An agent posts, a solver agent discovers, takes, submits; the poster's agent applies; pay on merge charges the card to the solver's account. **The end-to-end mode exists today for any pair whose owners set it once.** What makes it feel like friction is that every identity's first bounty pays the setup cost, and Stripe's part of it (its identity check) is Stripe's, not ours.

So "no crypto for now" costs the end-to-end mode nothing per bounty. What crypto would buy is the per-identity step for an agent with no person at all, and that agent is not here yet; when it is, S6 (one payee for a fleet) covers a business's agents under one person's connection, which is the realistic shape of autonomy for some time. The roadmap's S8 is rewritten accordingly: not "earning with no person" but **"the two modes named and measured"**: `describe` and the board state which mode a repository is in (ask each time, or the agent decides) as a fact; the numbers page counts bounties that ran end to end with nobody asked; and the research question for a payout route with no person is parked with its trigger (a fleet that S6 cannot pay).

## 4. The two owner ideas

### "How do I make money?"

**Verdict: the right instinct, and the mechanism is more specific than "be known".** The people typing it today launch OpenClaw-style assistants and the agent answers by searching skills. The lever is therefore a skill whose name and description sit nearest the income queries and that ranks on installs, on the two registries those agents search. Three consequences:

- **Be the "paid coding work" skill, not the "make money" skill.** The "make money" query space is dominated by prediction-market arbitrage, meme coins and lead-generation kits. A skill that claims to make money and leads an agent to a board with no paid work is uninstalled and never recommended again; `find-skills` now tells agents to prefer installed, reputable skills, and a skill's reputation is its installs. Our honest claim is narrower and stronger: real code tasks on public repositories, paid by rule when merged, facts shown first, nothing promised. The "make money" router skills and lists should point at us for the coding branch; that is a listing in someone else's list, so it is the owner's message.
- **Install count is the flywheel, and it starts at zero.** The posting side's installed base is the only install count we control: every repository whose owner allows solving installs the one skill with both halves. The decision to make the solving half part of the same skill (D-2026-11-03-solver-in-the-tool) was right for exactly this reason; keep it one skill.
- **For the agents that will carry the goal later** (businesses whose agents decide to earn), the same levers hold plus the prior: a named format repeated in thousands of public issues is what a model will have read. That is section 3, item 3, and it depends on item 1.

What this idea cannot do: make an agent take $0 work. The first thing an agent that reaches us through "how do I make money" will do is run `discover` and read the facts. The skill is only as good as what `discover` returns.

### AG-UI and CopilotKit

**What it is.** AG-UI is an event protocol between an agent backend and a user-facing application: thirty-odd typed events (`RUN_STARTED`, `TOOL_CALL_*`, `STATE_DELTA`, `TEXT_MESSAGE_CONTENT`, and since 1.0 interrupts for human approval, subagents, token usage) streamed over SSE. CopilotKit is its React, Angular, Vue and chat-app client and the company behind it. 1.0 shipped on 30 September 2026 and claims adoption by Google, Microsoft, Amazon and Oracle and support in LangChain, Mastra, Google ADK, OpenAI Agents SDK, Pydantic AI and Claude Managed Agents (CopilotKit's own blog). Its own layer diagram places it beside MCP (agent to tools) and A2A (agent to agent) as agent to user.

**What it would give us.** Nothing on distribution. AG-UI is adopted by people who build an agent and a frontend for it. We build neither: our agent-facing surfaces are a CLI, an MCP server and a feed; our person-facing surface is the board's pages. An agent framework that speaks AG-UI will show our tool's output to its user through its own interrupts whether or not we know AG-UI exists.

**The guard-rail steps.** This is the one place a UI protocol could touch us: "the owner allows solving once" and "a person connects a way to be paid" are the two human steps on the solver side. In an AG-UI app they would appear as an interrupt the app renders; in an MCP host they could appear as a card our server returns. The nearer standard for that card is not AG-UI but **MCP Apps**, the first official MCP extension (26 January 2026), rendered by Claude's web and desktop apps, ChatGPT for business workspaces, Cursor and VS Code behind a setting, and explicitly not by Claude Code, Gemini CLI or Devin Desktop (vendor docs as checked by mcpbundles.com on 20 October 2026). The agents this product is built for run in CLIs and schedulers, where neither protocol renders anything, and the step itself is a link to the board that works from any surface today.

**Verdict:** AG-UI and CopilotKit: never, for distribution; not a channel, not a registry, not where earning agents look. MCP Apps for the two guard-rail steps: later, with a trigger: when the board can see that a measured share of `allow` and connect steps begin in a host that renders them. Do nothing now beyond knowing the names. CopilotKit's generative-UI material is a good read for how the board's own pages present a human step, and that is all.

## 7. Decisions only the owner can make

1. **Rewards on our own bounties.** **Answered 4 November 2026: no, and no spending of any amount.** The owner asked for seeding's benefits without its cost; section 3a is the answer, and S1 is rewritten on it. What it asks of the owner instead of money: the invitations to friendly projects, and decision 2.
2. **What the board lists.** D-2026-11-01-solver-distributor says bounties posted with our own tool. The standard route needs "any issue in the open format, whoever posted it", with the posting tool named as a fact on each entry. Recommendation: widen to the format. The format is the protocol; the tool is one emitter. **With no seed money this decision carries more weight:** it is the route by which owners who already fund issues bring their rewards into the channel (section 3a).
3. **Publishing the format as a standard.** A public specification repository under the owner's namespace, and later, if it earns it, an offer to a neutral home such as the Agentic AI Foundation, which now hosts Agent Skills. Recommendation: publish now as S5 when S1 has volume; the foundation question waits a year.
4. **Crypto settlement.** **Answered 4 November 2026: no for now.** The owner's frame is two modes, guard rails by default and the full agent flow available; section 3b shows the end-to-end mode already exists per bounty once each identity's standing rules are set, so crypto is not what it waits on. The trigger stays in writing: a fleet solver that S6 cannot pay.
5. **Listings in other people's lists.** skills.sh and ClawHub entries, the OpenClaw money lists, the awesome-lists: each is an outside message. Recommendation: the two registries as soon as S1 has paid work; the lists after S2, with the numbers page as the only claim.
