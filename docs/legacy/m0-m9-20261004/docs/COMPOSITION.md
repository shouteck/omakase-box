# Tasks, work units and codebase breadth

This is a normative part of the MVP specification. A task represents a coherent customer outcome. Frontend, backend, security, infrastructure, data and tooling are overlapping disciplines, not mutually exclusive task types. A task can span several of them. Full-stack work is a required example, not the ceiling of the product.

## Task composition

An `ExternalTaskContract` contains `disciplines: string[]`, `workUnits: WorkUnit[]`, `interfaces: PublicInterface[]` and `endToEndRequirements: Requirement[]`. No exclusive task-level family discriminator is permitted. Discipline tags describe scope; they do not grant capabilities or determine support. A single-unit task uses the same schema as a composed task.

Each work unit has a stable public ID, registered `adapterKind` and adapter version, requirement IDs, exact editable paths, interface IDs, trusted check IDs and required capabilities. Interfaces declare producer/consumer unit IDs, schema/version, request/response or file semantics, error states, ownership and compatibility obligations. Paths may have only one writing owner. Reject conflicting schema ownership, duplicate IDs, dangling links and unsupported adapter/version/capability combinations. Runtime interactions may be bidirectional; model those as interfaces rather than pretending every service graph is acyclic. Only build/start dependency graphs must be acyclic.

Support is assessed against the complete set of work units, interfaces and the required execution profile. A frontend tag never excludes backend or other tags. Unsupported work produces a reasoned blocker with retained-private-work and possible boundary revisions; do not silently drop it. The customer reviews task granularity. The planner may suggest splitting when independence is justified, but must not automatically split a coherent feature into separate frontend/backend bounties.

One composed task has one immutable version, approved package, reservation, reward/terms, bounded patch, submission lineage and owner acceptance. It may contain several files and services. Per-unit checks are necessary but insufficient: require all published interface and end-to-end obligations, private transfer and unaffected-behaviour preservation to pass. Unknown required evidence blocks acceptance. Owner acceptance creates one aggregate candidate diff and payable event. No partial unit acceptance or implicit separate payment is introduced in this MVP. Budget counters count authoritative submission attempts, not internal child jobs; all child jobs remain subject to the attempt's deadline and resource policy.

## Initial adapter registry

The initial TypeScript/React deployment implements these building blocks:

| Adapter | Allowed responsibility | Trusted evaluation |
|---|---|---|
| `frontend_component` | React component/client behaviour and reviewed styles or client wiring | Browser interactions judged outside the candidate renderer |
| `backend_pure_module` | Typed deterministic computation with explicit inputs/outputs | Restricted child process; supervisor independently checks outputs |
| `backend_api` | A scoped TypeScript HTTP handler and approved API wiring | Candidate API in a separate sandbox; supervisor sends requests and checks responses |
| `application_policy` | An allowlisted application security-policy JSON file | Strict data parsing/schema checks, trusted policy validator and integration/preservation tests |

Adapters are versioned extensible capabilities, not a promise to handle arbitrary codebases. Future adapters can address databases/migrations, cloud configuration, CI, data pipelines and other work without changing the task model. Adding one requires declared edit scope, disclosure assumptions, fixed evaluation commands, isolation profile and private transfer semantics. Every candidate is retained in the breadth denominator even when its needed adapter is absent.

## Mandatory coherent full-stack fixture

The synthetic private shop contains an initially coupled plan-selection flow. Private code determines eligibility and prices; a newly parameterized boundary receives generic approved values. The contributor implements the selection UI, a selection API and typed client/server wiring in one task. Use the frontend and backend API adapters, optionally the pure-module adapter for a shared validator. A pair of unrelated UI and sorting exercises does not satisfy this example.

Freeze the public API contract before release: the browser POSTs only a selected ID; a trusted fixture wrapper attaches the session's generic option context for the candidate handler. The HTTP client cannot supply or override availability/pricing/context fields. Success returns the selected ID; unavailable/missing choices have specified safe error codes, and malformed inputs receive specified validation errors. Publish schemas, input bounds and these responsibilities. Production credentials and eligibility computation remain private. The public wrapper supplies synthetic option values; the private wrapper derives them internally. Neither wrapper can be edited by the contributor. The candidate sees the generic values needed for its responsibility but has no read access to the protected computation. Real authentication/billing changes are excluded from this fixture and recorded explicitly. Test forged browser context and direct access to the context-injection channel.

Publish behaviours for loading, empty and error states, disabled choices, keyboard access, success and rejection, request/response schema, input immutability where applicable and API/client compatibility. End-to-end checks drive the browser through the actual candidate API, including server rejection and error recovery. Add a mismatch patch whose unit checks pass but client/server schemas disagree: the whole task must fail with the correct contract/integration classification. Also test an unpublished private assumption as package defect, rather than penalizing the contributor.

## Mandatory work beyond full stack

Implement a separate codebase security-policy task using `application_policy`. The synthetic app has `config/response-security.json`, a versioned data-only schema and a trusted loader. A PM can request a response policy change using a plain-language goal. The private planner proposes exact obligations for `frameAncestors` (`none` or `self`), `noSniff` (boolean), `referrerPolicy` (published enum) and `hsts` (`enabled`, bounded integer `maxAgeSeconds`, `includeSubDomains`). Freeze required values, HTTPS/localhost behaviour and unaffected routes before release; do not assume every application should adopt a universal policy.

The contributor edits only that policy file. Strict JSON parsing rejects duplicate keys and unknown fields; no executable expressions, remote references, paths, environment interpolation or script hooks are allowed. A pinned trusted validator checks constraints. Private integration verifies that the existing loader emits the specified headers on synthetic HTTPS responses and preserves excluded routes. A trusted application wrapper applies the declared response policy after candidate API output and strips conflicting candidate headers. HTTPS/localhost state comes from the frozen synthetic scenario or trusted ingress context, never an untrusted X-Forwarded-Proto or Host header. The application policy is an evaluated application output; it cannot alter the evaluator proxy, renderer sandbox/CSP, task harnesses, package tooling, networking or commands. No live cloud deployment or credentials are needed. Include a valid alternative policy where the contract permits choices, an invalid policy, a changed policy that fails preservation, forged ingress headers and attempted candidate-header overrides.

This is real executable codebase security/configuration coverage. Other security/cloud/tooling candidates are recorded individually as supported, needing a new adapter, unsafe to release or unresolved; discipline alone cannot reject or accept them. Also test the full-stack feature with this policy unit in the same task: require one passing combined patch and one failing combined patch under the real public/private runner and aggregate acceptance rules. This requires no new task type. Arbitrary cloud execution, production rollout and broad empirical coverage remain later work.

## Composed runner and package rules

Compose vetted template fragments into one workspace with a fixed toolchain, public interface stubs/fixtures and trusted start/check instructions. The owner approves the complete union of released files, interfaces and capabilities. Any unit/interface change invalidates the whole package approval and affected readiness evidence. Check the combined disclosure: individually acceptable fragments may reveal proprietary relationships when joined.

A trusted supervisor outside candidate processes owns routing, expectations and result signing. Full-stack jobs may use only a per-job internal proxy between the browser, trusted static asset server and the scoped candidate API. That proxy is a fixed data-plane allowlist: no CONNECT/tunneling, arbitrary upstream URL, redirect following, forwarding-header trust or route escape. Only fixed template methods/routes/ports are granted; candidate-generated addresses are invalid. Both candidate backend and browser renderer are isolated from management, Playwright/CDP debugging, SSH and signed-result channels, other jobs, private stores and external networks. Unused capabilities stay denied. Pure-module jobs remain network-none. Application policies are validated as data, never executed as CI/shell/infrastructure instructions. The supervisor keeps management/signing credentials outside the candidate network and filesystem.

Public evaluation receives only approved public assets; private evaluation runs in a different fresh VM with a minimal credential-free integration bundle. Each composed job has an aggregate CPU/memory/process/time/storage budget, not an unlimited budget per unit. Trusted bootstrap binds all unit/interface/package digests. Missing unit results, incompatible versions, forged stdout, failing end-to-end requirements or unavailable checks cannot yield aggregate passed. Dispose of all service processes, networks, guest and ephemeral disk on completion/cancellation. Report bounded public diagnostics only from public jobs, and retain private logs internally.

## Delivery and measurement

M9 must demonstrate single-unit compatibility, the coherent full-stack task, the executable security-policy task, and actual frontend/backend/policy composition. Each mandatory example completes PM intent, owner disclosure, package preparation, assignment, patch, private evaluation, owner acceptance and aggregate payable recording. The three-discipline combination must have passing and failing real-runner cases, rather than schema support alone. Implementation of every future adapter is not a prerequisite.

Research candidates and results record nonexclusive discipline arrays, adapter sets, work-unit count, interfaces, composition failures and preparation/integration effort. Report exclusive composition categories separately if desired; per-discipline totals overlap and must not be summed as distinct tasks. Synthetic successes do not establish arbitrary breadth or real-human usefulness.
