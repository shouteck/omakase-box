## Scoped decisions: M6.3 bounded patch intake and atomic budgets

- The patch validator lives at the external intake boundary (`services/external-api/submissions/patch-validation.ts`), not under `packages/evaluation/`: the dependency-boundary checker forbids external services importing evaluation internals, and intake is where hostile bytes must be rejected before any persistence. The evaluation-package re-export is a consumer-side alias only; a literal NUL-byte constant in source is expressed as `String.fromCharCode(0)` because file writers normalize the escape into a raw byte that silently changed the check semantics.
- Intake is one atomic transaction: advisory xact lock serializes budget checks globally, then contributor identity, reservation ownership/state/expiry, exact task/version/package binding against the published contract, strict unified-diff validation, contract-frozen byte/line caps, reservation attempt counter, lineage counter (fixed cap 12), rolling workspace counter (fixed cap 100/7d), signed Ed25519 permit, submission row, reservation→in_review and the export outbox row commit together or not at all. Malformed or policy-rejected submissions roll back before any counter moves — verified live (rejectionUnspent).
- Idempotent replay resolves to the committed attempt before state/expiry/budget gating, so a replayed key is a read of the authoritative result and never a second spend; the same key against a different reservation is an explicit idempotency_conflict.
- The permit is the wire format pinned by the foundation guards: a flat Ed25519-signed packet (permitId/submissionId/taskVersion/packageDigest/submissionHash at top level) whose JSONB must equal both submissions.permit and the outbox payload (external_submission_committed_outbox, outbox_permit_mismatch). Export is pull-based FIFO over signed pull/ack envelopes; acks bind the stored payload hash. The ingest route is reachable only on the internal external-api:4001 host — the public contributor host gets 403 — because the Ed25519 envelope is the authority, not a session.
- Private import requires the signed permit plus a matching approved release row (private_release_approvals) and binds the permit to task/version/package hash/submission hash/lineage/reservation; replay is idempotent at the import row, and private_evaluations is created only after the import commits — no duplicate authoritative attempt across the bridge.
- Live fixture lifecycle: external_one_live_reservation (unique per task+version while active/in_review) and the reservation state machine (cancelled is terminal) mean each fresh fixture reservation retires the prior one to 'cancelled'; rejection/budget checks reuse the still-live conflictRes reservation. All rows remain synthetic.
- No candidate byte executes anywhere: intake validates and hashes the patch, the private side stores it for a future evaluation that still requires the deferred dedicated Linux KVM runner. assurance stays 'tested' for local components, 'unverified' for any execution claim.

## Scoped decisions: M5.2 guest sandbox, supervisor authority and run channel

- The trusted path is a three-layer split: the operator `broker.py` owns the host end of a single virtio-serial channel (`org.private-task.control`, qemu-bound unix socket per lease, no NIC/agent in the domain XML), the guest `supervisor.mjs` runs once per fresh VM as the only channel writer and the only reader of the root-only result key, and the candidate sees only a namespace-constrained worker. The broker forwards exactly `{job, leaseId, artifactHash, artifactBytes, deadline}` plus the raw artifact and returns only the strict `{result, signature}` pair; unsigned supervisor observations are persisted as host-side forensics (`result-observations.json`) and never ride inside the signed payload because `SignedResultSchema` is exact.
- The sealed check contract travels inside the hash-bound artifact bundle (`{files, contract}`), staged supervisor-side at `staging/contract.json` by `build.mjs` — expected outputs never enter the candidate tree and every contract check must cover the job's own `requiredCheckIds`. `build.mjs` runs deterministic JSON staging only: no candidate script, interpreter or archive semantics ever executes.
- The candidate container is unshare user/pid/ipc/uts/mount namespaces with root mapped to the unprivileged guest user, `container-init` applying rprivate propagation, a three-device private `/dev` (stashed before tmpfs, rebind after), read-only root, bounded `nodev,nosuid,noexec` tmpfs `/work`+`/tmp`, a read-only bind of the supervisor-staged candidate tree (the tmpfs would hide host-staged bytes — this ordering was a real defect found and fixed), scrubbed env, `setpriv` to pwuser and `prlimit` pinning cpu/as/nproc/fsize/nofile/locks/sigpending. cgroup v2 writes (`cpu.max`, `memory.max`, `memory.swap.max=0`, `pids.max`) happen before spawn and attach-failure kills the child and reports an unsigned infrastructure fault.
- Verdict authority is exclusively supervisor-side: the worker channel carries only `call`/`result`/`error` frames; `driver-pure-module` computes outcomes from the sealed expectation versus the bounded observed value with depth/node caps. `process.exit(0)`, forged stdout verdicts, assertion monkeypatching and silence produce `unverified`/`failed`, never `passed`; containment trips (timeout, flood, corrupt channel, OOM, pids) fail the job. Pre-envelope and infrastructure faults emit unsigned records (broker quarantines the lease); artifact/contract/harness faults emit signed `unverified` results so the controller receives verifiable evidence.
- Writable enforcement is the bounded tmpfs inside the candidate mount namespace — unobservable from the supervisor, so the result honestly reports `writableEnforcedBytes` with `writableBytesUsed: null` rather than fabricating a measurement. Writable budget over staged candidate bytes is enforced at staging time.
- Shared-file edits (`broker.py`, `tests/runner/protocol/broker_cases.py`) stay inside the sanctioned re-snapshot pattern: all recorded manifests are rebound by the coordinator after the sweep. The `run` wire shape `{version, operation, leaseId, job}` matches `provider.execute` exactly; strict per-operation key sets reject every extra field.
- The physical dedicated Linux KVM host remains absent: `guest-provision.yaml` documents the required baseline image contract, `run` real-execution gates stay `unverified`/`unavailable` by design (`--real` exits 2 honestly), and all local evidence is `tested`/`bounded` only.

## Scoped decisions: M5.4 fixed composition proxy and aggregate attempt verdicts

- The composed-attempt descriptor (`packages/evaluation/composition/descriptor.ts`) binds every work-unit artifact/image, interface schema digest, package/submission hash and fixed harness mapping to exactly one attempt. Child jobIds are sha256-derived (version/variant nibbles pinned) so a replayed fan-out yields the identical job set; `attemptsConsumed` is 1 regardless of width. Manual validation — not zod — keeps `packages/evaluation` free of direct dependency resolution, matching `runner-results` convention.
- `aggregateAttemptVerdict` (`services/runner-controller/composition/aggregate.ts`) is the trusted fold: unknown/duplicate job results, binding or harness mismatches, missing unit results, unverified children or checks, and self-contradictory "passed" results all keep the attempt out of `passed` — only `candidate_failure` yields `failed`; everything else yields `unverified`. `buildChildJobs` materializes protocol-`JobSchema`-valid children pinned to the attemptId and shared package/submission digests.
- The per-job data-plane proxy is an evaluator-authored fixed profile (`infra/runner/composition/proxy-profile.mjs`): two loopback upstreams (static GET/HEAD, declared API route prefixes with full method allowlist), the sole Host authority stamped by the proxy itself. CONNECT, foreign absolute-form targets, `*`/malformed targets, path traversal and double-encoding, forged Host headers and oversized request lines/headers all fail closed; forwarding headers are stripped and re-stamped; hop-by-hop headers never cross either direction; 3xx is returned verbatim — the proxy never follows Location.
- Trusted policy application (`infra/runner/composition/policy-apply.mjs`) mirrors `expectedPolicyHeaders` semantics guest-side: policy files validate as strict data-only documents (exact key set, enum values, no expressions/hooks) hashed against the allow-listed specification; the wrapper strips every candidate-controlled security header (CSP/XCTO/RP/STS/XFO) before stamping the policy, withholds HSTS unless supervisor-observed ingress says HTTPS-non-localhost, and passes declared excluded routes through without injection. Ingress context is a trusted parameter — forged X-Forwarded-* values can never reach it.
- `driver-composed.mjs` + `composed-supervisor.mjs` give the guest a real composed path: strict contract validation per check kind, fixed check evaluation through the proxy classifier and policy wrapper with injected transports (absent ⇒ unverified, never passed), one aggregate cgroup budget, and a finally-blocked cleanup ladder (browser→proxy→candidate-api→static→netns→ephemeral-disk→cgroup). The guest provisions no service launcher or browser adapter yet, so the supervisor's composed branch is live but honestly yields unverified until the dedicated runner exists; `servicesReady: false` is recorded in the unsigned observations.
- The physical dedicated Linux KVM host remains deferred: `--suite composition --real` exits 2 with `unverified`/`unavailable` for both runner and security suites. Every composition component is `tested` locally only.

## Scoped decisions: M4.3 readiness records and publication gate

- Readiness evidence is an append-only private model (`services/private-api/readiness/`): each record binds the exact `taskId`/`taskVersion`/`packageDigest`, a bounded kind vocabulary (fresh_build, traceability, ambiguity_review, external_solve, human_review, preservation_check, integration_check, reference_patch), a status (`passed`/`failed`/`unverified`) and an honest `assurance` (`tested`/`unverified` only — never `proved`). `unverified` means pending, not completed; it always blocks.
- A failed external-context solve must carry a `classified_outcome` from a fixed four-value class (infrastructure, specification, implementation, other) — enforced both in `validateReadinessRecord` and by a database CHECK + trigger (`solve_unclassified`). No code path maps failure to "ambiguity" or "human difficulty"; those labels do not exist in the schema. `classifySolveOutcome` returns `other` for every out-of-vocabulary value.
- `evaluatePublishGate` fails closed on: missing release approval (`missing_approval`), records bound to a different package digest (`binding_mismatch`), absent mandatory kinds (`missing_readiness`), pending evidence (`readiness_unverified`) and failures (`readiness_failure`). A passed `external_solve` satisfies the solve requirement; a failed or absent solve requires a passed `human_review` (`human_review_required`) — the qualified-owner alternative — while the classified failure stays permanently on record.
- Records and gate decisions are immutable PostgreSQL rows (`0010_readiness.sql`): UPDATE/DELETE triggers reject mutation (`immutable_readiness_record`), a trigger enforces `owner_review_required` (human_review rows only from non-disabled owner accounts), and CHECKs pin digest format, status/reason shape and solve classification. `decide()` runs inside one transaction — advisory xact lock on the task key + `FOR SHARE` record read — so a concurrent insert cannot race the evaluated snapshot; the persisted decision stores its exact `evaluated_record_ids`.
- Route authority mirrors the data split: `evaluation.operate` (operators) writes machine evidence, `publication.approve` (owner-only) writes `human_review` records and evaluates/persists gate decisions, `release.approve` reads records. A blocked gate is a persisted result returned with the decision record — not an HTTP error — because blocking is the gate working as designed. Server assigns `recordId`/`recordedBy`/`recordedAt`; clients cannot choose who recorded evidence. Responses carry only the bounded record/decision vocabulary.
- The console readiness panel is data-only: it cannot create evidence, only load records and evaluate the gate for an exact version+digest the owner supplies. It renders blocked reasons verbatim and keeps the honest disclaimer that real-runner evidence remains unavailable.
- Real-runtime evidence is unchanged by this unit: no fresh-VM execution exists on the deferred dedicated Linux KVM host, so `external_solve`/`integration_check`/`preservation_check`/`fresh_build` records can only ever be `unverified` until that environment exists — meaning the gate can only persist `blocked` decisions on real data today. All local evidence is `tested`/`bounded`.

## Scoped decisions: M7.1 evaluation orchestration and candidate-fit pipeline

- The orchestration layer is deliberately thin: services/private-api/jobs/store.ts (M5.3) remains the sole authority for job persistence, lease binding, signed-result verification, anomaly/interruption recording and the base evaluation transitions. A first draft that re-implemented enqueue/record/advance beside it was removed because a second writer would bypass signature verification, release-manifest authority and lease checks — composition, not duplication, is the only safe pattern.
- planEvaluationJobs (packages/evaluation/pipeline/jobs.ts) freezes one public and one private job from the pinned M5.4 attempt descriptors. Every binding field (evaluation, permit, attempt, submission, task/version, submission/package hashes, private base revision) is supplied by the orchestrator from the stored evaluation row — never by the caller. Both jobs share the trusted composed/v1 harness; its digest is derived from trustedHarness() internally, so a caller cannot supply a forged harness digest. EvaluationPipeline.plan() enqueues public first then private through EvaluationJobStore.enqueue, which re-checks release-manifest image digest, published check IDs and harness authority per job.
- mapPatchToUnits (patch-map.ts) maps validated M6.3 patch paths to declared work units through the template unit index. Path traversal and non-portable paths throw invalid_path (never silently ignored); unknown or undeclared paths land in unmappedPaths, which makes the diff builder reject — a patch must account for every touched path.
- buildCandidateDiff (candidate-diff.ts) produces the private candidate diff as pure data: a canonical digest over privateBaseRevision, submissionHash, patchDigest and per-unit file lists. No merge, no deploy, no file content — the diff is a binding object consumed by M7.2 acceptance, which recomputes it against the same stored binding.
- evaluatePrivateFit (fit.ts) composes the M3.4 contract-fit partition with the M5.4 aggregate: a mismatch patch that passes unit checks still fails whole-task fit; private expectations absent from published obligations yield package_defect, never a hidden obligation; contract-fit failure classes (contract_failure/integration_failure) are preserved rather than flattened.
- advanceEvaluation (advance.ts) is the honest transition fold: pending jobs, unverified or infrastructure-only evidence produce no verified advancement; only a complete verified aggregate plus passed fit reaches owner_review. EvaluationPipeline.applyFit persists trusted fit outcomes under a guarded UPDATE (private_evaluating/owner_review only, all jobs terminal first); passed/unverified never move the row — the job store's aggregate path owns the owner_review advance.
- The deadline is caller-supplied but bounded by the store's DEADLINE_WINDOW_MS (120 s) — deterministic plans in tests pin deadlineMs explicitly.
- No candidate byte executes: jobs are planned and enqueued, the dedicated Linux KVM runner remains absent, so every job completes only through recordInterruption(..., 'runner_unavailable') or stays queued. test:runner -- --real exits 2 honestly; all evidence is tested/bounded only.

## Scoped decisions: M7.2 owner review, controlled feedback and atomic acceptance

- Owner acceptance is a single PostgreSQL transaction (`PrivateAcceptanceStore` + `ledger/acceptance-transaction/record.ts`): the owner identity is re-verified inside the transaction against a live non-disabled owner session (`acceptance.approve`), the evaluation row is locked `FOR UPDATE` and must be non-superseded, in `owner_review`, at the caller-pinned `expectedVersion` and result `passed` — anything else rejects as `stale_version`/`forbidden_role` before a byte is written. One commit writes the immutable acceptance, the payable obligation, the `accepted` transition and the feedback outbox event; the deferred `(event_id)`/`(event_id, id)` payable foreign keys mean the database itself can never commit `accepted` without a payable record, and a crash mid-transaction leaves nothing.
- The obligation→acceptance foreign key is immediate while the acceptance→payable keys are deferred, so the in-transaction write order is acceptance first, obligation second — the earlier draft order failed against the real schema and the live guard script (`scripts/verify-acceptance.mjs`) now proves the working order plus every denial (non-owner insert, direct `accepted` transition, acceptance without payable, replay duplicates, immutable terms, settlement requiring a reference, outbox mutation, missing submission binding).
- Event identities are sha256-derived from `(evaluationId, decisionKind)` and the acceptance/feedback public ids from disjoint scopes of the same derivation — retries and replays converge on the same unique key and resolve to the recorded event (`created:false`) instead of ever minting a second payable row or feedback event. Money terms come only from the approved release contract (`reward` / `packageDefectCompensation`), never from request input.
- The candidate diff is recomputed server-side from the stored import patch bytes, validated editable paths and approved work units (`validatePatch` + `mapPatchToUnits` + `buildCandidateDiff`) — the acceptance binds exactly what was evaluated and a client-supplied hash is never trusted. One acceptance binds the whole evaluation row; there is no partial-unit accept path anywhere in the code.
- Feedback is allowlisted at every boundary: `renderPublicFeedback` produces only the strict `PublicFeedback` projection (category, policy version, public check id + bounded message code derived from outcome — `failed`→`requirement_not_met`, `unverified`→`check_unavailable`, `passed`→`passed`), the frozen `FeedbackPolicy` vocabulary rejects `privateDiagnostics: 'full'`, and both the private outbox store and the external status store re-validate payloads at write and at read so a corrupted row degrades to `feedback: null`, never to leakage.
- The package-defect path is a separate decision kind: `compensate()` records a payable `package_defect_compensation` obligation with `acceptance_id: null` (lawful by schema — the deferred payable keys are on the acceptance side), transitions `owner_review`→`package_defect` and emits `package_defect` feedback — the contributor is compensated for a defective package without any acceptance of the submission.
- Bridge delivery is signed and ack-gated: `FeedbackDeliverer` pushes the oldest undelivered outbox event as an `external-feedback-delivery/v1` Ed25519 packet (shared schemas in `packages/contracts/public/feedback-bridge.ts`, no private→external import), and `delivered_at` is written only after a receipt-signed `external-feedback-ack/v1` whose `payloadHash` equals the canonical payload hash and whose `eventId` matches — transport failure, forged/tampered/expired/cross-audience packets, unsigned acks, hash mismatches and foreign event ids all leave the event undelivered for retry. The external receiver stores only `publicId`/`submissionId`/validated payload and is idempotent at the `public_id` primary key.
- The contributor status route (`GET /v1/submissions/:id/status`) is owned by `installContributorStatusRoutes` and returns the bounded projection `schemaVersion/id/reservationId/state/version/feedback`; the pre-existing `resources.submission`/`resources.reservation` placeholder mounts were removed from `main.ts` because the M5.x reservation routes and this route already own those paths — mounting both crashed the service on duplicate route registration. The ingest endpoint is reachable only on the internal `external-api:4001` host, exempted from session auth alongside the existing signed-ingest paths.
- `private_feedback_outbox.submission_id` was added nullable with an INSERT trigger (`outbox_submission_required`) rather than `NOT NULL` because 103 already-delivered synthetic events predate the column — fabrication of a binding for history would be dishonest; every new event must carry the binding and the immutability trigger covers the column once set. `external_feedback` existed since 0000 with the trigger added by `0007_feedback.sql`.
- No candidate execution exists: every accepted evaluation the transaction sees is synthetic/tested evidence produced by the M7.1 pipeline without a VM; the acceptance machinery is `tested`/`bounded`, never `proved`, and the real-runner gate stays `unverified`.
