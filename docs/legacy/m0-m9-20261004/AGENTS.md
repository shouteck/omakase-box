# Instructions for implementation agents

## Scope and authority

When the user invokes `START.md` to start or resume this project, including by giving only that filename, execute START.md and the persisted task graph. No explicit milestone argument is required: the graph declares the target, and state plus verified handoffs determines the next work. A request only to inspect, explain or edit the plan is not a build kickoff. Do not implement anything simply because it appeared as a long-term possibility in the research PDF. The fixed MVP scope and default stack are in `docs/SPEC.md`; `docs/COMPOSITION.md` defines nonexclusive disciplines, connected work units and mandatory full-stack/security-policy coverage. This instruction authorizes coordination with subagents for this project when the runtime supports it, subject to higher-priority tool and user rules.

The product is a private task compiler and acceptance system. Product managers define user outcomes. The customer chooses human, AI or team execution. No AI-first routing. Internal intent/disclosure approvals are product-user actions; build agents may exercise them only with clearly synthetic test accounts and data.

## Engineering rules

Keep private and external data types, processes, credentials and stores separate. AI output is an untrusted proposal. The compiler accepts an approved, hash-bound release set; it cannot read an arbitrary repository. The runner handles hostile code outside the development host. Do not weaken either boundary to make tests pass.

Use the prescribed interfaces and schemas. Pin supported tool versions and dependencies during M0. Do not install global software or modify user app settings without required authorization. Use cross-platform Node scripts rather than platform-specific shell chains. On Windows, verify absolute workspace paths before recursive deletion or moving. Never delete an unknown directory or modify unrelated Desktop projects.

Write meaningful tests for state transitions, auth, immutable approvals, packaging, submission security, private fit and end-to-end behaviour. Tests must establish requirements independently of generated implementation. Do not edit evaluators or expected outputs to bless a failing patch. Unknown/timed-out verification is not passing verification.

Use structured public response projections. No serialization of an internal task object to a contributor. No raw private errors or logs outside the private process. Label every result `proved`, `bounded`, `tested` or `unverified`; only use `proved` if a real proof and its assumptions are present.

## Ownership and handoff

Only the coordinator writes `.execution/state.json`, assigns leases, accepts reviews and advances milestones. Workers write only their assigned implementation paths and a task-specific draft handoff. Request permission from the coordinator before shared-file edits. Never use external messaging or user-visible chat tools to report to another agent; use runtime collaboration tools.

Every accepted handoff records task ID, delivered interfaces, changed files, exact revision/content digest, commands actually run, observed outcomes, reviewer identity, limitations and next-agent context. Evidence goes under `.execution/evidence/<task-id>/`; public version-control history must not contain customer data, prompts or secrets.

The reviewer is different from the implementing worker. If unavailable, record sequential review honestly and keep the independent-review gate open. Do not mark unexecuted checks as passing. Do not mark M9 complete with a fake runner. Human study results cannot be generated by implementation agents.

## Persistence and stopping

Read state on every resumption. Preserve unrelated edits. Record scoped decisions in `docs/DECISIONS.md`; do not ask the user about routine choices already settled here. Continue eligible tasks while prerequisites are blocked. Respect actual session and tool limits; the file-based protocol enables resumption but does not provide an unattended scheduler.

## Cost and host-resource constraints

Keep this build free of paid services, subscriptions, paid model APIs, hardware purchases, rented servers and real participant/payment commitments unless the user separately authorizes the specific expense. Use synthetic accounts and data. Docker Desktop requires free-license eligibility; do not accept license terms or purchase a plan for the user. If no suitable existing dedicated Linux runner host is available, leave real-runner gates blocked instead of renting infrastructure or weakening isolation. On this 16 GB Windows host, run resource-heavy builds, browser checks and runtime checks sequentially; do not download/run model weights automatically or change Docker/WSL resource settings without user authorization.

## Local tool execution

The Windows host has Node 24.11.0 and no global pnpm; user-authorized per-user Docker Desktop/WSL setup is now operational. Docker CLI fallback is C:\Users\shout\AppData\Local\Programs\DockerDesktop\resources\bin\docker.exe. `scripts/docker.mjs` selects the local desktop-linux context on Windows without modifying PATH or Docker settings. Bootstrap pnpm locally with `npm ci --prefix scripts/tooling --ignore-scripts`, then use `node scripts/pnpm.mjs <arguments>` wherever the plan says `pnpm <arguments>`. The wrapper uses the pinned repository-local pnpm and does not install globally. Run `node scripts/pnpm.mjs check`, `build`, `test:bootstrap`, and `doctor --json` for foundation verification. Check now includes bootstrap/auth/contracts/planner suites and the external dependency-boundary checker; `test:auth -- --suite bootstrap` and `test:contracts` can also run separately. `scripts/audit-execution.mjs` checks recorded file digests and packet references, not product delivery or independent review. Unimplemented suites and `verify:mvp` return exit 2, not success. `scripts/evidence.mjs` captures bounded command evidence under a task ID; `scripts/execution.mjs` is coordinator-only and updates state atomically. Do not run its `checked` action until required implementation checks have actually passed. `test:planner -- --suite evidence` now includes an actual synthetic DB/API/browser journey; rebuild/start the identified synthetic runtime and run `node scripts/migrate-runtime.mjs` after service/migration changes. Browser probes require ports 3000/3001 free; do not terminate unknown user processes to free them. Fresh-migration reports distinguish the ten foundation tables from additional intake tables. Repeating login-heavy checks can trigger the existing rate policy; restart only identified synthetic processes if needed, never alter rate policy or drop/reset persistent data.
