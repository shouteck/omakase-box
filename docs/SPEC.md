# MVP product specification

## Product outcome and scope

An internal product manager describes a desired feature in ordinary language. A company-private AI uses a pinned repository snapshot and supplied product evidence to propose an internal intent. Internal owners approve the desired outcome and an exact external disclosure. The system creates a self-contained work package. A customer chooses a human, AI or team contributor. A returned patch is validated against the public contract and the private application. An owner records acceptance and the resulting payment obligation.

Initial support is one TypeScript/React stack and one company per deployment. Tasks contain composable work units using frontend, pure-module, backend API and application-policy adapters. A task may span frontend, backend and other codebase responsibilities; discipline tags are nonexclusive. The normative [composition specification](COMPOSITION.md) defines the initial coverage and acceptance rules. Deliver two independent applications: a private console and a contributor portal. Start with a local task board and existing invited contributors. Live provider configuration is local/customer-controlled. A labeled deterministic demo mode works without credentials.

Do not build a public marketplace, real payment processing, worker recruitment, model training, a hosted multitenant SaaS, arbitrary stack support, a remote coding IDE or automatic production deployment. Include executable bounded application security-policy/configuration work as specified in COMPOSITION.md. Record other security, cloud, data and tooling requirements individually; support depends on available adapters, safe disclosure and verification capabilities, not an exclusive discipline label. Arbitrary infrastructure execution and unsupported stacks require later adapter specifications. Screenshot uploads are private evidence in this MVP; image understanding is optional and must not be presented as present if absent. Audio/video transcription is deferred. A PM can instead attach a text description.

## Default implementation decisions

Use a pnpm workspace with Node 24 LTS, TypeScript, React with Vite, Fastify APIs, Zod application-owned schemas, PostgreSQL 17 with Drizzle migrations, Vitest, Playwright and Docker Compose for trusted services. Pin current compatible patch versions and image digests at M0; record the lockfile and compatibility decision. These are project defaults, not claims about the globally newest releases.

Use separate private and external database instances/credentials and filesystem roots. Runtime containers have only their own volumes. The external service must not possess private DB credentials or model credentials. The private-to-external release bridge transfers only a signed public envelope. The evaluator is a separate disposable Linux VM, with constrained containers inside it. The VM is an external prerequisite; development adapters can be fake only when visibly labeled and unable to satisfy runner gates.

## Personas and authorization

`requester` creates evidence and intent drafts. `owner` approves intent, disclosure, publication, customer assignment and final acceptance; it can be one individual in a small deployment. `operator` manages runtime configuration and private evaluation jobs but cannot manufacture outcome approval. `contributor` sees released tasks and its own reservations, patches and feedback. A deployment bootstrap creates an owner from a local one-time configuration secret. Disable public registration. Invite contributors through a one-time token displayed to the owner; the MVP does not send email.

Use server-verified sessions stored in the service's DB, passwords hashed with a supported password hashing library, CSRF protection and authorization on every route. A role value submitted by a client never creates authority. Sessions expire; revoked invitations and disabled accounts cannot act. Use distinct browser hosts: `private.localhost` for console/API and `contributor.localhost` for portal/API. Cookies are host-only with no Domain attribute; distinct names and signing keys are additional separation. Explicit origin allowlists and CSRF checks block cross-origin authority. Different ports alone do not isolate cookies. Doctor must verify hostname resolution and browser tests must verify no private cookie is sent to contributor endpoints. Bind local development listeners to loopback. Production mode requires TLS and secure cookies; document any explicit localhost-only demo exception. The two UIs never share privileged credentials.

## Requester journey

1. Choose a pinned repository snapshot and enter a goal, current behaviour, desired behaviour, constraints and exclusions. Only the goal is mandatory for an initial draft. Attach optional text or PNG/JPEG screenshots. The user is not required to write a technical spec.
2. The AI returns a typed intent with observed facts, explicit decisions, inferred assumptions, unresolved choices, acceptance examples and private evidence references. All factual claims need references or an `unverified` classification. Existing code is evidence about current behaviour, not authority about desired behaviour.
3. Show a plain-language before/after workflow and acceptance examples. For frontend tasks, render trusted template previews with escaped approved synthetic data; do not execute model-generated/contributor code in the private console origin. Any code preview instead uses an opaque-origin sandbox with no private access; a polished mockup cannot automatically approve intent. Show unresolved choices explicitly. The PM/owner resolves consequential choices internally.
4. Approve the exact intent revision. Unresolved required decisions block preparation/publication. Edits create a new revision and invalidate its downstream checks and approvals.
5. The planner proposes one coherent task with nonexclusive discipline tags, one or more work units, interfaces, end-to-end obligations, retained private work and an integration map. The customer reviews granularity; a full-stack feature is not automatically split into separate bounties. Unsupported cases yield a reasoned `not_supported` result. Do not silently shrink or invent the feature.
6. The release owner reviews the complete external contract, public listing, exact assets and feedback/payment vocabulary. Show both actual file contents and hashes, not just a summary. Approve this immutable release set.
7. A readiness build, traceability check, ambiguity review and external-context solve record support publication. A failed AI solve does not prove ambiguity: distinguish infrastructure, specification and implementation failures. A qualified owner may publish without an AI success only after recording a human readiness review. It remains evidence, not a universal no-clarification guarantee.
8. Publish to the local board or assign to an invited executor. Explicit choices are `human`, `ai`, `team`; these are descriptive assignment labels. The MVP does not automatically call a contributor AI or decide which executor is best.

## Contributor journey

The listing exposes generic scope, skills, reward, estimated effort and reservation terms. Reservation reveals the approved package, requirements, examples, edit boundary, environment instructions and acceptance/compensation rules. One live reservation is allowed per task version. A reservation stays alive across permitted revisions; uploads move it to in_review and an owner changes_required decision returns it to active without extending its original expiry. Acceptance, expiration or cancellation closes it. No concurrent upload while in_review; old attempts cannot be accepted after supersession. Reservation expiry is fixed before work starts. The task/version and terms are immutable.

The contributor downloads a reproducible package, starts its public environment, edits the allowed source and uploads a UTF-8 unified patch against the package digest. The portal offers no chat endpoint to the private AI and no private repository browsing. Provide a structured `package_defect` report for missing context; an owner freezes or withdraws the affected version, handles qualifying compensation and repairs it internally. Infrastructure support is a separate category and still contributes to friction metrics.

## Work-unit adapter: frontend component

The first example is a `PlanSelector` React component. Public props contain a list of `id`, display name, monthly price in integer cents, `available` flag and approved `disabledReason` text. Also provide selected ID, loading state, a generic error message and an `onSelect(id)` callback. No private eligibility computation, customer records or billing SDK is supplied.

Published obligations cover keyboard navigation, accessible names, selected-state indication, empty/loading/error states, formatting specified by locale/currency props, disabled choices and event behaviour. Public mocks exercise all published states. The private wrapper obtains eligibility and pricing internally and maps them into these props. For this single-unit example the contribution owns only the component file and approved stylesheet; it cannot modify tests, dependency manifests or the private provider/wrapper. A composed task may additionally allow reviewed client wiring, backend source and application policy paths in its other units, as declared in COMPOSITION.md. An alternative satisfying implementation need not match reference markup byte-for-byte.

## Work-unit adapter: backend pure module

The first example is `rankItems(items)` where each item has a unique ASCII string ID and a finite numeric score already supplied by a private adapter. It returns all items once in descending score order with ties broken by ascending bytewise ID. It must not mutate its input. Invalid duplicate IDs, nonfinite scores and malformed inputs throw the published `InvalidInput` error. Specify maximum input size and measured performance constraints in the frozen contract; do not invent hidden timing thresholds.

The private scoring formula and records remain private. Public fixtures are independently invented. The private adapter generates scores and satisfies the ranker assumptions. Add property tests and an exhaustive bounded checker for arrays of length 0..4, IDs a..d without repetition, all input orders and scores 0..2. Record bounds, case count and unknowns. That bounded check is not a proof for every possible input or TypeScript runtime behaviour. Test invalid cases separately.

## Private acceptance and payment records

The external service owns one transaction checking identity, reservation, expiry, package hash, edit paths and all three budgets, then storing the attempt permit and outbox event. The signed permit binds exact submission/package hashes. The private service imports it idempotently and never starts a job without that permit. These are separate transactions with explicit crash recovery, not a fictitious cross-database transaction. Treat a patch as hostile. Public checks and private integration run as separate jobs in the isolated evaluator with trusted immutable harnesses. A composed task includes per-unit, interface and end-to-end checks and yields one aggregate verdict, candidate diff and acceptance; passing independent units alone is insufficient. Private tests may exercise more values of published requirements but cannot invent an obligation. New-feature checks validate approved new behaviour; preservation checks cover unaffected behaviour.

Private outcomes are `contract_failure`, `integration_failure`, `package_defect`, `infrastructure_failure`, `passed` or `unverified`. An owner distinguishes contributor failure from an incomplete package. Only the authorized owner can accept; jobs cannot accept themselves. One private DB transaction creates acceptance, a hashed candidate diff against the pinned source, its payment obligation and an approved-feedback outbox event. Retries are idempotent; no accepted event can be published without its corresponding payable record. It does not merge or deploy production code. A stale private base requires revalidation and explicit handling of the reserved terms.

The ledger stores currency, reward in integer minor units, payee, task/submission hashes, payable reason, amount due and owner-recorded settlement reference. No real money moves. Every screen/export says `payment obligation` or `settlement recorded`, never falsely says a provider paid. Prevent double obligations with a unique acceptance/compensation event key. Include owner-recorded compensation for a qualifying package defect/cancellation, as frozen in the task terms. These rules are product requirements, not jurisdiction-specific legal advice.

## Invariants that must survive every milestone

Private AI cannot authorize release or run arbitrary tools. Approval binds exact content, assets, policy and template version. A compiler cannot fetch private files after approval. Published criteria never change silently. External DTOs are positive allowlists. No private logs, paths, commit history, prompts or source maps leak through default responses. Confidentiality of task meaning remains a policy/research question; filters are supporting checks.

A unavailable runner never triggers host execution or acceptance. A unavailable model is shown as unavailable, or a labeled demo provider is selected explicitly. Customer-selected executor labels persist without routing. Human evidence, measured capability gaps and broad abstraction coverage cannot be inferred from synthetic demo completion.
