# Dedicated runner protocol setup

Assurance: unverified real execution; tested protocol observations are recorded in the task handoff. No dedicated Linux KVM host is configured in this workspace. Local Windows and trusted Docker services cannot execute hostile submissions or satisfy the runner gate.

The operator must provide an existing dedicated Linux x86-64 KVM/libvirt host separate from the private service and ordinary workstation. Do not rent infrastructure, install host tools, change settings or accept license terms automatically. The host administrator and sanitized baseline are explicit trust assumptions. M5.2 supplies the constrained candidate sandbox and independent supervisor, and M5.4 supplies composed networking; they remain mandatory before actual evaluation.

The controller uses a private JSON configuration (`RUNNER_CONFIG_FILE` for capability reporting) with exactly: profile `dedicated-linux-kvm-fresh-vm`, hostname `host`, SSH `user`, local `identityFile`, pinned `knownHostsFile`, Ed25519 `resultPublicKey` PEM, `baselineDigest` (64 lowercase hex), `brokerVersion` 1 and `operatorDedicatedHostAttested` true. Never commit credentials or print this object. Host/URL/command fields never come from contributor or model input. Configuration alone reports configured_not_validated, never validated.

An operator separately provisions OpenSSH/SFTP, libvirt/QEMU, `/dev/kvm`, `/opt/private-task/broker/broker.py`, and protected `/var/lib/private-task/{leases,claims,staging}`. The fixed broker requires `/etc/private-task/runner.json` containing exactly profile, dedicatedHostAttested true, baselinePath (absolute read-only qcow2) and baselineDigest. Restrict these configuration/broker/baseline files to the trusted administrator. Restrict the transport account and its SFTP root; no candidate receives SSH, host management or signing credentials. The broker subprocesses use fixed absolute executables, argument arrays and no shell. The managed lease/staging roots must have no symlink components and belong only to the broker account. Keep overlays/claims/lease receipts durable and private.

Before each create, the broker verifies read-only baseline bytes, permanently claims the job ID, creates a unique overlay/domain and boots it with fixed CPU/memory/device settings. M5.1 grants no guest networking and does not execute candidates. The broker rejects run until an independently reviewed guest supervisor is installed by later tasks. Its lifecycle protocol is implemented but has not been exercised against actual KVM on this host. A VM boot by itself would not establish sandbox/egress/resource guarantees.

Disposal verifies stored job/lease/baseline ownership, destroys and undefines only the managed domain, then removes only its overlay/XML/staged artifact. Durable destroyed receipts and replay claims remain. Any exception leaves the lease quarantined and the result unverified. Do not delete unknown domains, reset claims, reuse a guest or claim that a container restart restored the baseline. Operator recovery must inspect a failed lease and establish cleanup before any new attempt; retries never refund disclosure budgets automatically.

Transport uses fixed SSH/SFTP operations, strict host-key checking, no forwarding, bounded output/time and no arbitrary commands. Authenticated result signatures bind the exact job, lease, public/private kind, package/submission/artifact/image/harness identities, deadline and complete required checks. Fake development adapters never return authoritative passed results. Public/private evaluations require separate fresh leases and bundles. Protocol tests inject synthetic transports and keys; they cannot establish actual candidate isolation, clean image provenance, supervisor secrecy or cross-job disposal. Real M5/M9 gates stay open until those separate live tests pass.
