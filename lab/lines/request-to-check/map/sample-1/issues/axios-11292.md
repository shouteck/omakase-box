## Title

Fetch adapter leaves response open after Content-Length limit rejection

## Body

### Describe the bug

With the Fetch adapter, a response whose declared `Content-Length` exceeds `maxContentLength` is rejected before stream tracking begins, but its unread body is not canceled. An unfinished response remains open after the Axios promise has already rejected.

### To reproduce

This uses a loopback server, declares a 1,000-byte response, writes only five bytes, and waits for Axios to cancel it. The `finally` block closes the test connections explicitly.

```js
import http from 'node:http';
import { once } from 'node:events';
import axios from 'axios';

let responseClosed = false;
const server = http.createServer((request, response) => {
  response.once('close', () => { responseClosed = true; });
  response.writeHead(200, { 'Content-Length': '1000' });
  response.write('first');
});
server.listen(0, '127.0.0.1');
await once(server, 'listening');
try {
  await axios.get(`http://127.0.0.1:${server.address().port}/`, {
    adapter: 'fetch', maxContentLength: 1,
  }).catch(error => console.log(error.code)); // ERR_BAD_RESPONSE
  await new Promise(resolve => setTimeout(resolve, 100));
  console.log({ responseClosed }); // Actual: false. Expected: true.
} finally {
  server.closeAllConnections();
  await new Promise(resolve => server.close(resolve));
}
```

### Expected behavior

Initiate cancellation of the unread body while preserving the existing size-limit rejection. A cleanup rejection, or a custom cleanup promise that never settles, should neither replace nor delay `ERR_BAD_RESPONSE`.

### Environment

Axios `v1.x` at `e1a8a57519d1b896c2a795d0ec0138fe24a77a33` (package version 1.20.0); Windows; Node.js 22.17.1 for the original reproduction. The patch was validated on Node.js 24.19.0 and in Chromium, Firefox and WebKit.

### Cause, related work, and proposed fix

The Fetch adapter throws from the header pre-check before constructing `trackStream`. Its catch path unsubscribes cancellation listeners but does not cancel this response body.

Open #11239 fixes source cleanup after a streaming size-limit error inside `trackStream`. This report concerns the earlier header-only rejection, so that patch does not run on this path. The two fixes are complementary. The older #1485 addresses the HTTP adapter rather than this Fetch-adapter branch.

Cancel the body when a cancellation method is available, and handle that cleanup promise separately from the size error. Read cleanup properties inside the caught callback so custom throwing getters also cannot replace the size error. The patch adds no successful-request work or per-chunk overhead and preserves custom responses without a cancellable body.

The new tests cover successful/throwing/rejected/nonsettling cancellation, throwing cleanup getters, missing body/cancellation support, a real unfinished local HTTP response, and a native browser response stream. Four Node regression cases fail before the initial fix; two throwing-getter cases fail before the review correction. All nine focused tests pass afterward.
