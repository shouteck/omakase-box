# K20: the tool against the command-line conventions it should follow

15 October 2026. An investigation: no product code or test changed. Every finding was run against `packages/box-cli/dist/cli.js` built from `d05dde8` (the wave's base, with BT16 in), in a scratch repository under `kitchen-K20-lab/` with `BOX_BOUNTY_SETTINGS_DIR` pointing at a scratch settings directory, so the owner's real settings were never read or written. Nothing was posted to GitHub; every GitHub-remote run used fake `github.com` remotes on the scratch repository. Reference evidence is a real run of `git` 2.45.1, `gh` 2.101.0 or `npm` 11.6.1 on this machine, or that tool's own `--help` text, quoted in the evidence column.

## For the owner: one page

**The departures an agent or owner would notice most, in order**

1. **`--help` does not work below the top level, and three subcommands handle it three ways.** `box bounty --help` and `box bounty create --help` are usage errors (exit 2), `box bounty config --help` is a named refusal (exit 3), and `box bounty status --help` is silently ignored — the status prints as if the flag were not there. `gh` and `git` answer help at every level (`gh issue list --help`, `git status -h`); `status -h` here is even read as a bounty id ("no bounty -h"). **Recommendation:** route `--help` and `-h` on any subcommand to the help screen, matching `gh`/`git`; cost is small — `renderHelp` already exists, and waves/BT12.md already sets this bar ("every command and sub-command answers `--help`").
2. **No machine-readable output on the agent-facing commands, and asking for it is silently ignored.** `box bounty status --json` prints the usual prose, exit 0 — the flag vanishes. `gh issue list --json`, `npm ls --json` and `git status --porcelain` all answer this; the tool itself already prints JSON for `submit`, `verify` and the host hook, so the habit exists. **Recommendation:** refuse unknown flags by name on every command (the silent drop is the real hazard — it breaks the tool's own "never fails silently" rule), then decide whether `status --json` earns a stable format; a `--json` format is new output to maintain.
3. **`--flag=value` is unsupported and inconsistent.** `create --task=TASK.md` fails loudly ("unexpected argument --task=TASK.md", exit 2) but `status --repo=<path>` is silently ignored, so the command runs against the wrong directory and refuses confusingly. `gh` (and every pflag/cobra tool) accepts both spellings. **Recommendation:** accept `--flag=value` on the shared parsers, or at minimum refuse an unknown `--x=y` loudly; cost is a parser change agents would notice only by it working.
4. **No version output.** `box --version` and `box bounty --version` are usage errors; `git`, `gh` and `npm` all print one, and BT12's brief already makes it an acceptance bar ("`box bounty --version` prints it"). **Recommendation:** none beyond BT12 — the gap is recorded and scheduled; cost is one line plus a version source to keep.
5. **A waiting post exits 0.** `box bounty post` with no owner decision prints "waiting for the owner" on stdout and exits 0. **Deliberate and still right:** docs/box-v4/BOUNTY.md states "Waiting is a successful command outcome with exit status 0. No command waits for typed input", and BT8a's Result records the reason ("a completed request waiting for authority, not a host crash"). Two K18 agents remarked on it but read it correctly; the cost of changing would be hosts reading a held post as failure.
6. **Bare `config` lists prose, not `key=value`.** `box bounty config` prints ~13 lines of sentences with inline "change:" hints; `git config --list` prints `key=value` and `npm config list` prints `key = value` with defaults hidden. **Deliberate:** BT8a built the owner side "after tools people already know" and K18's F7/BT14 already record "one verb per action" as the direction; not re-argued.
7. **Verbosity of a successful `status`.** A no-bounty `status` prints the owner and reward preamble before the answer every time; `git status` and `gh` lead with the answer. **Deliberate for now:** BT17 ("Every command says little, and says it once") is already scheduled after this wave to fix exactly this, by the owner's 14 October decision.

**Conventions the tool already follows well**

- **Named refusal streams and exit codes.** Every refusal ran printed `refused (<name>)` on stderr with exit 3, usage errors exit 2 on stderr, results on stdout — a documented contract (BOUNTY.md: "`refused (<name>)` and exit 3; usage errors exit 2; operational failures exit 1") that is *more* informative than `gh`'s flat exit 1 and matches `git`'s 129-for-usage in spirit.
- **`-` means standard input.** `create --task -` reads the task from stdin and says so ("standard input creates no task file"), the `gh issue create`/`git commit -F -` convention, deliberate since BT15.
- **Removed commands refuse by name and name the replacement** (`bounty undo` → "command-removed … git revert -m 1 <merge>", `config add repositories` → "was removed — box bounty allow upowner/proj"). Better than `npm`'s silent deprecations; nothing survives as a hidden alias.
- **Public and state-changing actions show before they land.** `post` waits on standing authority and `--preview` prints the exact publication first; `hook on` prints a disclosure and changes nothing until re-run with `--confirm` — the spirit of `gh repo delete`'s confirm-or-`--yes`, adapted to the tool's standing-rules model (owner answers once, no typed input ever — BOUNTY.md, PLAN).
- **Several remotes resolve through the owner's list** (BT16): `status` opened with "acting on forkowner/proj (2 GitHub remotes; the one on your list)" and a contested post names the matching `allow` per remote — after `gh repo set-default`, as the wave brief states.
- **Quiet where silence is right.** `hook start` prints nothing and exits 0 when there is nothing to report; `config set` confirms in one line. Matches the product rule "With nothing to say, nothing is said" (PLAN).
- **`status`, `close`, `help` are the verbs people know** (git status, gh issue close/status), and `bounty` alone prints a useful overview rather than a usage error.

## The table

Each row is a command (or command family) against a convention, marked **match**, **deliberate** (recorded reason, quoted), or **undeliberate** (no recorded reason found in PLAN.md, BOUNTY.md or a wave file). Evidence is the command as run, with output quoted or the exit code measured; "—" means the convention does not apply. Commands sharing a parser or the same documented contract are grouped where the finding is identical, and every `box bounty` command is covered.

## Departures recorded as deliberate — checked, not re-argued

- Waiting states exit 0 on stdout — BOUNTY.md + BT8a Result, quoted above. Still right.
- Prose `config` — BT8a/BT14, quoted above. Still right; a machine-readable config is the open edge, folded into finding 2.
- No typed confirmation anywhere — "No command waits for typed input" (BOUNTY.md); authority is pre-granted, `hook on --confirm` is the one two-step.
- Multi-remote resolution through the owner's list — BT16's selection model, after `gh repo set-default`.
- Long-flag-only surface — consistent everywhere it was tried; no wave argues for short flags.
- Verbose preambles on reads — BT17 is the scheduled fix, after this measuring wave.

## What the pass should spot-check

Any five rows above, re-run in a `kitchen-K20-lab/` equivalent: `status --help` (silent ignore), `status --repo=<path>` (silent ignore → wrong refusal), `bounty --help` vs `bounty help`, `post` under a fake two-remote checkout (waiting → stdout, exit 0), `config` bare vs `git config --list`.
