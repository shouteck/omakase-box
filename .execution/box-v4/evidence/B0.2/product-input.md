## 1. PM journey trace — how a PM goal becomes an approved decision today

Current lifecycle: sign-in -> pinned snapshot selection -> request intake -> evidence attach -> provider proposal -> intent review -> decision resolution -> ready -> owner approval bound to exact content hash. All routes are on the private service (`http://private.localhost:4000`, hardcoded in `apps/private-console/intake/private-client.ts:1`).

1. **Sign-in and roles.** `POST /v1/auth/login` returns a 64-hex CSRF token stored in sessionStorage (`private-client.ts` `signIn`, `rememberCsrf`); `GET /v1/auth/session` yields role `requester | owner | operator` (`PrivateRole`, `private-client.ts:4-5`). Server-side session/CSRF checks run inside each store transaction (`services/private-api/requests/store.ts` `PrivateIntakeStore.transaction`; `services/private-api/db/intent-store.ts` `PrivateIntentStore.actor`). Operators cannot create requests or intents (console gate at `apps/private-console/intake/intake-screen.tsx:8,70`; store roles `['owner','requester']`).
2. **Pinned snapshot (the "repository" stand-in).** An owner/operator registers `POST /v1/snapshots {sourceId}` -> `PrivateIntakeStore.registerSnapshot` -> `importPinnedSnapshot` (`services/private-api/snapshots/importer.ts`). Snapshots are **filesystem content imports, not Git**: operator-configured absolute roots + allowlisted relative paths (`SnapshotSourceSchema`, `services/private-api/requests/types.ts:17`, max 32 sources), extension allowlist (ts/tsx/js/jsx/json/css/md/txt), exclusions for dot-dirs, `node_modules`, `dist`, `coverage`, `reference-solutions`; <=1 MB/file, <=16 MB total, <=256 files; symlink/hardlink/TOCTOU checks on every read. `snapshotHash = contentHash(manifest)` is re-verified on each read (`snapshot_binding_mismatch`, `requests/store.ts:73`). Tables: `private_snapshots`, `private_snapshot_provenance`, `private_intake_objects` (`services/private-api/db/migrations/0005_private_intake.sql`). Console lists snapshots via `GET /v1/snapshots` (`store.listSnapshots`, max 100) in a picker (`intake-screen.tsx:73-77`). Per `docs/box-v4/reconciliation/census.md` (A3/M2.1) and `docs/box-v4/REUSE.md`, this still needs real Git snapshot identity for B1.2.
3. **Request intake.** `POST /v1/requests` -> `RequestInputSchema` (`services/private-api/requests/types.ts:9`): `snapshotId` uuid, `goal` required <=4096 chars, `currentBehaviour`/`desiredBehaviour` <=4096, `constraints`/`exclusions` <=16 items each; canonicalized payload <=65000 bytes. UI fields map 1:1 (`intake-screen.tsx:71-88`). Row: `private_requests` (`requester_id = actor`; snapshot must exist). Roles: owner + requester.
4. **Evidence attach (optional).** `POST /v1/requests/:id/evidence` (bodyLimit 1_400_000) -> `EvidenceUploadSchema` (`types.ts:11`): mediaType `text/plain | image/png | image/jpeg`, base64 <=1_398_104 chars, label <=160. `validateEvidence` (`services/private-api/requests/media.ts`) validates actual bytes. Quotas: `MAX_UPLOAD_BYTES` 1 MB, `MAX_REQUEST_EVIDENCE` 16, `MAX_REQUEST_EVIDENCE_BYTES` 8 MB -> HTTP 429 `evidence_limit`. Bytes dedup by sha256 in `private_intake_objects`; download via `GET /v1/requests/:id/evidence/:evidenceId` as sandboxed octet-stream (`requests/routes.ts:29-34`). UI copy is already honest: "Screenshots stay private evidence; this console never claims image understanding" (`intake-screen.tsx:92`).
5. **Planning input.** `GET /v1/requests/:id/planning-input` -> `store.planningInput` -> `collectPlanningEvidence` (`packages/planner/retrieval/index.ts`): <=256 source files, <=16 attachments, 65_536-byte total text budget with `truncated` flags, `imageUnderstanding: false`, `assurance: 'bounded'`. Read-only; also consumed internally by the orchestrator.
6. **Intent draft.** `POST /v1/requests/:id/intents {mode: 'demo'|'ollama'}` (`services/private-api/intents/routes.ts:19`) -> `IntentOrchestrator.createDraft` (`intents/orchestrator.ts:89-99`): fetch planning input -> `provider.proposeIntent` -> `validateIntentProposal` (`packages/planner/providers/contracts.ts:18-28`) enforcing: <=256 KB; proposal `goal` must equal the request goal verbatim; all `decisions[].answer` must be null; every evidence reference must be a supplied reference bound to the snapshotHash. `assemble` builds an `InternalIntentSchema` (`packages/contracts/private/index.ts:6-21`) at state `draft`, version 1, with a provenance line prepended to `scope.included` (`provenanceLine`, `orchestrator.ts:42-44`). `PrivateIntentStore.create` re-checks binding (request exists, requester owns it, snapshot hash matches, `db/intent-store.ts:92-96`) and appends `private_intent_revisions` + `private_intent_heads` rows (migrations 0000, 0004 monotonic head).
   - **Demo provider** (`packages/planner/providers/demo.ts`): deterministic fixture catalogue (`demo-fixtures.ts`); always emits a required `outcome_confirmation` decision plus the assumption that it is "a review aid, not model inference"; provenance `modelVerification: 'not_applicable'`. UI labels it "Deterministic demo planning (no model, no credentials; visibly fixture-based)" (`intake-screen.tsx:106`).
   - **Ollama provider** (`packages/planner/providers/ollama.ts`): operator-supplied config `{endpoint, model, timeoutMs<=30s}` (`OllamaConfigSchema`); loopback-only endpoint `http://127.0.0.1|[::1]:port/api/chat`; fails safe with `needs_configuration` when unconfigured; 512 KB request/response bounds; envelope checks (model match, `done:true`, no tool_calls); schema validation with 1 repair attempt; provenance `modelVerification: 'live_response_not_validated'` (or `'protocol_mock'` for injected transport). Failure -> 503 `provider_unavailable` with `{reason, mode}` (`intents/types.ts` `safeIntentError`).
   - Provider provenance `{mode, inputHash, proposalHash, repairAttempts, modelVerification}` is returned in the creation response (`IntentCreationView`) but is **not rendered on the review screen** — a UX gap flagged in section 5.
7. **Review.** `GET /v1/intents/:id/review` -> `reviewProjection` (`intents/types.ts:52-67`): version, `state`, `reviewedPayloadState`, `contentHash`, `approval`, `supersededApproval`, `blockage.requiredUnresolved`, goal, facts (with `assurance: tested|unverified` + evidence refs), evidence, decisions, assumptions (always `unverified`), unknowns, `acceptanceExamples` (`RequirementSchema`: inputs/outputs/states/invalidCases/exclusions + given/when/then examples), scope, `provenance {requestId, snapshotHash}`. `IntentsScreen` (`apps/private-console/intents/intents-screen.tsx`) renders cards for goal, first before/after example, unanswered decisions, scope and provenance, plus an "Edit outcome" panel. Lookup is **by intent ID or request ID only** — there is no list/browse of requests or intents.
8. **Decision resolution.** `POST /v1/intents/:id/decisions {decisionId, answer, expectedVersion}` -> `orchestrator.resolveDecision` (`orchestrator.ts:112-122`): `stale_version` on mismatch; writes the answer into a **new immutable revision** (version+1, state `draft`) via `store.revise`; returns `approvalInvalidated: true` if the previous head was approved. So each answered question bumps the version — the current "conversation" is an append-only revision chain plus structured Q&A fields, not a message transcript.
9. **Revise.** `POST /v1/intents/:id/revisions {expectedVersion, mode, optional field edits}` -> `orchestrator.revise` (`orchestrator.ts:123-143`): re-runs the provider on the edited planning input, carries resolved answers forward (`carriedAnswers`), produces a new immutable revision; `approvalInvalidated` likewise.
10. **Ready.** `POST /v1/intents/:id/readiness {expectedVersion, expectedHash}` -> `orchestrator.ready` (`orchestrator.ts:144-153`): `expectedHash` must equal current `contentHash` -> transition to `ready_for_approval`. `assertTransition` (`packages/contracts/workflow/index.ts:12,30`) requires `requiredDecisionsResolved` for ready/approve and restricts ready to requester/owner. Transition table allows `draft -> needs_decision -> ready_for_approval` and `draft -> ready_for_approval`; **no code path currently transitions to `needs_decision`** — it exists in schema, transition table and UI labels ("Needs your decision", `intents-screen.tsx:105`) but blocking is expressed through `blockage.requiredUnresolved` on the draft state instead. Flagged in section 5.
11. **Approve (exact-hash).** `POST /v1/intents/:id/approval {expectedVersion, expectedHash}` -> `orchestrator.approve` -> transition `approved`: **owner role only** (`workflow/index.ts:23`), requires `requiredDecisionsResolved` and `exactHashConfirmed` (`expectedHash === current.content_hash`). The store sets `state='approved'`, `approved_by`, `approved_hash = content_hash` on that revision row (`db/intent-store.ts:123-125`); approval binds the ready-for-approval payload bytes — the approve flip does not recompute `content_hash`, and read-path `binding()` (`intent-store.ts:47-52`) enforces `approved_hash === content_hash` for approved rows plus `contentHash(payload) === content_hash` for every row.
12. **Revision after approval.** A new head revision leaves the older approved row as history: `superseded()` (`intent-store.ts:53-56`) detects an approved revision with `version < current`; the projection sets `supersededApproval`, and the UI warns "A previous owner approval no longer binds this revision: your edits need a new approval" (`intents-screen.tsx:127`). Approval is never carried onto new bytes.
13. **End of the current lifecycle.** An approved intent feeds `POST /v1/intents/:id/preparation` (`services/private-api/preparations/routes.ts:19` -> `PreparationOrchestrator.propose`, `preparations/orchestrator.ts`) which validates `approvedIntentHash`/approval binding (`validatePartitionInput`, `providers/contracts.ts:34-45`) and calls `proposePartition` -> `composePartition` — the legacy restricted partition/release path. Nothing past approval is an Open Box surface.

## 3. Product position — open_trusted vs restricted boundary in the UX

Grounding: `docs/box-v4/SPEC.md` "Trust profiles" (lines 33-37); census defer rows A6b/A8 (`docs/box-v4/reconciliation/census.md`) and defer tasks M4.3, M5.2, M5.4, M6.1-M6.3, M7.1-M7.3, M8.1-M8.3, M9.1-M9.3.

**What users must see under open_trusted.**

- A visible profile label on every Box detail/list row: `open_trusted — approved synthetic/non-sensitive repository`. Users should never infer the trust level from an absent gate. SPEC line 35 makes open_trusted a deliberately approved substrate + pinned build/evaluator recipe + explicit executor policy; all three deserve first-class display.
- Executor policy and identity on each attempt (human/agent/hybrid, scope), per SPEC flow step 5 — mirroring the assignments screen's explicit-choice posture ("No executor is selected automatically", `assignments-screen.tsx:8`).
- Provenance labels on every model/provider-produced artifact: provider `mode` (`demo` vs `ollama_live`/`ollama_protocol_mock`), `modelVerification`, `repairAttempts`, `inputHash`/`proposalHash`. The plumbing exists (`IntentCreation.provider`); the gap is display (section 5, Q5/Q8). SPEC's "a simulator/demo adapter is labeled and never counts as a real agent integration receipt" should extend to executor adapters, not just planners.
- Bounded-context honesty: what the service actually read (snapshot hash, file count, truncation flags, `imageUnderstanding: false`) — already surfaced piecemeal via `provenance`/`planning-input` and should stay visible per Box.
- Blocked-with-reason states, never silent gates: unresolved required decisions, unsupported capabilities, missing evaluator/environment, stale-version/hash mismatches. Existing precedent is strong — `blockage.requiredUnresolved` banner, publish-gate reason codes, `provider_unavailable {reason, mode}`, `(unverified)` labels — and should be the house style for Box readiness too.

**What must stay gated (restricted_private / hostile_external).**

- `services/private-api/releases/**`, `services/private-api/readiness/**`, `services/private-api/ledger/**`, `services/private-api/acceptance/**` — restricted publication/readiness/payment path (census A8, M4.3, M7.x; `EvaluationAttemptSchema` KVM profile).
- `infra/runner/**`, `services/runner-controller/**` — hostile-runner surfaces; dedicated KVM/libvirt host still absent (census M5.2, REUSE.md).
- `services/external-api/**`, `apps/contributor-portal/**` — external/bounty surface (census A6b, M6.x).
- These screens already self-gate (owner-only readiness, `publicationReady` check in `assignments-screen.tsx:9`, "Real-runner evidence remains unavailable" in `review-panel.tsx:63`). open_trusted Box work must not route through or weaken any of them — and must not present a gated surface as if it were available.

**Making the boundary legible.** Recommended UX rules: (a) profile chip on every Box and attempt; (b) restricted surfaces rendered as "blocked — requires restricted_private profile, not authorized in this wave" rather than hidden or silently 403'd; (c) assurance vocabulary kept literal (`tested` / `unverified` / `blocked: <reason>`) — the console already speaks this way; (d) no open_trusted screen may display payment, publication, KVM-runner or external-board affordances at all, even disabled — the restricted console tabs remain a separate later-stage concern.

## 4. Proposal — first coherent full-stack Box + behavior surface (for a future approved wave; NOT implemented now)

Recommendation: one guided "Open Box" flow inside the existing private console, matching `docs/box-v4/ARCHITECTURE.md`'s placement (`apps/private-console/boxes/**`, `services/private-api/boxes/**`, `/v1/boxes*` routes). PM walks four steps in one flow, reusing the numbered-section pattern already in `intake-screen.tsx` (steps 1-3).

1. **Intake -> Box draft (adapt `intake-screen.tsx`).** Keep goal/currentBehaviour/desiredBehaviour/constraints/exclusions/evidence fields and the snapshot picker initially; add a repository-registration selector when `box-repositories` land. Reuse: `RequestInputSchema`-shaped validation, evidence bounds, `api()`/CSRF plumbing. New code: Box draft endpoints + repo selector UI; the intake section becomes step 1 of the Box create flow rather than a separate request object (or wraps it — decision Q1/Q2 affects this).
2. **Persisted conversation -> behavior draft (adapt `intents-screen.tsx` + intents API).** The review cards (goal, before/after, decisions, assumptions/unknowns, scope, provenance) carry over nearly unchanged; the decisions[] Q&A and revise-with-carried-answers mechanics become conversation turns. New code: a persisted `box_conversations`/turns aggregate feeding a behavior draft — the largest genuinely new product piece. Reuse: `resolveDecision`/`revise` optimistic-version + exact-hash mechanics, `reviewProjection` shape, provider adapters + provenance labels.
3. **Behavior approval -> artifact (adapt approval machinery).** Keep the owner-only exact-hash approve (`assertTransition` + `approved_hash`) but bind it to a distinct `behaviorArtifact` (or to InternalIntent promoted at approval — decision Q2). Display approved artifact hash + `supersededApproval` banner exactly as today. New code: artifact schema/binding + BoxVersion reference; reuse: the entire approval/invalidation state machine.
4. **Box readiness + list/detail (new screens, reuse visual patterns).** Minimal list: goal, version, state, profile chip, blocker count. Detail tabs: Behavior (approved artifact + provenance), Context (repo/base/manifest), Attempts (executor, diff, evaluation receipts), Assignment (explicit human/agent/hybrid choice reusing `assignments-screen.tsx` posture), Review. Blocked rows show reason, never disappear. New code: all of this surface. Reuse: card/projection layout of `intents-screen.tsx`, `api()` wrapper, session gates.
5. **Workbench surface (minimal first).** Per ARCHITECTURE.md "Workbench and service integration": a Box detail pane inside the console showing approved behavior, context, evaluator commands and attempt diff beside an editor/workspace link — no bespoke editor fork. New code: attempt diff view (first real diff UI in the repo) + evaluator-command display; reuse: CandidateDiff binding data and job/evaluation evidence shapes after B3 fit review.

Net new product code: conversation persistence, behavior artifact aggregate, Box list/detail/browse, attempt/diff/evidence surfaces, repo registration UI, Box-scoped assignment. Pure reuse candidates: auth/CSRF, api client, intake/evidence bounds, decision/exact-hash/superseded mechanics, provider provenance labels, blocked-with-reason and assurance vocabulary, explicit executor-choice pattern. Everything under `docs/box-v4/ARCHITECTURE.md` remains a proposal requiring its own approved wave.

## 5. Unresolved product decisions — named, not guessed

- **Q1 — Conversation model: single-shot proposal+decisions vs persisted multi-turn.** Options: (a) keep the revision+decisions model and treat each revision as a turn record (minimal new code, weak "conversation" semantics); (b) new persisted conversation/turns aggregate whose turns can update the behavior draft (matches SPEC step 2 "persisted conversation" literally). Recommendation: (b), reusing decisions/revision mechanics as the turn-transition primitives. Unblocked by: B0.2 contract decision on whether conversation is its own aggregate; feeds B2.1 scope in the next brief.
- **Q2 — Is the behavior artifact distinct from the intent record?** Options: (a) promote `InternalIntent` to be the `behaviorArtifact` referenced by `BoxVersion.behaviorArtifact/hash` (max reuse; couples artifact shape to legacy schema); (b) emit a separate immutable artifact at approval, with the intent record as provenance (cleaner SPEC match; new schema). Recommendation: (b). Unblocked by: B0.2 Platform contract doc + CEO sign-off on artifact boundary.
- **Q3 — Who approves behavior vs who approves merge.** Current: `owner` role does both legacy jobs (intent approve; acceptance/release approve). SPEC: "requester/owner approves the exact behavior artifact"; merge needs owner authority + reviewed candidate. Options: same owner for both; or requester approves behavior, owner approves merge. Recommendation: keep both actions owner-role initially but record them as separate approval objects so the roles can diverge later. Unblocked by: profile-contract + role decision in B0.2/W002 brief.
- **Q4 — Console and Box Web: one app or two.** Options: extend `apps/private-console` with `boxes/**` (ARCHITECTURE.md's placement; one auth/session surface) vs a separate Box Web app (matches SPEC's "Box Web" wording; more bootstrap/auth work). Recommendation: extend the existing console for the first Box surface; split only if a contributor/agent-facing surface later needs different trust. Unblocked by: W002 scope naming the app target.
- **Q5 — Demo vs live-model labeling and use.** Current labels are honest (`modelVerification: 'not_applicable' | 'protocol_mock' | 'live_response_not_validated'`) but the provider mode is not shown on the review screen. Options: ship demo-labeled-only in the first Box wave and gate `ollama_live` behind an independent model-quality check; or allow live output with prominent labels. Recommendation: demo-only for W002's first Box surface; add a provenance line to the review UI (small new code) regardless. Unblocked by: model/resource policy in the next brief + whether B2.1 requires live-model evaluation.
- **Q6 — Full-stack decomposition of the first demo Box.** SPEC requires a coherent UI/API feature Box, a separate application security-policy change, and one connected multi-discipline Box. Open: which `examples/**` fixture (19 files, census "reuse") and which demo-fixture goal becomes the first Box; whether the planner's partition suggestion is surfaced to the customer ("the customer decides whether a coherent feature should remain one Box"). Recommendation: one coherent full-stack feature Box first, planner suggestion shown but never auto-split. Unblocked by: synthetic-repo baseline decision (B0.2 Platform) + W002 demo-script choice.
- **Q7 — Orphaned `needs_decision` state.** The transition table, schema and UI label support it, but no orchestrator path sets it. Options: wire an explicit needs-decision transition (clarifies state machine), or drop the state and keep `blockage.requiredUnresolved` semantics. Recommendation: wire it during B2.1 conversation work — it maps naturally to "clarification pending". Unblocked by: Q1's conversation-model decision.
- **Q8 — Where provider provenance is displayed.** `IntentCreation.provider` is returned at creation but absent from `reviewProjection`/UI. Options: add provenance fields to the projection (small schema + UI change) vs leave provenance on creation responses only. Recommendation: add to projection — SPEC's labeling requirement applies to review-time decisions, not just creation. Unblocked by: any wave approving intents/review projection edits.
