## Limitations and blockers

- The extraction check is static and structural: it verifies type-identity, import/call removal, adapter retention and caller rewriting under a bounded model with ambient data-only externals. Actual generated-code preservation and integration execution remain the pending M4.3 gate after M5.2/M5.3 — this work does NOT claim them, and no isolated-runner gate can be claimed here.
- The baseline/transformed type programs use ambient module shims (every bare external declared data-only, a minimal ambient `useState` for react, global JSX namespace); external behaviour is not interpreted. Captured files using unsupported external usage fail the baseline check into explicit not_supported rather than widening the shim.
- The supported parameterization model is deliberately narrow (top-level exported consumers binding a single protected call to one const local, one removable trailing subject parameter or single-field props type, declared callers); everything else is explicit not_supported. Multiple different protected functions per proposal are refused (one protected computation per boundary).
- composePartition's declared integration targets are explicit, validated, private-side inputs; the demo source maps only the six demo fixture goals with synthetic shop paths. Any other goal yields explicit missing_evidence/not_supported. Deterministic UUIDs are hash-derived identifiers for PROPOSALS only — they are not task reservations, approvals or payments.
- The preparations API is a read-only proposal surface (permission 'intent.read'); no preparation persistence, workflow state transitions or approval/approval-bypass exist here. No production authentication, billing, deployment or model capability was exercised; all fixtures are synthetic.
